003 · Functional vs Non-Functional Requirements

High-Level System Design (HLD) › Phase 1: Foundations › Topic 3 of 140 · DEEP

0. TL;DR in Simple English — Functional Requirements (FRs) are the verbs a user can do ("Post a tweet, buy a ticket, send a message")—they decide your REST/gRPC APIs and core database tables. Non-Functional Requirements (NFRs) are the physics and survival rules under which those verbs must still work ("Under 150ms p99 latency, at 200,000 QPS, with 99.99% uptime and zero double-charges")—NFRs alone decide 90% of your 7-Box System Design architecture!

§2Why it exists — Same Functional Requirements, Completely Opposite Architectures!

Here is the single biggest revelation in System Design: Two systems can have 100% identical Functional Requirements, yet require completely opposite architectures because their Non-Functional Requirements differ!

Let's prove this on our flagship app PulseStream. Suppose the Functional Requirement is just 1 sentence: "Users can transfer $50 or send a message to another user." Look at what happens when we change the NFRs:

System Variant Functional Requirement (FR) Non-Functional Requirements (NFRs) Resulting 7-Box Architecture
Variant A: Internal Team Chat for a 50-Person Company Send message to user; view message history. QPS < 5/sec, Storage < 2 GB/year, 99% uptime (ok to reboot at night), single office region. 1 Box total: Single Spring Boot monolith + SQLite/PostgreSQL on a $20/month VM. Adding Kafka or sharding here is architectural malpractice!
Variant B: Global Creator Live-Chat (PulseStream Chat) Send message to user/room; view message history. (Exact same FR!) 500,000 messages/sec, p99 delivery < 100ms globally, 99.99% availability, Eventual Consistency allowed for old history. AP-Leaning 7-Box Fleet: Stateful WebSocket Gateways (Box 1/2), Redis Pub/Sub routing (Box 4), Kafka buffering (Box 5), Sharded Cassandra/ScyllaDB LSM-Tree storage (Box 6).
Variant C: PulseStream Wallet / Ticket Ledger Transfer $50 from User A to User B; view history. (Nearly identical CRUD verb!) 10,000 tx/sec, Strict Linearizable/Serializable Consistency (zero double-spend!), RPO = 0 (zero lost committed transactions). CP-Leaning ACID Fleet: Idempotency Key enforcement (Box 2), Double-Entry Ledger on synchronous Raft/Multi-AZ SQL shards (Box 6), Transactional Outbox (Box 5/6).

§3How it works — Formal Taxonomy, Strip the Magic & NFR-to-Box Compiler

3.1 Formal Definition & Guarantees

  • Functional Requirements (FRs): Specify what behavior, features, inputs, outputs, and business workflows the system must provide to its users. In code, FRs translate directly into API endpoints (POST /v1/posts), Request/Response DTOs, and Domain Entities.
  • Non-Functional Requirements (NFRs / Quality Attributes / Architectural Characteristics): Specify the operational constraints, measurable runtime qualities, and failure boundaries under which the functional requirements must execute (AWS Well-Architected Framework — The 6 Pillars).
  • Invariants of a Valid Requirement: An NFR without a number is a wish, not an engineering requirement!
    • Bad (Un-testable wish): "The feed must be very fast, highly available, and scalable."
    • Good (Testable engineering NFR): "GET /v1/feed must return in p50 < 40ms and p99 < 180ms at a peak load of 150,000 QPS, with 99.99% monthly availability and eventual consistency lag ≤ 3 seconds."

3.2 Strip the Magic — The "NFR-to-Architecture Compiler" Table

Senior and Staff architects have a mental compiler that translates every NFR directly into a specific mechanism on the 7-Box Map:

Non-Functional Requirement (NFR) Quantitative Metric Universal Law Exact Architectural Mechanism It Forces on the 7-Box Map
Low Read Latency p99 < 50 ms Law 1 (Physics) CDN at the Edge (Box 1) + L1 App Cache & L2 Redis Cache (Box 4) + Covering B+Tree Indexes / Materialized Views (Box 6).
High Write Throughput > 100,000 writes/sec Law 1 & Law 2 Consistent-Hash Sharding across $N$ DB nodes (Box 6) + Append-only LSM-Tree storage (Cassandra/RocksDB) + Kafka write buffering (Box 5).
High Availability (Fault Tolerance) 99.99% (≤ 52.6 min downtime/yr) Law 2 & Law 4 Zero single points of failure (SPOFs): redundant Load Balancers (Box 1), Stateless Multi-AZ Pods (Box 2), Automatic DB Replica Failover / Leaderless Quorums (Box 6/7).
High Durability 99.999999999% (11 Nines), RPO = 0 Law 1 & Law 4 Synchronous Write-Ahead Log (`fsync`) replicated across ≥3 Availability Zones before returning HTTP 200 (Box 6) + Point-in-Time WAL Archiving to S3 (Box 7).
Strong Consistency Linearizable / Serializable Law 4 (CAP/PACELC) Single-Leader primary reads/writes, `SELECT FOR UPDATE` / Serializable MVCC, or Raft/Paxos consensus groups (Spanner/CockroachDB in Box 6).
Spike / Burst Resilience $10\times$ traffic flash sale in 1 second Law 3 (Little's Law) Edge Rate Limiting / Virtual Waiting Room (Box 1/3) + Async Queue decoupling (Box 5) + Warm Auto-Scaling pools (Box 7).

§4When to use — Trade-Off Matrix (When NFRs Collide)

Because of Universal Law 4 and Universal Law 5, you cannot maximize every NFR at the same time. Here is what happens when two NFRs collide:

Colliding NFR Pair Why They Conflict (First Principles) How an Architect Resolves It
Ultra-Low Latency (`<10ms`) vs Strict Multi-Region Consistency Light in fiber takes `~70ms` one-way across the Atlantic (Law 1). You cannot synchronously wait for a quorum in Europe and still answer a US user in `10ms` (Law 4 / PACELC). Pin each user's writes to a local Home Region (or use eventual consistency for non-financial reads) and reserve cross-region sync consensus only for rare critical state changes.
99.999% Availability vs Lowest Cloud Cost Five Nines requires hot Active-Active multi-region redundancy ($2\times–3\times$ idle compute/DB headroom) to absorb a full region outage instantly. Tier services by criticality: Tier-0 (Auth, Checkout) gets Multi-AZ/Multi-Region Active-Active; Tier-2 (Recommendations, Analytics) uses cheaper single-region with graceful degradation.
Zero Data Loss (`RPO=0`) vs Maximum Write Throughput `RPO=0` requires `fsync` to disk + synchronous replication ACK from a standby before returning success (`~2–5ms` lock hold per write). Use Group Commit (batching 100 concurrent WAL flushes into a single disk `fsync`) for financial data; use async replication (`acks=1`) for high-volume clickstream/telemetry logs.

§5Explain it to a 12-year-old (The Feynman Pass)

Imagine you tell an engineer: "Build me a vehicle that carries people from Point A to Point B."

  • "Carry people from Point A to Point B" is the Functional Requirement (FR). A $100 bicycle, a family minivan, a Formula 1 race car, and an armored bank truck all satisfy that exact same functional requirement!
  • Now look at the Non-Functional Requirements (NFRs):
    • "Must go 220 mph on a smooth track" → You build a Formula 1 car (pure speed, zero trunk space—like an in-memory Redis cache!).
    • "Must survive a bomb blast and never lose the gold bars inside" → You build a 10-ton armored bank truck (slower, heavy locks, strict durability—like a synchronous ACID payment ledger!).
    • "Must carry 1,000 commuters every 5 minutes during rush hour" → You build a 10-car subway train (high throughput via batching—like Apache Kafka!).

If you start welding metal before asking about speed, armor, or passenger count, you will build a Formula 1 car for a bank robbery—or an armored tank for a bicycle race!

§7In practice — Production Incidents, Observability, Security, FinOps & Interview Playbook

7.1 Production Incident: Treating Availability and Durability as the Same Thing

Incident: The Single-Node Redis "Database" Wipeout
  • Symptoms: An EC2 host hardware reboot wiped 4 hours of user shopping carts and pending webhook state.
  • Root Cause: The team needed low latency (`NFR: p99 < 5ms`) and stored primary state in Redis with default `RDB snapshot every 15 minutes` and asynchronous replication, assuming "Redis Cluster is highly available, so our data is durable!"
  • Key Distinction: Availability means the service answers requests right now; Durability means committed data survives power loss forever. They are independent NFRs!
  • Prevention: Store durable truth in an ACID/WAL database (Box 6) and treat Box 4 (Redis) strictly as a disposable read cache—or if using Redis for transient locks/queues, pair with `AOF fsync=always/everysec` + fallback reconstruction from DB.

7.2 Interview Derivation Playbook (Junior vs Senior vs Staff/Principal)

Phase of Interview Junior Candidate Senior Candidate Staff / Principal Candidate
Defining Requirements (Minutes 1–5) Lists 10 functional features (login, profile picture, dark mode, forgot password, comments, shares) and skips NFRs. Scopes down to top 3 core functional workflows and writes down concrete NFRs: DAU/QPS, p99 latency, CAP preference, availability target. Splits NFRs by workflow path (e.g., "Write path for seat booking requires strict CP serializability at 1,000 QPS with p99 < 300ms; Read path for stadium seat map requires AP availability at 200,000 QPS with p99 < 30ms and up to 2s staleness"), immediately justifying why the two paths use different boxes!

§8Pitfalls & Traps

⚠️ Pitfall 1 — Designing Login, Registration, and Forgot-Password in an HLD Interview: Unless the interview question is specifically "Design an OAuth2 Identity Provider", never make Login/Signup one of your top 3 Functional Requirements! Focus on the unique core value of the prompt (e.g., for Uber: location ingestion + ride matching; for Twitter: post creation + home timeline generation).
⚠️ Pitfall 2 — Claiming "Strong Consistency + 100% Availability + 10ms Global Latency" Across All Features: Interviewers will immediately challenge this with the CAP/PACELC theorem. Always specify which critical table gets strong consistency and which read-heavy views use eventual consistency.

§9Recap, Reference Cheat-Sheet & Glossary

  • Functional Requirements (FRs) = The Verbs: Define the top 3–4 core user actions → maps to APIs and base schema.
  • Non-Functional Requirements (NFRs) = The Physics: Quantify Latency (`p50/p99`), Throughput (`QPS`), Availability (`99.99%`), Durability (`RPO=0`), and Consistency (`CP vs AP`) → dictates all 7 Boxes.
  • Split NFRs Per Path: Almost every real system mixes an AP read-heavy path (feeds, catalogs, search) with a CP write-critical path (payments, inventory, seat locks).

Glossary

Functional Requirement (FR)
A statement of a specific behavior, input-output transformation, or user action that a system must perform.
Non-Functional Requirement (NFR)
A measurable quality attribute or constraint on how the system performs its functions (latency, throughput, availability, durability, consistency, security, cost).
Durability vs Availability
Availability asks: "Can I read/write right now?" Durability asks: "Once I write X, will X still exist 10 years from now even if servers catch fire?"
