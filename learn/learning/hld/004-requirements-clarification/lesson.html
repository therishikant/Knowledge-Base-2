§2Why it exists — Watch an Unclarified Design Crash in 4 Minutes

Why do interviewers give you a 4-word prompt like "Design a Chat System"? Because they are testing whether you act like a junior coder (who immediately draws whatever tutorial they memorized) or a Principal Architect (who narrows the problem space first).

Suppose a candidate hears "Design a Chat System" and spends 30 minutes designing 1-on-1 encrypted mobile messaging with transient store-and-forward queues (WhatsApp). At minute 35, the interviewer says: "Actually, I wanted a public livestream chat room where 500,000 viewers watch one gaming streamer and type 20,000 messages/second in the same room (Twitch/YouTube Live)."

  • In WhatsApp (1-on-1 / small group ≤ 1,000), every message is delivered reliably to every member's device via per-user queues.
  • In Twitch Live Chat (500,000 viewers in 1 room), fanning out 20,000 messages/sec to 500,000 sockets = $10,000,000,000$ (10 billion!) deliveries per second—which would melt the planet unless you sample/batch messages at Edge Pub/Sub trees and drop messages for lagging clients!
  • One 15-second question in Minute 1 ("Are we designing 1-on-1 / small private groups up to ~500 users, or massive public broadcast rooms with 100K+ concurrent viewers?") saves the entire interview!

§3How it works — The 6-Switch Decision-Tree Protocol

3.1 Formal Rule: Only Ask Questions That Flip an Architectural Switch

Never ask low-leverage product trivia like "What color should the send button be?" or "Should usernames allow underscores?" Every question you ask must have a clear If Answer = A → Box X; If Answer = B → Box Y branch:

Switch # The High-Leverage Question to Ask If Answer = Option A If Answer = Option B
1. Core Scope & Actors "To keep us focused in 45 minutes, should we prioritize [Core Workflow 1] and [Core Workflow 2], and mark admin/billing out of scope?" Locks down the 3–4 APIs for Box 2. Prevents scope creep from eating your deep-dive time.
2. Scale & Burstiness "What is our target DAU (e.g., 50M DAU), and is traffic steady or spiky (e.g., 10x flash-sale / live event spike)?" Steady: Standard auto-scaling + capacity headroom. 10x Spiky (Law 3): Forces Edge Waiting Room / Token Bucket (Box 3) + Kafka shock-absorber queue (Box 5).
3. Read : Write Ratio "What is the approximate Read-to-Write ratio (e.g., 100:1 read-heavy vs 1:1 write-heavy)?" 100:1 Read-Heavy: Multi-tier CDN + Redis Cache + DB Read Replicas (Box 1 & 4). 1:1 or Write-Heavy: Sharded LSM-Tree DB (Cassandra/RocksDB) + Kafka batching (Box 5 & 6).
4. Payload Size & Media "Are payloads small structured records (<1 KB JSON), or do users attach photos/videos (10 MB – 4 GB)?" Small JSON: Flows directly through API Gateway → Box 2 → Box 6 DB. Large Blobs (Law 1): Bypass Box 2 via Pre-Signed URLs directly to S3 + Multipart Upload + CDN (Box 1 & 6).
5. Real-Time vs Pull Latency "Do clients pull updates on page load, or do we need sub-second server push? What is the p99 latency target?" Pull: Stateless HTTP/2 REST APIs + Redis cache. Real-Time Push (Law 2): Stateful WebSocket / SSE Gateways + Connection Routing Map (Box 1, 2, 4).
6. Consistency & Distribution Skew "Can reads tolerate a few seconds of eventual consistency, or do we need strict linearizability? And do we have 'celebrity' accounts with 50M followers?" Uniform + Eventual: Standard hash sharding + async replication. Celebrity Hot-Key Skew (Law 5): Hybrid Push/Pull fan-out + Salted shard keys + Local L1 hot-key cache.

3.2 Strip the Magic — Propose-and-Confirm (How Senior/Staff Engineers Drive)

In real architecture reviews and Google interviews, reading a robotic checklist of 12 questions feels like an interrogation. Instead, use the "Propose Defaults & Confirm" pattern: 

// JUNIOR INTERROGATION (Slow, passive, eats 10 minutes):
// "How many users? What is the read/write ratio? What is the latency? Do we support images?..."

// STAFF ARCHITECT "PROPOSE-AND-CONFIRM" (Crisp, proactive, takes 90 seconds):
"Let me align on scope and scale for PulseStream:
 1. Functional Scope: I'll focus on (a) publishing a post with optional media,
    (b) generating the personalized home feed, and (c) booking a limited-inventory VIP ticket.
 2. Scale & Traffic: I'll assume 50M DAU, ~100:1 read-to-write ratio on feeds,
    and extreme burstiness (100K concurrent requests) when a creator drops VIP tickets.
 3. NFRs: For the feed, I'll target p99 < 150ms with eventual consistency (≤ 3s lag)
    and handle the celebrity hot-key problem (creators with 20M followers).
    For ticket checkout, I'll enforce strict ACID serializability with zero double-booking.
 Does this framing match what you'd like to explore, or should we adjust any constraint?"

§4When to use — Prompt-to-Hidden-Bottleneck Cheat Sheet

Every classic System Design prompt hides one or two killer edge cases that the interviewer is waiting for you to uncover during clarification:

Vague Interview Prompt The Hidden Trap Question You MUST Ask How the Answer Changes the 7-Box Design
"Design Twitter / News Feed" "Can a single celebrity account have 50 million followers?" Forces Hybrid Fan-Out (Push to Redis timelines for normal users; Pull at read-time for celebrities so 1 tweet doesn't trigger 50M Redis writes).
"Design Ticketmaster / Flash Sale" "Do users pick a specific seat on a stadium map, or just a general-admission quantity? And how long is a seat held during payment?" Specific seat = exact row/key lock (`seat_id`) with 5-minute TTL release; General admission = atomic counter decrement in Redis/SQL.
"Design Dropbox / Google Drive" "If a user edits 10 KB inside a 2 GB video file, should we re-upload the whole 2 GB or only the changed block?" Forces Client-Side Content-Defined Chunking (4 MB SHA-256 blocks) so only the mutated 4 MB chunk is uploaded and synced.
"Design a Web Crawler" "Are we crawling HTML text only or executing headless JavaScript SPAs? And how strictly must we enforce per-domain politeness?" Forces separate Politeness Queues per target hostname (`crawl-delay`) so you don't accidentally DDoS small websites.

§5Explain it to a 12-year-old (The Feynman Pass)

Imagine a customer walks into your custom bakery and says: "Bake me a cake for tomorrow!"

A beginner baker immediately runs to the oven and bakes a small chocolate cupcake with peanuts on top. The next day, the customer arrives with 500 wedding guests, and the bride has a deadly peanut allergy!

A master baker pauses for 60 seconds before touching the flour and asks 4 smart questions:

  1. "How many people are eating it?" (Scale / QPS — 1 cupcake vs a 5-tier wedding cake)
  2. "Any allergies or strict dietary rules?" (Consistency / Security / Durability — peanuts = double-charging a credit card!)
  3. "Is this being eaten inside our shop or shipped across the desert in July?" (Network / Multi-Region / Edge CDN — prevents melting in transit!)
  4. "What time does the party start?" (Latency SLO / Deadlines)

Asking those 4 questions takes 1 minute and saves 10 hours of baking the wrong cake.

§7In practice — Real-World RFC Template & Interview Derivation Playbook

7.1 How Principal Engineers Clarify Requirements in Real Production RFCs

At companies like Google, Amazon, Stripe, and Uber, no team is allowed to write production code for a new system without first writing a 1-page Design Doc / RFC Header that locks down the 6 Switches: 

# RFC-042: PulseStream Real-Time Creator Tipping & Gift Ledger
1. Goals (Functional Scope):
   - Fans can send $1–$500 tips during a live stream; creator sees live alert < 500ms; ledger settles daily.
2. Non-Goals (Explicitly Out of Scope):
   - Crypto payouts, cross-currency FX trading, and tax-form PDF generation (handled by existing Batch Service).
3. Scale & Traffic Profile:
   - 10M concurrent viewers across top streams; Peak write rate = 25,000 tips/sec during viral moments.
4. SLO & Consistency Contract:
   - Payment & Ledger Write: Strict CP idempotency (zero duplicate charges), p99 < 450ms, RPO = 0.
   - Live Stream Overlay Animation: AP best-effort via WebSocket fan-out, p99 < 250ms, coalesced when >50 tips/sec.

§8Pitfalls & Traps

⚠️ Pitfall 1 — Spending 15 Minutes on Clarification: Clarification should take 3 to 5 minutes max in a 45-minute interview. Ask your 5–6 high-leverage questions (using Propose-and-Confirm), write the agreed numbers in the corner of the whiteboard, and move immediately to Capacity Estimation & High-Level Design.
⚠️ Pitfall 2 — Asking Questions But Ignoring the Answers: If you ask "What is the read-to-write ratio?", the interviewer says "1:1 write-heavy telemetry ingestion," and you still spend 15 minutes designing a read-through Redis cache instead of a write-optimized Kafka + LSM-Tree pipeline, you lose points for failing to connect requirements to architecture!

§9Recap, Reference Cheat-Sheet & Glossary

  • Every Clarification Question Must Flip a Switch: Ask about (1) Core 3 Verbs & Non-Goals, (2) DAU & Spike Multiplier, (3) Read:Write Ratio, (4) Payload Size/Media, (5) Push vs Pull Latency, and (6) Consistency & Hot-Key Skew.
  • Use "Propose and Confirm": State sensible production defaults and ask the interviewer if they want to adjust any knob.
  • Explicit Non-Goals Protect Your Clock: Naming what you are not building is just as important as naming what you are building.

Glossary

Non-Goals (Out of Scope)
Features or edge cases explicitly excluded from the current design iteration to keep the architecture focused on core value and risks.
Hot-Key Skew (Celebrity Problem)
A traffic distribution where a tiny fraction of keys (e.g., 1 celebrity account or 1 flash-sale item) receives 10,000× more reads or writes than the average key.
Peak-to-Average Ratio
The multiplier between average QPS across a 24-hour day and the highest 1-second burst QPS (typically $3\times$ to $10\times$, or $50\times$ for flash sales/live events).
