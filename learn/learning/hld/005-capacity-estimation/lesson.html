0. TL;DR in Simple English — Capacity Estimation is NOT doing math for the sake of math on a whiteboard. It is a 5-Step Sizing Formula (Traffic QPS → Peak QPS → Storage Growth → Cache RAM Working Set → Network Bandwidth & Server Count) where every number you calculate directly proves whether 1 server is enough or whether you are forced to shard, cache, or offload to a CDN.

§2Why it exists — The Naive Failure of Designing "Blind" Without Numbers

Watch what happens when an engineer designs a system without estimating capacity first:

  • Failure Case A (Under-Sizing by $100\times$): For PulseStream (`50M DAU`, each uploading `1 photo/day` of `2 MB`), the engineer decides to store images inside PostgreSQL `BYTEA` columns on a single 4 TB SSD. How long until the database disk hits 100% full and crashes?
    $\text{Daily Image Storage} = 50,000,000 \times 2\text{ MB} = 100\text{ TB per day!}$
    Their 4 TB database explodes in 57 minutes on Day 1! Doing 10 seconds of capacity math beforehand immediately proves: "100 TB/day cannot live in PostgreSQL; media MUST go to S3 Object Storage + CDN!"
  • Failure Case B (Over-Engineering by $100\times$): For a B2B SaaS invoicing portal with `10,000 DAU` generating `20,000 invoices/day`, the engineer proposes a 16-shard Cassandra cluster.
    $\text{Write QPS} = \frac{20,000}{100,000\text{ sec/day}} = 0.2\text{ writes/second!}$
    $\text{5-Year Storage} = 20,000 \times 365 \times 5 \times 2\text{ KB} \approx 73\text{ GB total!}$
    73 GB and 0.2 QPS fits on a single tiny PostgreSQL instance with 99.9% idle CPU!

§3How it works — The 5-Step Capacity Estimation Engine

3.1 Formal 5-Step Equations

In every system design problem, execute these 5 steps in order (using $1\text{ day} = 86,400\text{ seconds} \approx 10^5\text{ seconds}$): 

// ============================================================================
// STEP 1: TRAFFIC / QPS (Queries Per Second)
// ============================================================================
Avg Write QPS  = (DAU * Writes_Per_User_Per_Day) / 100,000
Avg Read QPS   = (DAU * Reads_Per_User_Per_Day)  / 100,000
Peak QPS       = Avg QPS * Peak_Multiplier       // Usually 2x to 5x (or 10x+ for flash events)

// ============================================================================
// STEP 2: STORAGE (Structured Metadata vs Unstructured Media Blobs)
// ============================================================================
Daily Structured DB Storage = (Daily Writes) * (Row + Index Size in Bytes)
5-Year Structured Storage   = Daily_DB_Storage * 365 * 5 * Replication_Factor(3)
Daily Blob/S3 Storage       = (Daily Media Uploads) * (AvgCompressedFileSize)

// ============================================================================
// STEP 3: CACHE MEMORY (The 80/20 Pareto Rule — Box 4 Sizing)
// ============================================================================
// 20% of daily active content generates 80% of reads:
Cache RAM Needed = 0.20 * (Daily Active Read Dataset Size) * (HashMap Overhead ~1.4x)

// ============================================================================
// STEP 4: NETWORK BANDWIDTH (Ingress & Egress — Box 1 Sizing)
// ============================================================================
Ingress Bandwidth (Bytes/sec) = Peak_Write_QPS * Avg_Request_Payload_Bytes
Egress Bandwidth  (Bytes/sec) = Peak_Read_QPS  * Avg_Response_Payload_Bytes
// Multiply Bytes/sec by 8 to get bits/sec (Gbps) for NIC capacity!

// ============================================================================
// STEP 5: COMPUTE & STORAGE NODE COUNT (Connecting Math -> Architecture!)
// ============================================================================
Stateless App Servers = Peak_QPS / (Max_QPS_Per_Server_At_60%_Headroom)
DB Shards Needed      = MAX( Total_Storage / Max_Disk_Per_Shard,  Peak_Write_QPS / Max_Writes_Per_Shard )

3.2 Reference Baselines: What Can ONE Modern Cloud Server Actually Handle?

To convert QPS and GB into a server count, keep these conservative single-node production limits in your head (Google SRE Workbook — Non-Abstract Large System Design):

Component (Single Production Node, e.g. 16–32 vCPU, 64–128 GB RAM, NVMe SSD) Safe Sustainable Throughput / Capacity (With 40% Headroom) When You MUST Add Replicas or Shards
Box 1: L7 Reverse Proxy / Envoy / Nginx ~50,000 – 100,000 QPS; ~500,000 concurrent idle TLS/WebSocket connections When QPS > 50K or active sockets > 300K per Gateway node.
Box 2: Stateless Spring Boot Pod (8 vCPU, 16 GB RAM) ~2,000 – 5,000 QPS (for typical JSON + DB/Cache I/O endpoints); ~500 QPS if CPU-heavy Divide Peak QPS by 3,000 QPS/pod to get your pod fleet size.
Box 4: Single Redis Instance (1 Core Event Loop) ~50,000 – 100,000 QPS (`O(1)` GET/SET); ~50 – 64 GB max RAM per instance (for fast `fork()` snapshots) When hot working set > 50 GB RAM or Cache QPS > 80K (or 1 hot key > 100K QPS → add L1 local cache!).
Box 5: Single Kafka Broker Node ~50,000 – 200,000 msgs/sec (`100–300 MB/s` sequential disk throughput) When streaming throughput exceeds `100 MB/s` per broker or storage exceeds `4–8 TB`/broker.
Box 6: Single Relational DB Node (PostgreSQL / MySQL) Writes: ~3,000 – 10,000 ACID writes/sec
Simple Indexed Reads: ~10,000 – 25,000 reads/sec
Storage: ~2 – 5 TB per node before index rebuilds/backups get painful		 Read QPS > 15K → Add Cache + Read Replicas.
Write QPS > 8K or DB Size > 4 TB → Shard the DB!

3.3 Worked Walkthrough — Full Capacity Estimation for PulseStream (50M DAU)

Let's run the 5-Step Engine on PulseStream (50M DAU, 2 posts/user/day, 40 feed reads/user/day, 20% posts have a 500 KB compressed image):
  1. Step 1 (QPS):
    • $\text{Avg Write QPS} = \frac{50\text{M} \times 2}{100,000\text{ s}} = \mathbf{1,000\text{ writes/sec}}$ → $\text{Peak Write QPS (3x)} = \mathbf{3,000\text{ writes/sec}}$.
    • $\text{Avg Read QPS} = \frac{50\text{M} \times 40}{100,000\text{ s}} = \mathbf{20,000\text{ reads/sec}}$ → $\text{Peak Read QPS (3x)} = \mathbf{60,000\text{ reads/sec}}$.
  2. Step 2 (Storage — Post Metadata vs Media Blobs):
    • Metadata Row Size: `post_id (8B) + author_id (8B) + text (500B) + media_url (100B) + indexes (~384B)` $\approx \mathbf{1\text{ KB/post}}$.
    • Daily Metadata Storage: $100\text{M posts/day} \times 1\text{ KB} = \mathbf{100\text{ GB/day}} \implies \mathbf{36.5\text{ TB/year}} \implies \mathbf{182.5\text{ TB over 5 years}}$.
    • Daily Media Blob Storage (S3): $100\text{M} \times 20\% = 20\text{M images/day} \times 500\text{ KB} = \mathbf{10\text{ TB/day}} \implies \mathbf{18.25\text{ PB over 5 years}}$.
  3. Step 3 (Cache RAM — Box 4):
    • Caching the hot 20% of the last 7 days of post metadata: $0.20 \times (7 \times 100\text{ GB}) = \mathbf{140\text{ GB of Redis RAM}}$ (easily fits in a 4-primary + 4-replica Redis Cluster with 64 GB RAM per node!).
  4. Step 4 (Bandwidth — Box 1):
    • Metadata Egress: $60,000\text{ peak reads/s} \times (20\text{ posts/feed} \times 1\text{ KB}) = 1.2\text{ GB/s} = \mathbf{9.6\text{ Gbps}}$.
    • Image Egress (Offloaded to CDN): $60,000\text{ reads/s} \times 2\text{ images viewed} \times 500\text{ KB} = 60\text{ GB/s} = \mathbf{480\text{ Gbps}}$ (Proves why a CDN is mandatory—480 Gbps would melt origin NICs!).
  5. Step 5 (Architectural Decisions Unlocked by Our Numbers):
    • Peak Write QPS = 3,000/s fits on 1 primary DB for CPU, BUT 5-Year Metadata = 182.5 TB exceeds the `~4 TB/shard` operational limit → We MUST shard PostgreSQL into 64 shards (~3 TB/shard)!
    • Peak Read QPS = 60,000/s would overwhelm a single DB (`~15K reads/s`) → Redis Cluster (140 GB RAM) absorbs 95% of reads, leaving only `3,000 cache-miss reads/s` across the 64 DB shards (`~47 reads/s` per shard!).
    • Stateless App Pods = $\frac{60,000\text{ Peak QPS}}{3,000\text{ QPS/pod}} = \mathbf{20\text{ Spring Boot pods}}$ across 3 Availability Zones.

§4When to use — Trade-Off Matrix (Right-Sizing vs Over-Provisioning)

Sizing Strategy Pros Cons When to Use
Design for 2–3× Current Peak + Horizontal Shard Hooks Optimal cost-to-safety balance; avoids premature 100-node complexity while ensuring no rewrite at $3\times$ growth. Requires proactive capacity review every 6–12 months. Default Staff-level recommendation in production and interviews.
Design for 100× Current Scale on Day 1 Zero re-architecture if the app goes viral overnight. Massive cloud waste ($50K/month for 100 users) and high operational tax. Only when launching a guaranteed day-1 global product (e.g., Apple/Google OS service or World Cup streaming).

§5Explain it to a 12-year-old (The Feynman Pass)

Imagine you are planning the school pizza party for 500 kids:

  • If you just say "Buy some pizzas and tables!" without doing 60 seconds of math, you might buy 5 pizzas (everyone starves!) or 5,000 pizzas (you waste $50,000!).
  • Instead, you do 4 lines of simple party math:
    1. 500 kids × 2 slices each = 1,000 slices (Total Volume).
    2. 1,000 slices ÷ 8 slices per box = 125 pizza boxes (Storage / Database Shards).
    3. All 500 kids rush the table during the 10-minute lunch bell = 50 kids per minute (Peak QPS).
    4. 1 parent can serve 10 kids per minute, so you need 50 ÷ 10 = 5 serving lines (Stateless App Servers behind a Load Balancer).

Every number tells you exactly how many pizza boxes and how many serving lines to set up!

§7In practice — Production Incidents, FinOps & Interview Playbook

7.1 Production Incident: The Forgotten Index & Replication Multiplier

Incident: Why a "1 TB" Database Filled a 4 TB Disk in Production
  • Symptoms: Disk utilization alert fired at `92% full` on a 4 TB NVMe volume even though raw row data was calculated at only `1.1 TB`.
  • Root Cause: The capacity estimate multiplied `rows × raw column bytes`, forgetting:
    1. Secondary B+Tree Indexes (4 indexes added $+80\%$ storage overhead),
    2. MVCC Dead Tuple / Compaction Headroom (PostgreSQL VACUUM / Cassandra LSM compaction requires $30\%–50\%$ free disk space to merge files without failing!), and
    3. Write-Ahead Log (WAL) retention during long backups.
  • Rule of Thumb: Always multiply raw row size by $1.5\times–2\times$ for indexes/overhead, and never run storage disks above $70\%$ capacity.

7.2 Interview Derivation Playbook (How to Make Capacity Math Score Staff-Level Points)

The Golden Rule of Interview Math: Never write a number on the board and walk away from it! Immediately finish every calculation with the sentence: "...and therefore, on the 7-Box Map, this number forces us to do X."
  • Bad: "Storage is 180 TB over 5 years. Okay, next let's draw the API."
  • Staff-Level: "Storage is 180 TB over 5 years. Since a single PostgreSQL instance becomes operationally painful around 4 TB, this 180 TB number proves a single database won't work—we need ~64 shards partitioned by `user_id`."

§8Pitfalls & Traps

⚠️ Pitfall 1 — Sizing for Average QPS Instead of Peak QPS: If average traffic over 24 hours is `10,000 QPS`, traffic at 4 A.M. is `1,000 QPS` and traffic at 8 P.M. is `30,000+ QPS`. Sizing pods or DB connections for Average QPS guarantees your system crashes every single evening at 8 P.M.! Always size compute, bandwidth, and rate limiters for Peak QPS.
⚠️ Pitfall 2 — Mixing Up Bytes (`B`) and Bits (`b`) in Bandwidth Math: Network cards are rated in Gigabits per second (`Gbps`), while payloads are measured in Bytes (`KB` / `MB`). Remember: $\mathbf{1\text{ Byte} = 8\text{ bits}}$. Moving `1.25 GB/sec` of data saturates a `10 Gbps` network link!

§9Recap & Glossary

  • The 5-Step Capacity Loop: (1) Avg & Peak QPS → (2) 5-Year Metadata & Blob Storage → (3) 20% Hot Cache RAM → (4) Ingress/Egress Bandwidth → (5) Node/Shard Counts.
  • Single-Node Anchors: 1 Spring Boot pod $\approx 3\text{K QPS}$; 1 Redis node $\approx 80\text{K QPS} / 50\text{ GB RAM}$; 1 SQL Primary $\approx 5\text{K–10K writes/s} / 4\text{ TB disk}$; 1 Kafka broker $\approx 100\text{K msgs/s}$.
  • Always Tie Math to Boxes: Every number must justify a specific architectural choice (CDN, Redis size, Shard count, or Pod count).

Glossary

Working Set
The subset of total stored data that is actively queried in a given time window (often modeled via the 80/20 Pareto rule) and must fit in RAM/Cache to avoid disk IOPS bottlenecks.
Headroom
Reserved spare capacity (typically 30%–40% of CPU/disk/IOPS) kept free to absorb unexpected traffic bursts, GC pauses, and Availability Zone failovers without breaching latency SLOs.
