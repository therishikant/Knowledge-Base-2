007 · Latency, Throughput, QPS, Concurrency (Little's Law) & Bandwidth

High-Level System Design (HLD) › Phase 1: Foundations › Topic 7 of 140 · DEEP

0. TL;DR in Simple English — Five words get mixed up constantly in interviews: Latency is how long 1 car takes to drive down the highway (`ms`); Throughput / QPS is how many cars exit the highway per second (`requests/sec`); Concurrency is how many cars are currently on the highway at the exact same instant ($L = \lambda \times W$, Little's Law); and Bandwidth is the width of the highway in bytes/sec (`Gbps`). Understanding how these 4 numbers lock together via Little's Law and the Queueing Knee Curve is the secret to diagnosing every production outage.

§2Why it exists — The Naive Myth: "Average Latency is 30ms, So Everything is Fine!"

Why do production systems meltdown when dashboards show "Average Latency = 30 ms" and "CPU = 40%"?

  1. Trap 1 — Average Latency Hides the p99 Tail (& Tail Latency Amplification): Suppose 99 out of 100 requests hit Redis in `2 ms`, and 1 request hits a slow unindexed DB query + GC pause taking `2,800 ms`. The arithmetic mean is $\frac{99(2) + 2800}{100} = \mathbf{29.98\text{ ms}}$ ("looks great!"), while 1 in 100 requests takes nearly 3 seconds! Worse: if your homepage calls 20 microservices in parallel and each service has a `1%` chance of a slow p99 spike, the probability that your homepage waits for at least one slow service is $1 - (0.99)^{20} = \mathbf{18.2\%}$ of all page loads! (Jeff Dean & Luiz André Barroso — The Tail at Scale, CACM)
  2. Trap 2 — Ignoring Little's Law ($L = \lambda \times W$): If your service handles $\lambda = 1,000\text{ QPS}$ and each request takes $W = 0.02\text{ s}$ (`20 ms`), you only have $L = 1,000 \times 0.02 = \mathbf{20}$ concurrent requests in flight at any moment. Your 200-thread Tomcat pool is 90% idle. Now a downstream payment API slows down from `20 ms` to `1.0 second` ($W = 1.0\text{ s}$). Even though traffic (`1,000 QPS`) and CPU did NOT increase, concurrency jumps to $L = 1,000 \times 1.0 = \mathbf{1,000\text{ concurrent requests}}$—instantly exhausting all 200 Tomcat threads and freezing the entire JVM!

§3How it works — Little's Law, M/M/1 Queueing Knee & Tail Percentiles

3.1 Level 1 (Inside the Box): The Highway & Queueing Diagram

3.2 The 5 Metrics Defined Precisely

Metric Unit Exact Meaning & Formula How It Breaks
Latency ($W$) ms or s Total time a single request spends from arrival to response: $W = T_{\text{queue}} + T_{\text{service}}$. Queueing delay ($T_{\text{queue}}$) explodes exponentially when utilization $\rho \to 100\%$.
Percentiles (`p50`, `p95`, `p99`, `p99.9`) ms If `p99 = 180 ms`, then 99% of requests finish in $\le 180\text{ ms}$ and the slowest 1% take $> 180\text{ ms}$. GC pauses, lock contention, cold cache misses, and noisy neighbors hit `p99` first while `p50` stays flat.
Throughput / QPS ($\lambda$) req/sec or ops/sec Rate of requests completed per second. Max single-resource throughput is bounded by $\lambda_{\max} = \frac{\text{Concurrency Capacity}}{T_{\text{service}}}$. When a system passes 100% capacity without load shedding, throughput actually drops (congestion collapse) due to context-switching & retries!
Concurrency ($L$) In-flight requests / threads Little's Law: $L = \lambda \times W$. Number of requests simultaneously inside the box. Exceeds Tomcat thread pool (`200`), HikariCP DB pool (`20`), or OS file descriptors (`65,535`).
Bandwidth Gbps or MB/s $\text{Bandwidth} = \lambda \times \text{Payload Size}$. Saturates NIC or switch buffer (`10 Gbps = 1.25 GB/s`), causing TCP packet drops and retransmissions.

3.3 Code Dissection — Computing HikariCP & Tomcat Pool Sizes + Bounding Tail Latency in Spring Boot

// ============================================================================
// 1. HOW TO SIZE HIKARICP CONNECTION POOL (PostgreSQL Official Formula):
//    connections = (core_count * 2) + effective_spindle_count
//    For an 8-core DB server on SSD: ~18 to 25 connections PER DB NODE total!
//    Why so small? Because 500 concurrent active SQL queries thrash CPU caches
//    and LWLocks! Let requests queue cleanly in memory rather than thrashing DB CPU.
// ============================================================================

// 2. BOUNDING CONCURRENCY (L) IN SPRING BOOT USING LITTLE'S LAW + SEMAPHORE:
//    Suppose Downstream Inventory RPC supports λ = 500 QPS at W = 50ms (0.05s).
//    By Little's Law: Normal Concurrency L = 500 * 0.05 = 25 in-flight calls.
//    We cap concurrency at L_max = 40 and timeout at W_max = 150ms so a slow
//    Inventory Service can NEVER consume more than 40 of our 200 Tomcat threads!

@Service
public class BoundedInventoryClient {
    private final Semaphore bulkhead = new Semaphore(40); // Caps L ≤ 40 threads!
    private final HttpClient http = HttpClient.newBuilder().build();

    public InventoryDto fetchStock(Long itemId) {
        if (!bulkhead.tryAcquire()) {
            // Fail fast in 100 nanoseconds instead of queuing to death!
            throw new BulkheadFullException("Inventory concurrency cap (40) reached");
        }
        try {
            HttpRequest req = HttpRequest.newBuilder()
                .uri(URI.create("http://inventory-svc/v1/items/" + itemId))
                .timeout(Duration.ofMillis(150)) // Caps W ≤ 0.15s!
                .build();
            // ... execute request ...
            return new InventoryDto(itemId, 10);
        } finally {
            bulkhead.release();
        }
    }
}

§4When to use — Latency vs Throughput Optimization Trade-Offs

Optimization Technique Effect on Throughput (QPS / MB/s) Effect on Latency ($W$) Where We Use It on the 7-Box Map
Micro-Batching (`linger.ms = 5ms` in Kafka / Group Commit in DB WAL) Massive increase ($10\times–50\times$) by amortizing network RTT and disk `fsync` across 100 events. Slightly increases `p50` latency by `+2–5 ms` while waiting for the batch to fill. Box 5 (Kafka Producers) & Box 6 (Database WAL Group Commit).
Hedged Requests (Send duplicate read to Replica 2 if Replica 1 hasn't replied in `p95 = 10ms`) Costs $+5\%$ extra QPS load on the cluster. Slashes `p99.9` tail latency by $70\%+$ by routing around transient GC/disk hiccups. Box 2 → Box 4/6 read paths at Google/AWS scale.

§5Explain it to a 12-year-old (The Feynman Pass)

Picture a Starbucks coffee shop:

  • Latency ($W$) is how many minutes you stand inside the shop from the moment you walk in the door until you walk out holding your latte (say, `3 minutes`).
  • Throughput ($\lambda$) is how many customers walk out the door with coffee per minute (say, `5 customers/minute`).
  • Concurrency ($L$, Little's Law) is how many people are standing inside the shop right now: $\text{5 customers/min} \times \text{3 min} = \mathbf{15\text{ people inside the room}}$.
  • Now imagine the espresso machine gets jammed so each latte takes `30 minutes` ($W = 30$) instead of `3 minutes`, while `5 new people` still walk in the door every minute! Suddenly $\text{5} \times \text{30} = \mathbf{150\text{ people}}$ are crammed inside a tiny room built for 30 people—nobody can move, the fire marshal shuts the building down, and even people who just wanted a bottle of water can't get inside! That is why we put a bouncer at the door (Load Shedding / Bulkhead) and a timer on the espresso machine (Timeout).

§7In practice — Why M/M/1 Queueing Math Forbids Running Servers at 95% CPU

The Mathematical Proof of the 70% Utilization Rule:

In queueing theory (Kingman's formula / M/M/1 queue), average total latency $W$ as a function of server utilization $\rho \in [0, 1)$ and base service time $T_s$ is: $$W = \frac{T_s}{1 - \rho}$$ Look at what happens to a `10 ms` ($T_s = 10\text{ ms}$) API endpoint as CPU utilization $\rho$ rises:

  • At $\rho = 50\%$ utilization: $W = \frac{10\text{ ms}}{1 - 0.50} = \mathbf{20\text{ ms}}$ (Smooth!).
  • At $\rho = 70\%$ utilization: $W = \frac{10\text{ ms}}{1 - 0.70} = \mathbf{33\text{ ms}}$ (Still fast—the edge of the safe zone).
  • At $\rho = 90\%$ utilization: $W = \frac{10\text{ ms}}{1 - 0.90} = \mathbf{100\text{ ms}}$ ($10\times$ base latency!).
  • At $\rho = 98\%$ utilization: $W = \frac{10\text{ ms}}{1 - 0.98} = \mathbf{500\text{ ms}}$ ($50\times$ base latency—and p99 is in the multi-seconds!).

Architect's Rule: Auto-scale your stateless Box 2 fleet when CPU or thread utilization crosses 65%–70%, never 95%!

§8Pitfalls & Traps

⚠️ Pitfall 1 — Averaging Percentiles Across Servers ("The Average of p99s"): Never take the `p99` metric from 20 pods and average them together! Percentiles are statistically non-aggregatable by averaging. In Prometheus/Datadog (Box 7), always aggregate latency using Histogram buckets (`histogram_quantile(0.99, sum(rate(http_bucket[1m])) by (le))`) or DDSketch.
⚠️ Pitfall 2 — Fixing a Concurrency Bottleneck by Setting `tomcat.max-threads = 5000`: In platform-thread Java, 5,000 OS threads consume `~5 GB` of stack memory (`1 MB/thread`) and spend all CPU time in OS kernel context-switching. Instead of bloating OS thread pools, bound latency ($W$) with timeouts, cache hot reads, or use non-blocking I/O / Java 21 Virtual Threads (`spring.threads.virtual.enabled=true`) while still protecting the downstream DB with a small HikariCP pool!

§9Recap & Glossary

  • Little's Law ($L = \lambda \times W$): In-flight concurrency equals arrival QPS times average response time.
  • Tail Latency Amplification: Calling $N$ services in parallel multiplies the probability that the user experiences the slowest service's `p99`.
  • The 70% Utilization Knee: Because $W = \frac{T_s}{1 - \rho}$, queueing wait time grows hyperbolically past 70%–80% utilization.

Glossary

p99 (99th Percentile Latency)
The response time threshold below which 99% of requests complete; reflects the experience of your slowest 1% of requests (and often your most valuable, data-heavy customers!).
Hedged Request
A tail-latency reduction technique where a client sends a secondary read request to a replica if the first request takes longer than the `p95` latency, taking whichever response returns first.
