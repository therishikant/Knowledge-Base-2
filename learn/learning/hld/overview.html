LEVEL 1Opening the 7 Boxes: What Plain Data Structure Lives Inside Each?

In our Spring course, we demystified ApplicationContext by showing it is just a ConcurrentHashMap<String, Object>. We do the exact same thing in System Design: every piece of distributed infrastructure is just a familiar in-memory or on-disk data structure wrapped in a network socket.

Box 1 Inside: OS Kernel Socket Queues, Connection Pools & Routing Tables

Covers: DNS, CDN, L4/L7 Load Balancers, Reverse Proxy, API Gateway (Topics 11–22)

A Load Balancer or API Gateway is not magic hardware. Inside Linux/JVM, every listening port holds two kernel ring-buffer queues (syn_backlog for half-open handshakes and accept_queue for completed connections) plus an in-memory routing table:

// Inside an L7 Load Balancer / Reverse Proxy (Netty / Envoy / Nginx):
Map<String, List<InetSocketAddress>> routeTable = new ConcurrentHashMap<>(); // "/api/v1/orders" -> [10.0.1.4:8080, 10.0.1.5:8080]
Map<InetSocketAddress, Deque<SocketChannel>> keepAlivePool = new ConcurrentHashMap<>(); // Reuses warm TCP+TLS sockets!

// Power-of-Two-Choices Load Balancing (O(1) — avoids herding onto one slow server):
InetSocketAddress pickBackend(List<Server> healthyPool) {
    Server a = healthyPool.get(random.nextInt(healthyPool.size()));
    Server b = healthyPool.get(random.nextInt(healthyPool.size()));
    return (a.activeRequests.get() <= b.activeRequests.get()) ? a.address : b.address;
}

Box 2 Inside: Worker Thread Pools, Service Registry Maps & Idempotency Keys

Covers: Stateless Compute, Service Discovery, REST/gRPC/WS, Idempotency, Outbox, Sagas (Topics 23–36)

Inside each microservice is your familiar Spring Boot Tomcat ThreadPoolExecutor (or Java 21 Virtual Threads / Netty EventLoop). Across services, safe retries and transactional messaging rely on two plain SQL tables inside the service's database:

// Inside a Payment/Order Service (Handling Safe Retries + Outbox Dual-Write Prevention):
@Transactional // Single local ACID transaction on 1 DB connection!
public OrderResult createOrder(String idempotencyKey, OrderRequest req) {
    // 1. Atomic Idempotency Guard: INSERT INTO idempotency_keys (key, status) VALUES (?, 'IN_PROGRESS') ON CONFLICT DO NOTHING
    if (!idempotencyRepo.tryClaimKey(idempotencyKey)) {
        return idempotencyRepo.getSavedResponse(idempotencyKey); // Safe duplicate retry!
    }
    Order order = orderRepo.save(new Order(req));
    // 2. Transactional Outbox: Write event to local SQL table in the SAME commit (never call Kafka directly inside @Transactional!)
    outboxRepo.save(new OutboxEvent(order.getId(), "ORDER_CREATED", toJson(order)));
    return idempotencyRepo.completeKey(idempotencyKey, OrderResult.from(order));
}

Box 3 Inside: Token Buckets, Semaphore Bulkheads & Circuit Breaker State Machines

Covers: Rate Limiting, Backpressure, Timeouts, Retries + Jitter, Circuit Breakers, Bulkheads (Topics 58–59, 71–75)

Resilience patterns are tiny state counters that stop a slow downstream dependency from exhausting all 200 Tomcat threads in your caller:

// 1. Token Bucket Rate Limiter (2 numbers per user/key):
class TokenBucket {
    double tokens = MAX_BURST;
    long lastRefillNanos = System.nanoTime();
    synchronized boolean allowRequest() {
        long now = System.nanoTime();
        tokens = Math.min(MAX_BURST, tokens + (now - lastRefillNanos) * REFILL_RATE_PER_NS);
        lastRefillNanos = now;
        if (tokens < 1.0) return false; // Return HTTP 429 Too Many Requests immediately!
        tokens -= 1.0;
        return true;
    }
}
// 2. Bulkhead = java.util.concurrent.Semaphore(20) — caps concurrent calls to Service B at 20 so 180 Tomcat threads stay free!
// 3. Circuit Breaker = AtomicReference<State> (CLOSED -> OPEN when failureRate > 50% in sliding ring buffer -> HALF_OPEN probe).

Box 4 Inside: Hash Table + Doubly-Linked List (LRU) + Singleflight Stampede Lock

Covers: App Cache (Caffeine), Redis Internals, Eviction, Cache Invalidation, Stampede Protection (Topics 52–57)

Why is Redis so fast (~100,000+ QPS on 1 core)? Because a single-threaded event loop reads commands from epoll sockets and mutates an in-memory Hash Table (dict) or SkipList (zset) in ~100 nanoseconds with zero thread locks:

// Inside an O(1) LRU Cache + Singleflight Stampede Protection:
Map<String, Node> hashIndex = new HashMap<>();         // O(1) lookup by key
DoublyLinkedList<Node> recencyList = new DoublyLinkedList<>(); // O(1) move-to-head on read; O(1) evict-tail when RAM full
ConcurrentMap<String, CompletableFuture<Product>> inFlight = new ConcurrentHashMap<>(); // Singleflight coalescing!

// If 10,000 threads miss hot key "iphone-16" at the exact same millisecond, ONLY ONE hits the DB:
Product getProduct(String key) {
    Product cached = cache.get(key);
    if (cached != null) return cached;
    return inFlight.computeIfAbsent(key, k -> CompletableFuture.supplyAsync(() -> {
        Product p = db.query(k);
        cache.put(k, p, ttlWithJitter(300)); // Add random jitter so keys don't expire together!
        inFlight.remove(k);
        return p;
    })).join();
}

Box 5 Inside: Append-Only Segment Files, Sparse Index & OS Zero-Copy

Covers: Message Queues, Pub/Sub, Kafka Brokers/Partitions/ISR, Consumer Groups, DLQ (Topics 61–70)

Why can Kafka handle millions of messages per second on spinning disks or SSDs? Because it never does random disk updates. A Kafka Partition is literally an append-only file plus an integer offset counter:

// Inside a Kafka Broker Partition Folder (/data/orders-topic-partition-0/):
FileChannel segmentLog = FileChannel.open("00000000000000000000.log", APPEND);   // Sequential byte append only!
FileChannel sparseIndex = FileChannel.open("00000000000000000000.index", READ_WRITE); // Maps Offset -> Physical Byte Position

// Producer append = O(1) sequential write to OS Page Cache:
long assignedOffset = nextOffset++;
segmentLog.write(serializeRecord(assignedOffset, key, payload));

// Consumer read at offset 48,291 = Binary search sparseIndex -> Zero-Copy DMA transfer directly from Page Cache to NIC!
long fileBytePos = binarySearchBytePosition(sparseIndex, 48291L);
segmentLog.transferTo(fileBytePos, batchSize, consumerSocketChannel); // Linux sendfile() — zero copies into JVM heap!

PLAYBOOKThe 5 Universal Laws of System Design (Derive, Don't Memorize)

Whenever an interviewer asks "Why does X break at 50,000 QPS?" or "Why did you pick X over Y?", you never need to guess. Every phenomenon in distributed systems is governed by one of these 5 Universal First-Principles Laws:

Law 1: The Physics of Hardware (Latency Hierarchy & Sequential vs Random I/O)

Software runs on physical silicon and fiber-optic cables. Two hardware facts dictate almost every storage and caching design (Jeff Dean / Peter Norvig — Latency Numbers Every Programmer Should Know):

  • The Distance Ladder: CPU L1/L2 Cache (~1–4 ns) → RAM (~100 ns) → Local NVMe SSD (~100 μs = 1,000× slower than RAM) → Same-Datacenter Network Round-Trip (~500 μs) → Cross-AZ Round-Trip (~1–2 ms) → US-to-Europe/Asia Transoceanic Fiber (~100–150 ms = 1,000,000× slower than RAM).
  • Sequential Append vs Random Seek: Appending bytes sequentially to the end of a file is orders of magnitude faster than seeking to random disk blocks and updating in place. This single hardware fact explains why Database Write-Ahead Logs (WAL), Kafka Segment Logs, Event Sourcing, and LSM-Trees exist!

Law 2: Follow the State (Where Does State Live?)

Ask of every box: "If I pull the power plug on this server right now, or put a Load Balancer in front of 10 copies of it, what state is lost or inconsistent?"

  • Stateless Compute (Easy to Scale): If a worker holds zero client session or lock state in its local RAM/disk between requests, you can scale from 2 servers to 200 servers behind a Load Balancer in seconds.
  • Stateful Storage (Hard to Scale): The moment state lives on a machine (logged-in session, WebSocket TCP connection, local cache, database row, distributed lock), horizontal scaling requires either pushing state to the client (signed JWT), sticky routing (consistent hashing), or replicated consensus/quorum storage.

Law 3: Little's Law, Queueing & Blast Radius (L = λ × W)

In any system at steady state, the number of active concurrent requests in flight (L) equals the arrival rate (λ = QPS) multiplied by the average response time (W = Latency):

  • Example: At λ = 1,000 QPS and fast database latency W = 10 ms (0.01 s), your Spring Boot server only has L = 1,000 × 0.01 = 10 active threads working at any instant.
  • Why Slow Is Worse Than Down: If a downstream service slows down from 10 ms to 2 seconds, then L = 1,000 × 2 = 2,000 concurrent requests! Your 200 Tomcat threads fill up in 200 milliseconds, queues explode, and the entire upstream fleet crashes (Cascading Failure)—unless guarded by Strict Timeouts + Bulkheads + Circuit Breakers + Load Shedding.

Law 4: No Free Coordination Across a Network (CAP / PACELC / Two Generals)

The moment the same piece of truth lives in more than one place (Primary DB + Read Replica, DB + Redis Cache, Postgres + Kafka, Region US + Region EU), network packets will be delayed, dropped, or duplicated:

  • During a Partition (CAP) & During Normal Operation (PACELC): You must trade off Synchronous Coordination (blocking the caller until a quorum/replica confirms, paying cross-network latency and availability risk) vs Asynchronous Propagation (returning fast in ~2 ms, accepting temporary replication lag / stale reads, and repairing via Idempotency Keys + Transactional Outbox + Sagas + Read-Your-Own-Writes).

Law 5: Every Optimization Shifts the Bottleneck

No architectural pattern is free. A Senior/Staff engineer immediately names the new problem created by their own solution:

  • Add a Cache (Box 4) to save the DB → creates Cache Invalidation bugs, Cold-Cache Stampedes, and Hot-Key bottlenecks.
  • Shard the Database (Box 6) to scale writes → breaks Cross-Shard Joins/Transactions and risks Hot Partitions (Celebrity Problem).
  • Add Network Retries (Box 3) to mask transient blips → creates Retry Storms (without exponential backoff + jitter) and Double Charges (without idempotency keys).
  • Add Async Queues (Box 5) to smooth traffic spikes → creates Consumer Lag, Out-of-Order Events, and Duplicate Delivery.

Glossary (Core Foundation Terms)

HLD (High-Level Design)
Macro-level system architecture: processes, network protocols, caches, queues, databases, sharding, replication, and multi-region topology across the 7 Boxes.
LLD (Low-Level Design)
Micro-level software design inside a single process (Box 2): classes, interfaces, design patterns, thread safety, and in-memory object graphs.
QPS / RPS (Queries / Requests Per Second)
The rate of incoming requests arriving at a component ($\lambda$ in Little's Law).
Tail Latency (p95 / p99 / p99.9)
The response time experienced by the slowest 5%, 1%, or 0.1% of requests. If p99 is 1.8s, 1 out of every 100 requests takes at least 1.8s.
Little's Law ($L = \lambda \times W$)
Fundamental queueing law stating that concurrent in-flight requests ($L$) equal arrival rate ($\lambda$) times average latency ($W$).
SLO / SLI / SLA
SLI is the quantitative measurement (e.g., 99th percentile latency or % of HTTP 2xx/3xx responses); SLO is the internal engineering target (e.g., 99.95% availability); SLA is the external legal contract with financial penalties if breached.
WAL (Write-Ahead Log)
An append-only disk file where every database mutation is sequentially recorded and flushed (`fsync`) before modifying in-memory pages, guaranteeing crash durability at sequential I/O speed.
CAP / PACELC
During a network Partition ($P$), a distributed data store must choose between linearizable Consistency ($C$) and 100% Availability ($A$). Even when no partition exists ($E$), it must choose between low Latency ($L$) and strong Consistency ($C$).
