The Bytecode Pipeline

Java › JVM cluster · lesson 1 of 4 · DEEP — the complete journey from source to running program

In one line — Running Hello.java takes six steps: you type the code → javac turns it into bytecode → the java command starts the JVM → the class loader brings your class in → the engine runs main (slow at first, then fast) → the JVM stops. This lesson walks through all six steps. The next three lessons open up the loader, the memory, and the engine one by one.

§1Where it fits

This is the big map for all four JVM lessons. Get the whole path in your head first. After that, every hard question becomes easy — "why is start-up slow?", "where does StackOverflowError come from?", "why can Kotlin run on the JVM?" All of them are really just: which step are we talking about?

§2Why it exists — the one big idea

Java had one main goal: write once, run anywhere. The same program should run on any computer — Windows, Mac, Linux — with no changes (Oracle, JVM Spec SE 21, §1.1). Here is the trick. Java does not turn your code into machine code made for one kind of computer. It turns it into bytecode — a simple middle language. Then a small program called the JVM lives on each computer and reads that bytecode. Because the JVM sits in the middle, your code does not care which computer it lands on. The JVM only understands bytecode — it does not even know the word "Java" (§1.2). Every step below is there to make this one idea work.

§3How it works — the complete flow

1
You write the code. Hello.java is just text you can read. It does not belong to any one computer yet.
2
javac turns it into bytecode. The compiler reads your code, checks the types, and looks up names — all now, before the program runs. So most mistakes are caught here, not later. Then it writes a .class file. Note: it does not make machine code. It makes bytecode. Because the types are already checked here, the JVM can skip most of that work later (§2.2).
3
The .class file. This is the file the JVM reads. Inside it: a start tag (0xCAFEBABE), a version, a constant pool (a list of all the names the class uses), and the bytecode for each method (§2.1).
4
java Hello starts the JVM. This command starts the JVM, loads your class, gets it ready, and calls your public static void main(String[]) method (§5.2). That one call kicks off everything else.
5
Loading the class. The class loader finds the bytes of Hello.class, checks they are safe, sets up its fields, and links up the names it uses. Classes are loaded only when first needed, not all at once. (Lesson 2 covers this in detail.)
6
Running the code. For each method call, the JVM makes a frame — a small workspace that holds the method's values. The engine runs the bytecode. It reads it line by line at first, then turns the busy parts into fast machine code. New objects go on the heap (shared memory), and the garbage collector quietly clears out ones you no longer use. When main finishes and no other work is left, the JVM stops (§5.7). (Lessons 3 & 4 cover the memory and the engine.)

§4When this matters

  • Seeing the whole map — most JVM interview questions are just "which step?"
  • Build error vs run error — a compile error (step 2) is not the same as a NoClassDefFoundError (step 5).
  • Other languages on the JVM — Kotlin, Scala, and Groovy also make .class files, so they join at step 3 and run the same way.

§5Explain it to a 12-year-old

You write a story (your code). A translator (javac) rewrites it in a picture-language that every robot can read (bytecode). To act out the story, a robot (the JVM) picks up the pictures, checks they are safe, grabs some scratch paper (memory and frames), and starts acting. It is slow at first. Once it has seen a scene many times, it remembers it and does it fast (the fast-code step). A helper keeps clearing away props nobody is using (garbage collector). When the story ends, the robot goes home (the JVM stops).

§7In practice — watch the hand-offs happen

Real commands on a JDK (javac 1.8.0_411), tracing Hello through the pipeline:

# step 1–2: write, then compile
$ javac Hello.java        # produces Hello.class (bytecode)

# step 3: inspect the bytecode the JVM will run
$ javap -c Hello

# step 4–6: boot the JVM and run main
$ java Hello
sum=5

The bytecode that javap shows is the same bytecode the loader checks (step 5) and the engine runs (step 6):

  static int add(int, int);
    Code:
       0: iload_0      // put a on the pile
       1: iload_1      // put b on the pile
       2: iadd         // take a and b off, put a+b back
       3: ireturn      // hand back the top value
The JVM works like a pile of plates: you put values on top, and each step takes values off the top and puts a result back. Each step also says its type (i = int). The compiler already checked the types in step 2, so here the engine just adds and returns — no guessing. Compiler checks, JVM runs: that split is what makes it fast.
Try this: run java -verbose:class Hello. Now watch the class loader (step 5) print every class as it loads it, in order. You will see java.lang.Object, then String, then Hello. That list is the JVM showing you its own steps.

§8Watch out for

Mixing up build errors and run errors. A missing semicolon breaks at step 2 (javac). A missing class breaks at step 5 (NoClassDefFoundError). Different steps.
Thinking javac makes an .exe. It makes bytecode, not machine code. Machine code shows up later, at step 6, when the busy parts get sped up.
Thinking every class loads at start. Classes load only when first used. So a class used deep inside the program loads late — which is why some errors show up late too.

§9Recap

  • Six steps: write → compile → .class → start → load → run → stop.
  • Steps 1–3 happen when you build. Steps 4–6 happen when you run, inside the JVM.
  • javac makes bytecode, not machine code. It checks types early so the JVM does less later.
  • The .class file (start tag 0xCAFEBABE + constant pool + method bytecode) is what the JVM reads.
  • Classes load only when first needed. The JVM stops when main is done and no work is left.
  • The next three lessons open up the loader, the memory and frames, and the engine.

Glossary

Bytecode
The JVM's portable instruction set, stored in .class files.
Constant pool
Per-class symbol table of names and references inside the .class file.
Launcher
The java command that creates a JVM and calls main.
Lazy loading
Classes are loaded on first active use, not all up front.
JIT
Just-In-Time compiler; turns hot bytecode into native code at run time.
