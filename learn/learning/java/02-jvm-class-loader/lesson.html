The Class Loader Subsystem

Java › JVM cluster · lesson 2 of 4 · DEEP — finding, verifying, and preparing types

In one line — The class loader turns the bytes of a .class file into a live, ready-to-use class. It does this in three stages — Load → Link (check · set up · wire) → Start. It loads a class only when first needed, and it always asks its parent loader first. This is where the JVM checks that code is safe to run.

§1Where it fits

This is step 5 of the bytecode pipeline. Nothing can run until a class is loaded and ready. Getting it there is the class loader's job.

§2Why it exists

Java code can come from many places — a jar file, a download, even code made on the fly. The JVM must not trust it blindly. So it needs a careful way to bring in new classes and check them first. That is what the class loader does: find the bytes, make sure they are safe, and wire the class into the running program. It also lets you write your own loader — for example, to pull classes from an encrypted file or keep plugins separate (JVM Spec SE 21, §5.3).

§3How it works — three phases

Loading

The loader finds the bytes for a class name and turns them into a class in memory. If it cannot find the bytes, you get ClassNotFoundException, which shows up as NoClassDefFoundError where the class is used (§5.3.1).

Linking = check → set up → wire

  • Check (verify) — makes sure the bytecode is well-formed and safe. A bad file gives VerifyError. This check is why even code you don't trust is safe to run (§5.4.1).
  • Set up (prepare) — creates the class's static fields and gives them starting values (0, null, false). Your real values are not set yet (§5.4.2).
  • Wire (resolve) — turns the names in the constant pool (#n) into real links to other classes, loading them if needed. This can happen later, when first used (§5.4.3).

Start (initialize)

Runs <clinit>: your static field values and static { } blocks, top to bottom. The JVM promises this runs once, safely, even if many threads hit the class at the same time (§5.5). This is the trick behind the "holder" singleton pattern.

Starting value vs your value — a favourite trick question. During set up, static int COUNT = 5; first becomes 0. Your 5 is only put in later, during start (<clinit>). So if a class reads its own static too early, it can see 0. Order matters.

§4Asking the parent first, and class identity

There are three built-in loaders: Bootstrap (loads the core classes like Object and String), Platform, and Application (loads your own classes). When a loader needs a class, it asks its parent first. Only if the parent cannot find it does the loader try itself. This means nobody can sneak in a fake java.lang.String — the core classes always come from the trusted bootstrap loader.

One more key idea: a class's identity is its name plus the loader that loaded it. So the same class file loaded by two different loaders becomes two different classes. Mixing them gives a ClassCastException or LinkageError (§5.3.4). This is exactly how an app server keeps two web apps apart even when both ship a class called com.acme.Util.

§5When this matters

  • Inside frameworks — Tomcat, OSGi, and Spring Boot fat-jars all use custom loaders to keep parts separate or reload them.
  • Dependency problems — NoClassDefFoundError and LinkageError are almost always loader or classpath problems.
  • Safety — the safety check is why browsers could once run untrusted applets.

§6Explain it to a 12-year-old

A librarian (the loader) gets a book only when you ask for it. Before putting it on the shelf, they check it has nothing dangerous inside (check), stick blank notes where the totals will go (set up), look up every other book it mentions (wire), and then fill in the totals (start). And they always ask the head librarian first, so no one can slip in a fake copy of an important book (ask the parent first).

§8In practice — watch loading happen

$ java -verbose:class Hello
[Loaded java.lang.Object from ...]
[Loaded java.lang.String from ...]
...
[Loaded Hello from file:...]        // your class, loaded lazily, last
sum=5
The order shows the two rules in action. Core java.lang classes load first, from the bootstrap loader, because Hello needs them. Hello itself loads last, and only when the JVM actually needs it.
Try this: make a class with static { System.out.println("init!"); }, and a main that only mentions it inside an if (false) block. Does "init!" print? Guess first, then run it. You are seeing "load only when needed" in action.

§9Watch out for

ClassNotFoundException vs NoClassDefFoundError. The first: the loader could not find the bytes (often during a reflection lookup). The second: the class was there when you built, but missing or broken when you ran.
Thinking statics get your values in "set up." They only get starting values there (0/null). Your real values come in "start."
Forgetting the loader is part of a class's identity. Same bytes, two loaders = two classes that do not match.

§10Recap

  • Three stages: Load → Link (check·set up·wire) → Start.
  • Check makes code safe; set up gives starting values; wire links up names; start runs once, safely.
  • Classes load only when needed. Loaders ask the parent first.
  • A class's identity = its name + its loader. This lets apps stay separate, and causes "same class" mismatches.

Glossary

Defining loader
The loader that actually created a class (part of its identity).
Delegation
Asking the parent loader before loading a class yourself.
Linking
Verify → prepare → resolve; wiring a class into the running JVM.
<clinit>
The class initializer method the JVM runs once per class.
Metaspace
Native-memory method area where loaded class metadata lives.
