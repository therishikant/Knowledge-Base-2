Runtime Data Areas & Frames

Java › JVM cluster · lesson 3 of 4 · DEEP — where state lives, and the anatomy of a stack frame

In one line — To run your code, the JVM needs memory. It splits that memory into parts. Some parts are shared by every thread (the Heap and the Method Area). Some parts are private to one thread (the PC, the JVM Stack, and the Native stack). The JVM Stack is a pile of frames — one frame per method call. Each frame holds the method's values and its little work area. Frames are where method running really happens.

§1Where it fits

This opens up step 6 of the bytecode pipeline. Once a class is loaded (lesson 2), running it means using memory, and making a frame for every method call. Understanding this is what lets you see why StackOverflowError and OutOfMemoryError are different, how deep recursion can go, why each thread costs memory, and (later) why threads need careful rules to share data safely.

§2Why it exists

A running program has two very different kinds of data. First, long-lived objects that many parts of the program share. Second, short-lived scratch data for one method call — its inputs, its local variables, its in-between results — which should be private to one thread and thrown away when the call ends. The JVM gives each kind its own home: a shared heap for objects, and a private pile of frames for calls (JVM Spec SE 21, §2.5). Splitting memory this way is what lets many threads run at once without stepping on each other.

§3How it works — the five areas

Shared (made when the JVM starts, gone when it stops):

  • Heap — holds every object and array. This is the only part the garbage collector cleans. Full → OutOfMemoryError: Java heap space (§2.5.3).
  • Method Area — holds facts about each class: its fields, its methods, its method bytecode, and its list of names (the constant pool) (§2.5.5). Today this is called Metaspace, which Java 8 moved out into normal system memory (the end of the old "PermGen") (§2.5.4).

Private to each thread (made with the thread, gone with it):

  • PC — remembers which instruction the thread is running right now (§2.5.1).
  • JVM Stack — the pile of frames. Too many → StackOverflowError (§2.5.2).
  • Native stack — used when Java calls code written in C (JNI) (§2.5.6).

§4Frames — up close

This is the part you asked to see. Think of a frame as one sheet of scratch paper for one method call. The spec says a frame is used "to store data and partial results, as well as to perform dynamic linking, return values for methods, and dispatch exceptions" (JVM Spec §2.6).

The rules of a frame

  • One frame per method call. A new frame is made every time you call a method, and thrown away when that call ends — whether it returns a value or throws an error (§2.6).
  • Frames sit on the thread's stack. A frame belongs to one thread only. No other thread can touch it.
  • Only the top frame is "live." That is the method running right now. When it calls another method, a new frame goes on top and becomes the live one. When that method returns, the frame below wakes up again (§2.6).
  • The size is known before it runs. The compiler already wrote down how many value-slots and how much work space each method needs, so the frame's size is set before it is even made (§2.6, §4.7.3).

What's inside a frame

Three things (§2.6.1–§2.6.3):

PartWhat it isKey facts
Value slots (local variables)Numbered boxes for the method's inputs and local variables. For an instance method, box 0 holds this, then the inputs follow. For a static method the inputs start at box 0. A long or double uses two boxes (§2.6.1).
Work pile (operand stack)A small pile where the method does its math. Empty when the frame is made. Steps put values on top and take them off. iadd takes two ints off and puts their sum back. It also holds the inputs when calling another method, and catches the result (§2.6.2).
Link to the name listA pointer to this class's constant pool. Lets the JVM turn a name (#2) into a real method or field the first time it is used (§2.6.3).

Why recursion has a limit. Each time a method calls itself, another frame goes on the stack. The stack has a fixed size, so enough calls fill it up → StackOverflowError. This is not about the heap — the objects might be tiny. It is the frames piling up. You can make the stack bigger with -Xss, but the real fix is usually to stop calling so deep.

§5When this matters

  • Fixing a StackOverflowError — read the stack trace. The same method repeating means runaway recursion.
  • Thread cost — every thread needs its own stack. Thousands of threads means a lot of stack memory. (This is a big reason virtual threads were added later.)
  • Reading a debugger — the "call stack" panel is this pile of frames. The "locals" are the value slots.

§6Explain it to a 12-year-old

Every time you start a task, you grab a fresh sheet of scratch paper (a frame). On it you write the numbers you were given (the value slots) and do your rough working in a little column (the work pile). If your task needs a smaller task, you grab another sheet and put it on top — you can only work on the top sheet. When the smaller task is done, you copy its one answer onto the sheet below, then throw the finished sheet away. Stack up too many sheets and you run out of desk — that is a stack overflow.

§8In practice — see the frame sizes

javap -v prints each method's pre-computed frame limits. Real output for add:

  static int add(int, int);
    Code:
      stack=2, locals=2, args_size=2   // max operand depth 2, 2 local slots
       0: iload_0
       1: iload_1
       2: iadd
       3: ireturn
stack=2 means the work pile never holds more than two values (we put a and b on it). locals=2 means two value slots (a and b). The JVM reads these numbers to size the frame before running a single step — it never has to grow it (§4.7.3).
Guess, then check: add a third input int c and return a+b+c. Before you run javap -v, guess the new stack= and locals= numbers. (Hint: three slots now; but the work pile still only holds two values at once, because iadd keeps folding pairs into one.)

§9Watch out for

Mixing up the two stacks. The JVM stack is the pile of frames. The work pile is a tiny area inside one frame. Different things.
Thinking locals live on the heap. A number and an object pointer live in the frame's value slots (private to the thread). The object it points to lives on the shared heap.
Blaming the heap for a StackOverflowError. Deep recursion fills the thread's stack, not the heap.
Thinking a long uses one slot. long and double each use two.

§10Recap

  • Memory splits into shared (Heap, Method Area) and private to each thread (PC, JVM Stack, Native stack).
  • A frame is made for each method call, sits on the thread's stack, and is thrown away on return or error.
  • A frame holds value slots, a work pile, and a link to the name list.
  • Slot 0 = this (for instance methods). A long/double uses two slots.
  • On return, the answer is placed on the caller's work pile. On error, no answer is returned.
  • StackOverflowError = too many frames. OutOfMemoryError = heap full. Different parts.

Glossary

Frame
Per-method-call record on the JVM stack: locals + operand stack + constant-pool link.
Local variable array
Indexed slots holding arguments and locals; slot 0 is this for instance methods.
Operand stack
LIFO work area inside a frame where bytecode computes.
Current frame
The frame of the method currently executing in a thread.
Dynamic linking
Resolving a frame's symbolic references to concrete ones as they're first used.
Metaspace
Native-memory method area holding class metadata (replaced PermGen in Java 8).
