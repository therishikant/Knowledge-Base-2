The Execution Engine

Java › JVM cluster · lesson 4 of 4 · DEEP — turning bytecode into action

In one line — The engine is the part that actually runs the bytecode. It reads it line by line so the program can start right away. Then it turns the busy parts into fast machine code so they run quickly. It also picks which method to call (the five invoke* steps) and can call code written in C (JNI). This is why saying "Java is slow because it's interpreted" is only half true.

§1Where it fits

This is the last part of step 6 in the pipeline. The loader (lesson 2) brought the class in. The memory (lesson 3) gave it frames. The engine is what actually runs the instructions.

§2Why it exists

There are two goals that pull against each other: start fast (don't wait to translate everything first) and run fast (don't keep reading a busy loop the slow way forever). The engine gets both by doing two things: read the code line by line at first, then speed up the parts that run a lot. The spec allows exactly this — an implementation may turn bytecode "into the native instruction set of the host CPU (sometimes referred to as just-in-time, or JIT, code generation)" (JVM Spec SE 21, §2.13).

§3How it works

The interpreter

The basic loop: look at the current instruction, do it, move to the next one, repeat (§2.11). It needs no warm-up, so the program starts right away. But going one line at a time is slow for code that runs millions of times.

The JIT (the fast-code maker)

A counter watches how often each method and loop runs. Once a method has run enough times, it is "busy," and the JIT turns it into fast machine code that gets saved and reused. In practice it works in two levels: a quick one gets you fast machine code sooner, and a stronger one later rewrites the busiest methods with better tricks — inlining (pasting a small method's body straight in), escape analysis (skipping objects that never leave the method), unrolling loops, and dropping dead code. If the JIT made a smart guess that later turns out wrong, it can fall back to reading the code line by line again. This is why a warmed-up server can be nearly as fast as C++.

Choosing which method to call — the five invoke steps

OpcodeUsed forBinding
invokestaticstatic methodsDirect
invokespecialconstructors, private, super.Direct (no override)

invokedynamiclambdas, dynamic langsLazy, via bootstrap method

invokevirtual and invokeinterface are how Java does polymorphism: the real method is chosen from the object's actual type at run time (§2.11.8, §5.4.6). invokedynamic (Java 7+) is how a lambda gets wired up the first time you use it.

Calling C code (JNI)

When Java calls a native method (written in C or C++), the engine steps out into that code using the thread's native stack. Newer Java also has a safer way to do this, called the Foreign Function & Memory API.

§4When this matters

  • "Slow for a minute, then fast" — that's the slow line-by-line start, then the fast-code kicking in. Tools: -XX:+PrintCompilation, and CDS/AppCDS to start faster.
  • Benchmarks can lie — if you measure too early you measure the slow start, not the real speed. Use JMH, which warms up first.
  • Cost of polymorphism — understanding how the engine picks the method, and how the JIT often makes it fast anyway.

§5Explain it to a 12-year-old

A new cook reads the recipe one line at a time (the interpreter) — slow, but starts right away. A helper notices which dishes get ordered again and again and hands the cook a memorized shortcut card for those (the fast-code maker). If a shortcut turns out wrong because the recipe changed, they tear up the card and go back to reading (fall back). That way the kitchen opens fast and is quick at rush hour.

§7In practice — see the JIT fire

$ java -XX:+PrintCompilation Hello        # prints each method as it's compiled
$ java -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining ...   # see inlining decisions
In a tight loop that calls add a few million times, you will see the interpreter run first. Then a line appears in the log showing add being turned into fast code once it counts as busy — the engine speeding itself up, live.
Guess the answer: after warm-up, which is faster — always calling the same subclass, or calling many different ones? Why might the JIT be able to speed up the first but not the second? (Hint: the JIT bets on the type it keeps seeing.)

§8Watch out for

"Java is interpreted." It starts by reading line by line, then turns busy code into fast machine code. Saying just "interpreted" is a red flag in senior interviews.
Testing speed without warm-up. The first runs measure the slow start. Use JMH and let the fast code kick in first.
Expecting the JIT to fix a bad plan. It speeds up how code runs, not a slow algorithm. It won't fix an O(n²).

§9Recap

  • The engine = interpreter + JIT + method choosing + JNI.
  • Read line by line to start fast; turn busy code into machine code to run fast (and it can fall back if a guess was wrong).
  • Five invoke* steps; invokevirtual/invokeinterface = polymorphism; invokedynamic = lambdas.
  • The garbage collector works next to the engine, on the heap — see memory-model-and-gc.

Glossary

Interpreter
Executes bytecode instruction-by-instruction; instant startup.
JIT
Just-In-Time compiler; turns hot bytecode into native code at run time.
C1 / C2
HotSpot's fast-but-light and slow-but-aggressive JIT tiers.
Escape analysis
JIT optimization that stack-allocates or eliminates non-escaping objects.
Deoptimization
Reverting compiled code to the interpreter when a speculation fails.
invokedynamic
Lazily-linked call site; how lambdas and dynamic languages dispatch.
