Inheritance & Polymorphism

Java › type system & OOP cluster · lesson 5, part 2 of 3 · DEEP — how types relate, and how one command becomes many behaviours

Type & OOP cluster: 1. What a type really is · 2. Inheritance & polymorphism · 3. Generics & erasure

In one line — Part 1 built one type at a time. This part connects them. Inheritance says "a Dog is an Animal" and reuses the parent's code. An interface says "this thing can do X" without caring what it is. Both exist so that polymorphism can work: you write one line of code against the general type, and the JVM picks the right behaviour from the real object at run time. That one trick is what lets you add new behaviour to a program without editing the code that uses it.

§1Where it fits

Part 1 answered "what is one type, and how do I keep it honest?" You can now build a correct, sealed, self-guarding class.

But a real program is never one class. It is hundreds, and they must relate to each other. The same code has to handle an email notification and an SMS notification. The same report has to print a credit-card payment and a UPI payment. The question this part answers is: how do I write code once, when "the thing" can be several different kinds of thing?

This also closes the loop with lesson 4. Back there you saw five invoke* bytecodes and learned that invokevirtual picks a method by looking at the real object. That was the machinery. This lesson is the design idea that machinery exists to serve.

§2Why it exists

2.1 The problem: the growing if-ladder

Imagine you must send a notification, and there are three channels. Without polymorphism you write this: 

if (type.equals("email"))      sendEmail(to, body);
else if (type.equals("sms"))  sendSms(to, body);
else if (type.equals("push")) sendPush(to, body);

It works. Now look at what happens over a year:

  • A fourth channel arrives (WhatsApp). You must find and edit this ladder.
  • And the other ladder in the retry logic.
  • And the one in the audit logger.
  • And the one in the admin screen that nobody remembered.

Miss one and you ship a bug. The ladder has made adding a new kind of thing require editing existing, working, tested code — in several places at once. That is the thing good design is trying to avoid.

2.2 The fix: let the object know its own behaviour

Polymorphism inverts the ladder. Instead of the caller asking "what kind are you?" and then deciding, the caller just says "send yourself", and the object does the right thing because of what it is: 

notification.send(body);   // that's the whole thing

Now adding WhatsApp means writing one new class. No existing file is touched. No ladder is missed, because there is no ladder. This is the Open/Closed Principle — software should be open to extension, closed to modification — and polymorphism is how Java implements it.

The deeper payoff: testability. If your service depends on a PaymentGateway interface rather than on StripeGateway, your test can hand it a fake that returns whatever you want. No network, no sandbox account, no flakiness. Every testing framework and every dependency-injection container — all of Spring, which you learn next — is built on this one capability.

2.3 Why inheritance exists, and why it is dangerous

Inheritance gives you two things at once, and this is the source of all the confusion around it:

  1. Subtyping — "a Dog may be used wherever an Animal is expected." This is the valuable part.
  2. Code reuse — "a Dog automatically gets the parent's fields and method bodies." This is the tempting part.

People reach for extends because of #2, and then are stuck with #1 forever. The parent's internals become part of the child's behaviour, so changing the parent can silently break every child, in code you may not own (Bloch, Effective Java, Item 18 — "inheritance violates encapsulation").

That is why Java's answer evolved: use interfaces for subtyping, and composition for reuse. Use extends only when the is-a relationship is genuinely true and permanent.

§3How it works

3.1 The two type relationships

Java gives you exactly two ways to say one type relates to another:

extends (inheritance)implements (interface)
Reads as"is a kind of""is able to"
How manyone parent class, evermany interfaces
You inheritfields + method bodies + the contractthe contract (plus default bodies since Java 8)
Couples you tothe parent's internal designa list of method signatures only

Java allows only one parent class on purpose. Multiple class inheritance creates the "diamond problem": if both parents define save() with different bodies, which one runs? C++ allows it and needs complex rules. Java sidesteps the whole mess by letting you inherit state and behaviour from just one place, while implementing as many contracts as you like.

3.2 Overriding — the real polymorphism

Overriding is a child class replacing a parent method with its own version, keeping the same name and the same parameters. When you call that method, the JVM ignores the declared type of your variable and uses the real class of the object to choose which body runs. This is called dynamic dispatch or late binding. 

Notification n = new SmsNotification("+91-99999");
n.send("hello");     // declared Notification, really an Sms -> sms behaviour runs

Under the hood this is the invokevirtual instruction from lesson 4. Every class has a method table; invokevirtual looks up the entry in the table belonging to the object's actual class. The JIT often then optimises it away entirely — when only one implementation has been loaded, it inlines the method and leaves a cheap guard behind.

Always write @Override. It is not decoration. If your signature does not actually match a parent method — a typo, a wrong parameter type, equals(MyType) instead of equals(Object) — the compiler fails immediately instead of silently creating a brand-new method that never gets called (Bloch, Effective Java, Item 40).

3.3 Overriding vs overloading vs hiding — the three look-alikes

These three are constantly confused, and interviewers know it. The difference is who decides, and when.

Never hide a field deliberately. Declaring name in both parent and child gives the object two fields, and which one you read depends on the type of the variable you happened to use. It compiles, it runs, and it produces different answers from different places. The demo in §7 prints this happening.

3.4 abstract classes — a base with a blank to fill

An abstract class is a class you cannot instantiate, because it is deliberately incomplete. It can hold fields, a constructor, finished methods, and abstract methods that every child must supply.

That makes it perfect for the template method pattern: the parent fixes the sequence of steps, the children fill in the one step that differs.

abstract class Notification {
    protected final String to;              // shared state

    abstract String channel();              // the blank each child fills

    final String send(String body) {         // the fixed recipe
        return "via " + channel() + " to " + to + ": " + body;
    }
}
Notice send is final. That is deliberate: children may change one step (channel), but they may not rewrite the recipe. Fixing which parts are open and which are closed is the entire skill of designing a class for inheritance.

3.5 Interfaces — a capability, not a family

An interface is a named list of method signatures. A class that implements it promises to provide them. No state, no constructor, no family relationship — just "I can do these things."

Since Java 8 an interface may also contain:

  • default methods — a method with a body, inherited by every implementer. These exist so the JDK could add forEach to Iterable and stream() to Collection without breaking a decade of existing code.
  • static methods — helpers that live with the interface itself, e.g. Comparator.comparing.
  • constants — any field is implicitly public static final.

Java 9 added private interface methods, so default methods can share helper code.

Default to the interface. Reach for an abstract class only when siblings genuinely share state plus partial behaviour. A very common and good combination is both: publish the interface as your public type, and provide an AbstractXxx skeleton implementation for people who want the easy path — exactly how the JDK ships List + AbstractList (Bloch, Effective Java, Item 20).

3.7 Composition — reuse without the family bond

Composition means your class holds another object in a field and delegates to it. "A Car has an Engine", not "a Car is an Engine".

Inheritance (extends)Composition (a field)
Relationshipis-ahas-a
Fixed whencompile time, permanentlyrun time — you can swap the part
You inheriteverything, including the parent's mistakesonly the methods you choose to expose
Breaks whenthe parent changes its internalsthe part's public contract changes
Testingyou drag the whole parent into every testpass in a fake part
"Favor composition over inheritance." The oldest reliable rule in OO design (Gamma et al., Design Patterns, 1994; Bloch, Effective Java, Item 18). The test before you type extends: "Is every single thing the parent can do also true and sensible for the child, forever?" If you hesitate, compose.
The classic cautionary tale. java.util.Stack extends Vector — so a "stack" exposes get(int), insertElementAt, and remove(int). You can reach into the middle of a stack, which defeats the entire concept. It is in the JDK forever because removing it would break compatibility. Had it held a Vector instead of extending one, it would have exposed only push, pop and peek.

3.8 Casting, instanceof, and why you rarely need them

Upcasting (child → parent) is always safe and implicit: Notification n = new SmsNotification(...). Downcasting (parent → child) is a claim the compiler cannot verify, so it is checked at run time and throws ClassCastException if you were wrong. 

Object box = Integer.valueOf(7);
String bad = (String) box;      // compiles fine; explodes at run time

instanceof lets you check first. But reaching for instanceof plus a cast is usually a sign that polymorphism has been skipped: you are asking "what kind are you?" again, which is the if-ladder from §2.1 in disguise.

Modern Java softens this. Java 16's pattern matching lets you write if (o instanceof String s) { ... } — test and bind in one step, no separate cast. Combined with sealed types and switch patterns (Java 21), this makes "check the kind" legitimate again for closed sets of types, like an AST or a state machine. Lesson 12 covers it. On Java 8 you still write the cast by hand.

3.9 The rules an override must obey

When you override, the compiler enforces a contract so that callers of the parent type are never surprised (JLS SE 21, §8.4.8):

RuleWhy
Same name and parameter listotherwise it is an overload, not an override
Return type must be the same or a subtype (covariant return)the caller's expectation still holds
Access may widen, never narrow (protected → public is fine; the reverse is not)a caller who could reach the parent method must still reach the child's
No new or broader checked exceptionsthe caller's catch blocks were written against the parent
Cannot override final, static or private methodsthey are not dispatched virtually

Behind all five sits the Liskov Substitution Principle: anywhere the parent type is expected, any child must work without the caller noticing. The compiler enforces the signature half; keeping the behaviour half is on you. A Square that extends Rectangle and quietly forces width to equal height compiles perfectly and still violates the principle.

§4When to use

  • Use an interface whenever more than one implementation of a role is plausible: payment gateways, storage backends, notification channels, parsers. Also use one whenever you want to fake the dependency in a test.
  • Use an abstract class when siblings share real state and a fixed sequence of steps where only a piece varies (template method).
  • Use composition for everything else — which in practice is most of the time.
  • Use extends on a concrete class only when you control both classes, the is-a is permanent, and the parent was documented and designed for extension.
  • Use final on a class when it was not designed to be extended. "Design for inheritance, or prohibit it" (Bloch, Item 19).
  • Avoid instanceof chains in business logic; they are the ladder polymorphism was invented to delete.

§5Explain it to a 12-year-old

Think about a school play. The script says "the NARRATOR walks on and says the opening line." The script does not name a person. Whoever is cast as narrator that night walks on and says it in their own voice. The script never changes; the performance does.

That is polymorphism. "Narrator" is the type. The actual kid on stage is the object. Your code is the script, and it keeps working when a new kid takes the part.

Inheritance is like saying "a labrador is a dog, so it already knows everything dogs know — barking, eating, sleeping — and it adds a few things of its own." You did not have to teach it barking again.

An interface is different. It is a badge that says "I can swim." A fish can swim. A person can swim. A robot can swim. They are not related at all — they do not share a family — but anyone organising a swimming race only needs to see the badge. That is why a class can wear many badges but can only belong to one family.

And composition? That is a toy car with a battery inside. The car is not a battery. It just has one, and you can swap it for a better one whenever you like. If the car had been built as a battery, you would be stuck with it forever.

§6Connections

  • ← jvm-execution-engine: overriding is invokevirtual; interface calls are invokeinterface; private, super and constructors use invokespecial; static calls use invokestatic.
  • ← part 1: a final class cannot be extended, and a private method cannot be overridden — the access rules from part 1 decide what part 2 can do.
  • → part 3: once types form a hierarchy, "a list of Dogs is not a list of Animals" becomes a real problem, and wildcards are the fix.
  • → java8-functional: a lambda is just an instance of a one-method interface; everything here underpins Function, Predicate and Comparator.
  • → application-architecture: "depend on interfaces, not implementations" is the whole basis of ports-and-adapters and of Spring's dependency injection.
  • → modern-java-9-to-21: sealed types let you say "these are all the subtypes", which makes exhaustive switch patterns safe.
  • Transfers everywhere: Kotlin, C# and TypeScript copy this model almost exactly. Go drops inheritance entirely and keeps only interfaces plus composition — which is this lesson's advice turned into a language rule.

§7In practice — one file, dissected

Full source: code/TypeDemo2.java. Compile with javac TypeDemo2.java, run with java TypeDemo2. Output below is real, from JDK 1.8.0_411.

Chunk 1 — an abstract base with one blank

static abstract class Notification {
    protected final String to;

    Notification(String to) {
        System.out.println("   [parent ctor] Notification(" + to + ")");
        this.to = to;
    }

    abstract String channel();                    // children MUST fill this

    final String send(String body) {                // children may NOT change this
        return "via " + channel() + " to " + to + ": " + body;
    }
}
The print in the constructor exists to prove the ordering in the output: the parent constructor always finishes before the child's body starts. That is why calling an overridable method from a constructor is dangerous — the child's override would run while the child's own fields are still null.

Chunk 2 — the ladder, deleted

for (Notification n : new Notification[]{ n1, n2 })
    System.out.println(n.send("your order shipped"));
One loop, no if, no switch, no type check. Two different behaviours come out. Adding a third channel means adding a class and nothing else — this loop is never edited again. This single loop is the entire argument for polymorphism; if you can explain why it needs no if, you understand the lesson.

Chunk 3 — overriding vs hiding, in the same object

static class Parent {
    String name = "parent-field";                  // fields HIDE
    String whoAmI()       { return "Parent.whoAmI"; }  // instance methods OVERRIDE
    static String label() { return "Parent.label"; }  // static methods HIDE
}
...
Parent p = new Child();     // declared Parent, really a Child
p.whoAmI();                  // -> Child's version  (real type wins)
p.name;                      // -> parent-field     (declared type wins!)
Same variable, same object, two opposite rules — and this is exactly the trap in interviews. The object really does carry two name fields. Which one you see depends on the type you look through, which is why ((Child) p).name gives a different answer on the very next line of output.

Chunk 4 — overloading is frozen at compile time

static String describe(Object o) { return "describe(Object)"; }
static String describe(String s) { return "describe(String)"; }
...
Object asObject = "I am really a String";
describe(asObject);     // -> describe(Object), NOT describe(String)
The object on the heap is a String, but the compiler only saw a variable declared Object, and it had already made its choice before the program started. Overloading never looks at the real object. This is why list.remove(1) and list.remove(Integer.valueOf(1)) do completely different things.

Chunk 5 — one class, two capabilities

static class Invoice implements Auditable, Archivable {
    @Override public String auditLine()  { return "invoice " + number; }
    @Override public String archiveKey() { return "INV/" + number; }
}

interface Auditable {
    String auditLine();
    default String auditLoud() { return auditLine().toUpperCase(); }
}
Invoice wears two badges at once — impossible with extends. The default method gives every implementer auditLoud() free, and the interface can be extended later without breaking anyone. That is exactly how Java 8 added stream() to every existing Collection.

Chunk 6 — composition, and a bad cast

static class Car {
    private final Engine engine;                 // has-a, not is-a
    String drive() { return "car moves because " + engine.start(); }
}
...
Object box = Integer.valueOf(7);
String bad = (String) box;                      // ClassCastException at run time
Car exposes only drive(). Nothing about Engine leaks out, and you can hand in a different engine — or a fake one in a test — at any time. The cast below it is the opposite story: the compiler allows the claim, and the JVM punishes it.

Section 3 is the money shot: one variable, one object, three different answers. The method came from the child (run time, real type). The field came from the parent (compile time, declared type). Cast the variable and the field answer flips. Section 4 shows the same compile-time rule applied to overloading.

(2) Add @Override to the label() methods in Parent/Child. What does the compiler say, and what does that tell you about static methods? (3) Change describe(Object) to describe(CharSequence) and call it with a String. Which overload wins, and what rule decided it? (4) Make Auditable and Archivable both declare a default String id() and have Invoice implement both. What is the compile error, and what is the one way out?

§8Pitfalls

Using extends just to reuse code. You bought a permanent is-a relationship to save a few lines. Hold the object in a field instead and delegate.
Forgetting @Override. Without it, a mistyped signature silently becomes a new method that is never called. equals(MyType other) instead of equals(Object other) is the classic, and it quietly breaks every collection.
Hiding a field or a static method. It looks like overriding and behaves like the opposite. Rename one of them.
Calling an overridable method from a constructor. The child's version runs before the child's fields are initialised, so it sees nulls. Make it private, static or final.
Deep hierarchies. Four or five levels of extends means nobody can predict what a change does. Flatten it: one abstract base at most, or interfaces plus composition.
protected fields. They are public to every subclass forever, so they freeze your internal representation. Prefer private fields plus a protected method if a hook is really needed.
instanceof chains over your own types. Every new subtype means hunting down every chain. That is the exact pain polymorphism removes.
Breaking Liskov quietly. An override that throws UnsupportedOperationException, or narrows what the parent promised, compiles cleanly and breaks callers who only know the parent type.

§9Recap

  • Polymorphism exists to delete the if-ladder: the caller says what, the object decides how. New behaviour = new class, no edits to existing code.
  • extends = is-a (one parent only, inherits state and bodies). implements = can-do (as many as you like, contract only).
  • Overriding is chosen by the JVM from the real object at run time — this is invokevirtual.
  • Overloading is chosen by the compiler from the declared argument types, before the program runs.
  • Fields and static methods hide, they do not override — they follow the declared type. Almost always a bug.
  • Abstract class = shared state + a fixed recipe with blanks. Interface = a capability unrelated classes can share. Default to the interface.
  • Favor composition over inheritance. Before typing extends, ask whether every parent behaviour is true for the child forever.
  • Upcasting is free and safe; downcasting is an unverified claim that throws ClassCastException when wrong.
  • An override may widen access and return a subtype, but may not narrow access or add checked exceptions — all of it serving Liskov substitution.
  • Always write @Override. It turns a silent run-time bug into a compile error.

Reference — quick answers

QuestionAnswer
Why no multiple class inheritance?The diamond problem — two parents with conflicting state and bodies. Interfaces avoid it by carrying no state.
Can an interface have a constructor?No. It has no state to initialise.
Can an abstract class have no abstract methods?Yes — it just cannot be instantiated.
Can you override a static method?No. You can only hide it.
Can you override a private method?No. It is not visible to the subclass; you are declaring a new method.
Can an override return a different type?Yes, if it is a subtype of the original (covariant return).
Can an override throw new checked exceptions?No. Unchecked ones, yes.
Two interfaces, same default method?Compile error. The class must override it and may call Iface.super.method().
What does super.m() do?Calls the parent's version explicitly, via invokespecial.
Which bytecode for an interface call?invokeinterface.

Glossary

Inheritance
Building a new class on an existing one with extends; an is-a relationship.
Subtype
A type usable anywhere its supertype is expected.
Polymorphism
One call site, many possible behaviours, selected by the real object.
Dynamic dispatch
The JVM choosing the method body at run time from the object's actual class.
Overriding
A subclass replacing a parent instance method with the same signature.
Overloading
Several methods with one name and different parameter lists; resolved by the compiler.
Hiding
A subclass declaring a field or static method with the parent's name; resolved by declared type.
Abstract class
A class that cannot be instantiated and may leave methods unimplemented.
Interface
A named set of method signatures a class promises to provide.
Default method
An interface method with a body, inherited by all implementers (Java 8+).
Composition
Reuse by holding another object as a field and delegating to it.
Upcast / downcast
Treating an object as its supertype (always safe) / as a subtype (checked at run time).
Covariant return
An override returning a subtype of the parent's return type.
Liskov Substitution Principle
A subtype must be usable wherever its supertype is, without surprising the caller.
Template method
A parent fixing the sequence of steps while children supply individual steps.
