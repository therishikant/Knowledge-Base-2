Generics & Erasure

Java › type system & OOP cluster · lesson 5, part 3 of 3 · DEEP — type safety that the compiler keeps and the JVM forgets

Type & OOP cluster: 1. What a type really is · 2. Inheritance & polymorphism · 3. Generics & erasure

In one line — Generics let you write one class or method that works for many types while the compiler still checks every use — so List<String> can never hold a number and you never write a cast. The catch is erasure: after checking, the compiler deletes the type argument, so at run time List<String> and List<Integer> are literally the same class. Almost every generics "gotcha" is a direct consequence of that one deletion.

§1Where it fits

Part 1 built single types. Part 2 connected them into hierarchies. Both answered "what kind of thing is this?"

This part answers a different question: "a container of what?" A List is not interesting on its own; what matters is what it holds. Generics are how Java attaches that answer to a type, and they are the reason the entire Collections API (lesson 8) and the entire Streams API (lesson 7) are usable without casting.

It also closes a thread from part 2. Once types form a family tree, an awkward question appears: a Dog is an Animal, so is a List<Dog> a List<Animal>? The answer is no, and understanding why is the most valuable thing in this lesson.

§2Why it exists

2.1 Life before 2004

Generics arrived in Java 5. Before that, every collection held plain Object, and code looked like this:

List names = new ArrayList();
names.add("Asha");
names.add(Integer.valueOf(42));            // nobody stopped this

String first = (String) names.get(0);      // cast, every single time
String second = (String) names.get(1);     // ClassCastException at RUN time

Two separate miseries:

  • No safety. Nothing stopped the wrong type going in. The mistake surfaced far away, much later, in unrelated code — and the stack trace pointed at the innocent reader, not the guilty writer.
  • Casts everywhere. Every read needed a cast. Noisy to write, and each cast was an unchecked promise waiting to fail.

2.2 What generics changed

List<String> names = new ArrayList<String>();
names.add("Asha");
names.add(Integer.valueOf(42));   // COMPILE ERROR — caught instantly, at the guilty line

String first = names.get(0);      // no cast needed

The bug moved from run time to compile time, and from the reader's line to the writer's line. That is the whole value proposition. The casts did not disappear — the compiler now writes them for you, and it can only do that because it has already proved they are safe (Oracle Java Tutorials — Why Use Generics?).

2.3 Why the type vanishes at run time

When generics were designed, there were already millions of lines of Java and thousands of compiled libraries in the wild. Sun had a hard constraint: old code and new code must work together, and old .class files must keep running on the new JVM.

They had two options:

OptionHowCost
Reified generics (C# took this route)teach the JVM about type arguments; List<String> becomes a real, distinct run-time typea new, incompatible JVM and a broken ecosystem
Erasure (Java took this route)check everything in the compiler, then delete the type arguments and emit ordinary pre-generics bytecodeno run-time type information — all the gotchas in §3.4

Java chose compatibility. Generics are therefore a compile-time-only feature: a very thorough proof, followed by a deliberate forgetting (Oracle Java Tutorials — Type Erasure).

This is a trade-off worth being able to argue. Erasure bought Java a smooth migration that C# paid for with a version break. The bill arrives as new T() being impossible, generic arrays being unsafe, and instanceof List<String> being illegal. Project Valhalla is a long-running effort to bring some reification back.

§3How it works

3.1 A type parameter is a blank you fill at the call site

<T> is a placeholder for a type, exactly as a method parameter is a placeholder for a value. You fill it in when you use the class. 

class Box<T> {              // T is a blank
    private T item;
    void put(T item) { this.item = item; }
    T get()          { return item; }
}

Box<String> b = new Box<String>();   // the blank is filled with String
b.put("hello");
String s = b.get();                 // no cast — the compiler knows
// b.put(42);                     // compile error — the blank says String

The conventional single letters are worth knowing because the JDK uses them everywhere:

LetterMeans
TType — the general-purpose one
EElement — used by collections
K, VKey and Value — used by maps
RResult — used by functions
NNumber

3.2 Generic methods and bounded types

A method can declare its own type parameter, written before the return type. The compiler usually infers it from the arguments, so you rarely spell it out at the call site: 

static <T> T firstOrDefault(List<T> list, T fallback) {
    return list.isEmpty() ? fallback : list.get(0);
}

Sometimes a blank cannot be completely blank. If your method must compare values, T has to have a compareTo. That is a bound: 

static <T extends Comparable<T>> T max(List<T> list) { ... }

Read <T extends Comparable<T>> as "any T, as long as it can be compared with itself". Inside the method you may now call compareTo. Note that extends here means "is a subtype of", and it works for interfaces too — the keyword is reused.

3.4 The five consequences of erasure

Every generics restriction you have ever hit comes from the table above. Here they are, with the reason attached:

You cannot…Because at run time…Do this instead
new T()there is no T to constructpass a Class<T> or a factory (Supplier<T>)
new T[10]arrays do know their type; T does notuse a List<T>, or create Object[] and cast internally
x instanceof List<String>only List existsx instanceof List<?>

There is also a static rule worth naming: a static member cannot use the class's type parameter. T belongs to an instance, and a static member belongs to the class, which is shared by every T at once. A static method must declare its own <T>.

3.5 Invariance — why List<Dog> is not a List<Animal>

This is the single most-asked generics question. The rule is: generics are invariant. Even though Dog is a subtype of Animal, List<Dog> is not a subtype of List<Animal>. Here is why that must be true:

Arrays made the opposite choice, and it is a known wart. Dog[] is an Animal[] (arrays are covariant). So Object[] objs = new String[1]; objs[0] = 42; compiles — and throws ArrayStoreException at run time. Arrays need a run-time check precisely because the compile-time check was given away. Generics refused to repeat that mistake. Interview-ready one-liner: arrays are covariant and reified; generics are invariant and erased (Bloch, Effective Java, Item 28).

3.6 Wildcards — getting flexibility back safely

Invariance is correct, but it makes a method like "sum any list of numbers" impossible to write with plain generics. Wildcards are the controlled relaxation.

WildcardRead asYou mayYou may not
List<? extends Number>"a list of some unknown subtype of Number"read items as Numberadd anything (except null)
List<? super Integer>"a list of some unknown supertype of Integer"add Integersread as anything better than Object
List<?>"a list of something, I don't care what"read as Object, call size()add anything (except null)

Why the restrictions are exactly right, in one sentence each:

  • ? extends cannot accept writes because nobody knows which subtype it really is — it might be a List<Double>, so adding an Integer would corrupt it.
  • ? super cannot give you a precise read because it might be a List<Object>, so the only thing you can safely promise about an item is that it is an Object.
PECS — "Producer Extends, Consumer Super." If the parameter produces values you read, use ? extends T. If it consumes values you write, use ? super T. If you do both, use plain T and accept the lost flexibility (Bloch, Effective Java, Item 31).

You can see PECS in the JDK's own signature for Collections.copy:

static <T> void copy(List<? super T> dest, List<? extends T> src)
//              consumer (we write)        producer (we read)
A rule of thumb for API design: use wildcards on method parameters to accept more callers; do not use them on return types, because you would force every caller to deal with a wildcard too.

3.7 Raw types and heap pollution

A raw type is a generic type used with no type argument — plain List instead of List<String>. It exists only for backward compatibility with pre-Java-5 code, and using one switches off all generic checking for that reference. 

List<String> strings = new ArrayList<String>();
List raw = strings;                   // raw — checks off
raw.add(Integer.valueOf(42));         // warning only; succeeds
String s = strings.get(0);            // ClassCastException on a line with no cast!

That corrupted state — a List<String> holding a non-String — is called heap pollution. Note where the explosion happens: not on the line that did the damage, but on an innocent line somewhere else. This is exactly the pre-generics misery of §2.1, re-created by opting out.

Never use raw types in new code. If you genuinely do not care about the element type, write List<?> — it is safe, because the compiler refuses to let you add anything to it (Bloch, Effective Java, Item 26). Treat every "unchecked" warning as an error you have not fixed yet; suppress it only on the narrowest possible scope, with a comment explaining why it is provably safe.

3.8 Where the type information does survive

Erasure removes type arguments from values, but generic signatures of classes, fields and methods are kept in the class file as metadata, so the compiler can check code compiled against a library later. That is why your IDE knows Collections.sort takes a List<T> even though the bytecode works on a raw List.

Frameworks exploit this through reflection. Spring and Jackson can discover that a field is a List<Customer> by reading Field.getGenericType(). The famous "super type token" trick — new TypeReference<List<Customer>>(){} — works because an anonymous subclass records its superclass's type argument in the class file. Clever, and a direct workaround for erasure.

3.9 Enums — the other way to make a type precise

Generics narrow a type by parameter. An enum narrows it by listing every legal value. An enum Status { OPEN, CLOSED } is a class whose instances are fixed at compile time — so an invalid status is not a run-time error, it is a compile error.

Enums are real classes: they may have fields, constructors and methods, and each constant is a singleton, which is why == is the correct comparison for them. Use an enum any time a String or int constant is standing in for "one of a small, known set" (Bloch, Effective Java, Item 34).

§4When to use

  • Write a generic class when the logic is identical for every element type: containers, caches, result wrappers, repositories.
  • Write a generic method when just one operation varies by type — far more common than a whole generic class.
  • Add a bound (<T extends Something>) the moment you need to call a method on T.
  • Use ? extends T on parameters you only read from; ? super T on parameters you only write into.
  • Use List<?> rather than a raw List whenever the element type genuinely does not matter.
  • Use an enum instead of string or int constants for any fixed set of values.
  • Do not reach for generics when one concrete type is all you will ever need — <T> that is only ever String is noise.

§5Explain it to a 12-year-old

Imagine a box in a shop. A plain cardboard box takes anything — shoes, fruit, a cat. That is convenient right up to the moment you reach in expecting shoes and grab the cat.

Now imagine the shop gives you boxes with a label slot on the front: SHOES ONLY. The person packing the box can see the label, so they will not put fruit in. And you, opening it, do not need to check — the label already promised.

That is generics. Box<Shoes> is a box with a label.

Here is the strange part. The shop checks the label very carefully while packing — and then peels it off before the box leaves. Once the box is on the truck, no one can tell what is inside. Why peel it off? Because the delivery trucks are old and were built before labels existed, and they must still be able to carry every box. That is erasure: the checking is real, but the label does not survive the journey.

And this explains the weird rules. You cannot ask a box on the truck "what is your label?" — it is gone. You cannot tell the truck "make me a new one of whatever this is" — it does not know. The checking all happened back at the shop.

§7In practice — one file, dissected

Full source: code/TypeDemo3.java. Compile with javac TypeDemo3.java, run with java TypeDemo3. Output below is real, from JDK 1.8.0_411.

Chunk 1 — a generic class

static class Box<T> {
    private T item;
    void put(T item) { this.item = item; }
    T get()          { return item; }
}
...
Box<String> box = new Box<String>();
box.put("hello");
String s = box.get();        // no cast
// box.put(42);            // compile error — this is the whole point
The commented line is the feature. The value of generics is measured in code that refuses to compile, which makes it invisible in the output — so read the comment as the real result. In the bytecode, item is just an Object and box.get() is followed by checkcast java/lang/String.

Chunk 2 — proving erasure in three lines

List<String>  strings = new ArrayList<String>();
List<Integer> ints    = new ArrayList<Integer>();
System.out.println(strings.getClass() == ints.getClass());   // true
Two different declared types, one run-time class. If you only remember one experiment from this lesson, remember this one — it answers "are generics reified in Java?" definitively, and every gotcha in §3.4 follows from it.

Chunk 3 — heap pollution, caught in the act

List raw = strings;                   // raw type: all checks off
raw.add(Integer.valueOf(42));         // compiles with a warning, runs fine
try {
    String oops = strings.get(0);     // the compiler inserted a hidden cast HERE
} catch (ClassCastException e) { ... }
Look at where it fails. The damage was done on line 2; the exception lands on line 4, in code that is entirely innocent and contains no visible cast at all. That distance between cause and symptom is the exact bug generics were invented to prevent — and a raw type hands it straight back to you. This is also why javac printed "uses unchecked or unsafe operations" when compiling this file.

Chunk 4 — a bound lets you call methods on T

static <T extends Comparable<T>> T max(List<T> list) {
    T best = list.get(0);
    for (T candidate : list)
        if (candidate.compareTo(best) > 0) best = candidate;
    return best;
}
Without the bound, T erases to Object and compareTo does not exist. With it, T erases to Comparable and the call is legal. One method now works for Integer, String, LocalDate and any class you write — the output shows numbers and text going through the same code.

Chunk 5 — PECS, both halves

static double sum(List<? extends Number> producer) {   // we only READ
    double total = 0;
    for (Number n : producer) total += n.doubleValue();
    return total;
}

static void addIntegers(List<? super Integer> consumer) {  // we only WRITE
    consumer.add(1);
    consumer.add(2);
}
Thanks to ? extends, sum accepts List<Integer> and List<Double> — with a plain List<Number> parameter neither would compile. Try it: add producer.add(1) inside sum and the compiler refuses, because the list might really be a List<Double>. The restriction is not arbitrary; it is the proof.

Chunk 6 — an enum is a type with a complete value list

enum Status {
    OPEN("awaiting action"), CLOSED("finished");
    private final String blurb;
    Status(String blurb) { this.blurb = blurb; }
}
An enum is a class with private final fields and a constructor — everything from part 1 — with the instances fixed at compile time. Each constant is a singleton, which is why Status.valueOf("OPEN") == Status.OPEN prints true. Gotcha: never persist ordinal() to a database; inserting a new constant silently renumbers everything. Store name(), or an explicit code field.

§8Pitfalls

Using raw types. One raw reference disables checking for everything reached through it and re-creates pre-generics bugs. Use List<?> when the type truly does not matter.
Ignoring unchecked warnings. Each one is a place where the compiler has stopped being able to guarantee safety. Fix it, or suppress it on the smallest possible scope with a comment justifying it.
Expecting List<Dog> to be a List<Animal>. Generics are invariant. Use ? extends Animal if you only need to read.
Mixing arrays and generics. new List<String>[10] is illegal, and (T[]) new Object[n] is an unchecked lie that can bite later. Prefer a List.
Trying to use T in a static member. The class's T belongs to an instance. Declare a fresh <T> on the static method.
Putting wildcards in return types. It pushes the wildcard onto every caller. Keep wildcards in parameters, where they widen what you accept.
Forgetting boxing costs. List<Integer> is thousands of separate heap objects where int[] is one. In a hot loop this matters.
Persisting enum.ordinal(). Add a constant in the middle and every stored number now means something else. Persist name() or an explicit code.

§9Recap

  • Generics move container type errors from run time to compile time, and remove the casts you used to write by hand.
  • <T> is a blank filled at the use site; <T extends X> is a blank with a minimum requirement, which lets you call X's methods.
  • Erasure: the compiler checks, then deletes the type argument and inserts casts. Java chose this for backward compatibility; C# chose reification instead.
  • At run time List<String> and List<Integer> are the same class — the demo proves it.
  • Erasure explains all the restrictions: no new T(), no new T[], no instanceof List<String>, no overloading that differs only by type argument, no primitives as type arguments.
  • Generics are invariant: List<Dog> is not a List<Animal>, and the four-line proof shows why it must not be.
  • Arrays are covariant and reified; generics are invariant and erased. That is why arrays throw ArrayStoreException and generics do not need to.
  • PECS: ? extends T to read from a producer, ? super T to write into a consumer, plain T when you do both.
  • Raw types cause heap pollution — the failure appears far from the damage. Use <?> instead.
  • Generic signatures survive in the class file, which is how reflection-based frameworks and super type tokens work.
  • Enums are the other precision tool: a type whose complete set of values is fixed at compile time, each constant a singleton.

Glossary

Generic type
A class or interface declaring one or more type parameters, e.g. List<E>.
Type parameter
The blank in a declaration (T).
Type argument
The concrete type you supply at the use site (String).
Parameterised type
A generic type with its arguments filled in: List<String>.
Bounded type parameter
<T extends Number> — restricts which types may fill the blank.
Type erasure
Compile-time checking followed by deletion of type arguments from the bytecode.
Reification
Type information surviving to run time; Java arrays have it, Java generics do not.
Invariance
List<Dog> is unrelated to List<Animal>.
Covariance
Subtyping that follows the element type — how Java arrays behave.
Wildcard
? — an unknown type argument, optionally bounded by extends or super.
PECS
Producer Extends, Consumer Super — the rule for choosing a wildcard.
Raw type
A generic type used with no type argument; all checks are disabled.
Heap pollution
A parameterised reference pointing at an object of the wrong parameterisation.
Super type token
An anonymous subclass used to capture a generic type at run time, e.g. new TypeReference<List<X>>(){}.
Enum
A type whose complete set of instances is fixed at compile time; each constant is a singleton.
