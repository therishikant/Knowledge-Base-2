What a Type Really Is

Java › type system & OOP cluster · lesson 5, part 1 of 3 · DEEP — classes, objects, and the small door

Type & OOP cluster: 1. What a type really is · 2. Inheritance & polymorphism · 3. Generics & erasure

In one line — A type is a promise about what a piece of data can do, and the compiler checks that promise before your program ever runs. A class is how you write a new promise down. An object is one real thing built from that class. And encapsulation — keeping fields private and letting callers in only through methods — is how you make sure a broken object can never exist in the first place.

§1Where it fits

Lessons 1–4 were about how Java runs code: source becomes bytecode, the class loader brings it in, memory areas hold it, and the execution engine runs it. Those lessons answered "what happens to my code?"

This lesson is the first one that answers a different question: "how do I shape my code in the first place?" It is the start of the design half of Java. Everything after it — memory, collections, strings, concurrency, application architecture — assumes you are comfortable here.

You already write Java 8 every day, so you have used all of this. The goal is not new syntax. The goal is to make the why underneath it so clear that you can defend every design choice, in an interview and in a code review.

Because this area is large, lesson 5 is split into three parts, the same way the JVM and memory lessons were:

§2Why it exists

2.1 The problem: a computer only sees bytes

Deep down, memory holds nothing but numbers. A number sitting in memory could be an integer, part of a price, a pixel colour, or the first half of a date. The bytes do not say.

So somebody has to remember what each chunk of memory means, and what you are allowed to do with it. There are only two candidates for that job:

  • You, the programmer, remember it. This is how the earliest languages worked. It is fine for 50 lines and collapses at 50,000.
  • The language remembers it, and checks you. That is a type system.

A type is simply a label attached to data that says two things: what shape the data has, and which operations are legal on it. String means "text, and you may call length() on it". int means "a whole number, and you may add it".

2.2 Why Java checks types before running

Java is statically typed: every variable has a type written in the source, and the compiler checks all the promises before producing a single byte of bytecode (JLS SE 21, §4 — Types, Values, and Variables).

If you write this:

String name = "Asha";
name.lenght();        // typo

the compiler stops you immediately. A dynamically typed language would happily start your program and blow up weeks later, at 2 a.m., in production, on the one code path nobody tested. That difference — failure at build time instead of failure at run time — is the entire pitch for static typing.

The cost, honestly stated. Static typing makes you write more. You must declare types, and occasionally you must fight the compiler to express something it cannot see. The trade is deliberate: more typing up front, far fewer surprises later. Dynamic languages (Python, JavaScript) take the opposite trade — which is why both ecosystems eventually bolted on type checkers (mypy, TypeScript). Large codebases keep rediscovering that they want types.

2.3 The second problem: big programs tangle

Types alone are not enough. Imagine a 200,000-line program where any function can read and change any piece of data. Change one field and you must re-check the whole program, because anything might be touching it. That is not a theoretical worry — it is the normal state of a large codebase without discipline.

Object-oriented programming is Java's answer, and it comes down to one move, repeated everywhere:

Put data and the code that guards that data in the same box, and let the outside world in only through a small, deliberate door.

That is it. Everything else — inheritance, interfaces, polymorphism — is a refinement of that one idea. If you keep only one sentence from this cluster, keep that one.

§3How it works

3.1 Java has exactly two families of types

Every value in a Java program is one of two kinds. There is no third kind.

Primitive typeReference type
Which ones exactly eight: byte, short, int, long, float, double, char, boolean everything else: classes, interfaces, arrays, enums, String
The variable holdsthe value itselfan arrow (reference) to an object, or null
Can it be null?noyes
Has methods?noyes
Default value0 / false / '\u0000'null

Primitives exist for speed. An int is four raw bytes the CPU adds in a single instruction, with no object header and no garbage collection. Reference types exist for everything that needs behaviour, identity, or the ability to be absent.

Every reference type, without exception, sits under one root class: java.lang.Object. Even an array is an Object. That single family tree is what makes polymorphism possible in part 2 (JLS SE 21, §4.3.2).

3.2 Class vs object — the difference people blur

A class is a description. It says: "a thing of this kind has these fields and can do these things." It is text.

An object is one real thing built from that description with new. It lives on the heap and has its own copy of every instance field.

The usual analogy is blueprint vs house, and it is a good one. One blueprint, many houses. Each house has its own address and its own furniture. Rearranging house A does not touch house B. 

class Account {        // the blueprint — written once, exists as text
    private long balance;
}

Account a = new Account();   // house #1 — its own balance
Account b = new Account();   // house #2 — its own balance
The one place the blueprint does exist at run time. The class loader (lesson 2) builds a Class object for every class and keeps the field list, method bytecode and constants in Metaspace. So there is one run-time thing per class — it just is not where your object's data lives.

3.3 Instance vs static — "one each" vs "one total"

This is the whole meaning of static, and it is simpler than people make it:

Instance member (no static)static member
How many existone per objectone per class, for the whole program
Where it livesinside the object, on the heapwith the class, in Metaspace
How you reach itaccount.balancePaise()Account.accountsOpened()
Can it use this?yesno — there is no object to point at

That last row explains the error every beginner hits: "non-static variable cannot be referenced from a static context." It is not a mysterious rule. A static method belongs to the class, so when it runs there may be no object at all — there is literally nothing for this to mean.

Use static for: constants (public static final), stateless helpers that depend on nothing but their arguments (Math.max), and factory methods (Integer.valueOf). Avoid static for: mutable shared state. A static mutable field is a global variable in a Java costume — shared by every thread, invisible in method signatures, and it leaks state between tests.

3.4 Encapsulation — the small door

Here is the most important design idea in the cluster, and the real reason private exists.

An object usually has rules about its own data that must always be true. A balance must never be negative. An order must always have at least one line. A date range must end after it starts. These always-true rules are called invariants.

If a field is public, you cannot protect an invariant, because any line of code anywhere can set it to anything. If the field is private and the only way in is a method, the method gets to refuse.

3.5 The four access levels

Java gives you exactly four visibility settings, from most open to most closed (Oracle Java Tutorials — Controlling Access to Members of a Class):

ModifierVisible toUse it for
publicevery class, everywherethe API you promise to keep working
protectedsame package and subclasses anywheredeliberate hooks for subclasses
nothing written ("package-private")same package onlyhelpers one package shares internally
privatethe same class onlystate and helpers nobody outside should know about
Default to the most closed option that works, and open up only when you must. Widening access later is easy and harmless. Narrowing it later breaks every caller — so public is a promise you may never be able to take back (Bloch, Effective Java, Item 15: "minimize the accessibility of classes and members").

3.6 Constructors — the gate every object must pass through

A constructor is code that runs once, during new, to put the object into a valid starting state. Its real job is not "assign the fields" — it is make it impossible to build a broken object.

Five facts worth knowing precisely:

  1. If you write none, Java gives you a free no-argument one. Write any constructor yourself and that free one disappears.
  2. You can have several (constructor overloading) — different ways to build the same kind of thing.
  3. One constructor can call another in the same class with this(...), so the rules are written once.
  4. A subclass constructor always runs its parent's constructor first, via an explicit or implicit super(...), all the way up to Object (JLS SE 21, §8.8).
  5. this(...) or super(...) must be the very first statement, so a half-built parent is never observed.

3.7 final — "cannot be re-pointed", not "cannot change"

static and final get mixed up constantly, so pin them down: static answers "how many copies?", final answers "can this be assigned again?" They are unrelated ideas that simply appear together often, because a constant wants both.

final on a…Means
variable or fieldassigned exactly once; any later assignment is a compile error
methodno subclass may override it
classno class may extend it (e.g. String, Integer)
The classic misreading. final List<String> names = new ArrayList<>(); does not make the list unmodifiable. names.add("x") still works. final freezes the arrow, not the object the arrow points at. To freeze contents you need an immutable object or a wrapper such as Collections.unmodifiableList.
Make fields final by default. A class where every field is private final and set in the constructor is immutable: it cannot be corrupted, it is automatically thread-safe, and it is always a safe map key. Drop final only when you have a real reason for the field to change (Bloch, Effective Java, Item 17).

3.8 What every object inherits for free

Because all reference types descend from Object, every object you create already has a handful of methods. Three matter constantly:

MethodDefault behaviourWhy you usually override it
toString()class name + @ + a hex number — useless in a logreadable logs and debugging
equals(Object)same as ==: "is it literally the same object?"you usually want "same contents"
hashCode()derived from object identitymust agree with equals, or hash collections break

That gives the rule you will be asked about in every interview: == asks "same object?" and equals asks "same value?" For objects you almost always mean the second. The full contract — including why overriding equals without hashCode silently breaks HashMap — is lesson 8.

§4When to use

  • Make a class when you have data plus rules about that data. With no rules and no behaviour, a plain value or a small data holder is enough.
  • Make every field private as the starting point. Open it up only with a concrete reason.
  • Write a getter when callers genuinely need the value. Do not auto-generate a getter and a setter for every field — a setter for every field is a public field with extra steps, and it throws away your invariants.
  • Validate in the constructor whenever "an object of this type is always…" is a true sentence you can finish.
  • Use static for constants, stateless helpers and factory methods — never for mutable shared state.
  • Use final fields by default, and reach for full immutability for value-like things: money, dates, IDs, configuration.

§5Explain it to a 12-year-old

Imagine a vending machine. On the outside there are only buttons and a coin slot. That is the small door — the only way you can interact with it. Inside there are shelves, a motor and a cash box, and you cannot reach any of them. That is encapsulation.

Why bother? Because the machine has a rule it must never break: never hand out a snack that wasn't paid for. If the front of the machine were open, anyone could just take things and the rule would be meaningless. With only buttons and a coin slot, the machine gets to check first, every single time. The rule is safe because the inside is unreachable.

The class is the factory's design document for that machine. The object is one actual machine in one actual hallway, with its own snacks and its own coins. A static thing would be something printed on every machine from that factory — like the helpline number. One helpline for all of them, however many machines exist.

And final? That is the serial-number sticker. Put on once at the factory, never changed — though the snacks inside can still be refilled all day long. Freezing the label is not the same as freezing the contents.

§7In practice — one file, dissected

Full source: code/TypeDemo.java. Compile with javac TypeDemo.java, run with java TypeDemo. The output at the end of this section is real output from JDK 1.8.0_411, not remembered behaviour.

Chunk 1 — the three kinds of field, side by side

static class Account {
    private static int accountsOpened = 0;   // ONE for the whole class
    private final String id;                 // one per object, set once, frozen
    private long balancePaise;                // one per object, changes over time
}
Three fields, three completely different lifetimes. accountsOpened is shared by every Account ever created. id belongs to one object and never changes. balancePaise belongs to one object and does change — which is exactly why it is the one that needs guarding. Idiom: money is stored as a long of the smallest unit (paise/cents), never as double. Binary floating point cannot represent 0.1 exactly, so double money drifts.

Chunk 2 — the constructor as a gate

Account(String owner, long openingPaise) {
    if (owner == null || owner.trim().isEmpty())
        throw new IllegalArgumentException("owner required");
    if (openingPaise < 0)
        throw new IllegalArgumentException("opening balance cannot be negative");
    accountsOpened++;
    this.id = owner.trim().toUpperCase() + "-" + accountsOpened;
    this.balancePaise = openingPaise;
}

Account(String owner) {
    this(owner, 0L);     // delegate — the rules are written exactly once
}
Checks come before any assignment. If a check fails, the constructor throws and the caller never receives a reference — the broken object simply does not exist. The second constructor contains no logic at all; it hands over with this(...). Gotcha: if you copy-paste the validation into both constructors instead, the day someone fixes a rule in one and forgets the other is the day you get a bug that appears on only one code path.

Chunk 3 — behaviour public, state private

boolean withdraw(long paise) {
    if (paise <= 0) throw new IllegalArgumentException("withdrawal must be positive");
    if (paise > balancePaise) return false;    // the invariant: never below zero
    balancePaise -= paise;
    return true;
}

long balancePaise() { return balancePaise; }   // read-only window — no setter exists
There is a getter but deliberately no setter. The only way the balance moves is deposit and withdraw, and both enforce the rule. Note the two different failure styles: an illegal argument throws (the caller has a bug), while an insufficient balance returns false (a normal business outcome, not a bug). Choosing between those two is a real design decision — lesson 10 goes deep on it.

Chunk 4 — what a public field costs you

static class LeakyAccount {
    public long balancePaise;    // no door at all
}
...
leaky.balancePaise = -999;         // compiles, runs, corrupts
This is the control experiment: same data, no guard. The object is now in a state your business rules call impossible, and nothing in the language can stop it. Worse, you can never change how the value is stored without breaking every caller — the field name is part of your public API forever.

Chunk 5 — what final actually freezes

final StringBuilder note = new StringBuilder("hello");
note.append(" world");        // allowed! the OBJECT is not frozen
// note = new StringBuilder();  // NOT allowed — the arrow is frozen
One line compiles, the other does not. That is the whole final rule in two lines: the variable may not be re-pointed, but whatever it points at can still change inside. Immutability must come from the object's own design, not from the keyword on the variable.

§8Pitfalls

Getters and setters for everything. A setter for every field is not encapsulation — it is a public field with two extra lines. Expose behaviour (withdraw), not raw field access (setBalance).
Returning your internal collection. return this.items; hands the caller a live arrow into your object, and they can add and remove behind your back. Return an unmodifiable view or a copy.
Thinking final means immutable. It freezes the variable, not the object. A final field holding a mutable object is still mutable.
static mutable state. It is a global variable: shared across every thread, invisible in method signatures, and it leaks state between tests. Almost always a design smell.
Doing real work in a constructor. Opening sockets, reading files or starting threads during new makes the class untestable and can publish a half-built object. Build the object; do the work in a method.
Calling an overridable method from a constructor. The subclass's version runs before the subclass's own fields are initialised, so it sees nulls. Make such methods private or final (Bloch, Effective Java, Item 19).
Using == on objects. It compares arrows, not contents. Correct for enum constants and null checks; wrong for String, Integer and your own classes.

§9Recap

  • A type is a promise about shape and legal operations; Java checks it at compile time, so whole classes of bugs never reach production.
  • Every value is either one of 8 primitives (the box holds the value) or a reference type (the box holds an arrow). All reference types descend from Object.
  • Class = blueprint, object = one real thing. One class, many objects, each with its own instance fields.
  • static = one per class; instance = one per object. A static method has no this because there may be no object.
  • Encapsulation exists to protect invariants, not to generate getters. A private field can refuse bad data; a public one cannot.
  • Access levels: private → package-private → protected → public. Start closed; opening up later is cheap, closing down later breaks callers.
  • The constructor is the gate. Validate first, assign second, let other constructors delegate with this(...). Parent constructors always run first.
  • final freezes the arrow, not the object. Prefer final fields; real immutability comes from the class's own design.
  • == asks "same object?", equals asks "same contents?"

Reference — quick answers

QuestionAnswer
How many primitive types are there?Eight. Everything else is a reference type.
Does every class extend something?Yes — Object, directly or through its parents.
Why can't a static method use this?It belongs to the class; there may be no object at all.
What happens to the default constructor?It exists only if you declare no constructor yourself.
Can a constructor call another constructor?Yes — this(...) for the same class, super(...) for the parent. First statement only.
Does final make an object immutable?No. It only stops the variable being reassigned.

Glossary

Type
A label on data saying what shape it has and which operations are legal.
Static typing
Types are declared in source and checked by the compiler before the program runs.
Primitive type
One of the eight built-in value types; the variable holds the value itself.
Reference type
Class, interface, array or enum; the variable holds an arrow to a heap object, or null.
Class
The blueprint: the fields and methods a kind of object has.
Object / instance
One real thing built from a class with new, living on the heap.
Instance field
A field with one copy per object.
static
Belongs to the class — one copy shared by everything.
final
Assigned once (variable), not overridable (method), not extendable (class).
Encapsulation
Hiding internal state behind a deliberately small public surface.
Invariant
A rule about an object's state that must always hold true.
Access modifier
Who may see a member: private, package-private, protected, public.
Constructor
Code that runs during new to produce a valid starting state.
Constructor chaining
One constructor calling another via this(...) or its parent via super(...).
Immutable
An object whose state cannot change after construction.
