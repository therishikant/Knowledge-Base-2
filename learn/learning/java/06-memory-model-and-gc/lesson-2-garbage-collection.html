How Garbage Collection Works

Java › memory cluster · lesson 6, part 2 of 3 · DEEP — reachability, marking, and generations

Memory cluster: 1. Where your data lives · 2. How garbage collection works · 3. Collectors, leaks & tuning

In one line — You never delete objects in Java. Instead, the JVM regularly starts from a few known roots (the live local variables of every thread, plus static fields) and follows every arrow it can. Whatever it can reach is alive; everything else is garbage and its memory is reused. Because most objects die very young, the heap is split into a small young area that is cleaned often and cheaply, and an old area that is cleaned rarely.

§1Where it fits

Part 1 showed you the two areas and the arrows between them. One question was left open: the stack cleans itself by popping frames — but who cleans the heap?

That is this lesson. We will build the garbage collector from first principles: the question it has to answer, the two honest ways to answer it, the one Java picked, and the single trick (generations) that makes it fast enough to use everywhere. Part 3 then covers the actual collectors you choose between, and what still goes wrong.

§2Why it exists

2.1 Life without a collector

In C you ask for memory and you give it back yourself:

/* C */
Node *n = malloc(sizeof(Node));
use(n);
free(n);   /* your job — and only yours */

Three bugs are now permanently available to you, and they are famous for a reason:

MistakeWhat happens
You forget freeMemory leak. Memory is never returned; the process grows until it dies.
You free twiceDouble free. The allocator's own bookkeeping is corrupted — usually a crash, sometimes a security hole.
You free, then use the pointerDangling pointer / use-after-free. You read or write memory that now belongs to something else. This is one of the most exploited bug classes in software.

The deeper problem is not that these mistakes are easy. It is that "who frees this?" is not a local question. If you hand an object to three other modules, somebody must know when the last one is finished with it. That knowledge is scattered across the program, so manual freeing stops being a coding detail and becomes an architecture-wide contract.

Java's answer is blunt: take the decision away from the programmer entirely. The JVM decides when memory is free, which "completely eliminates some classes of errors related to memory management at the cost of some additional runtime overhead" (Oracle — HotSpot GC Tuning Guide, §1).

2.2 Two honest ways to automate it

If the machine must decide when an object is dead, it needs a definition of "dead". There are two classic ones.

(a) Reference counting. Every object keeps a counter of how many arrows point at it. The counter goes up when an arrow is created and down when one is removed. At zero, delete immediately.

  • Good: memory is freed the instant it becomes garbage; cost is spread smoothly instead of coming in pauses.
  • Bad: every single assignment has to update counters, which is slow and awkward with many threads.
  • Fatal: cycles. If a points to b and b points to a, both counters stay at 1 forever even when nothing else can reach them. The pair leaks. Doubly-linked lists, parent/child trees, and listener registrations are full of cycles.

(b) Tracing. Forget counting. Start from the places the program can definitely reach right now, and walk the arrows. Anything you never arrive at is garbage — including cycles, because walking never arrives at an isolated island.

Java (like Go, C#, Python's cycle detector, and JavaScript) uses tracing.

And a third way: do neither, and make the compiler prove when memory dies. That is Rust's ownership model. It costs you nothing at run time, but you must satisfy the borrow checker while writing the code. Java chose runtime cost over programmer cost; Rust chose the reverse. Neither is "correct" — it is a trade-off, and it is a good one to be able to explain.

§3How it works

3.1 The whole idea in one sentence

An object is alive if the program can still reach it by following arrows from a root; otherwise it is garbage. In Oracle's words, an object "is considered garbage and its memory can be reused by the VM when it can no longer be reached from any reference of any other live object in the running program" (Oracle — GC Tuning Guide, §3 Generational Garbage Collection).

Notice what this definition does not say. It does not say "an object you are still using". The JVM has no idea what you intend to use. It only knows what you can still reach. Hold that thought — in part 3 it turns out to be the exact definition of a Java memory leak.

3.2 What counts as a root

Roots are the starting points: the handful of places the JVM knows are live without having to prove anything.

RootWhy it is obviously live
Local variables in every active frame, on every threadSome method is running right now and can use them at any moment.
static fields of loaded classesAny code can read them at any time, for as long as the class stays loaded.
Active Thread objectsThey are running.
JNI references held by native codeC code outside the JVM is holding them.
Objects used as monitors (locks held by a thread)A thread is inside a synchronized block on them.

3.3 Step one: mark

The collector walks the graph from the roots and marks everything it visits. This is a plain breadth-first or depth-first search. The cost of marking is proportional to the number of live objects — not to the size of the heap and not to the amount of garbage. Dead objects cost nothing to find. Remember that sentence; it is the reason the next trick works.

3.4 Step two: get the space back

There are three ways to reclaim the unmarked space, and real collectors mix them.

StrategyHowTrade-off
SweepWalk the heap and add every unmarked block to a free list.Cheap, but leaves holes — the heap gets fragmented, and allocation becomes a search for a big-enough hole.
CompactSlide the live objects together, leaving one big empty area.Fixes fragmentation and makes allocating trivial, but moving objects means fixing up every arrow pointing at them.
Copy (evacuate)Copy the live objects into a fresh empty area and declare the old area empty.Cost depends only on the survivors, so it is almost free when nearly everything is dead. Needs spare space to copy into.

3.5 Why allocating in Java is so cheap

Because the young area is kept compact, creating an object is usually just: take the current "next free" pointer, add the object's size, done. That is a handful of machine instructions — often faster than C's malloc, which has to search a free list.

On top of that, each thread gets its own private slice of the young area, a TLAB (thread-local allocation buffer), so threads do not even have to coordinate with each other while allocating. This is why the advice "don't create objects, reuse them" is usually wrong in modern Java — you will measure this yourself in §7.

3.6 The big trick: generations

Marking costs money proportional to live objects, so the collector wants to look at regions where almost everything is dead. Luckily, programs cooperate. The weak generational hypothesis says: most objects die very young (Oracle — GC Tuning Guide §3). Think of the temporary objects in a loop, an iterator, a parsed request, a StringBuilder — all dead within microseconds. A few things (your cache, your connection pool, your configuration) live for the whole run. Very little sits in between.

So the heap is divided by age:

  • Young generation — where new objects are born. It is small, and it is collected often. Because nearly everything in it is already dead, a collection copies out the few survivors and wipes the rest. This is a minor collection.
  • Old generation (tenured) — where objects that have survived several young collections are promoted. It is big, and it is collected rarely. A collection here is a major (or full) collection and is much more expensive.

The young generation is itself split into eden plus two survivor spaces. Most objects are allocated in eden. One survivor space is always empty and serves as the destination for the live objects found in eden and in the other survivor space; after the collection, eden and the source survivor space are empty. Objects bounce between the survivor spaces, their age counter rising each time, until they have been copied enough times (or there is no room) — then they are copied into the old generation. Oracle calls this process aging (Oracle — GC Tuning Guide §3, "Generations").

Why two survivor spaces and not one? Because the collector copies survivors instead of sweeping them. Copying needs an empty destination. Keeping one survivor space empty at all times guarantees there is always somewhere to copy to, and the "from" space can then be wiped in one go. The two swap roles at every collection.

3.7 Stop-the-world pauses and safepoints

There is a problem with walking a graph that is being edited: if application threads keep moving arrows around while the collector traces, the collector's answer is wrong. The simplest fix is to stop all application threads while the critical work happens. That is a stop-the-world pause.

Threads do not stop instantly. The JVM waits for each thread to reach a safepoint — a spot in the compiled code (method returns, loop back-edges) where the JVM knows exactly what is in every register and frame, so the stack can be scanned accurately. Then everyone waits, the GC works, and everyone resumes.

Pauses are the real cost of garbage collection, and they are the thing modern collectors fight over. The two numbers people care about are throughput ("what percentage of total time is not spent collecting") and latency ("how long is the longest pause") (Oracle — GC Tuning Guide §3, Performance Considerations). Modern collectors shrink pauses by doing most of the marking concurrently, while your code keeps running, and stopping the world only for short bookkeeping phases. That is part 3.

3.8 The life of an object

3.9 What the collector does not clean

  • Files, sockets, database connections. These are operating-system handles, not heap memory. GC will never close them for you. Use try-with-resources.
  • Native memory held by direct ByteBuffers or JNI libraries — only loosely tied to GC.
  • Metaspace. Class metadata lives in native memory and is only freed when the whole class loader becomes unreachable. This is why redeploying an app repeatedly on an old server could throw OutOfMemoryError: Metaspace.
  • Thread stacks. Freed when the thread ends, not by GC.
The rule: GC manages memory. You manage resources. Anything with a close() method is your job.

§4When to use this knowledge

  • Explaining why a cycle is not a leak in Java — a very common interview question, and the cleanest way to show you understand tracing versus counting.
  • Deciding whether to "optimize" allocations. Knowing that young-gen allocation is a pointer bump stops you from writing object pools that make the code worse and slower.
  • Reading a GC log. -verbose:gc prints lines like 239M->57M(307M): used before → used after (total heap) (Oracle — GC Tuning Guide §3). If "after" keeps creeping up over hours, you have a leak.
  • Diagnosing latency spikes. A request that is usually 5 ms and sometimes 400 ms is often sitting in a stop-the-world pause.
  • Choosing where to hold data. Anything that survives the young generation is now your long-term cost; that is what caches really charge you.

§5Explain it to a 12-year-old

Back to the warehouse from part 1. Boxes pile up all day. Nobody is allowed to throw a box out themselves, because someone else might still need it — and if two people both throw out the same box, chaos.

So once in a while the warehouse manager does a sweep. She starts at the front desk, where all the notes people are currently holding are kept. Every note points to a box. She walks to that box, and if that box contains more notes, she follows those too, and so on. Every box she reaches gets a sticker.

When she has followed every note she can, she looks around. Any box without a sticker is garbage — nobody could possibly reach it. Even if two unstickered boxes contain notes pointing at each other, it does not help them: she never walked in, so they both go.

Here is her clever shortcut. She has noticed that most new boxes are rubbish within minutes, while boxes that have survived a month usually survive forever. So she keeps new boxes in a small room near the door and checks that room constantly — it is quick, because almost everything in it is rubbish and she only has to carry out the few keepers. Boxes that keep surviving get moved to the big back room, which she only cleans out occasionally.

And the naive question — why not just tidy up after yourself? — is answered by the C column in §2.1: because people forget, people throw out things others still need, and nobody can see the whole warehouse at once.

§7In practice — proving it, line by line

Full source: code/GcDemo.java. Compiled and run on JDK 1.8.0_411.

Chunk 1 — unreachable really does mean collectable

WeakReference<Node> watch = new WeakReference<Node>(new Node(1));
System.out.println("before gc: still there = " + (watch.get() != null));
System.gc();
Thread.sleep(100);
System.out.println("after  gc: still there = " + (watch.get() != null));
A WeakReference lets you look at an object without holding it — it is deliberately not counted as a root (part 3 explains the family). So the Node(1) has no strong arrow at all, and the collector takes it. Note the honesty: System.gc() is only a request. It happens to be honoured here, which is why this is a teaching demo and not production code.

Chunk 2 — a cycle is still garbage

Node x = new Node(2), y = new Node(3);
x.friend = y;   // x -> y
y.friend = x;   // y -> x : each has an incoming arrow
WeakReference<Node> watchCycle = new WeakReference<Node>(x);
x = null;       // drop the only arrows from a root
y = null;
System.gc();
Under reference counting both objects would have a count of 1 and would leak forever. Under tracing, no root can reach the island, so both die. This five-line demo is the whole counting-vs-tracing argument.

Chunk 3 — short-lived objects are nearly free

for (int i = 0; i < 2_000_000; i++) {
    Node temp = new Node(i);   // ~1 KB each, dies immediately
    if (temp.id == -1) System.out.println("never");
}
Two million objects, roughly two gigabytes of total allocation, in about half a second — and the heap is no bigger at the end than at the start. Every one of them was born in eden and wiped by a minor collection that only had to copy out zero survivors. The if is there on purpose, so the JIT cannot simply delete the loop.

Real output (JDK 1.8.0_411, default heap)

--- 1. unreachable means collectable ---
before gc: still there = true
after  gc: still there = false

--- 2. a cycle is still garbage ---
cycle survived gc? false

--- 3. short-lived objects are cheap ---
allocated 2,000,000 short-lived objects in 533 ms
used before = 10 MB, used after gc = 10 MB
Read the last line twice. Two million allocations later, memory use is unchanged. That is the weak generational hypothesis paying for itself — and the reason "reuse objects to help the GC" is usually bad advice.
See it live. Run java -verbose:gc GcDemo and watch the minor collections scroll past during chunk 3. Then (1) raise the loop to 20 million and see whether memory use still stays flat; (2) change Node temp to LEAK.add(new Node(i)) and watch it stop being flat; (3) run with -Xmx64m and predict which chunk fails first. Predict before running.

§8Pitfalls

Calling System.gc() in real code. It is a hint, and it typically triggers an expensive full collection at exactly the wrong moment. Use it in demos, never in production.
Setting variables to null everywhere "to help GC". A local variable dies when its frame pops. Nulling only matters for long-lived fields — for example clearing a slot in a cache or an array you still hold.
Relying on finalize(). It is deprecated for removal, runs at an unpredictable time, may never run at all, and can even resurrect objects. Use try-with-resources, or java.lang.ref.Cleaner.
Expecting memory to return to the OS. Freed heap usually stays owned by the JVM for reuse. A flat "used" number inside the JVM is the thing to watch, not the process size.
Thinking GC is instant. An object becomes unreachable at a precise moment, but it is collected whenever the JVM feels like it. Never tie correctness to collection timing.
Assuming GC means "no memory bugs". It removes double-free and use-after-free. It does not remove leaks — see part 3.

§9Recap

  • Manual malloc/free buys three bug classes: leaks, double frees, use-after-free. Java removes two of them outright by taking the decision away from you.
  • Reference counting frees promptly but cannot handle cycles; tracing handles cycles because it asks "can I reach it?" Java traces.
  • An object is alive if reachable from a GC root: live locals on any thread, static fields, active threads, JNI references, held monitors.
  • Marking costs time proportional to live objects — garbage is free to ignore.
  • Space is reclaimed by sweep (fast, fragments), compact (tidy, must move), or copy (cost scales with survivors only).
  • Weak generational hypothesis: most objects die young. Hence a small young gen (eden + two survivor spaces, aging, minor GC) and a big old gen (promotion, rare major GC).
  • Allocation is a pointer bump in a per-thread TLAB, so creating short-lived objects is extremely cheap — measured above as 2,000,000 objects with zero net heap growth.
  • Correct tracing needs stop-the-world pauses at safepoints; the two metrics that matter are throughput and latency.
  • GC manages heap memory only — not files, sockets, native memory, or thread stacks.

Glossary

Garbage
An object that can no longer be reached from any GC root.
GC root
A starting point for tracing: live locals, static fields, active threads, JNI refs, held monitors.
Reachability
Whether a path of references exists from some root to an object.
Tracing collector
A collector that finds live objects by walking the graph from the roots.
Reference counting
The alternative scheme that counts incoming references; defeated by cycles.
Mark–sweep–compact
Mark the live set, reclaim the rest, then slide survivors together.
Young / old generation
Heap regions for newly created vs long-surviving objects.
Eden / survivor space
The allocation area and the two copy-destination areas inside the young generation.
Aging
Counting how many collections an object has survived, to decide when to promote it.
Throughput
The share of total time not spent collecting.
Latency / pause time
How long the application is stopped for a single collection.
