Collectors, Leaks & Tuning

Java › memory cluster · lesson 6, part 3 of 3 · DEEP — choosing a collector, and why Java still leaks

Memory cluster: 1. Where your data lives · 2. How garbage collection works · 3. Collectors, leaks & tuning

In one line — There is no single best garbage collector, only a trade between throughput, pause time and memory footprint, so the JVM ships several and picks a sensible default. And because the collector keeps everything reachable, Java still leaks in one specific way: objects you forgot to stop pointing at. Finding those is a skill, and it has standard tools.

§1Where it fits

Part 1 showed where data lives. Part 2 showed how the collector decides what to delete. Both were about mechanism. This part is about decisions: which collector to run, how to express what your application cares about, how to hold a reference that does not prevent collection, and what to do when memory still climbs.

This is the part that shows up in production incidents and in senior interviews.

§2Why it exists

Consider two real programs:

  • An overnight batch job crunching a hundred gigabytes. Nobody is watching. If it stops for four seconds every minute but finishes 10% sooner, that is a clear win.
  • A trading API or a web service with a 50 ms budget per request. A single four-second pause is an outage, even though total time lost is small.

These two want opposite collectors. The batch job wants maximum throughput (do the collection work in bulk, with all cores, as rarely as possible). The service wants minimum latency (do the work in tiny slices, concurrently with the application, even if the total work is larger).

There is also a third corner: footprint. Doing GC work concurrently costs extra CPU and extra memory; a tiny container may prefer a simple collector that uses almost nothing.

§3How it works

3.1 What you get if you do nothing

The JVM configures itself — Oracle calls this ergonomics. On a modern machine the defaults are:

SettingDefault
CollectorG1 on a server-class machine; Serial otherwise
"Server-class" meansat least 2 processors and at least 1792 MB of physical memory
Initial heap (-Xms)1/64 of physical memory
Maximum heap (-Xmx)1/4 of physical memory
Compilertiered, using both C1 and C2 (lesson 4)

(Oracle — GC Tuning Guide, §2 Ergonomics)

This bites people in containers. "1/4 of physical memory" used to mean the host's memory, so a JVM in a 512 MB container would happily plan for a multi-gigabyte heap and get killed by the OOM-killer. Modern JVMs are container-aware (they read cgroup limits), but setting -Xmx explicitly in production remains the safe habit. Oracle's own first piece of advice is to run with the defaults, and only then adjust heap size.

3.2 The collector menu

CollectorHow it worksChoose it whenFlag
SerialOne thread does everything, stop-the-world. Generational. Small data sets (up to roughly 100 MB), single-processor machines, tiny containers. Simple and efficient because there is no thread coordination. -XX:+UseSerialGC
Parallel ("throughput collector")Same design as Serial but many threads per pause. Medium-to-large data sets on multiprocessor hardware where peak throughput matters and pauses of a second or more are acceptable — batch, ETL, analytics. -XX:+UseParallelGC
G1 — Garbage-First (default)Mostly concurrent. Splits the heap into many equal regions and collects the ones with most garbage first; aims at a pause-time target. Almost everything. The balanced choice when response time matters but you also want throughput; scales from small to very large heaps. -XX:+UseG1GC
ZGCFully concurrent; pause times independent of heap size. Response time is the top priority. Max pauses under a millisecond, at the cost of some throughput. Works from a few hundred MB up to 16 TB. -XX:+UseZGC
ShenandoahAlso concurrent, including compaction (OpenJDK builds). Same goal as ZGC — very short pauses on large heaps. -XX:+UseShenandoahGC

Descriptions and selection guidance from Oracle — GC Tuning Guide, Available Collectors. Oracle's summary: run with the default first; adjust heap size next; only then change collector.

3.3 What makes G1 different

Classic collectors treat young and old as two big contiguous blocks. G1 chops the heap into a few thousand equal-sized regions and labels each one as eden, survivor, or old at runtime. A collection picks a set of regions — the ones with the most garbage, hence "garbage first" — and evacuates the live objects out of them.

This buys two things:

  • A pause-time target you can state. -XX:MaxGCPauseMillis=200 is a hint; G1 picks how many regions it can evacuate within that budget. It is a goal, not a guarantee (GC Tuning Guide §2, Maximum Pause-Time Goal).
  • Compaction for free. Evacuating a region empties it completely, so fragmentation is handled as a side effect.

3.4 References that do not keep objects alive

Part 2 said: reachable means alive. That is true for the normal kind of reference, called a strong reference — the ordinary variable or field. But Java gives you three weaker kinds in java.lang.ref, and they are the tool for building caches that cannot cause an out-of-memory error.

KindDoes it keep the object alive?Typical use
Strong — Object o = ...Yes, always.Everything normal.
Soft — SoftReferenceYes, until memory runs short; then the GC may clear it.Memory-sensitive caches you would like to keep but can rebuild.
Weak — WeakReferenceNo. Cleared as soon as no strong reference remains.Side tables keyed by object identity — exactly what WeakHashMap and ThreadLocal use.
Phantom — PhantomReferenceNo, and get() always returns null.Being told after an object is gone so you can release a native resource. The modern face of this is Cleaner.
In practice: most teams never write SoftReference by hand. They use a real cache library (Caffeine, Guava) with a maximum size and an expiry policy, because a bounded cache is easier to reason about than one that depends on GC timing. Reach for weak references mainly when you need identity-keyed metadata that must not keep the key alive.

3.5 Java leaks — the one memory bug GC cannot remove

The collector's rule is "reachable = keep". It has no idea whether you will ever use the object again. So the Java definition of a leak is:

a leak is an object that is still reachable but will never be used again.

Five patterns cause nearly all of them:

PatternWhy it holds onFix
A growing static collection
static List<X> ALL = new ArrayList<>();		 static fields are GC roots and the class usually lives forever, so everything inside lives forever. Do not accumulate in statics. Bound it, or scope it to a request/session.
An unbounded cacheEvery entry is strongly reachable from the map. Use a cache with a max size and eviction (LRU/TTL).
Listeners and callbacks never removedThe publisher keeps a strong arrow to every subscriber, so the subscriber (and everything it points at) never dies. Always pair addListener with removeListener; consider weak listeners.
ThreadLocal in a thread poolPool threads are reused for the lifetime of the app, so whatever you stashed stays attached to them. remove() in a finally block at the end of each task.
Inner classes and lambdas capturing thisA non-static inner class holds a hidden arrow to its outer object. Store it somewhere long-lived and the whole outer object is pinned. Prefer static nested classes; capture only the fields you need.

A sixth, subtler one: mutating a key after putting it in a HashMap. The entry is now in the wrong bucket, so you can neither find nor remove it — but the map still holds it. See lesson 8.

3.6 The cheapest collection: objects that never reach the heap

The JIT compiler (lesson 4) performs escape analysis: if it can prove an object never leaves the method that created it, it may skip heap allocation entirely and keep the fields in registers — this is called scalar replacement. The object effectively never exists, so the collector has nothing to do.

This is the technical reason "pool everything" is bad advice. A pooled object must escape, so you lose this optimization, you make it survive into the old generation, and you add bugs around reuse and cleanup. Pool things that are genuinely expensive to create — threads, database connections, sockets — not plain objects.

3.7 Reading the failure modes

3.8 How to actually find a leak

  1. Confirm it. Turn on -verbose:gc (or -Xlog:gc* on Java 9+) and watch the "used after GC" number over hours. A real leak makes the post-collection floor rise steadily. Saw-tooth that always returns to the same floor is healthy.
  2. Capture evidence automatically. Always run production with -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/var/log/app. Debugging an OOM without a dump is guesswork.
  3. Or capture on demand — jcmd <pid> GC.heap_dump app.hprof (or the older jmap).
  4. Open the dump in Eclipse MAT or VisualVM. Look at the dominator tree: it tells you which single object is keeping the most memory alive. Then ask MAT for the path to GC roots of a suspect object — that path is your bug, spelled out.
  5. For live, low-overhead observation, use Java Flight Recorder (-XX:StartFlightRecording) and read it in JDK Mission Control (lesson 14).
The one question that solves it: not "what is using memory?" but "who is still pointing at this?" That is the path-to-GC-roots view, and it comes straight from part 2's definition of liveness.

§4When to use

  • Deploying a new service: set -Xmx explicitly, leave the collector at the default (G1), and enable heap dump on OOM.
  • Latency complaints / p99 spikes: check GC pauses first; consider a pause target, a bigger heap, or ZGC.
  • Batch workloads: consider Parallel GC and a large heap — pauses are free when nobody is waiting.
  • Tiny containers and CLI tools: Serial GC starts fast and uses little memory.
  • Building a cache: bound it. Use weak/soft references only when identity semantics or memory-sensitivity genuinely demand it.
  • Memory climbing in production: GC log → heap dump → dominator tree → path to GC roots.

§5Explain it to a 12-year-old

The warehouse manager from part 2 can clean in different styles. She can lock the doors and have ten helpers clean the whole place at once — fastest overall, but nobody can work while she does it. Or she can tidy one shelf at a time while everyone keeps working — nobody is blocked for long, but the total tidying takes more effort. Or, if the warehouse is tiny, she can just do it herself with no helpers at all. None of these is "the best"; it depends on whether people are waiting.

Now the sad part. Imagine someone writes a note for every box that arrives, and pins all the notes to the wall by the front desk. They never take any note down. The manager walks in, sees a note for every single box, and must keep every single box — the warehouse fills up even though nobody wants any of it. Nothing is broken. The rule is being followed perfectly. The mistake was pinning notes to the wall forever.

That is a Java memory leak, and it is why "the garbage collector handles memory" never means "I can stop thinking".

§7In practice — building a leak, then fixing it

Full source: code/GcDemo.java. Compiled and run on JDK 1.8.0_411.

Chunk 4 — a leak with no missing free()

static final List<Node> LEAK = new ArrayList<Node>();   // static = GC root
...
for (int i = 0; i < 100_000; i++) {
    LEAK.add(new Node(i));     // ~1 KB each; nobody ever removes them
}
System.gc();                   // collects nothing — they are all reachable
...
LEAK.clear();                  // THE fix: drop the arrows
System.gc();                   // now the memory comes back
Compare this with chunk 3 in part 2, which allocated twenty times more and cost nothing. The only difference is that these objects are reachable from a static field. Allocation is not the problem; retention is. Also notice that the fix is one line, and it is not a free() — it is "stop pointing".

Chunk 5 — ask the JVM what it is actually doing

for (GarbageCollectorMXBean gc : ManagementFactory.getGarbageCollectorMXBeans()) {
    System.out.println(gc.getName()
        + " | collections = " + gc.getCollectionCount()
        + " | total pause time = " + gc.getCollectionTime() + " ms");
}
These beans are the same numbers your monitoring system scrapes. Two useful habits: the collector names tell you which GC is running, and collectionTime / uptime is a rough "how much of my CPU is going to GC?" ratio — anything above a few percent is worth investigating.

Real output (JDK 1.8.0_411)

--- 4. a leak: reachable but useless ---
after gc, still holding 100000 nodes, used = 112 MB
after clear() + gc, used = 10 MB

--- 5. who is collecting, and how big is the heap? ---
max heap  = 4444 MB
collector: PS Scavenge | collections = 8 | total pause time = 85 ms
collector: PS MarkSweep | collections = 5 | total pause time = 104 ms
Three things to read out of this. (a) 112 MB → 10 MB after a single clear(): the memory was never lost, only held. (b) max heap = 4444 MB on a 16 GB machine is ergonomics choosing ¼ of physical memory, exactly as documented. (c) The collector names reveal the default: PS Scavenge (young) and PS MarkSweep (old) are the Parallel collector — the JDK 8 default. On JDK 9+ the same code prints G1 Young Generation / G1 Old Generation, which is the clearest possible demonstration that the default changed.
Experiments. (1) Re-run with java -XX:+UseSerialGC GcDemo and then -XX:+UseParallelGC; compare collection counts and total pause time. (2) Run with -Xmx128m -XX:+HeapDumpOnOutOfMemoryError and raise the leak loop to 1,000,000 — then open the .hprof file in VisualVM and find LEAK in the dominator tree. (3) Replace the ArrayList with a Map<Node,String>, then with a WeakHashMap — which one survives System.gc(), and why?

§8Pitfalls

Tuning before measuring. Flags copied from a blog post are the most common cause of worse performance. Get a GC log first; change one thing at a time.
Changing collector before changing heap size. Oracle's order is: defaults → heap size → collector. Most "GC problems" are really "heap too small".
Believing a pause target is a guarantee. -XX:MaxGCPauseMillis is a goal. Set it absurdly low and G1 will shrink the young generation, collect constantly, and destroy your throughput.
Soft references as a cache strategy. They make memory behaviour unpredictable and can delay collection. A bounded cache with explicit eviction is almost always better.
Forgetting ThreadLocal.remove() in a pooled thread. A pool thread may live for the whole application, and so will whatever you attached to it.
Letting a non-static inner class or lambda capture this into something long-lived. You have pinned the entire outer object without writing a single reference to it.
Running production without -XX:+HeapDumpOnOutOfMemoryError. The one crash that could have told you everything, and you did not record it.

§9Recap

  • There is no best collector — only the trade between throughput, latency and footprint.
  • Defaults (ergonomics): G1 on server-class machines (≥2 CPUs, ≥1792 MB), Serial otherwise; heap starts at 1/64 and maxes at 1/4 of physical memory.
  • Serial = tiny/simple · Parallel = raw throughput · G1 = balanced default with a pause goal · ZGC/Shenandoah = sub-millisecond pauses on huge heaps.
  • G1 uses regions with dynamic roles and collects the most-garbage regions first, compacting as it evacuates.
  • Reference strengths: strong (always keeps) · soft (keeps until memory is tight) · weak (cleared at the next GC) · phantom (post-mortem cleanup; use Cleaner).
  • A Java leak = still reachable, never used again. Statics, unbounded caches, un-removed listeners, ThreadLocal in pools, inner classes capturing this.
  • Escape analysis can delete allocations entirely — so pool expensive resources, not ordinary objects.
  • Different OOM messages mean different bugs: heap space, GC overhead, Metaspace, native thread.
  • Diagnosis path: GC log → heap dump → dominator tree → path to GC roots. Always run with heap-dump-on-OOM enabled.

Glossary

Ergonomics
The JVM choosing collector, heap size and compiler for you based on the machine.
Throughput collector
Parallel GC — optimizes total work done, accepts longer pauses.
Concurrent collector
Does most of its work while the application runs, to keep pauses short (G1 mostly, ZGC/Shenandoah fully).
Region
One of G1's equal-sized heap chunks, labelled eden/survivor/old at runtime.
Pause-time goal
A target, not a promise, given via -XX:MaxGCPauseMillis.
Soft / weak / phantom reference
References that permit collection under different conditions.
Memory leak (Java)
An object that stays reachable but is never used again.
Dominator tree
Heap-dump view showing which object is responsible for keeping which memory alive.
Path to GC roots
The chain of references that explains why an object was not collected.
Escape analysis
JIT analysis proving an object never leaves a method, allowing it to skip the heap.
Heap dump
A snapshot of every object in the heap, written as a .hprof file.
