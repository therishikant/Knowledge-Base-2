Where Your Data Lives

Java › memory cluster · lesson 6, part 1 of 3 · DEEP — the stack, the heap, and what a variable really holds

Memory cluster: 1. Where your data lives · 2. How garbage collection works · 3. Collectors, leaks & tuning

In one line — A Java variable holds one of two things: a value (a number, a character, a true/false) or an arrow that points to an object. Values and arrows live on a small, fast, per-thread area called the stack. The objects they point at live in one big shared area called the heap. Almost every confusing thing in Java — "why did my object change?", "is Java pass-by-reference?", "why is my copy not really a copy?" — becomes obvious once you can see which box holds a value and which box holds an arrow.

§1Where it fits

Lesson 3 (runtime data areas) gave you the map of JVM memory: heap, method area, stacks, PC. Lesson 5 (type system & OOP) taught you that Java has two kinds of types: primitives and reference types.

This lesson joins the two. It answers one plain question — when I write a line of code, where does each piece of data actually sit? That question is the base for everything that follows: part 2 explains how the JVM cleans the heap, part 3 explains how to pick a cleaner and how to find leaks. It is also the base for collections, strings, and threads.

§2Why it exists

A program has two very different kinds of data

Think about what a running method needs:

  • Scratch data. A loop counter. A temporary sum. The argument you were given. This data belongs to one method call, on one thread, and it is useless the moment the method returns.
  • Real data. A Customer. A List of orders. These must stay alive after the method that made them returns, because they get handed to other methods, stored in fields, or shared with other threads.

These two kinds want opposite things. Scratch data wants to be cheap and instantly thrown away. Real data wants to outlive the method that made it. One single memory area cannot be good at both jobs. So the JVM uses two: a stack per thread for scratch data, and one shared heap for real objects (JVM Spec SE 21, §2.5).

Why not just put everything on the heap?

Because stack memory is almost free. The stack is a simple pile. Calling a method pushes one block on top; returning pops it off. No search, no bookkeeping, no cleaner thread. Heap memory is slower to manage: objects there have different sizes, live for different lengths of time, and somebody has to notice when they become garbage. So the JVM keeps the cheap area for the data that is cheap to handle.

Why not just put everything on the stack?

Because a stack frame dies when the method returns. If an object lived inside the frame, this would be a disaster: 

static Customer load() {
    Customer c = new Customer("Asha");
    return c;      // the frame is about to be destroyed...
}                     // ...but the Customer must survive!

The object must outlive the call, so it cannot live inside the call's frame. It goes to the heap, and the method returns an arrow to it. That is the whole reason the heap exists.

§3How it works

3.1 The one rule for variables

Every Java variable is a small labelled box. What goes in the box depends only on its type:

If the type is…The box holds…Example
a primitive (int, long, double, char, boolean, byte, short, float) the value itselfint age = 30; → the box contains 30
anything else — a class, an interface, an array, String, a boxed Integer an arrow to an object on the heap (or null, meaning "arrow pointing nowhere") String s = "hi"; → the box contains an arrow

That is it. There is no third case. Java has exactly two shapes of data (JLS SE 21, §4.1 — types are divided into primitive types and reference types).

Vocabulary note. The official word for "arrow" is reference. In C it would be called a pointer, but Java's references are safer: you cannot do arithmetic on them, and you cannot make one point at a random address.

3.2 The stack: one private desk per thread

Each thread gets its own stack. A stack is a pile of frames, and one frame = one method call. A frame holds that call's parameters and local variables, plus the bookkeeping needed to return to the caller.

The stack only does two things: push a frame when a method is called, and pop it when the method returns. Popping is the cleanup. Nothing has to be searched, and no garbage collector is involved. This is why a local int costs essentially nothing.

Two consequences you will meet in real life:

  • Deep recursion crashes. Each call pushes a frame. Recursion with no stopping condition keeps pushing until the stack is full, and you get StackOverflowError (JVM Spec §2.5.2).
  • Threads are not free. Every thread needs its own stack (commonly around 512 KB–1 MB of reserved space), which is one reason you cannot simply start a hundred thousand platform threads. That is exactly the problem virtual threads (lessons 11–12) were created to solve.

3.3 The heap: one shared warehouse

Every object you create with new goes on the heap. So does every array, and every String. The heap is shared by all threads, which is both its superpower (threads can hand objects to each other) and its danger (two threads editing the same object need rules — lesson 11).

The heap is also the only area the garbage collector cleans (JVM Spec §2.5.3). That is part 2 of this cluster.

3.4 Putting it together — one picture

Read this code, then read the picture under it:

class Engine { int horsepower; }

static void demo() {
    int speed = 60;                        // value, on the stack
    Engine e1 = new Engine();             // arrow on stack, object on heap
    e1.horsepower = 150;
    Engine e2 = e1;                         // SECOND arrow to the SAME object
}

3.5 What is actually inside an object

An object on the heap is not only your fields. HotSpot stores each object as:

  • a header — a few bytes of JVM bookkeeping: which class this is, lock state, identity hash code, GC age;
  • your fields, laid out by the JVM (it may reorder them and add padding so each field sits on a tidy boundary);
  • for arrays only, an extra length field.

So an object with one int field costs far more than 4 bytes. This is the real reason people say "ArrayList<Integer> is heavy compared to int[]": the int[] is one object holding packed numbers, while the list holds arrows to many separate Integer objects, each with its own header.

3.7 Pass-by-value — the question every interviewer asks

Java is always pass-by-value. There are no exceptions. The confusion comes from forgetting what the value is: for a reference variable, the value is the arrow, not the object.

When you call a method, the JVM copies what is in the box into the new frame. So:

CaseWhat gets copiedCan the method affect the caller?
void f(int n) { n = 999; }the numberNo. The caller's number is untouched.
void f(Engine e) { e.hp = 999; }the arrowYes. The copied arrow leads to the same object, and the method edits that object.
void f(Engine e) { e = new Engine(); }the arrowNo. It only re-aimed its own copy of the arrow.
How to say it in an interview: "Java is strictly pass-by-value. For reference types the value being passed is the reference itself, so the callee can mutate the shared object but can never rebind the caller's variable."

3.8 Shallow copy vs deep copy

Same idea, one level up. Suppose a Car has an Engine:

  • A shallow copy makes a new Car box and copies the fields as they are. The engine field is an arrow, so the copy gets the same arrow — both cars share one engine.
  • A deep copy makes a new Car and a new Engine for it. Nothing is shared.
The modern way out. Deep copying is fiddly and easy to get wrong. The idiomatic fix is to make the inner object immutable — if nobody can change the Engine, sharing it is perfectly safe and copying is pointless. This is why String, LocalDate and records exist. Covered in lessons 8, 9 and 12.

3.9 Why == lies to you

Now the classic trap is obvious. == compares what is in the boxes:

  • for primitives that is the values, so == means "same number". Correct.
  • for references that is the arrows, so == means "same object", not "same contents".

To compare contents you need equals. This is the root of new String("a") == new String("a") being false, and of the Integer caching surprises. We return to both in lesson 8 (equality) and lesson 9 (strings).

§4When to use this knowledge

  • Debugging "it changed by itself". A value changed in a place you never touched? Someone else holds an arrow to the same object. Draw the boxes and arrows and you will find them.
  • Designing APIs. If you return your internal List field, the caller can modify your object's insides. Return an unmodifiable view or a copy. The same applies to constructor arguments you store.
  • Writing equals/hashCode. You are literally deciding "when should two different heap objects count as the same thing?"
  • Reading errors. StackOverflowError = too many frames (usually bad recursion). OutOfMemoryError: Java heap space = too many live objects. Different area, different cause, different fix.
  • Sizing a service. Threads cost stack; caches and sessions cost heap.

§5Explain it to a 12-year-old

Imagine you work at a big warehouse. On your desk you keep small notes. Some notes have a number written straight on them: "60". Other notes just say "box 42, aisle 7".

The desk is the stack. It is yours alone, it is small, and when you finish a job you sweep the whole desk clean in one motion. The warehouse is the heap. It is huge, everyone shares it, and the real boxes are there.

Now everything follows:

  • If you photocopy a note that says "60" and scribble "999" on the copy, the first note still says 60. (Primitives.)
  • If you photocopy a note that says "box 42" and hand it to a friend, your friend walks to the same box 42 and can paint it red. Your box is now red. (Objects.)
  • If your friend crosses out their copy and writes "box 99" instead, your note still says "box 42". They changed their paper, not yours. (Re-assigning a parameter.)
  • Copying the note is a shallow copy. Walking to the warehouse and building a second identical box is a deep copy.

And the naive question — why not keep everything on the desk? — answers itself: because the desk gets swept clean when you finish, and some things have to survive the sweep.

§7In practice — one file, dissected

Full source: code/MemoryDemo2.java. Compiled and run on JDK 1.8.0_411.

Chunk 1 — primitives copy the value

int a = 10;
int b = a;   // copies the number 10 into a new box
b = 20;
Two boxes, two numbers. Changing b cannot possibly reach a. Output: a = 10, b = 20.

Chunk 2 — references copy the arrow

Engine e1 = new Engine(100);
Engine e2 = e1;            // copies the ARROW, not the object
e2.horsepower = 250;
One object, two arrows. e1.horsepower is now 250, and e1 == e2 is true. Gotcha: people read line 2 as "make me another engine". It creates nothing — there is no new on that line, and only new creates objects.

Chunk 3 — the three passing cases

static void changeNumber(int n)         { n = 999; }
static void changeInside(Engine e)      { e.horsepower = 999; }   // follows the arrow
static void pointSomewhereElse(Engine e) { e = new Engine(999); }  // re-aims its own copy
These three one-liners are the pass-by-value answer. changeInside works because the copied arrow leads to the caller's object. pointSomewhereElse does nothing visible because it only overwrote its own box — and the new Engine(999) it made becomes garbage the moment the method returns (part 2).

Chunk 4 — shallow vs deep

Car shallowCopy() { return new Car(name, this.engine); }               // shares the engine
Car deepCopy()    { return new Car(name, new Engine(engine.horsepower)); } // own engine
Spot the difference: the deep version has a second new. That one keyword is the entire difference between "shares" and "owns". Alternative: make Engine immutable and you can delete deepCopy entirely.

Chunk 5 — arrays hold arrows too

Engine[] garage = { new Engine(100), new Engine(200) };
Engine[] copy = Arrays.copyOf(garage, garage.length);
copy[0].horsepower = 777;
The array object itself is new (garage == copy is false), but its slots were filled with copies of the arrows, so garage[0] == copy[0] is true and the edit is visible through both. Arrays.copyOf, clone(), List.copyOf and new ArrayList<>(other) are all shallow.

Real output (JDK 1.8.0_411)

Read the two lines in section 4 together. The shallow edit pushed the original to 500. The deep edit then set the copy to 1 and the original stayed at 500 — proof that the deep copy owns a different Engine.
Predict, then run. (1) Add static void swap(Engine x, Engine y) that swaps its two parameters, and call it. Does the caller see a swap? Why not? (2) Make horsepower final — which methods stop compiling, and what does that tell you about immutability? (3) Write static int sum(int... nums) and pass it an int[] — is the array copied, or shared?

§8Pitfalls

"Java is pass-by-reference for objects." No. It passes a copy of the reference. The test: can a method make the caller's variable point at a different object? In Java, never.
Assuming = copies an object. b = a only copies an arrow. If you wanted a second object, you must write new.
Thinking clone() is deep. Object.clone() copies fields as they are, so every reference field stays shared. The same goes for Arrays.copyOf and collection copy constructors.
Leaking your internals. return this.items; hands the caller an arrow straight into your object. Return Collections.unmodifiableList(items) or a copy instead.
Using == on String, Integer or any object. It asks "same object?", which is almost never your question. Use equals (or Objects.equals for null safety).
Confusing the two errors. StackOverflowError → look at recursion. OutOfMemoryError → look at what is being kept alive on the heap.

§9Recap

  • A variable is a box. Primitive boxes hold values; reference boxes hold arrows (or null).
  • Stack = one per thread, a pile of frames, one frame per call, popped on return — free cleanup, no GC.
  • Heap = one shared area for every new object and array — the only area the GC cleans.
  • Locals live in the frame; fields live inside their object; class and static data lives with the class in Metaspace.
  • An object = header + fields (+ length for arrays), which is why many tiny objects cost more than one packed array.
  • Java is always pass-by-value: a method can mutate a shared object through a copied arrow, but can never rebind the caller's variable.
  • Shallow copy copies the arrows; deep copy rebuilds what they point at; immutability makes the question disappear.
  • == compares boxes (same object); equals compares contents.
  • Too many frames → StackOverflowError. Too many live objects → OutOfMemoryError: Java heap space.

Glossary

Stack
Per-thread memory holding one frame per active method call; cleared by returning.
Frame
One method call's private workspace: its parameters, locals, and return bookkeeping.
Heap
The shared area where every object and array lives; managed by the garbage collector.
Reference
The "arrow" a non-primitive variable holds; null means it points at nothing.
Primitive
One of the eight built-in value types; the variable holds the value itself.
Object header
JVM bookkeeping bytes stored in front of every object's fields (class pointer, lock, hash, GC age).
Pass-by-value
Arguments are copied into the callee's frame; for references, the arrow is what is copied.
Shallow copy
A new object whose reference fields point at the same inner objects as the original.
Deep copy
A new object with freshly built copies of everything it points at.
Aliasing
Two or more references pointing at the same object.
Metaspace
Native memory holding class metadata (the method area since Java 8).
