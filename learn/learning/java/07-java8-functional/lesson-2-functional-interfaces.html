Functional Interfaces & Method References

Java › Java 8 & functional cluster · lesson 7, part 2 of 9 · DEEP — the vocabulary every stream method is written in

Java 8 & functional cluster: 1. Lambdas · 2. Functional interfaces & method refs · 3. How a stream actually runs · 4. Intermediate operations · 5. Terminal operations & reduce · 6. Collectors & groupingBy · 7. Optional · 8. default methods & java.time · 9. Recall & interview playbook

In one line — A functional interface is an interface with exactly one abstract method — the "shape" a lambda is allowed to fill. Java ships about 43 of them in java.util.function, but they are not 43 things to memorise: they are four basic shapes plus a small set of naming rules. Learn the rules once and you can derive any name on the spot, which is exactly the skill you need when a stream method asks for Function<? super T, ? extends R>.

§1Where it fits

Part 1 said a lambda is an object implementing a one-method interface. This part answers the obvious follow-up: which interface? Every single method in the Stream API is declared in terms of these types — filter takes a Predicate, map takes a Function, forEach takes a Consumer. So reading a stream signature is just reading this vocabulary.

Why this matters for your interview problem. People freeze on stream questions not because the logic is hard but because they cannot recall whether the argument is a Function or a Predicate, and whether the method is apply or test. After this part you will derive those names rather than recall them.

§2Why it exists

Java 8 needed a common vocabulary. If every library invented its own one-method interface — StringMapper, IntChecker, ThingMaker — then a lambda written for one library could not be handed to another, and every API would look different.

So the JDK defined a small standard set in java.util.function. Now any library that wants "give me a transformation" writes Function<T,R>, and your lambda works everywhere. Think of it as standardising plug sockets rather than letting every appliance invent its own.

The older one-method interfaces (Runnable, Callable, Comparator) were simply re-labelled as functional interfaces. Nothing about them changed; they were already the right shape.

§3How it works

Step 1 — what makes an interface "functional"

An interface is functional if it has exactly one abstract method. These do not count against that total:

  • default methods (they have a body)
  • static methods (they have a body)
  • public methods of Object — equals, hashCode, toString

That last rule is why Comparator is a functional interface even though it declares int compare(T,T) and boolean equals(Object): equals is already on Object, so every implementer inherits it. It is a favourite trick interview question.

Idiom. Put @FunctionalInterface on your own ones. It is documentation that the compiler enforces — adding a second abstract method later becomes a build error instead of a surprise for every caller.

Step 2 — the four shapes everything is built from

Ask two questions: does it take something in? does it give something back? Four answers, four interfaces.

Step 3 — the naming rules that generate the other 39

This is the part that fixes "I forget the names". There are only four modifiers:

ToIntBiFunction<T,U> → "to int" (returns int) + "bi" (two inputs) + function → (T,U) → int.

ObjIntConsumer<T> → an object and an int in, nothing out → (T,int) → void.

Step 4 — the single abstract method name of each

The second half of the recall problem is "what do I call on it?". There are only five method names in the whole package, and each one matches the shape's verb:

Primitive variants swap in the type: IntPredicate.test(int), IntSupplier.getAsInt(), ToIntFunction.applyAsInt(T). The pattern is always verb + As + primitive when the return type is a primitive.

Step 7 — method references: four kinds

A method reference is a lambda whose body does nothing but call one existing method. If your lambda is s -> s.toUpperCase(), the parameter is pure plumbing — String::toUpperCase says the same thing with the plumbing removed.

KindSyntaxExampleEquivalent lambda
Static methodType::staticMethodInteger::parseInts -> Integer.parseInt(s)
Instance method of an arbitrary objectType::instanceMethodString::toUpperCases -> s.toUpperCase()
Instance method of a specific objectobject::instanceMethodSystem.out::printlnx -> System.out.println(x)
ConstructorType::newArrayList::new() -> new ArrayList<>()
The confusing pair, settled. String::toUpperCase and myString::toUpperCase look alike but differ in arity. In the first, the receiver is the parameter: it works as a Function<String,String>. In the second, the receiver is already fixed, so no parameter is needed: it works as a Supplier<String>.
Rule of thumb: a Type::method reference silently uses the first argument as this.

§4When to use

  • Predicate — any keep/drop or yes/no decision: filter, anyMatch, removeIf, Optional.filter.
  • Function — any "turn A into B": map, computeIfAbsent, Collectors.groupingBy's classifier, Optional.map.
  • Consumer — "do this with each": forEach, ifPresent, peek.
  • Supplier — delayed work: orElseGet, orElseThrow, Stream.generate, lazy logging, toCollection(TreeSet::new).
  • BinaryOperator — combining two values of the same type: reduce(Integer::sum), toMap's merge function.
  • Primitive variants — when you are inside an IntStream or in hot numeric code and boxing would hurt.
  • Method references — whenever the lambda body is exactly one existing call. Not a style rule: it is shorter and it names the operation.

§5Explain it to a 12-year-old

Think of a workshop with four kinds of helper, and you can hire any of them by writing a tiny instruction card:

  • A changer — give it something, it hands back something else. (Give it a lemon, get lemonade.) That is Function.
  • A judge — give it something, it says only yes or no. (Is this lemon ripe?) That is Predicate.
  • A taker — give it something, it just does something with it and hands back nothing. (Throw this in the bin.) That is Consumer.
  • A maker — give it nothing, it hands you something. (Fetch me a fresh lemon.) That is Supplier.

And the naive question: "why so many names for the same thing?" Because the workshop has to know in advance what shape of helper a job needs. "Sort this" needs a judge, not a maker. The names are just the shapes written down so the compiler can check you hired the right one.

A method reference is saying "you already know how to do this — just do that" instead of writing a new instruction card. String::toUpperCase means "use the shouting machine that already exists".

§6Connections

  • ← part 1: a lambda has no type of its own; these interfaces are the types it takes.
  • ← generics: this is why Stream.map is declared <R> Stream<R> map(Function<? super T, ? extends R> f) — PECS applied to a function parameter.
  • ← equality & ordering: Comparator is a functional interface, which is why comparing(...) works.
  • → part 3: every stream method signature is written in this vocabulary — you can now read them all.
  • → concurrency: Runnable and Callable are functional interfaces, so submit(() -> ...) just works.
  • Same idea elsewhere: TypeScript writes these inline as (x: T) => R; Kotlin writes (T) -> R. Java needs a named interface because it reused the existing type system.

§7In practice — dissected

From code/LambdaDemo.java, the method-reference block:

Function<String,Integer> parse = Integer::parseInt;     // 1 static
Function<String,String>  upper = String::toUpperCase;   // 2 unbound instance
String prefix = "ID-";
Function<String,String>  withPrefix = prefix::concat;   // 3 bound instance
Supplier<ArrayList<String>> maker = ArrayList::new;     // 4 constructor
1 is the easy one — a static method takes the argument directly.
2 is the one people misread. toUpperCase() takes no argument, yet this is a Function<String,String> — because the incoming String becomes the receiver. Mentally rewrite Type::method as (x, rest...) -> x.method(rest...).
3 fixes the receiver up front, so withPrefix.apply("77") runs "ID-".concat("77"). The captured prefix must be effectively final, exactly as in part 1.
4 ArrayList::new as a Supplier means the no-arg constructor. Had the target been IntFunction<ArrayList<String>>, the compiler would have picked the ArrayList(int) constructor instead — the target type chooses the overload, just like with lambdas.

Composition, and why the order trips people up

Predicate<String> notEmpty = s -> !s.isEmpty();
Predicate<String> isLong   = s -> s.length() > 3;
notEmpty.and(isLong).test("hello")   // true
isLong.negate().test("hello")         // false
and/or short-circuit exactly like &&/||, so put the cheap test first. negate() returns a new predicate — these methods never mutate the original, because a functional interface instance is conceptually a value.

(Answers: (T,U)→double applyAsDouble; int→int applyAsInt; (T,long)→void accept; long→int applyAsInt; ()→boolean getAsBoolean.)

§8Pitfalls

Reaching for the wrong shape. If you find yourself writing Function<T,Boolean>, you want Predicate<T> — same idea, but Predicate avoids boxing and composes with and/or/negate.
Type::method vs object::method arity confusion. The first consumes one extra argument (the receiver). If the compiler complains about "non-static method cannot be referenced from a static context", you meant the bound form.
Method reference on a null receiver. obj::method evaluates obj immediately, at the point the reference is created — so a null blows up there, not when the function is later called. A lambda x -> obj.method(x) defers it.
Ambiguous overloads. If two overloads both accept functional interfaces of the same arity, a lambda can be ambiguous. Fix it with an explicit cast — (Supplier<String>) () -> "x" — or explicit parameter types.
Forgetting that Consumer returns nothing. peek and forEach take a Consumer, so .forEach(s -> s.toUpperCase()) does absolutely nothing — String is immutable and the result is thrown away. This is a popular trick question.
Boxing in hot loops. Function<Integer,Integer> boxes on every call. Use IntUnaryOperator or an IntStream where it matters.

§9Recap

  • A functional interface has exactly one abstract method; default, static and Object methods do not count.
  • Four shapes generate everything: Function (T→R), Predicate (T→boolean), Consumer (T→void), Supplier (()→T).
  • Modifiers: Bi = two inputs, Operator = same type in and out, Int/Long/Double = primitive, ToX = primitive result.
  • Method names follow the verb: apply, test, accept, get (+ …AsInt etc. for primitives).
  • Function.identity() is x -> x; you will need it in Collectors.toMap.
  • Four method-reference kinds: Type::static, Type::instance, obj::instance, Type::new.
  • Type::instance uses the first argument as the receiver — that is the whole trick.

Glossary

Functional interface
An interface with exactly one abstract method.
SAM
"Single Abstract Method" — another name for the same thing.
@FunctionalInterface
A compile-time check that an interface still has exactly one abstract method.
Method reference
Type::method — a lambda whose body is a single existing call.
Bound vs unbound reference
Bound fixes the receiver (obj::m); unbound takes it as the first argument (Type::m).
identity()
Function.identity() = x -> x.
Boxing
Wrapping a primitive in its object type; what the Int/Long/Double variants exist to avoid.
