How a Stream Actually Runs

Java › Java 8 & functional cluster · lesson 7, part 3 of 9 · DEEP — laziness, fusion and one-shot pipelines, proved by real output

Java 8 & functional cluster: 1. Lambdas · 2. Functional interfaces & method refs · 3. How a stream actually runs · 4. Intermediate operations · 5. Terminal operations & reduce · 6. Collectors & groupingBy · 7. Optional · 8. default methods & java.time · 9. Recall & interview playbook

In one line — A Stream is not a collection. It holds no data. It is a recipe — a plan for walking over some source and doing things to each element. Writing .filter(...).map(...) builds the plan and executes nothing. Only the final operation (collect, forEach, count…) actually runs it, and when it does, elements go through the whole chain one at a time.

§1Where it fits

This is the part of streams that interviews actually probe, and the part most people skip. If you understand the execution model, then every operation in part 4 and part 5 becomes obvious, and every "what does this print?" question becomes mechanical. If you skip it, you are memorising method names with no frame to hang them on — which is exactly the problem.

§2Why it exists

The problem with a plain loop

Here is "upper-case the long names, sorted, joined with commas" the old way:

List<String> tmp = new ArrayList<>();
for (String n : names) {              // HOW to iterate
    if (n.length() > 3) {             // WHAT I actually wanted
        tmp.add(n.toUpperCase());     // WHAT I actually wanted
    }
}
Collections.sort(tmp);
StringBuilder sb = new StringBuilder();
for (int i = 0; i < tmp.size(); i++) {  // HOW again, plus an index to get wrong
    if (i > 0) sb.append(", ");
    sb.append(tmp.get(i));
}

Three problems, and only the first is about typing:

  1. Intent is buried. The two lines you cared about are hidden inside loop scaffolding, a temporary list, and an index.
  2. It is a specification of how. You told Java to walk the list front-to-back, one element at a time, on this thread. Java is not allowed to do anything smarter, because you dictated the mechanism.
  3. Every step materialises a whole collection. Filter builds a list, map builds another list. For a million elements that is a million wasted objects.

The stream version states only the what:

names.stream()
     .filter(n -> n.length() > 3)
     .map(String::toUpperCase)
     .sorted()
     .collect(Collectors.joining(", "));

Why "lazy"? Three concrete payoffs

  • No intermediate collections. filter and map are fused into a single pass. One element goes all the way through before the next one starts.
  • Short-circuiting is possible. findFirst() on a billion-element source can stop after three elements, because nothing was computed in advance.
  • Infinite sources work. Stream.iterate(1, n -> n * 2).limit(5) is fine. An eager implementation would hang forever.

§3How it works

Step 1 — the three parts of every pipeline

Every stream expression, no matter how long, has exactly this shape:

  SOURCE          INTERMEDIATE (zero or more)        TERMINAL (exactly one)
list.stream()  .filter(...).map(...).sorted()     .collect(...)
  |               |                                 |
  where elements  each returns a NEW Stream;        returns something that is
  come from       builds the plan, runs nothing     NOT a Stream; runs the plan
The test that never fails. Is an operation intermediate or terminal? Look at its return type. Returns a Stream (or IntStream…) → intermediate, lazy. Returns anything else — a List, a long, an Optional, void, a boolean → terminal, eager. You never have to memorise two lists of method names.

Step 3 — proving it, not just claiming it

These four experiments are in code/StreamOpsDemo.java. The output is real.

Proof 1 — without a terminal operation, nothing happens at all

names.stream()
     .peek(n -> System.out.println("  peek: " + n))
     .filter(n -> n.length() > 3);          // no terminal op
-- building a pipeline with no terminal op --
  (nothing printed above - the pipeline never ran)
Not one peek line printed. The chain of objects was built and then thrown away. This single experiment is the clearest possible definition of "lazy".

Proof 2 — elements flow one at a time (operation fusion)

names.stream()
     .filter(n -> { System.out.println("  filter " + n); return n.length() > 3; })
     .map(n -> { System.out.println("    map  " + n); return n.toUpperCase(); })
     .forEach(n -> System.out.println("      got " + n));
  filter ann
  filter bob
  filter carol
    map  carol
      got CAROL
  filter dave
    map  dave
      got DAVE
  filter erin
    map  erin
      got ERIN
Read the indentation. If streams worked stage-by-stage you would see five filter lines, then three map lines, then three got lines. Instead carol goes all the way through before dave is even looked at. That is fusion: no intermediate list is ever created. This is the single most common "what is the output?" interview question about streams.

Proof 3 — short-circuiting really stops early

names.stream()
     .peek(n -> System.out.println("  saw " + n))
     .filter(n -> n.length() > 3)
     .findFirst();
  saw ann
  saw bob
  saw carol
  first = carol
Five names in the list, three lines printed. dave and erin were never touched. Because the plan was lazy, findFirst could simply stop asking. Short-circuiting operations are findFirst, findAny, anyMatch, allMatch, noneMatch, limit.

Proof 4 — a stream is one-shot

Stream<String> s = names.stream();
s.count();
s.count();   // boom
java.lang.IllegalStateException: stream has already been operated upon or closed
A stream is consumed, like an iterator, not re-readable like a list. If you need two results from the same data, either call .stream() twice on the collection, or keep a Supplier<Stream<T>> and call get() each time. Note it is the stream that is spent, not the list.

Step 5 — stateless vs stateful operations

This distinction explains several surprises later. A stateless operation (filter, map, peek) can decide about an element knowing only that element. A stateful operation (sorted, distinct, limit, skip) needs to remember something about the elements it has already seen.

Consequence: sorted() cannot emit anything until it has seen every element — it is a barrier in the middle of a lazy pipeline. That is why sorted() on an infinite stream never finishes, and why putting filter before sorted is a genuine performance win, not just style.

Step 6 — the three stream "flavours" and the primitive bridge

Stream<T> holds objects. IntStream, LongStream and DoubleStream hold raw primitives and so avoid boxing — and they add arithmetic methods (sum, average, summaryStatistics) that Stream<T> does not have. Moving between them: 

stream.mapToInt(String::length)       // Stream<String> → IntStream
intStream.boxed()                     // IntStream → Stream<Integer>
intStream.mapToObj(i -> "#" + i)     // IntStream → Stream<String>
intStream.asLongStream()              // IntStream → LongStream
Why you keep hitting this: IntStream has sum() but no collect(Collectors.toList()) that gives you a List<Integer>. The fix is always .boxed() first. Conversely Stream<Integer> has no sum() — use .mapToInt(Integer::intValue).sum().

§4When to use

  • Use a stream when you are describing a transformation of a collection: filter, map, group, aggregate, join. The code should read like the sentence you would say out loud.
  • Use a stream when the source is huge or infinite and you want short-circuiting or laziness.
  • Use a plain loop when you need the index, when you mutate several variables, when you must break on a complex condition, or when checked exceptions are involved.
  • Use a loop for trivial cases too — for (String s : list) System.out.println(s); is not worse than a stream.
Idiom. One operation per line, aligned under the source. It makes the pipeline read top-to-bottom like a recipe and makes diffs clean: 
List<String> result = names.stream()
        .filter(n -> n.length() > 3)
        .map(String::toUpperCase)
        .collect(Collectors.toList());

§5Explain it to a 12-year-old

Imagine you order a pizza. You tell the shop: thin base, no olives, extra cheese, cut into eight. You have just described a pipeline. Nothing is cooked yet — you only gave instructions.

The moment you say "okay, make it", the kitchen starts. That final word is the terminal operation. Before it, nothing happens — you can change your mind for free.

And here is the part people get wrong: the kitchen does not make a hundred bases, then put sauce on all hundred, then cheese on all hundred. It makes your pizza start to finish, then the next one. That is why "no olives" means the cheese station never even sees an olive pizza.

Finally, the naive question: "why can't I eat the same pizza twice?" Because a stream is the order, not the ingredients. Once it has been made, that order is done. The ingredients (your list) are still in the fridge — place a new order.

§7In practice — dissected

Full file: code/StreamOpsDemo.java, run on JDK 1.8.0_411.

List<String> names = Arrays.asList("ann","bob","carol","dave","erin");

names.stream()                                    // 1 source: a view over the list
     .filter(n -> { print("filter "+n); return n.length()>3; })   // 2
     .map(n -> { print("map "+n); return n.toUpperCase(); })        // 3
     .forEach(n -> print("got "+n));                               // 4
1 stream() does not copy the list. It wraps a Spliterator over it, so creating a stream on a million-element list is essentially free.
2–3 Each call returns a new Stream object that remembers "my upstream is the previous stage, and my job is X". No data moves. Writing them on separate lines costs nothing at run time.
4 The terminal operation walks the chain backwards to the source, then pulls. This is why the filter/map/got interleaving in Proof 2 happens.
Gotcha: the lambdas here print, which is a side effect. That is fine for a teaching demo and wrong in real code — see the pitfalls.

The ordering experiment

filter-then-skip : names.stream().filter(len>3).skip(1)   →  [dave, erin]
skip-then-filter : names.stream().skip(1).filter(len>3)   →  [carol, dave, erin]
Same two operations, opposite results. filter first leaves [carol, dave, erin] and then drops carol; skip first drops ann and then filters the rest. Streams are an ordered sequence of stages — rearranging them changes meaning, not just speed. Always read a pipeline top to bottom and track what the list looks like after each line.
Predict the output. 
Stream.of("a","bb","ccc","dddd")
      .peek(s -> System.out.println("peek " + s))
      .filter(s -> s.length() % 2 == 0)
      .limit(1)
      .forEach(s -> System.out.println("out " + s));
How many lines print, and in what order?
(Answer: peek a, peek bb, out bb — three lines. limit(1) short-circuits, so ccc and dddd are never fetched.)

§8Pitfalls

Forgetting the terminal operation. The most common beginner bug. The code compiles, runs, and does nothing. If your stream "didn't work", check for a missing collect/forEach.
Reusing a stream variable. IllegalStateException: stream has already been operated upon or closed. Create a new one, or hold a Supplier<Stream<T>>.
Using peek for real work. peek exists for debugging. It is tied to laziness, so elements that get short-circuited away are never peeked, and an implementation is allowed to skip it entirely when the result is not needed (for example count() on a sized source). Never put business logic in it.
Side effects inside lambdas. Adding to an outside list from inside map/filter works by accident in sequential code and corrupts data in parallel. The stream contract asks for non-interfering, stateless functions. Use a collector instead.
Modifying the source while streaming it. Adding to the list mid-pipeline throws ConcurrentModificationException — the same hazard as mutating a list during a for-each loop.
Infinite source without limit. Stream.iterate and Stream.generate never end on their own. And sorted() or count() on an infinite stream hangs forever, because they need to see every element.
Assuming parallel is faster. parallelStream() uses the shared common ForkJoin pool, costs coordination, and is a real loss for small collections or IO-bound work. Measure before using it.

§9Recap

  • A stream is a plan, not a container. It stores no elements and never changes its source.
  • Pipeline shape: source → zero or more intermediate ops → exactly one terminal op.
  • Returns a Stream = intermediate and lazy; returns anything else = terminal and eager. That one rule replaces memorising two lists.
  • Nothing executes until the terminal operation — proved by the peek experiment.
  • Elements are fused: one element travels the whole chain before the next is fetched.
  • Short-circuiting ops (findFirst, anyMatch, limit…) can stop early.
  • A stream is one-shot; reuse throws IllegalStateException.
  • Stateful ops (sorted, distinct) must buffer; keep them late and after filtering.
  • Cross the primitive bridge with mapToInt / boxed / mapToObj.

Reference — the execution model on one card

source  .stream() / Stream.of / IntStream.range / Arrays.stream / Files.lines
        |
        v  LAZY: builds a plan, runs nothing
intermediate  filter map flatMap distinct sorted limit skip peek mapToInt boxed
        |
        v  EAGER: runs the whole plan exactly once
terminal     collect forEach count min max reduce anyMatch findFirst toArray

RULES
1. no terminal op            -> nothing happens
2. one element at a time     -> filter(x) map(x) collect(x), then next x
3. short-circuit             -> findFirst/anyMatch/limit may stop early
4. one-shot                  -> second terminal op throws IllegalStateException
5. stateful ops buffer       -> sorted/distinct wait for all elements
6. source is never modified  -> streams produce new results

Glossary

Stream
A lazily evaluated sequence of elements supporting aggregate operations; not a data structure.
Pipeline
A source plus its chain of operations, ending in one terminal operation.
Intermediate operation
Returns a new Stream; lazy.
Terminal operation
Returns a non-stream result and triggers execution.
Laziness
Work is deferred until a result is actually demanded.
Fusion
Running several stages per element in a single pass, with no intermediate collections.
Short-circuiting
An operation that can produce its result without consuming the whole source.
Stateful operation
One that must remember earlier elements (sorted, distinct, limit, skip).
Spliterator
The low-level object a stream uses to traverse and, for parallel streams, split its source.
Encounter order
The order a source defines (a List has one; a HashSet does not).
