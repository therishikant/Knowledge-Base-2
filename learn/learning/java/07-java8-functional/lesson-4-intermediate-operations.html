Intermediate Operations — the Middle of the Pipeline

Java 8 & functional cluster: 1. Lambdas · 2. Functional interfaces & method refs · 3. How a stream actually runs · 4. Intermediate operations · 5. Terminal operations & reduce · 6. Collectors & groupingBy · 7. Optional · 8. default methods & java.time · 9. Recall & interview playbook

In one line — There are only eleven intermediate operations you will ever use, and each one answers a single plain-English question: keep which ones? (filter), turn each into what? (map), flatten what? (flatMap), remove repeats (distinct), in what order? (sorted), how many / from where? (limit, skip), plus the primitive bridge (mapToInt, boxed, mapToObj) and the debug hook (peek).

§1Where it fits

Part 3 gave you the execution model: these operations are lazy, they are fused, and they run one element at a time. This part is the catalogue. Every entry follows the same template — the question it answers, its signature, a worked example with real output, and the gotcha. Read it once end-to-end, then use it as a lookup.

Remember the identification rule. All of these return a Stream. That is why they are intermediate, and it is also why they chain. If you ever cannot remember whether something is intermediate, ask "could I put another .map() after it?"

§2Why it exists

Pre-Java-8 code expressed every one of these as loop scaffolding. "Keep the adults" was an if inside a for. "Get their names" was a second for filling a second list. "Drop duplicates" was a HashSet you remembered to create. "Take the top three" was a counter and a break.

Every one of those is a named idea that had no name in the language. Giving them names does three things: the code says what it means, the library can optimise across them (fusion, short-circuiting, parallel splitting), and — most relevant to you — problems become compositional. "Top 3 distinct salaries" stops being a loop you must design and becomes distinct().sorted(reverseOrder()).limit(3), which you can assemble from pieces you already know.

§3How it works — the catalogue

1. filter — keep which ones?

Stream<T> filter(Predicate<? super T> p)
names.stream().filter(n -> n.contains("a"))   // [ann, carol, dave]
Keeps elements where the predicate is true. Stateless, lazy, never changes the type. Chain several filters freely — .filter(a).filter(b) is the same as .filter(a.and(b)) and costs the same, because of fusion. Put the cheapest or most selective filter first.
filter does not remove from the original list. If you want to actually mutate a collection, that is list.removeIf(predicate) — a different method, added in Java 8 to Collection.

2. map — turn each one into what?

<R> Stream<R> map(Function<? super T, ? extends R> f)
names.stream().map(String::length)   // [3, 3, 5, 4, 4]
Exactly one output per input, so the count never changes and the type usually does. This is where method references shine: map(String::toUpperCase), map(Employee::getName), map(Integer::parseInt).
The classic no-op. map(s -> s.trim()) works because trim returns a new string. map(s -> { s.trim(); return s; }) does nothing, because String is immutable. Same trap with forEach(s -> s.toUpperCase()).

3. flatMap — one becomes many, then flatten

<R> Stream<R> flatMap(Function<? super T, ? extends Stream<? extends R>> f)

This is the operation people find hardest, and it is nearly always one of these two situations.

Situation A — a list of lists

List<List<Integer>> nested = [[1,2],[3,4],[5]];
nested.stream().map(List::stream)      // Stream<Stream<Integer>>  ← nested, useless
nested.stream().flatMap(List::stream)  // Stream<Integer>          → [1, 2, 3, 4, 5]

Situation B — one item explodes into several

Stream.of("a b", "c d")
      .flatMap(x -> Arrays.stream(x.split(" ")))   // [a, b, c, d]
The one-line rule for flatMap: if your mapper function already returns a collection, a stream or an Optional, use flatMap; otherwise use map. That single sentence resolves it every time.
A flatMap mapper that returns null throws a NullPointerException. Return Stream.empty() to contribute nothing.

4. distinct — drop repeats

Stream<T> distinct()
Stream.of(1,2,2,3,1).distinct()   // [1, 2, 3]
Uses equals/hashCode, not ==. For your own classes this silently does nothing useful unless you implemented both — see equality & ordering. It is stateful: it holds every distinct element seen so far, so it costs memory on large inputs. It keeps the first occurrence.
"Distinct by one field" does not exist as a method. The usual answers are collect(toMap(Employee::getDept, e -> e, (a,b) -> a)).values(), or a stateful-filter trick with a Set (works sequentially only). This is a frequent interview follow-up — see part 9.

5. sorted — in what order?

Stream<T> sorted()                              // natural order; T must be Comparable
Stream<T> sorted(Comparator<? super T> cmp)      // your order
names.stream().sorted()                                      // [ann, bob, carol, dave, erin]
names.stream().sorted(comparing(String::length)
                      .thenComparing(naturalOrder()))        // [ann, bob, dave, erin, carol]
Stable — equal elements keep their original relative order, which is what makes thenComparing meaningful. sorted() with no argument throws ClassCastException at run time if the elements are not Comparable. Build comparators with the kit from part 2: comparing, thenComparing, reversed, nullsFirst.
Stateful and expensive. sorted buffers the entire stream before emitting anything, so it never terminates on an infinite stream and it kills short-circuiting upstream. Always filter before you sort, never after.

6–7. limit and skip — how many, and from where?

Stream<T> limit(long maxSize)   // take the first n — SHORT-CIRCUITS
Stream<T> skip(long n)         // drop the first n
names.stream().limit(2)   // [ann, bob]
names.stream().skip(3)    // [dave, erin]
Together they do pagination: .skip(page * size).limit(size). limit is the operation that tames infinite sources. "Second highest salary" is .distinct().sorted(reverseOrder()).skip(1).findFirst() — the skip(1) is doing the real work there.

8. peek — look without changing (debug only)

Stream<T> peek(Consumer<? super T> action)
Debugging tool, not a processing step. Because it is lazy, peek never sees short-circuited elements, and the javadoc explicitly allows an implementation to skip it entirely when the element count can be computed without traversal (e.g. count() on a sized source). Putting logic in peek produces bugs that appear only in production.

9–11. The primitive bridge

MethodFrom → toWhy you need it
mapToInt / mapToLong / mapToDoubleStream<T> → IntStreamto use sum(), average(), max(), summaryStatistics()
boxedIntStream → Stream<Integer>to use collect(toList()) or any Collectors
mapToObjIntStream → Stream<R>turning numbers or chars into objects
asLongStream / asDoubleStreamwiden the primitiveavoid overflow before summing
 
names.stream().mapToInt(String::length).sum()        // 19
IntStream.range(0,4).boxed().collect(toList())       // [0, 1, 2, 3]
"hello".chars().mapToObj(c -> (char) c)              // [h, e, l, l, o]
The chars() line is worth memorising outright: String.chars() gives an IntStream of code points, so without mapToObj(c -> (char) c) you get a list of numbers like [104, 101, …]. Every character-frequency interview question starts with this exact line.

Interview framing: filter tests every element; takeWhile stops at the first failure. On [2,4,5,6] with "is even": filter gives [2,4,6], takeWhile gives [2,4]. The demo code in this cluster is compiled on JDK 8, so these are described but not run here.

§4When to use

  • Order matters for correctness: filter then skip ≠ skip then filter (proved below).
  • Order matters for speed: filter → map → sorted → limit. Cut elements early, do expensive mapping on fewer items, sort last.
  • Reach for flatMap whenever a field is itself a list: orders → line items, users → roles, sentences → words.
  • Reach for mapToInt the moment you want sum/average.
  • Reach for limit immediately after any infinite source.
Idiom — the canonical order. 
source
  .filter(...)      // 1 shrink first: everything downstream gets cheaper
  .map(...)         // 2 transform the survivors
  .distinct()       // 3 stateful ops after shrinking
  .sorted(...)      // 4 the most expensive step, on the fewest elements
  .limit(10)        // 5 cut to size
  .collect(...);    // 6 terminal

§5Explain it to a 12-year-old

Picture a conveyor belt in a factory, with stations along it. Each station does exactly one job:

  • filter — a person who throws the bad apples off the belt.
  • map — a machine that slices each apple. Same number of items, different items.
  • flatMap — a machine that opens each crate and puts the apples inside onto the belt. One thing in, many things out.
  • distinct — someone with a notebook who removes any apple identical to one already seen.
  • sorted — the only station that must collect everything into a pile first, arrange it, and then put it back. That is why it is slow and why it cannot work on a belt that never ends.
  • limit/skip — a counter: "stop after ten" or "ignore the first ten".
  • peek — an inspector with a clipboard who only writes things down.

Naive question: "why does the order of the stations matter?" Because removing the bad apples before the expensive slicing machine means you slice fewer apples. And "throw out bad ones, then ignore the first ten" is obviously different from "ignore the first ten, then throw out bad ones" — the same stations, a different result.

sortedBy is the interesting one. The comparator was comparing(String::length).thenComparing(naturalOrder()) on [ann, bob, carol, dave, erin]. Lengths are 3,3,5,4,4 — so the length groups are {ann,bob}, {dave,erin}, {carol}, and within each group alphabetical order decides. Result: ann, bob, dave, erin, carol. Trace it yourself before reading on; that trace is the interview answer.

The ordering experiment, run for real

filter-then-skip : [dave, erin]
skip-then-filter : [carol, dave, erin]
filter(len>3) on [ann,bob,carol,dave,erin] gives [carol,dave,erin]; then skip(1) drops carol. The other way round, skip(1) drops ann first, leaving [bob,carol,dave,erin], and the filter then drops bob. Two operations, two orders, two answers.
Build it yourself. Given List<String> words, write one pipeline for each:
  1. the 3 longest distinct words, longest first;
  2. all distinct letters used across every word, sorted;
  3. the total number of characters in words starting with "a".
Answers: 
words.stream().distinct().sorted(comparing(String::length).reversed()).limit(3)
words.stream().flatMap(w -> w.chars().mapToObj(c -> (char) c)).distinct().sorted()
words.stream().filter(w -> w.startsWith("a")).mapToInt(String::length).sum()

§8Pitfalls

sorted() before filter(). You sort elements you are about to throw away. Correctness is fine; performance is not.
distinct() on a class without equals/hashCode. Every object looks unique and nothing is removed. Silent, not an error.
Using map where flatMap is needed. You get Stream<Stream<T>> or Stream<List<T>> and the next line will not compile. The compiler error is the clue: read your mapper's return type.
Logic inside peek. It may not run. Use map or forEach.
sorted() or distinct() on an infinite stream. Hangs forever. Put limit before them.
Expecting IntStream to have collect(toList()). It does not — call .boxed() first. This exact compile error wastes interview minutes.
A stateful lambda inside filter. The "first duplicate" trick filter(x -> !seen.add(x)) works sequentially but violates the stream contract and breaks in parallel. Mention this caveat if you use it in an interview — it turns a hack into a demonstration of understanding.

§9Recap

  • Every intermediate operation returns a Stream, is lazy, and chains.
  • Element-changing: map, mapToInt, boxed, mapToObj.
  • Count-changing: filter, distinct, limit, skip.
  • Both: flatMap — use it whenever the mapper already returns a stream/collection.
  • Neither: sorted (reorders), peek (debug only).
  • Stateful: sorted, distinct, limit, skip — they buffer or count, so keep them late and never on an infinite stream (except limit).
  • Canonical order: filter → map → distinct → sorted → limit.
  • Post-8 additions worth naming: takeWhile, dropWhile, Stream.ofNullable, three-arg iterate, mapMulti.

Glossary

filter
Keeps elements matching a predicate.
map
Transforms each element one-to-one.
flatMap
Maps each element to a stream and splices those streams into one.
distinct
Removes duplicates using equals/hashCode.
sorted
Reorders; stable; buffers the whole stream.
limit / skip
Take the first n / drop the first n.
peek
Observes elements as they pass; for debugging only.
Primitive bridge
mapToInt, boxed, mapToObj — moving between object and primitive streams.
Stable sort
Equal elements keep their original relative order.
