Terminal Operations & reduce

Java › Java 8 & functional cluster · lesson 7, part 5 of 9 · DEEP — the operations that actually run the pipeline

Java 8 & functional cluster: 1. Lambdas · 2. Functional interfaces & method refs · 3. How a stream actually runs · 4. Intermediate operations · 5. Terminal operations & reduce · 6. Collectors & groupingBy · 7. Optional · 8. default methods & java.time · 9. Recall & interview playbook

In one line — A terminal operation is the one that actually does the work, and it answers one of four questions: give me a collection (collect, toArray), give me a single value (count, sum, min, max, reduce), answer yes or no / find one (anyMatch, findFirst), or just do something with each (forEach). Of these, reduce is the one that is really worth understanding, because every other value-producing operation is a special case of it.

§1Where it fits

Part 4 shaped the data. This part ends the pipeline. After a terminal operation the stream is spent, and you are back in ordinary Java with a List, a number, a boolean or an Optional.

collect is by far the biggest terminal operation and gets its own lesson — part 6. Here we cover everything else, and we build reduce from the ground up, because "implement sum/max/join without the built-in method" is a standard interview probe.

§2Why it exists

A lazy plan is useless until something demands a result. The terminal operation is that demand. But there is a second reason the API is shaped this way: by making the last step declare what kind of answer you want, the library can choose how to execute everything before it.

  • findFirst() tells the library "I need one element", so it can stop early.
  • count() on a sized source can skip the whole traversal and just read the size.
  • collect(...) tells the library exactly how to combine partial results, which is what makes the same code work on a parallel stream.

If you had written a for loop instead, none of those choices would be available — you would already have dictated the mechanism.

§3How it works

Family 1 — counting and aggregating

names.stream().count()                                     // 5
nums.stream().min(Comparator.naturalOrder()).get()         // 1
nums.stream().mapToInt(Integer::intValue).sum()            // 31
nums.stream().mapToInt(Integer::intValue).average()        // OptionalDouble[3.875]

Idiom. When an interviewer asks for several numbers at once (count and average and max), reach for summaryStatistics(). One pass, one object, and it shows you know the API beyond the basics.
Stream<Integer> has no sum(). You must cross the primitive bridge: .mapToInt(Integer::intValue).sum(). This is the single most common compile error in stream interviews.

Family 2 — reduce, the general case

reduce means: take the running answer and the next element, produce the new running answer. Repeat until the stream is empty. That is all. Summing is (a, b) -> a + b; finding the max is (a, b) -> a > b ? a : b; joining is (a, b) -> a + "|" + b.

The three overloads

// 1. no seed → Optional, because an empty stream has no answer
Optional<T> reduce(BinaryOperator<T> accumulator)

// 2. with a seed → always a value; the seed is the answer for an empty stream
T reduce(T identity, BinaryOperator<T> accumulator)

// 3. seed + combiner → the accumulator type differs from the element type
<U> U reduce(U identity, BiFunction<U,? super T,U> accumulator, BinaryOperator<U> combiner)
Overload 3 confuses people. The combiner is only used by parallel streams: each thread builds its own partial U, and the combiner merges two partials. In a sequential stream it is never called — but you must still supply a correct one, or your code breaks the day someone adds .parallel().

Verified output

reduce1  : 31          // nums.reduce((a,b) -> a+b).get()
reduce2  : 31          // nums.reduce(0, (a,b) -> a+b)
reduce3  : 19          // names.reduce(0, (acc,n) -> acc+n.length(), Integer::sum)
empty+seed  : 0
empty-seed  : Optional.empty
reduce max  : 9        // nums.reduce(Integer::max).get()
reduce join : ann|bob|carol|dave|erin
The identity must really be an identity. reduce(0, (a,b) -> a+b) is correct because 0 + x == x. reduce(1, (a,b) -> a+b) is wrong, and in parallel it is wrong by an unpredictable amount, because the seed gets added once per split. For multiplication the identity is 1; for string concatenation it is ""; for max it is Integer.MIN_VALUE.
Never reduce("", (a,b) -> a + b) on strings. It builds a new String at every step — O(n²). Use Collectors.joining(), which uses a StringBuilder.

Family 3 — matching and finding (all short-circuit)

The empty-stream trap — know this cold

allMatch on empty  : true
anyMatch on empty  : false
noneMatch on empty : true
allMatch on an empty stream returns true even for a predicate that is always false. This is "vacuous truth": there is no element that violates the rule, so the rule holds. It is mathematically right and it has caused real production bugs ("all orders are validated" — there were no orders). Interviewers ask this exact question.
findFirst vs findAny: identical on a sequential stream. On a parallel stream, findFirst must respect encounter order and so costs coordination; findAny returns whatever any thread found first. Use findAny when order genuinely does not matter.

Family 4 — consuming

void forEach(Consumer<? super T> action)
void forEachOrdered(Consumer<? super T> action)

Verified, on a parallel stream

forEach        : 54763012   <- order not guaranteed
forEachOrdered : 01234567   <- always encounter order
Sequentially both print in order, so the difference is invisible until someone parallelises. forEachOrdered forces encounter order and therefore gives up much of the parallel speed-up. Also note forEach returns void: it is the one terminal operation whose entire purpose is a side effect, which is why printing and saving belong here and nowhere else.

Family 5 — toArray

Object[] a  = names.stream().toArray();                // always Object[]
String[] b  = names.stream().toArray(String[]::new);   // typed — pass the array constructor
String[]::new is a constructor reference for an array: given a size n it does new String[n]. Without it you get Object[] and a ClassCastException later.

§4When to use

  • Need a list/map/string? collect — see part 6.
  • Need one number? Prefer the named operation (count, sum, max) over reduce; it reads better and is often optimised.
  • Need one number that has no named operation? That is what reduce is for.
  • Need yes/no? anyMatch/allMatch/noneMatch — not filter(...).count() > 0, which scans everything.
  • Need one element? findFirst if order matters, findAny if it does not.
  • Need a side effect? forEach, and nowhere else in the pipeline.
Idiom. stream.anyMatch(p) beats stream.filter(p).count() > 0 and stream.filter(p).findFirst().isPresent(). It short-circuits and it says what you mean.

§5Explain it to a 12-year-old

You and your friends are counting sweets in a long line of jars. There are four kinds of question anyone can ask you, and which one they ask changes how you work:

  • "Put them all in a bag." — you must open every jar. That is collect.
  • "How many altogether?" — you keep one running number in your head and add each jar to it. That is reduce (and count, sum, max are just famous versions of it).
  • "Is there a red sweet anywhere?" — the moment you see one, you stop walking. That is anyMatch.
  • "Shout the name of each jar." — you walk the whole line and produce nothing at the end. That is forEach.

And the naive question: "why can't 'how many' just be 'put them in a bag and count the bag'?" It could — but then you would have carried a huge bag for nothing. Telling the library what kind of answer you want lets it pick the cheapest route. That is the whole design.

§7In practice — dissected

From code/StreamTerminalDemo.java:

int r3 = names.stream().reduce(
            0,                                 // 1 identity — type U = Integer
            (acc, n) -> acc + n.length(),      // 2 accumulator: (U, T) → U
            Integer::sum);                     // 3 combiner: (U, U) → U, parallel only
1 The element type is String, but the answer is an Integer. That mismatch is exactly when you need the three-argument form.
2 Note the asymmetry — the accumulator takes an answer and an element, not two elements.
3 Two partial answers are both Integer, so the combiner is plain addition. Run sequentially this is never invoked, which is why bugs here hide for years.
Honest alternative: names.stream().mapToInt(String::length).sum() gives the same 19 and is clearer. Use three-arg reduce only when no simpler form exists.

Emptiness, made explicit

empty+seed : new ArrayList<Integer>().stream().reduce(0, Integer::sum)  → 0
empty-seed : new ArrayList<Integer>().stream().reduce(Integer::sum)     → Optional.empty
This pair is the whole argument for Optional in one line. With a seed, "nothing" has a sensible answer and you get a plain value. Without a seed, there is genuinely no answer, so the API refuses to invent one and hands you an empty Optional instead of null.
Predict the output. 
List<String> empty = new ArrayList<>();
System.out.println(empty.stream().allMatch(s -> s.length() > 100));
System.out.println(Stream.of(1,2,3).reduce(10, (a,b) -> a + b));
System.out.println(Stream.of("a","b").reduce("", (a,b) -> b + a));
(Answers: true — vacuous truth; 16 — the seed 10 is included; ba — the accumulator was written backwards, which is also why a non-associative accumulator is unsafe in parallel.)

§8Pitfalls

allMatch on an empty stream is true. Guard with !list.isEmpty() && list.stream().allMatch(...) when "there must be at least one" is part of the requirement.
Calling .get() on the Optional from min/max/ findFirst. It throws NoSuchElementException on an empty stream. Use orElse, orElseThrow or ifPresent — see part 7.
A non-associative accumulator in reduce. Subtraction is the classic: reduce(0, (a,b) -> a - b) gives different answers sequentially and in parallel, because grouping changes the result.
A wrong identity. It must satisfy f(identity, x) == x. In parallel a wrong identity is applied once per split, so the error scales with the number of threads.
Mutating a shared collection in forEach. stream.parallel().forEach(list::add) corrupts an ArrayList. Use collect(Collectors.toList()), which is designed for it.
Using forEach when you want a result. If you are building something inside forEach, you almost certainly want collect or reduce instead.
String concatenation in reduce. O(n²). Collectors.joining() is O(n).

§9Recap

  • A terminal operation returns a non-stream, runs the pipeline, and spends the stream.
  • Four families: container (collect, toArray), value (count, min, max, sum, reduce), answer/find (anyMatch, findFirst), side effect (forEach).
  • reduce = running answer + next element → new running answer. Three overloads: no seed (gives Optional), seed, seed + combiner (parallel).
  • The identity must satisfy f(identity, x) == x, and the accumulator must be associative.
  • sum/average/summaryStatistics exist only on primitive streams — cross with mapToInt.
  • allMatch on an empty stream is true.
  • findFirst respects order; findAny does not and is cheaper in parallel.
  • forEach is unordered in parallel; forEachOrdered is not.
  • Use Collectors.joining(), never reduce, to concatenate strings.

Glossary

Terminal operation
The operation that triggers execution and produces a non-stream result.
Reduction / fold
Collapsing many elements into one by repeatedly combining.
Accumulator
The function combining the running result with the next element.
Identity
The seed value i such that f(i, x) == x.
Combiner
Merges two partial results; used only in parallel execution.
Associative
(a op b) op c == a op (b op c) — required for correct parallel reduction.
Vacuous truth
Why allMatch returns true for an empty stream.
Encounter order
The order defined by the source; respected by findFirst and forEachOrdered.
