Collectors & groupingBy

Java › Java 8 & functional cluster · lesson 7, part 6 of 9 · DEEP — the lesson that fixes "groupingBy is out of my mind"

Java 8 & functional cluster: 1. Lambdas · 2. Functional interfaces & method refs · 3. How a stream actually runs · 4. Intermediate operations · 5. Terminal operations & reduce · 6. Collectors & groupingBy · 7. Optional · 8. default methods & java.time · 9. Recall & interview playbook

In one line — collect is one terminal operation with a plug-in: the Collector tells it what container to build. There are only five families of collector (container, number, map, group, decorate), and groupingBy is a single idea with one optional extra argument: "put things in buckets by this key — and optionally, instead of keeping a list in each bucket, do this to each bucket".
Read this part slowly. This is where interview stream questions actually live. "Group employees by department", "count word frequency", "find the highest-paid person per city", "convert a list to a map" — all of them are a groupingBy or a toMap. Once the shape below is in your head, you stop recalling names and start assembling them.

§1Where it fits

Part 5 covered every terminal operation except the biggest one. collect is big because it is not really one operation — it is a socket, and Collectors is a box of plugs. Learning collect means learning the box.

Everything here rests on maps and hashing: a groupingBy produces a HashMap, so the key's hashCode/equals matter, and the result has no predictable order.

§2Why it exists

reduce can only fold elements into a single immutable value. Building a List is different: you want one mutable container that you keep adding to. Doing that with reduce would mean copying the list at every step, which is O(n²), and doing it with forEach(list::add) breaks in parallel.

So Java 8 added mutable reduction. A Collector packages four things so the library can do it safely, sequentially or in parallel:

PartQuestion it answersFor toList()
supplierwhat empty container do I start with?new ArrayList<>()
accumulatorhow do I add one element?list.add(e)
combinerhow do I merge two containers? (parallel)a.addAll(b)
finisherany final transformation?none

You will almost never write those four by hand — Collectors has ~30 ready-made ones. But knowing the structure is what lets you understand why collectors nest, which is the key to groupingBy.

§3How it works

name    dept    city     salary

Full source: code/CollectorsDemo.java. Every output below was produced on JDK 1.8.0_411.

Family 1 — into a container

.collect(Collectors.toList())                              // [ann, bob, carol, dave, erin, frank]
.collect(Collectors.toSet())                               // [hr, sales, eng]   (no order)
.collect(Collectors.toCollection(TreeSet::new))            // [eng, hr, sales]   (sorted)
.collect(Collectors.joining(", ", "[", "]"))                 // [ann, bob, carol, dave, erin, frank]
toList() gives some List (an ArrayList today) with no guarantee of mutability — if you need a specific type, say so with toCollection. joining has three overloads: no args, a separator, or separator + prefix + suffix. It only works on a Stream<String>, so map to strings first. Internally it uses a StringBuilder, which is why it beats reduce for concatenation.

Family 2 — into a number

.collect(Collectors.counting())                             // 6        (Long)
.collect(Collectors.summingInt(Employee::getSalary))        // 630
.collect(Collectors.averagingInt(Employee::getSalary))      // 105.0    (Double)
.collect(Collectors.maxBy(comparingInt(Employee::getSalary))) // Optional[carol]
.collect(Collectors.summarizingInt(Employee::getSalary))
IntSummaryStatistics{count=6, sum=630, min=70, average=105.000000, max=140}
"Why would I use counting() when count() exists?" You would not — at the top level. These exist to be used inside groupingBy, where you cannot call a terminal operation. That is the whole reason family 2 exists, and it is the insight that makes groupingBy click.

Family 3 — toMap: one entry per element

Collectors.toMap(keyFn, valueFn)
Collectors.toMap(keyFn, valueFn, mergeFn)
Collectors.toMap(keyFn, valueFn, mergeFn, mapSupplier)
toMap    : {frank=70, ann=120, carol=140, dave=90, bob=100, erin=110}
dup key  : java.lang.IllegalStateException: Duplicate key ann
toMap+mrg: {hr=frank, sales=dave+erin, eng=ann+bob+carol}
toMap+sup: {eng=ann+bob+carol, hr=frank, sales=dave+erin}
Line 1 — keys are names, which are unique, so the two-argument form is safe. Note the jumbled order: a HashMap has no encounter order.
Line 2 — using dept as the key means three employees map to eng, and the two-argument form throws IllegalStateException: Duplicate key. Memorise this exception. It is the number-one toMap bug and a favourite interview trap.
Line 3 — the third argument is the merge function, called with the two colliding values. Common choices: (a, b) -> a (keep first), (a, b) -> b (keep last), Integer::sum, (a, b) -> a + "+" + b.
Line 4 — the fourth argument picks the map type; TreeMap::new gives sorted keys, as the output shows.
toMap throws on a null value, even though HashMap allows them. It is an implementation consequence of using merge internally. Filter nulls out first.
Idiom. To key a list by an id, keeping the whole object as the value: collect(toMap(Employee::getName, Function.identity())). That is what Function.identity() is for.

Family 4 — groupingBy, properly understood

groupingBy is SQL GROUP BY. You give it a classifier: a function from element to key. Every element is dropped into the bucket for its key. By default each bucket is a List.

The three overloads

groupingBy(classifier)                           // Map<K, List<T>>
groupingBy(classifier, downstream)               // Map<K, D>
groupingBy(classifier, mapFactory, downstream)   // pick the Map type too
Say this sentence when you write it: "group by <key>, and for each group give me <downstream>." The sentence maps one-to-one onto the two arguments. If the sentence ends at "group by X", you need the one-argument form.

Every shape, with verified output

groupingBy(Employee::getDept)
  {hr=[frank], sales=[dave, erin], eng=[ann, bob, carol]}

groupingBy(Employee::getDept, counting())
  {hr=1, sales=2, eng=3}

groupingBy(Employee::getDept, summingInt(Employee::getSalary))
  {hr=70, sales=200, eng=360}

groupingBy(Employee::getDept, mapping(Employee::getName, toList()))
  {hr=[frank], sales=[dave, erin], eng=[ann, bob, carol]}

groupingBy(Employee::getDept, TreeMap::new, counting())
  {eng=3, hr=1, sales=2}                       // sorted keys

groupingBy(Employee::getDept, groupingBy(Employee::getCity))
  {hr={delhi=[frank]}, sales={pune=[dave], delhi=[erin]}, eng={pune=[ann, bob], delhi=[carol]}}

groupingBy(e -> e.getSalary() >= 110 ? "senior" : "junior", counting())
  {senior=3, junior=3}                         // the key can be computed, not just a field
Four things to notice. (1) The default bucket is a List — the one-argument form is just the two-argument form with toList() implied. (2) mapping(f, toList()) is how you keep only one field per group instead of whole objects; it is the most under-used collector in the whole API. (3) Nesting groupingBy inside groupingBy gives multi-level grouping and needs no new concept. (4) The classifier is an ordinary function, so computed keys ("senior"/"junior", first letter, salary band) work exactly the same.

The maxBy-inside-a-group problem

"Highest-paid employee per department" is asked in interviews constantly. The naive version:

groupingBy(Employee::getDept, maxBy(comparingInt(Employee::getSalary)))
  {hr=Optional[frank], sales=Optional[erin], eng=Optional[carol]}   // ugly Optional values

The fix is collectingAndThen — "run this collector, then apply this function to its result":

groupingBy(Employee::getDept,
    collectingAndThen(
        maxBy(comparingInt(Employee::getSalary)),
        Optional::get))
  {hr=frank, sales=erin, eng=carol}
maxBy must return an Optional because, in general, a collector may see zero elements. Inside a groupingBy a bucket can never be empty — a bucket only exists because something landed in it — so Optional::get is safe here and nowhere else. Being able to explain why it is safe is what separates a memorised answer from an understood one.

partitioningBy — grouping into exactly two buckets

partitioningBy(e -> e.getSalary() > 100)
  {false=[bob, dave, frank], true=[ann, carol, erin]}

partitioningBy(e -> e.getSalary() > 100, counting())
  {false=3, true=3}

partitioningBy(e -> e.getSalary() > 999)
  {false=[ann, bob, carol, dave, erin, frank], true=[]}   // BOTH keys always present
partitioningBy vs groupingBy: the classifier is a Predicate, the key type is Boolean, and both true and false keys always exist, even when one side is empty. groupingBy would simply have no entry for the empty side. That guarantee is the only real reason to prefer it — it also avoids boxing the key.

Family 5 — the decorators

CollectorMeaningSince
mapping(f, down)transform each element, then collect8
collectingAndThen(down, fin)collect, then transform the final result8
reducing(id, f, op)reduce usable as a downstream collector8
filtering(p, down)drop non-matching elements inside a group9
flatMapping(f, down)flatMap inside a group9
teeing(c1, c2, merger)run two collectors over one stream and combine12
toUnmodifiableList/Set/Mapimmutable results10
filtering vs a plain filter before the collect. Filtering upstream removes elements entirely, so a group whose every member was filtered out disappears. Collectors.filtering keeps the empty group. Different answers — and a sharp interview follow-up. (Java 9+.)
Idiom. Make a collected list immutable in one step: collectingAndThen(toList(), Collections::unmodifiableList).

§4When to use

  • toList/toSet — you just want the elements back.
  • joining — building a CSV, a log line, a message. Never reduce for this.
  • toMap — one value per key: an id-to-object lookup, a config map. Always think about duplicates and supply a merge function.
  • groupingBy — many values per key: reports, buckets, counts, "per department / per city / per status".
  • partitioningBy — a yes/no split where you need both sides even if one is empty (valid vs invalid, passed vs failed).
  • mapping — inside a group, when you want a field rather than the whole object.
  • collectingAndThen — unwrapping an Optional from maxBy, or making the result immutable.

§5Explain it to a 12-year-old

Imagine sorting a huge pile of Lego into a tray with compartments.

  • groupingBy — you decide the rule for which compartment a brick goes in ("by colour"). Then you throw each brick into its compartment. At the end each compartment holds a pile.
  • The downstream collector — instead of leaving a pile, you say what to do with each compartment before you finish: "just write down how many" (counting), "only keep their sizes" (mapping), "keep the biggest one" (maxBy), or even "split each pile again, by shape" (a nested groupingBy).
  • partitioningBy — a tray with exactly two compartments, yes and no. Even if nothing is a "yes", the yes compartment still exists; it is just empty.
  • toMap — a tray where each compartment may hold only one brick. If two bricks want the same slot, you must say in advance which one wins — otherwise the whole job stops with an error.

Naive question: "why is counting() different from counting the pile afterwards?" Because you would have to build every pile first and then walk back over all of them. Telling the tray up front "just count" means no pile is ever built. Same answer, much less work.

§6Connections

  • ← maps & hashing: groupingBy and toMap build a HashMap, so the key class needs correct hashCode/equals, and the result order is unspecified.
  • ← part 5: collect is mutable reduction; reduce is immutable reduction. Same family, different tool.
  • ← part 2: the classifier is a Function, the partitioner a Predicate, the merge function a BinaryOperator, mapFactory a Supplier.
  • → part 7: maxBy/minBy return Optional, which is why collectingAndThen keeps appearing.
  • Same idea elsewhere: SQL GROUP BY … COUNT(*); Python collections.Counter / itertools.groupby; JavaScript Object.groupBy. If you can write the SQL, you can write the collector — the classifier is the GROUP BY column and the downstream is the aggregate function.

§7In practice — the classic problems, solved and verified

These are the exact questions interviews ask. Output is real, from code/CollectorsDemo.java.

1. Word frequency

Arrays.stream(text.split(" "))
      .collect(groupingBy(w -> w, counting()));
{over=1, the=3, quick=1, lazy=1, jumps=1, end=1, brown=1, dog=1, fox=1}
The classifier is the identity function — "group each word under itself". Function.identity() also works and reads better. This one line replaces about fifteen lines of HashMap plus containsKey code.

2. Character frequency, in first-seen order

"banana".chars()
         .mapToObj(c -> (char) c)
         .collect(groupingBy(c -> c, LinkedHashMap::new, counting()));
{b=1, a=3, n=2}
Two things worth stealing: chars().mapToObj(c -> (char) c) is the way to stream characters, and the three-argument groupingBy with LinkedHashMap::new is how you keep insertion order. With a plain HashMap the order would be arbitrary — a detail interviewers probe.

3. Group words by length

Stream.of("ann","bob","carol","dave").collect(groupingBy(String::length));
  {3=[ann, bob], 4=[dave], 5=[carol]}

4. Group anagrams

Stream.of("eat","tea","tan","ate","nat","bat")
      .collect(groupingBy(CollectorsDemo::sortLetters));
  {aet=[eat, tea, ate], abt=[bat], ant=[tan, nat]}
A famous algorithm question that becomes trivial once you see it as grouping: the key is "the word's letters, sorted". Any "group things that are equivalent under some rule" problem is a groupingBy whose classifier computes the rule.

5. Top 3 entries of a map, by value descending

map.entrySet().stream()
   .sorted(Map.Entry.<String,Long>comparingByValue().reversed()
                    .thenComparing(Map.Entry.comparingByKey()))
   .limit(3)
   .collect(toMap(Map.Entry::getKey, Map.Entry::getValue,
                  (a, b) -> a, LinkedHashMap::new));
  {the=3, brown=1, dog=1}
Three things most people get wrong here. (a) Map has no stream() — you must go via entrySet(). (b) Map.Entry.comparingByValue() and comparingByKey() exist; use them instead of hand-written comparators, and note the explicit type witness Map.Entry.<String,Long>comparingByValue() that inference needs when you chain .reversed(). (c) Collecting back into a plain HashMap would throw the sorted order away — you must ask for LinkedHashMap::new.

6. Second-highest value

staff.stream().map(Employee::getSalary)
     .distinct()
     .sorted(Comparator.reverseOrder())
     .skip(1)
     .findFirst();
  120
distinct() is not optional: without it, two people on 140 would make the "second highest" 140 again. Mentioning that unprompted is the kind of detail that passes interviews.

7. First duplicate (and the honest caveat)

Set<Integer> seen = new HashSet<>();
xs.stream().filter(x -> !seen.add(x)).findFirst();
  2
Set.add returns false when the element was already there, so !seen.add(x) means "already seen". It is neat, and it is a stateful lambda — it breaks on a parallel stream and violates the stream contract. Use it, but say so.
Write these without looking. Using the employee list:
  1. a Map<String, List<String>> of city → employee names;
  2. a Map<String, Double> of department → average salary;
  3. a Map<String, Map<String, Long>> of department → city → head count;
  4. the single highest-paid employee in each city, with no Optional in the result.
Answers: 
groupingBy(Employee::getCity, mapping(Employee::getName, toList()))
groupingBy(Employee::getDept, averagingInt(Employee::getSalary))
groupingBy(Employee::getDept, groupingBy(Employee::getCity, counting()))
groupingBy(Employee::getCity, collectingAndThen(
        maxBy(comparingInt(Employee::getSalary)), Optional::get))

§8Pitfalls

IllegalStateException: Duplicate key. toMap with two arguments and a non-unique key. Add a merge function, or you probably wanted groupingBy.
toMap with a null value throws NullPointerException. Filter or map nulls away first.
Expecting the result map to be ordered. groupingBy and toMap return a HashMap. Pass TreeMap::new or LinkedHashMap::new if order matters.
Forgetting that the downstream collector replaces the list. groupingBy(f, counting()) gives Map<K,Long>, not Map<K,List<T>>. Read the return type off the downstream collector.
Optional values from maxBy/minBy inside a group. Wrap with collectingAndThen(..., Optional::get).
Assuming toList() returns something mutable or immutable. It guarantees neither. Use toCollection(ArrayList::new) for mutable, toUnmodifiableList() (Java 10+) or collectingAndThen for immutable.
Grouping by a mutable key. If the key object changes after insertion, its hash changes and you can never find the bucket again — the same hazard as any HashMap key.
groupingByConcurrent is not a drop-in replacement. It only helps on an unordered parallel stream, and it abandons encounter order.

§9Recap

  • collect performs mutable reduction; a Collector is supplier + accumulator + combiner + finisher.
  • Five families: container, number, map, group, decorator.
  • toMap = one value per key; duplicates throw unless you pass a merge function.
  • groupingBy(classifier) = buckets with lists; groupingBy(classifier, downstream) = "instead of a list, do this to each bucket".
  • The downstream can be anything, including another groupingBy — that is multi-level grouping for free.
  • mapping(f, toList()) keeps a field instead of whole objects inside each group.
  • collectingAndThen(maxBy(cmp), Optional::get) is the "best per group" idiom.
  • partitioningBy = exactly two Boolean keys, both always present.
  • Choose the map type with the three-argument form: TreeMap::new sorts, LinkedHashMap::new preserves insertion order.

Glossary

Collector
A recipe for accumulating stream elements into a result container.
Mutable reduction
Accumulating into a mutable container instead of folding into a new value each step.
Classifier
The function groupingBy uses to compute each element's group key.
Downstream collector
The collector applied to the contents of each group.
Merge function
toMap's rule for resolving two values competing for one key.
Finisher
The final transformation applied to a collector's accumulated result.
collectingAndThen
Wraps a collector with a finishing function.
partitioningBy
Grouping with a Boolean key; both keys always present.
