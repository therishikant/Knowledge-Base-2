default Methods & java.time

Java › Java 8 & functional cluster · lesson 7, part 8 of 9 · DEEP — the feature that made streams possible, and the API that fixed dates

Java 8 & functional cluster: 1. Lambdas · 2. Functional interfaces & method refs · 3. How a stream actually runs · 4. Intermediate operations · 5. Terminal operations & reduce · 6. Collectors & groupingBy · 7. Optional · 8. default methods & java.time · 9. Recall & interview playbook

In one line — Two more Java 8 features, for two different reasons. default methods let an interface ship a method body, which is the only reason Collection.stream() could be added without breaking every class in the world. java.time replaced the mutable, confusing Date/Calendar with an immutable API whose type names say exactly what they mean.

§1Where it fits

Parts 1–7 were one connected story about functions and data. This part closes the Java 8 feature set with the two remaining pieces you are expected to know. They are smaller, but default methods in particular explain how the whole streams feature was delivered at all — a question interviewers like because it tests whether you understand library evolution, not just syntax.

§2Why they exist

The interface evolution problem

Java 8 wanted to add stream() to Collection. But Collection is an interface, and before Java 8 every method on an interface was abstract. Adding one abstract method would have meant that every single class implementing Collection, anywhere in the world, stopped compiling — including thousands of classes in libraries the JDK team had never seen.

The options were:

OptionWhy it fails
Add an abstract methodBreaks every implementer. Non-starter.
Make a new Collection2 interfaceSplits the ecosystem forever; nothing old gets streams.
Put stream() in a static helper classStreams.of(collection) — works, but reads badly and cannot be overridden by implementations that could do it better.
Let the interface supply a bodyOld classes inherit it and keep compiling; new classes may override it. This is default.
The sentence for an interview: "default methods exist for interface evolution — they let a published interface grow new methods without breaking existing implementations. That is the only reason Collection.stream() and Comparator.thenComparing() could be added in Java 8."

The Date problem

The old API was a well-known catalogue of bad decisions:

  • Date is mutable, so any method you pass it to can change it under you, and it can never be safely shared between threads.
  • Date.getYear() returns the year minus 1900.
  • Calendar months are zero-based — January is 0, a perennial off-by-one bug.
  • java.sql.Date extends java.util.Date but throws on half its methods.
  • SimpleDateFormat is not thread-safe, which has caused countless production incidents.
  • There is no type for "a date with no time" or "a time with no date" — concepts people need constantly.

Verified, on JDK 1.8

Date year : 70  <- 70, because years count from 1900
Calendar  : month 0 means January - a classic off-by-one bug source

§3How it works — default and static interface methods

interface Vehicle {
    String name();                                  // abstract
    default String describe() {                      // a body on an interface
        return "a " + name() + " with " + wheels() + " wheels";
    }
    default int wheels() { return 4; }
    static Vehicle of(String n) { return () -> n; }   // static factory on the interface
}

Verified output

inherited : a car with 4 wheels
overridden: a bike with 2 wheels
diamond   : AB
Three things to take away. (1) describe() calls name(), an abstract method — a default method may use the rest of the interface, which is how Comparator.thenComparing is built. (2) Vehicle still has exactly one abstract method, so () -> n is a legal lambda for it; default and static methods do not break functional-interface status. (3) The diamond printed AB because class C explicitly called A.super.hello() + B.super.hello(). Without that override it would not compile.

The resolution rules, in order

  1. Class wins over interface. A method inherited from a superclass always beats a default.
  2. More specific interface wins. If B extends A and both define it, B's wins.
  3. Otherwise you must choose. Unrelated interfaces with the same signature → compile error until the class overrides it, optionally delegating with A.super.hello().
"Does this make Java multiple-inheritance?" The standard interview question. Answer: it adds multiple inheritance of behaviour, but not of state — interfaces still cannot have instance fields. That is precisely why the C++ diamond problem does not recur: there is no duplicated data, only a method-name clash, which the compiler makes you resolve.
static interface methods also arrived in Java 8 and are not inherited — you call them on the interface name. They exist so a type's factory methods can live with the type: Stream.of, Comparator.comparing, Function.identity, Predicate.isEqual. (Java 9 later added private interface methods for sharing code between defaults.)

§3bHow it works — java.time

Pick the type by asking what you actually mean

You meanTypeExample value
a date, no time, no zone (a birthday)LocalDate2024-03-15
a time of day, no date (a shop opening)LocalTime09:30
both, still no zoneLocalDateTime2024-03-15T09:30
a real instant somewhere in the worldZonedDateTime2024-03-15T09:30+05:30[Asia/Kolkata]
a machine timestamp (UTC, for logs/DBs)Instant1970-01-01T00:00:00Z
an amount of time (hours/minutes)DurationPT1H30M
an amount of date (years/months/days)PeriodP9M10D
The split that matters: Duration is machine time — exact seconds. Period is human time — "one month" is 28–31 days depending on where you start. Adding Period.ofMonths(1) to 31 January gives 29 February, not 31 February. Using the wrong one is a classic production bug.

Every object is immutable

LocalDate d = LocalDate.of(2024, Month.MARCH, 15);
d.plusDays(20)   // returns a NEW date 2024-04-04
d                // still 2024-03-15
LocalDate : 2024-03-15
plusDays  : 2024-04-04   (original still 2024-03-15 - immutable)
Every method starting with plus, minus or with returns a new object. That makes these types thread-safe and safe to share — the opposite of Date. The flip side: ignoring the return value is a silent no-op, exactly like String.trim().

The operations you will actually use

LocalDate.now()  ·  LocalDate.of(2024, 3, 15)  ·  LocalDate.parse("2024-03-15")
d.plusDays(1) · d.minusWeeks(2) · d.withDayOfMonth(1) · d.getDayOfWeek()
d.isBefore(other) · d.isAfter(other) · d.isEqual(other)
ChronoUnit.DAYS.between(a, b)        // 285 — a plain count
Period.between(a, b)                 // P9M10D — human-readable
d.format(DateTimeFormatter.ofPattern("dd MMM yyyy", Locale.ENGLISH))   // 15 Mar 2024
Idiom. DateTimeFormatter is immutable and thread-safe, so unlike SimpleDateFormat you can and should keep one in a static final field. That single difference removes an entire class of concurrency bug.
Always pass a Locale to ofPattern when the pattern contains text (MMM, EEE). Otherwise output depends on the machine's default locale and your tests will pass locally and fail on the build server.

§4When to use

  • default — yes: adding a method to an interface that already has implementers; providing a convenience method expressible in terms of the abstract ones (describe() from name()).
  • default — no: as a way to share state or build a "base class". Interfaces have no fields; if you need state, use an abstract class.
  • static on an interface: factory and helper methods that belong with the type.
  • LocalDate: birthdays, invoice dates, anything a human writes on a form.
  • Instant: timestamps you store or log; always UTC, always unambiguous.
  • ZonedDateTime: only when a specific place and its daylight-saving rules genuinely matter (scheduling a meeting).
  • Never: new code with Date, Calendar or SimpleDateFormat. Convert at the boundary with date.toInstant() and Date.from(instant).

§5Explain it to a 12-year-old

default methods. Imagine a club with a rulebook. The rule says "every member must bring snacks". One day the club wants to add "every member must bring a chair" — but there are already a thousand members, and none of them has a chair. Instead of throwing everyone out, the club writes: "every member must bring a chair; if you do not have one, use the spare in the cupboard." Now the old members are still fine, and new members can bring a fancier chair if they want. The spare in the cupboard is the default method.

And if you somehow belong to two clubs with different spare chairs, nobody can decide for you — you must say which one you are taking. That is the diamond rule.

java.time. The old date class was one messy box with everything in it, and anybody could reach in and change your date. The new one has separate labelled boxes: one for "just a day on the calendar", one for "just a time on a clock", one for "an exact moment anywhere on Earth". And none of them can be changed — asking for "twenty days later" gives you a brand-new box and leaves yours alone.

§6Connections

  • → part 3: Collection.stream() is itself a default method. No default, no streams.
  • ← part 2: default/static methods do not count toward the one-abstract-method rule, which is why Comparator and Function can be packed with helpers and still take lambdas.
  • ← inheritance & polymorphism: the class-wins and most-specific-interface rules are the same dispatch rules, extended to interfaces.
  • → strings: the "ignoring the return value is a no-op" trap is identical for immutable dates and immutable strings.
  • → sharing data safely: immutability is why java.time types and DateTimeFormatter are safe to share between threads, while SimpleDateFormat never was.
  • Same idea elsewhere: java.time is based on the Joda-Time library (JSR-310, by the same author); Python's datetime and JavaScript's new Temporal API follow the same date/time/instant split.

§7In practice — dissected

From code/Java8MiscDemo.java:

interface A { default String hello() { return "A"; } }
interface B { default String hello() { return "B"; } }
static class C implements A, B {
    public String hello() { return A.super.hello() + B.super.hello(); }
}
Remove that override and the file does not compile: "class C inherits unrelated defaults for hello() from types A and B". The syntax A.super.hello() is unique to this situation — it means "the default implementation from interface A". Being able to write it from memory is a reliable interview win. 
System.out.println(Period.between(d, LocalDate.of(2024, 12, 25)));
System.out.println(ChronoUnit.DAYS.between(d, LocalDate.of(2024, 12, 25)));
Period    : P9M10D
daysUntil : 285
Two answers to "how far apart are these dates", and both are correct. Period gives the human breakdown ("9 months and 10 days") in ISO-8601 notation — P for period, then the parts. ChronoUnit.DAYS.between gives the flat count. Pick by what the user needs to read; never try to convert a Period into days by multiplying.

§8Pitfalls

Treating default as a base class. Interfaces hold no state. If you want shared fields, you want an abstract class.
Unresolved diamond. Two unrelated interfaces with the same default signature → compile error. Override and delegate with X.super.method().
Forgetting that a default cannot override Object methods. You cannot write a default toString(), equals() or hashCode() — the class always wins, so the language forbids it outright.
Discarding an immutable result. date.plusDays(1); on its own does nothing. Assign it.
Using LocalDateTime for a timestamp. It has no zone, so it does not identify a real moment. Store Instant (or UTC) and convert for display.
Mixing Period and Duration. Duration.ofDays(1) is exactly 24 hours and is wrong across a daylight-saving change; Period.ofDays(1) means "the next calendar day".
Reusing SimpleDateFormat across threads. It is mutable and not thread-safe — the classic intermittent bug. DateTimeFormatter is safe.
ofPattern without a Locale. Text months and day names change with the machine's default locale.

§9Recap

  • default methods exist for interface evolution — adding methods without breaking implementers.
  • They gave us Collection.stream(), Iterable.forEach(), Comparator.thenComparing() and the Map helpers.
  • They do not count toward the one-abstract-method rule, so functional interfaces can still be rich.
  • Conflict resolution: class wins → most specific interface wins → otherwise you must override, delegating with A.super.m().
  • Multiple inheritance of behaviour, never of state.
  • static interface methods hold factories (Stream.of, Comparator.comparing) and are not inherited.
  • java.time types are immutable and thread-safe; every plus/minus/ with returns a new object.
  • Pick by meaning: LocalDate / LocalTime / LocalDateTime / ZonedDateTime / Instant.
  • Duration = machine time (seconds); Period = human time (years/months/days).
  • DateTimeFormatter is thread-safe; SimpleDateFormat never was.

Glossary

default method
An interface method with a body, inherited by implementers.
Interface evolution
Adding methods to a published interface without breaking existing code.
Diamond problem
Two unrelated interfaces supplying the same default; must be resolved explicitly.
A.super.m()
Syntax for invoking a specific interface's default implementation.
LocalDate
A date with no time and no time zone.
Instant
A point on the UTC timeline; the machine timestamp type.
Duration vs Period
Exact time-based amount vs calendar-based amount.
ISO-8601
The standard text format java.time uses by default (2024-03-15, PT1H30M).
