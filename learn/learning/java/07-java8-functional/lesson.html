In one line — Before Java 8 you could pass data into a method (a number, a list, an object). Java 8 let you also pass an action — a small piece of code — as if it were data. That small piece of code, written in short form, is a lambda. Everything else in this cluster (streams, Optional, CompletableFuture) is just a different place to hand your action to.

§1Where it fits

This cluster sits on top of the type system. That matters more than it sounds: a lambda is not a new kind of thing in Java. Java still has only classes, objects and interfaces. A lambda is a short way of writing an object that implements a one-method interface. If you hold on to that one sentence, nothing in Java 8 will ever feel like magic.

Below this lesson: types and interfaces, and how the JVM dispatches calls. Above it: streams (part 3 onward), collections, and concurrency.

§2Why it exists

The problem, in plain words

Imagine a method that sorts a list of people. Sorting is mostly the same every time — compare two things, put the smaller one first, repeat. The only part that changes between "sort by name" and "sort by age" is one tiny decision: given two people, which one comes first?

So the sorting method wants you to hand it that tiny decision. But before Java 8, the only way to hand a piece of code to a method was to wrap it inside an object: 

Collections.sort(people, new Comparator<Person>() {   // 1. make a nameless class
    public int compare(Person a, Person b) {            // 2. name the method
        return a.getAge() - b.getAge();                  // 3. the ONE line you cared about
    }                                                   // 4. close it all
});

Four lines of packaging around one line of thought. That is the problem Java 8 solved. The packaging is noise — the compiler already knows the interface is Comparator, it already knows the only method is compare, and it already knows the arguments are two Persons. So why make you type all of it? 

people.sort((a, b) -> a.getAge() - b.getAge());   // same thing, Java 8

Why not just add "functions" to Java, like JavaScript has?

This is the question that unlocks everything. Java could have added a brand-new "function" type. It deliberately did not, for three reasons:

  1. Twenty years of existing libraries already used interfaces. Runnable, Comparator, ActionListener — thousands of APIs already said "give me an object with one method". If a lambda is such an object, every one of those APIs instantly accepts lambdas with zero changes. That is exactly what happened.
  2. The type system stays simple. No new kind of type to teach, to store in a field, or to put in a generic parameter. A lambda's type is just an interface name you already understand.
  3. The JVM barely had to change. Lambdas are wired up at run time by the invokedynamic instruction (see lesson 4), which already existed for other languages on the JVM.
The sentence to memorise. A lambda is an object that implements an interface which has exactly one abstract method. Say it out loud. Every confusing thing about lambdas dissolves into this.

§3How it works

Step 1 — the shape of a lambda

A lambda has exactly two halves, separated by an arrow ->:

(a, b)   ->   a.getAge() - b.getAge()
  ^            ^
  |            |
what comes in  what to do with it (and give back)

Four syntax forms, all the same idea:

WrittenMeansNotes
() -> "hi"no input, returns "hi"empty brackets are required when there is no parameter
x -> x + 1one input, returns x + 1with exactly one parameter you may drop the brackets
(x, y) -> x + ytwo inputstwo or more always need brackets
x -> { int y = x * 2; return y; }a block bodybraces mean you must write return yourself
Idiom. Prefer the short expression form x -> x + 1. The moment you need braces and a return, ask whether the logic deserves its own named method instead. A lambda longer than about three lines is almost always better as a method, then referenced with :: (part 2).

Step 2 — where the type comes from

A lambda on its own has no type. x -> x + 1 compiled by itself is meaningless — is x an int? a String? The type comes from where you put it. This is called the target type.

Concretely, the exact same characters mean two different things in two different places:

Runnable r       = () -> System.out.println("go");   // becomes a Runnable
Supplier<Void> s = () -> { System.out.println("go"); return null; };

Step 3 — what the lambda is allowed to see (capture)

A lambda body can read variables from around it. Those variables are captured — copied into the object the lambda becomes. Java has one firm rule here:

Effectively final. A local variable used inside a lambda must never be reassigned after it is set — either declared final, or simply never changed (that is what "effectively final" means). The compiler rejects anything else.
int base = 10;
Supplier<Integer> f = () -> base + 1;   // fine — base never changes

int counter = 0;
Runnable bad = () -> counter++;          // COMPILE ERROR
                                         // "local variables referenced from a lambda
                                         //  expression must be final or effectively final"

Why the rule? A local variable lives on the thread's stack frame, and that frame disappears when the method returns. But the lambda object lives on the heap and may run much later, on a different thread. So Java copies the value into the lambda. If you were allowed to change the original afterwards, the copy and the original would silently disagree — a bug factory. Java removes the possibility instead of documenting it.

Fields are different: this.counter++ is allowed, because the lambda captures the object reference this and reads the field through it each time. (That is also why a lambda created inside an instance method can be a quiet source of memory leaks — it keeps the whole enclosing object alive.)

Step 4 — lambda vs anonymous inner class: not the same thing

Anonymous inner classLambda
What this meansthe anonymous object itselfthe enclosing object — a lambda has no this of its own

Classic interview question: "What does this refer to inside a lambda?" Answer: the enclosing instance, not the lambda. Lambdas do not introduce a new scope for this, for names, or for super. An anonymous inner class does.

§4When to use

  • Comparators — list.sort(comparing(Person::getAge)). The single most common real use.
  • Callbacks and event handlers — "when this finishes, do that": button.setOnAction(e -> save()), future.thenApply(x -> x + 1).
  • Handing work to a thread pool — executor.submit(() -> doJob()).
  • Map helpers — map.computeIfAbsent(key, k -> new ArrayList<>()), map.merge(k, 1, Integer::sum), map.forEach((k, v) -> ...).
  • Lazy values — pass a Supplier so expensive work only happens if it is actually needed (orElseGet, logging).
  • Streams — every stream operation takes a lambda. That is the whole of parts 3–6.
Do not use a lambda where a plain loop is clearer: when you need an index, when you must break out early with complex conditions, when you are mutating several variables at once, or when you need to throw a checked exception. Lambdas are a tool, not a style contest.

§5Explain it to a 12-year-old

Think about a vending machine. The machine already knows how to do the hard, boring parts: take the money, turn the spiral, drop the item, give change. What it does not know is which item you want. So it gives you a keypad and you press B4.

A method like sort is the vending machine. It knows all the boring sorting work. The one thing it cannot know is how you want things ordered. The lambda is you pressing B4.

And the naive question: "why couldn't we do this before?" You could — but you had to fill in a whole paper form just to press one button. The lambda is the keypad replacing the form. The machine is identical inside; only the way you tell it your choice got shorter.

§6Connections

  • ← type system & OOP: a lambda's type is an interface. Interfaces with one abstract method have existed since Java 1.0 — only the shorthand is new.
  • ← JVM execution engine: invokedynamic builds the lambda object the first time it is reached, then caches it. No class file per lambda.
  • ← runtime data areas: the "effectively final" rule exists because locals live on a stack frame that dies, while the lambda object lives on the heap.
  • → part 2: which interfaces can a lambda become, and what are they all called?
  • → concurrency: executor.submit(() -> ...) and CompletableFuture are lambdas all the way down.
  • Same idea elsewhere: JavaScript arrow functions (a,b) => a+b, Python lambda a,b: a+b, Kotlin { a, b -> a + b }. Identical concept; Java's twist is that it must land in an interface.

§7In practice — dissected

Run file: code/LambdaDemo.java (JDK 1.8). Each block below is annotated.

a) The same behaviour, two ways

@FunctionalInterface
interface Greeter { String greet(String name); }   // exactly ONE abstract method

Greeter anon = new Greeter() {                        // the old way
    public String greet(String n) { return "Hi " + n; }
};
Greeter lambda = n -> "Hi " + n;                       // the Java 8 way — identical behaviour
@FunctionalInterface is optional but you should always write it. It does nothing at run time; it tells the compiler "fail the build if anyone ever adds a second abstract method here", which protects every caller that passed a lambda. Note that the interface is yours — lambdas are not limited to the JDK's interfaces.

b) The four core shapes

Function<String,Integer> length = s -> s.length();      // takes one, gives one back
Predicate<String>        isLong = s -> s.length() > 3;  // takes one, answers true/false
Consumer<String>         shout  = s -> System.out.println("shout: " + s.toUpperCase());
Supplier<String>         now    = () -> "a fresh value";  // takes nothing, produces one
These four cover maybe 90% of all lambdas you will ever write. Part 2 turns them into a memorable system; for now just notice the pattern — in → out, in → boolean, in → nothing, nothing → out.

c) Composition — small behaviours glued into bigger ones

Function<Integer,Integer> twice = n -> n * 2;
Function<Integer,Integer> plus3 = n -> n + 3;

twice.andThen(plus3).apply(5)   // twice FIRST, then plus3  → (5*2)+3 = 13
twice.compose(plus3).apply(5)   // plus3 FIRST, then twice  → (5+3)*2 = 16
Gotcha worth memorising: andThen reads left-to-right (do me, and then the other); compose reads right-to-left, like maths f(g(x)). Interviewers love this because the names sound similar but the order is opposite. Predicate has the matching trio and, or, negate.

d) Capture, and the Comparator payoff

people.sort(Comparator.comparingInt(Person::getAge)      // primary key
                      .thenComparing(Person::getName));   // tie-breaker
people.sort(Comparator.comparing(Person::getName).reversed());
This is the most interview-relevant line in the file. comparing / comparingInt build a comparator from a "how do I get the sort key" lambda; thenComparing chains tie-breakers; reversed() flips the whole thing. Use comparingInt/comparingLong/comparingDouble for primitives to avoid boxing. Never write (a,b) -> a.getAge() - b.getAge() in production — subtraction overflows for large or negative values.

(Answers: 16 and 26. If you had them backwards, re-read §7c — this exact trap shows up in interviews.)

§8Pitfalls

Thinking a lambda is a new type. It is not. It is an instance of an interface. The sentence "a lambda is an object implementing a one-method interface" answers roughly half of all lambda interview questions.
Trying to mutate a local variable inside a lambda. Compile error, always. If you truly need a counter, use an AtomicInteger, a field, or — far better — restructure so you do not need mutation at all (count(), reduce, a collector).
Expecting this to mean the lambda. Inside a lambda, this is the enclosing object. Inside an anonymous inner class it is the anonymous object. This difference breaks code when people mechanically convert one into the other.
Checked exceptions. Function.apply declares no checked exception, so you cannot throw IOException from inside a plain lambda. You must catch it inside, wrap it in an unchecked exception, or define your own throwing interface. This surprises everyone the first time.
Giant lambdas. A twenty-line lambda inside a stream is unreadable and untestable. Extract it to a named method and pass a method reference — same code, with a name that explains it.
Lambdas holding onto objects. A lambda stored in a long-lived list, created inside an instance method, captures this and keeps the whole enclosing object alive — a real memory leak pattern.

§9Recap

  • A lambda is a short way to create an object implementing an interface that has exactly one abstract method.
  • It exists so you can pass behaviour to a method the same way you pass data.
  • Java reused interfaces instead of inventing a function type, so every pre-Java-8 API accepts lambdas for free.
  • Its parameter types come from the target type — the slot it is assigned or passed into.
  • Captured local variables must be final or effectively final, because the frame they live in will die.
  • this inside a lambda = the enclosing object; a lambda creates no new scope.
  • andThen runs left-to-right; compose runs right-to-left.
  • Build comparators with Comparator.comparing(...) + thenComparing(...) + reversed(), never with subtraction.

Glossary

Lambda expression
A compact anonymous function: parameters -> body.
Functional interface
An interface with exactly one abstract method; the type a lambda becomes.
Target type
The type of the slot a lambda is assigned to, which supplies its parameter and return types.
Capture
A lambda reading a variable from the surrounding scope; the value is copied in.
Effectively final
A variable never reassigned after initialisation, even without the final keyword.
invokedynamic
The JVM instruction that links a lambda to an implementation the first time it runs.
Behaviour parameterisation
The design idea of passing an action into a method so one method serves many cases.
