Maps & How Hashing Works

Java › collections cluster · lesson 8, part 2 of 3 · DEEP — looking something up by name, instantly

Collections cluster: 1. Lists, sets & queues · 2. Maps & how hashing works · 3. Equality & ordering

In one line — A Map stores pairs: a key and the value that belongs to it. Its one trick is that finding a value by key takes the same tiny amount of time whether the map holds ten entries or ten million. That trick is hashing: turn the key into a number, turn the number into an array position, and go straight there.

§1Where it fits

Part 1 covered boxes that hold single items. This part covers the box that holds pairs. It is the single most important data structure in day-to-day programming: caches, config, counting, grouping, lookup by ID — all maps.

It also closes a loop from Part 1. HashSet is literally a HashMap with the values thrown away, and TreeSet is a TreeMap with the values thrown away. So understanding maps hands you the sets for free.

§2Why it exists — the problem of finding things

Try it with what you already have

Say you want to find a user's age from their name. With a list of pairs, you must look at each one:

for (Pair p : pairs) {
    if (p.name.equals("ana")) return p.age;   // might check every single pair
}

With 10 pairs, fine. With 10 million, that is 10 million string comparisons — every time you look something up. Searching is O(n), and O(n) inside a loop becomes O(n²), which is how programs die.

The clue is already in the array

Think about what a plain array does. names[7] is instant, no searching at all, because the computer can calculate where slot 7 sits in memory: start address + 7 × item size. One sum, one jump.

So arrays are instant if your key is a small number. But our key is "ana", a string. The whole idea of hashing is this leap:

Turn the key into a number, then use that number as an array position. If we can do that calculation cheaply, then looking up "ana" becomes as fast as names[7].

Why the alternatives fall short

  • One array slot per possible key. Correct, but impossible — there are more possible strings than atoms to store them in. We need a small array, so many keys must share slots.
  • Keep the pairs sorted and binary-search them. That is O(log n) — much better than O(n), and genuinely useful: it is exactly what TreeMap does. But it is still not constant, and every insert has to keep the order intact.
  • Hashing. O(1) on average. The price is that you lose any sensible order, and you depend on the key's hashCode being decent.

Java ships all three ideas, which is why there are several map builds rather than one.

§3How it works

A map is a separate family

First a structural note that trips people up in interviews: Map is not a Collection. It does not extend it. A Collection holds single elements; a Map holds pairs, so add(e) would make no sense. You reach its contents through three views: keySet(), values() and entrySet() (Oracle — The Map Interface).

The four steps of get and put

1
Ask the key for its number. key.hashCode() returns an int — any int, possibly negative, possibly huge. "apple" gives 93029210 (and it is always the same number for the same text, which is the point).
2
Spread the bits. h ^ (h >>> 16) folds the top 16 bits down into the bottom 16. Why? Because step 3 throws the top bits away. Without this, two keys differing only in their high bits would always collide. One cheap instruction, far fewer collisions.
3
Squeeze it into the table size. h & (n - 1) where n is the table length (16, 32, 64 …). Because n is a power of two, n-1 is all ones in binary, so the & keeps only the low bits — the same result as h % n, but much faster, and it never goes negative.
4
Look inside that one bucket. The bucket may hold several entries. Walk its short chain and compare with equals() until you find the key, or run out. Both methods are needed: hashCode finds the right bucket, equals picks the right entry inside it. (That is Part 3.)

Collisions are normal, not a bug

Two different keys will sometimes land in the same bucket — an int has about 4 billion values but the table only has, say, 16 slots. That is a collision, and a map handles it by keeping a small chain in the bucket. You will see a real collision in §7: "Aa" and "BB" have the exact same hashCode (2112), yet they are different keys, and the map keeps both.

Collisions are only a performance problem. If every key collided, the map would degrade into one long list and lookup would be O(n). Since Java 8, a bucket that grows past 8 entries (in a table of at least 64) is converted into a balanced tree, so the worst case is O(log n) rather than O(n). This also defuses a real denial-of-service attack where someone deliberately feeds you colliding keys (Oracle — HashMap, "treeify").

Load factor and resizing

A 16-slot table holding 500 entries would have chains everywhere. So the map watches how full it is. The load factor is that threshold, and it defaults to 0.75. When size > capacity × 0.75, the map doubles the table and re-places every entry. 

capacity 16 → resize when size hits 13
capacity 32 → resize when size hits 25
capacity 64 → resize when size hits 49   // and so on

Why 0.75? It is the published trade-off point: lower wastes memory, higher produces long chains (Oracle — HashMap). And here is the consequence most people miss: resizing moves keys to different buckets, because the mask & (n-1) now keeps one more bit. In §7 you will see "apple" sit in bucket 1 in a 16-slot table and bucket 17 in a 32-slot table. That is precisely why HashMap iteration order can change as the map grows — and why you must never depend on it.

Idiom: expecting ~1,000 entries? new HashMap<>(2048). You skip several rounds of rehashing everything.

LinkedHashMap — order for almost no cost

It is a HashMap plus a doubly-linked chain threaded through the entries. Lookups use the buckets exactly as before; iteration follows the chain instead. Build it with new LinkedHashMap<>(16, 0.75f, true) and the chain re-orders on every access, not just insertion — which, with an overridden removeEldestEntry, gives you a working LRU cache in about five lines (Oracle — LinkedHashMap).

TreeMap — sorted, and it can answer questions HashMap cannot

A red-black tree keeps keys in order at all times, so you pay O(log n) but you gain abilities hashing simply does not have: firstKey, lastKey, floorKey(x) ("the biggest key ≤ x"), ceilingKey(x), headMap/tailMap/subMap. Price tiers, time ranges and leaderboards live here. Note it compares keys, so keys must be Comparable (or you supply a Comparator) and null keys are rejected.

ConcurrentHashMap — and why not the old ones

Hashtable and Collections.synchronizedMap lock the whole map for every operation, so threads queue up one behind another. ConcurrentHashMap locks only the bucket being touched, so unrelated threads never wait on each other, and reads are usually lock-free. It is both safer and faster — use it, not Hashtable (Oracle — ConcurrentHashMap).

Careful: thread-safe per operation is not the same as thread-safe per sequence. if (!map.containsKey(k)) map.put(k, v); is still a race — two threads can both pass the check. Use the atomic combinations instead: putIfAbsent, computeIfAbsent, merge. More in lesson 11.

§4When to use which

  • Plain lookup by ID, caching, counting, grouping? → HashMap. Start here always.
  • Output must look the same on every run (logs, API responses, golden-file tests)? → LinkedHashMap.
  • A small cache that drops the least recently used? → LinkedHashMap in access-order with removeEldestEntry.
  • Sorted output, or "the nearest key below X"? → TreeMap. Price bands, timestamps, ranges.
  • Shared by several threads? → ConcurrentHashMap, and use its atomic methods.
  • Keys are a fixed enum? → EnumMap. It is a plain array indexed by ordinal() — tiny and extremely fast.
  • Never → Hashtable. It only survives for backwards compatibility.

§5Explain it to a 12-year-old

A map is the coat check at a cinema. You hand over your coat (the value) and get a ticket (the key).

A bad coat check hangs the coats in a long row. When you come back, the attendant walks the whole row looking for your coat. A thousand coats, a thousand looks.

A clever coat check does something smarter. It has 16 numbered hooks. The attendant does a quick sum on your ticket number and gets a hook number — say hook 1 — and walks straight there. One step, whether there are 10 coats or 10,000. That sum is hashCode.

Of course two tickets can produce the same hook. So each hook holds a few coats, each with a name tag, and the attendant reads the tags to grab the right one. That reading is equals.

And when the place gets busy — about three-quarters full — the owner installs twice as many hooks and re-hangs every coat, so the piles stay short. That is resizing. Two more things follow naturally from the story: if your ticket number is wrong the attendant goes to the wrong hook and your coat is "lost" (a broken hashCode), and after the re-hang the coats are in a totally different arrangement (which is why HashMap order means nothing).

§6Connections

  • ← Part 1: HashSet is a HashMap whose values are ignored. Everything here applies to sets too.
  • → Part 3: all of this assumes your keys implement hashCode/equals correctly. That is the contract.
  • → strings: String is the most common key, and it caches its hash after the first call — computed once, reused forever. Immutability is what makes that safe.
  • → concurrency: a plain HashMap written by two threads can corrupt itself (historically, even spin forever). ConcurrentHashMap exists for this.
  • → memory: a static Map that only ever grows is leak #1 in Java. WeakHashMap lets entries be collected when the key is unreachable.
  • → streams: groupingBy and toMap build maps straight out of a pipeline.
  • Same idea elsewhere: Python dict, JavaScript Map, C++ unordered_map, Ruby Hash, Go map — identical machinery, down to the load factor.

§7In practice — one file, dissected

Run on JDK 1.8. Every output block below is copied from a real run of code/CollectionsDemo3.java.

A — doing the map's own arithmetic by hand

// exactly the two steps HashMap performs internally
static int bucketOf(Object key, int tableSize) {
    int h = key.hashCode();
    h = h ^ (h >>> 16);              // 1. fold the high bits down
    return h & (tableSize - 1);      // 2. keep only the low bits
}
"apple"  hashCode=    93029210  bucket=1
"banana" hashCode= -1396355227  bucket=0
"cherry" hashCode= -1361513063  bucket=1
"Aa"     hashCode=        2112  bucket=0
"BB"     hashCode=        2112  bucket=0
"Aa".equals("BB")? false  -> same bucket, different keys = a collision
Three things to take from this table.

(1) "banana" has a negative hash — perfectly normal, and the & mask still yields a valid bucket (0–15). That is one reason the mask is used instead of %, which can return a negative result.

(2) "apple" and "cherry" have wildly different hashes yet share bucket 1. Only the last 4 bits survived the mask. Collisions are ordinary.

(3) "Aa" and "BB" have the identical hash code, 2112 — a famous example of how String.hashCode works (31·h + ch). Same hash, but equals says false, so the map correctly keeps both as separate keys. Same hash never means same key.

B — why iteration order can change under you

"apple" in a 16-slot table : 1
"apple" in a 32-slot table : 17
Same key, same hash code, different bucket — because the mask now keeps 5 bits instead of 4. The map grew, so everything moved. This is the mechanical reason behind the rule "never depend on HashMap order": adding one extra entry can trigger a resize and rearrange the entire map.

C — the three orders, side by side

for (String k : new String[]{"banana", "apple", "cherry"}) {
    hash.put(k, 1); linked.put(k, 1); tree.put(k, 1);
}
HashMap       = [banana, apple, cherry]
LinkedHashMap = [banana, apple, cherry]
TreeMap       = [apple, banana, cherry]
The HashMap line matching insertion order here is a coincidence of these three keys in a 16-slot table — look at section A and you can see why (buckets 0, 1, 1). Change the keys, or add a few more, and it scrambles. LinkedHashMap is the only one promising insertion order; TreeMap promises sorted order.

D — an LRU cache in five lines

LinkedHashMap<String,Integer> lru =
    new LinkedHashMap<String,Integer>(16, 0.75f, true) {   // true = access order
        @Override protected boolean removeEldestEntry(Map.Entry<String,Integer> eldest) {
            return size() > 3;                                 // keep the 3 newest
        }
    };
lru.put("a",1); lru.put("b",2); lru.put("c",3);
lru.get("a");     // touching "a" makes it the newest
lru.put("d",4);  // full -> drop the oldest, which is now "b"
after get(a) then put(d): [c, a, d]
Trace it: after the three puts the order is [a, b, c]. get("a") moves a to the end → [b, c, a]. Putting d makes size 4, so removeEldestEntry returns true and the eldest — now b — is evicted, leaving [c, a, d]. That third flag in the constructor is the whole feature; the JDK then does the bookkeeping for you.
Idiom: fine for a small single-threaded cache. For anything shared or large, use Caffeine or Guava — you get sizing, expiry and thread safety for free.

E — the questions only a sorted map can answer

prices.put(100, "pen"); prices.put(250, "mug"); prices.put(900, "chair");
firstKey()      = 100
floorKey(300)   = 250
ceilingKey(300) = 900
headMap(900)    = {100=pen, 250=mug}
There is no key 300 in the map, yet TreeMap answers "the nearest below" and "the nearest above" instantly, by walking down the tree. A HashMap cannot do this at all — it would have to scan every key. This is the moment where paying O(log n) buys you something real.

F — counting without if/else

for (String w : "tea coffee tea milk tea".split(" ")) {
    counts.merge(w, 1, (oldV, newV) -> oldV + newV);   // Java 8
}
counts            = {coffee=1, milk=1, tea=3}
getOrDefault(juice) = 0
merge reads as: "put 1 under this key; if something is already there, combine the two with this function." It replaces the familiar four-line if (map.containsKey(w)) … else …, and on a ConcurrentHashMap it is atomic as well. (The printed map is wrapped in a TreeMap purely so the output is stable for this lesson.)

G — nulls: three classes, three answers

HashMap.get(null)   = allowed in HashMap
TreeMap.put(null)   -> NullPointerException (it must compare keys)
Hashtable.put(null) -> NullPointerException (legacy rule)
HashMap special-cases a single null key into bucket 0. TreeMap cannot, because it must call compareTo on the key. Hashtable simply forbids it, and ConcurrentHashMap forbids it too — there, get returning null must unambiguously mean "absent", with no race.
Predict the output, then run it. (1) Put 20 entries into a HashMap, printing keySet() after each put. Spot the entry where the whole order suddenly rearranges — then work out why that one. (Hint: 16 × 0.75.) (2) Write a key class whose hashCode() just return 1;. Is it correct? Is it fast? Time 100,000 lookups against a normal key class and explain the gap in one sentence.

§8Pitfalls

Depending on HashMap iteration order. There is none, and resizing proves it (section B). Use LinkedHashMap or TreeMap when order matters.
Using a mutable object as a key. Change a field that feeds hashCode after inserting and the entry is stranded in the old bucket — unreachable, but still occupying memory. Keys should be immutable. Demonstrated in Part 3.
A key class with no hashCode. You get identity hashing, so a freshly built "equal" key lands elsewhere and your lookup silently misses. The single most common collections bug.
map.get(k) == null read as "absent". It can also mean "present, with a null value". Use containsKey when you must tell them apart.
Check-then-act on a shared map. if (!map.containsKey(k)) map.put(k, v); is a race even on ConcurrentHashMap. Use putIfAbsent / computeIfAbsent / merge.
Sharing a plain HashMap between threads. Concurrent writes can corrupt the internal structure; on Java 7 a resize race could even hang a CPU at 100% forever. Use ConcurrentHashMap.
Hashtable or synchronizedMap for thread safety. They work but serialise every single call. ConcurrentHashMap is strictly better.
Forgetting TreeMap uses compareTo, not equals. Two keys that compare equal are one key to a TreeMap, even when equals disagrees. See Part 3.

§9Recap

  • Map stores key → value pairs and is not a Collection; you view it through keySet, values, entrySet.
  • Lookup = hashCode → spread → mask → bucket → equals. Hash finds the bucket; equals finds the entry.
  • h & (n-1) works only because the table length is a power of two; it is a fast, never-negative %.
  • Collisions are normal. Chains over 8 entries become trees (Java 8+), so the worst case is O(log n), not O(n).
  • Load factor 0.75 → double the table and move everything. Keys change buckets: "apple" 1 → 17.
  • HashMap = no order · LinkedHashMap = insertion/access order · TreeMap = sorted + range queries · ConcurrentHashMap = shared across threads.
  • Learn getOrDefault, putIfAbsent, computeIfAbsent, merge — shorter and atomic where it matters.
  • Keys must be immutable and must implement equals/hashCode properly → Part 3.

Glossary

Map / entry
A store of key → value pairs; one pair is an Entry.
Hashing
Turning a key into a number so it can be used as an array position.
Bucket (bin)
One slot of the table; holds a chain or tree of entries.
Collision
Two different keys landing in the same bucket. Normal; resolved by searching the chain.
Spread function
h ^ (h >>> 16) — mixes high bits down so the mask does not discard them.
Load factor
Fullness threshold (default 0.75) that triggers a resize.
Rehash / resize
Doubling the table and re-placing every entry — which changes iteration order.
Treeify
Converting an over-long bucket chain into a balanced tree (Java 8+).
LRU cache
"Least recently used" eviction — a LinkedHashMap in access order.
Red-black tree
The self-balancing tree behind TreeMap/TreeSet, giving O(log n).
