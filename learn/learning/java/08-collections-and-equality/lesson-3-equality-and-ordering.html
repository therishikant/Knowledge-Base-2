Equality & Ordering

Java › collections cluster · lesson 8, part 3 of 3 · DEEP — the two rules that make every collection work

Collections cluster: 1. Lists, sets & queues · 2. Maps & how hashing works · 3. Equality & ordering

In one line — Parts 1 and 2 quietly assumed two things: that Java knows when two of your objects are "the same", and that it knows how to put them in order. Neither is automatic. equals + hashCode define sameness; Comparable / Comparator define order. Get them wrong and your object silently disappears from a set, or a sort throws at random.

§1Where it fits

This is the lesson that makes the other two actually work. A Set promises "no duplicates" — but what is a duplicate? A HashMap promises "find the value for this key" — but which key counts as the same key? A TreeMap promises sorted keys — but sorted how? Those answers do not come from the collection. They come from your class.

It is also the highest-value lesson for interviews and for real bugs. "Why isn't my object found in the set?" is the single most common Java collections question, and the answer is always here.

§2Why it exists

Two different meanings of "same"

Hold two £10 notes. Are they "the same"? It depends what you mean:

  • The same object — literally the one item, the same piece of paper. In Java that is ==: are these two references pointing at the same spot on the heap?
  • The same value — different paper, same worth, interchangeable for your purpose. In Java that is equals.

Java cannot guess which one you mean, so it gives you both and lets you define the second.

What Java does if you say nothing

Every class inherits equals and hashCode from Object. The inherited versions are identity-based: equals is just ==, and hashCode is derived from the object's identity. So two separately built objects holding exactly the same data are, by default, not equal (Oracle — Object.equals). 

Point a = new Point(1,2), b = new Point(1,2);
a == b        // false — two different objects
a.equals(b)   // false too, unless Point overrides equals

That default is right for things with an identity — a Thread, a database connection, a running order. It is wrong for value objects like a point, a money amount, an email address, an ID. For those, two instances carrying the same data should be treated as one.

Why hashCode has to come along for the ride

From Part 2, a hash lookup does two things: use hashCode to pick a bucket, then use equals inside that bucket. If you override only equals, the lookup goes to the wrong bucket first — and never even reaches your clever equals. The object is there, in the set, and yet contains says false. Hence the contract.

§3How it works

The lookup path, and where it breaks

The equals contract — five rules

These are not style advice. The collections rely on them, and Object's own docs state them (Oracle — Object.equals):

RuleMeansTypically broken by
Reflexivex.equals(x) is truealmost nobody
Symmetricx.equals(y) ⇔ y.equals(x)letting a subclass equal its parent, or a String-accepting equals
Transitivex=y and y=z ⇒ x=zadding a field in a subclass and comparing it
Consistentsame answer every time, unless the data changedcomparing mutable fields, or a network/clock call
Null-safex.equals(null) is false, never a crashcasting before checking the type

The hashCode contract — three rules

  1. Consistent. Called twice on an unchanged object, it returns the same number.
  2. Equal ⇒ same hash. If a.equals(b), then a.hashCode() == b.hashCode(). This is the one that breaks collections.
  3. Unequal objects may share a hash — allowed, but spreading them out improves performance.
Read the arrow carefully. Equal ⇒ same hash. The reverse is not required: same hash does not mean equal. You saw that in Part 2 — "Aa" and "BB" share hash 2112 and are still different keys. That is why the bucket is only step one, and equals is step two (Oracle — Object.hashCode).

How to write them (the boring, correct shape)

@Override public boolean equals(Object o) {
    if (this == o) return true;                 // 1 fast path for the same object
    if (!(o instanceof Point)) return false;    // 2 handles null AND the wrong type
    Point p = (Point) o;                        // 3 safe: the check above passed
    return x == p.x && y == p.y;                // 4 compare the fields that define identity
}

@Override public int hashCode() {
    return Objects.hash(x, y);                  // 5 the SAME fields, in any order
}
Line 1 is purely a speed shortcut. Line 2 earns its keep twice over: instanceof is false for null, so the null rule is handled free, and it blocks the ClassCastException that a blind cast on line 3 would cause. Line 4 is the actual decision — and choosing which fields belong here is a design choice, not a mechanical one (an entity usually compares only its ID; a value object compares everything). Line 5 must use the same field list, or rule 2 of the hash contract breaks. For objects, use Objects.equals(a, b) on line 4 so null fields do not blow up.
Idiom — let the language do it. On Java 16+, a record generates a correct equals, hashCode and toString from its components, and its fields are final, so it is immutable by construction — the perfect map key. record Point(int x, int y) {} replaces the entire block above. Before records, let your IDE or Lombok generate it; hand-written versions rot when someone adds a field. See lesson 12.

Mutability: the quiet killer

A hash collection computes the bucket once, when you insert. It does not watch your object afterwards. So if you change a field that feeds hashCode, the entry is now sitting in a bucket that no longer matches its hash: the map cannot find it, and it cannot be removed either — it just occupies memory. You will see this happen in §7.

Rule: keys and set elements should be immutable, or at least never mutated in their equality fields while stored. This is exactly why String makes such a good key.

Ordering — two different tools

ComparableComparator
Livesinside the classoutside, as a separate object
MethodcompareTo(other)compare(a, b)
How manyexactly one — the "natural" orderas many as you like
Use whenthere is one obvious order (numbers, dates, text)order depends on the situation, or you cannot edit the class
ExampleString, Integer, LocalDateby name · by age · by name then age · reversed

Both return an int, and only its sign matters: negative = first argument comes first, zero = tie, positive = second comes first.

// Java 8 comparators read like a sentence
list.sort(Comparator.comparing(User::getName)
                    .thenComparing(User::getAge)
                    .reversed());

Comparator.comparing(User::getName, Comparator.nullsFirst(Comparator.naturalOrder()));
Idiom: always use Integer.compare(a, b), never a - b. The subtraction overflows for large or negative values and silently returns the wrong sign — a bug that hides for years and then corrupts a sort.

When ordering and equality disagree

A sorted collection does not call equals at all. TreeSet and TreeMap decide duplicates purely by "did compareTo return 0?". So if the two disagree, the same two objects are "one thing" to a TreeSet and "two things" to a HashSet. The JDK is upfront about this: it recommends ordering be consistent with equals, and names BigDecimal as a deliberate exception (Oracle — Comparable). You will see the real numbers in §7.

§4When to use

  • Override both for any value object — money, coordinates, IDs, DTOs, anything you will put in a set, use as a map key, or compare in a test.
  • Override neither for things with a real identity — threads, connections, mutable JPA entities mid-transaction, anything where "two of these are never interchangeable".
  • Implement Comparable when one order is obviously the order for the type, and you own the class.
  • Pass a Comparator for everything else: sorting a table by whichever column the user clicked, ordering a third-party class, or any second/third ordering.
  • Use a record (Java 16+) whenever the class is "just data" — it hands you a correct, immutable implementation for free.

§5Explain it to a 12-year-old

Think about identical twins. Are they "the same person"? If you ask "is this literally the same human standing in front of me?" — no. That question is ==. If you ask "do these two match on everything I care about: same birthday, same face, same height?" — yes. That question is equals.

Now picture a huge school where students are sorted into rooms by the first letter of their name. To find a student you go to their room and then check faces. The room number comes from the name; the face check decides who it actually is.

Here is the disaster. Suppose you teach the school that twins count as the same person (you changed equals) but you forget to teach it that twins must go to the same room (you forgot hashCode). Now twin A is in room 3 and twin B is sent to room 9. You look in room 9, find it empty, and declare "no such student" — while the student sits happily in room 3. Nothing crashed. The answer was just wrong.

And ordering? That is the school lining students up. Comparable is the school's own default line-up rule — alphabetical, say. Comparator is you saying "no, today line up by height", which you can change any time without rewriting the school rules.

§6Connections

  • ← Part 2: this is the contract that the whole hashing machine stands on.
  • ← type system & OOP: equals/hashCode/toString live on Object, so every class already has them — you are always overriding, never inventing.
  • → strings: == vs equals on strings is this lesson applied to one class, plus the string pool making == look like it works.
  • → modern Java: record is the language saying "this pattern was so common we made it a keyword".
  • → streams: distinct() uses equals/hashCode; sorted() and min/max use comparators.
  • → architecture: "entity vs value object" is a Domain-Driven Design idea, and the choice shows up right here, in what equals compares.
  • Same idea elsewhere: Python has __eq__/__hash__ with the identical rule; C# has Equals/GetHashCode; C++ needs operator== plus std::hash. The contract is universal, not Java trivia.

§7In practice — one file, dissected

Run on JDK 1.8. Every output block is copied from a real run of code/CollectionsDemo.java.

A — both methods overridden: it just works

Set<Point> good = new HashSet<Point>();
good.add(new Point(1, 2));
good.contains(new Point(1, 2));   // a DIFFERENT object, judged equal
contains a fresh (1,2)? true
equal objects share a hash? true
The object you look up was never inserted — it is a brand-new instance. It is found because hashCode sends the search to the same bucket and equals confirms the match there. The second line is the contract itself, verified.

B — the same class minus hashCode

static final class BrokenPoint {
    final int x, y;
    @Override public boolean equals(Object o) { /* identical to Point */ }
    // no hashCode — inherits Object's identity hash
}
equals says equal?      true
contains a fresh (1,2)? false
Stare at those two lines together. The class knows the two objects are equal — line one proves it. The set still says no. Nothing threw. No warning at compile time. The lookup went to the identity-hash bucket, found it empty, and stopped — exactly the lower path in the diagram in §3.

This is why "override one, override both" is stated as a hard rule rather than a suggestion. In real code the symptom appears far from the cause: a duplicate row in the database, a cache that never hits, a distinct() that does nothing.

C — mutating a key after inserting it

MutablePoint key = new MutablePoint(1, 2);
mutable.add(key);
key.x = 99;                  // the hash changed; the entry did not move
mutable.contains(key);
contains(the very same object)? false
set is not empty though, size = 1
This one is worse than B, and it is the clearest proof that the bucket is computed once. We are not asking about a copy here — we are handing the set the exact same object it is holding, and it says no. Its new hash points at a different bucket, and nothing lives there.

The entry is now unreachable: you cannot get it, you cannot remove it, but size() still counts it and the garbage collector still keeps it alive. A slow leak that no stack trace will ever point to. Make your keys immutable.

D — one natural order, many external orders

Collections.sort(words);                              // natural: String implements Comparable
Collections.sort(words, String.CASE_INSENSITIVE_ORDER); // external rule, passed in

Collections.sort(users, Comparator.comparing(User::getName)
                                  .thenComparing(User::getAge));
natural order    = [Fig, apple, pear]
case-insensitive = [apple, Fig, pear]
name, then age   = [ana/25, ana/30, bob/25]
Line 1 looks wrong until you remember how text sorts: String's natural order is by character code, and every capital letter sorts before every lowercase one, so "Fig" beats "apple". The class only gets one natural order, and that is it.

Line 2 shows the escape hatch: pass a different rule and get a different answer, without touching String. Line 3 shows thenComparing acting as the tie-breaker — the two anas tie on name, so age decides, and 25 lands before 30.

E — when compareTo and equals disagree

BigDecimal a = new BigDecimal("1.0"), b = new BigDecimal("1.00");
a.equals(b)?       false
a.compareTo(b)==0? true
HashSet size = 2  (uses equals)
TreeSet size = 1  (uses compareTo)
The same two values, put into two sets, give two different sizes. BigDecimal.equals compares value and scale, so 1.0 ≠ 1.00; compareTo compares numeric value only, so they tie. HashSet asks equals and keeps both. TreeSet asks compareTo, sees a tie, and treats the second as a duplicate.

Neither set is buggy — they are asking different questions. The lesson is that "duplicate" is defined by the collection you chose, so keep your own classes consistent between the two unless, like BigDecimal, you have a very deliberate reason not to.

(2) Build a TreeSet<Point> with no Comparator. What happens at the first add, and why is the message about Comparable rather than equals? (3) Write a Comparator<User> as (a, b) -> a.getAge() - b.getAge() and feed it ages Integer.MIN_VALUE and 1. Does the sort come out right? Now redo it with Integer.compare.

§8Pitfalls

Overriding one and not the other. The number-one Java collections bug. Objects vanish from sets and maps, with no exception to point at the cause.
Writing public boolean equals(Point p). That is an overload, not an override — the parameter must be Object. Collections call the Object version, so yours never runs. Always write @Override; the compiler will catch it.
Using mutable fields in equals/hashCode. Change one after inserting and the entry is stranded, as in §7C.
getClass() != o.getClass() vs instanceof. The strict version keeps symmetry but breaks for proxies and subclasses (think Hibernate); instanceof is lenient but can break symmetry with subclasses. Simplest escape: make value classes final (or records) and stop worrying.
a - b inside a comparator. Overflows and returns the wrong sign for extreme values. Use Integer.compare.
An inconsistent comparator. If your compare contradicts itself, Java's sort may throw IllegalArgumentException: Comparison method violates its general contract! — usually only on large inputs, in production, never in your tests.
Assuming TreeSet uses equals. It uses compareTo/compare only. See §7E.
Putting a JPA entity with a generated ID into a HashSet before it is saved. Its ID (and so its hash) changes on persist, and the entity goes missing — the real-world version of §7C.

§9Recap

  • == asks "the same object?"; equals asks "the same value?". Object's default makes them identical.
  • Override both or neither, always using the same fields.
  • The contract: equals is reflexive, symmetric, transitive, consistent, null-safe; equal ⇒ same hashCode (never the other way round).
  • hashCode picks the bucket, equals picks the entry. Break the first and the second never runs.
  • Hash collections compute the bucket once, at insert → keys must be immutable.
  • Comparable = one natural order inside the class; Comparator = any number of external orders, chainable with thenComparing/reversed.
  • Sorted collections judge duplicates with compareTo, not equals — keep them consistent (BigDecimal shows the cost when they are not).
  • Integer.compare, never a - b. record (Java 16+) when the class is just data.

Glossary

Reference equality (==)
Do two references point at the same object?
Value equality (equals)
Do two objects carry the same meaningful data?
Value object
A class defined entirely by its data (money, point, ID) — should override both methods.
Entity
A class with its own identity that outlives its data (user, order) — usually compares by ID, or not at all.
Identity hash code
Object's default hash, derived from the object itself, not its fields.
Natural order
The single order a class defines for itself via Comparable.compareTo.
Comparator
An external ordering rule you pass in; many can exist per class.
Consistent with equals
compareTo returns 0 exactly when equals returns true. Recommended, not enforced.
Stable sort
A sort that keeps the original order of tied elements — Java's object sorts are stable.
