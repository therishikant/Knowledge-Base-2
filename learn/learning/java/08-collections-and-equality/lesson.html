Lists, Sets & Queues

Java › collections cluster · lesson 8, part 1 of 3 · DEEP — the boxes you put your data in

Collections cluster: 1. Lists, sets & queues · 2. Maps & how hashing works · 3. Equality & ordering

In one line — A program almost always holds many things, not one thing. Java gives you ready-made boxes for that. There are three shapes of box: a List (keeps order, allows copies), a Set (no copies), and a Queue (things come out in a fixed order). Each shape has a few different builds — and the only real difference between them is how they store the data inside.

§1Where it fits

This is the most-used library in all of Java. You will touch it in almost every file you ever write. It sits on top of everything you have learnt so far: it uses generics to say what it holds, it lives on the heap, and streams read from it.

The subject is big, so it is split into three small lessons:

  • Part 1 (this one) — the three box shapes: List, Set, Queue. What each promises, and which build to pick.
  • Part 2 — Map: pairs of key → value, and the hashing trick that makes lookups instant.
  • Part 3 — the two rules your own classes must follow for these boxes to work: equals/hashCode, and ordering.

§2Why it exists — the problem before the framework

Start from nothing: the plain array

Without any library, Java gives you one way to hold many things — the array:

String[] names = new String[3];
names[0] = "ana";

An array is fast, but it hurts in three ways:

  • Its size is fixed forever. You said 3. You cannot make it 4. To "add" a fourth name you must build a bigger array by hand and copy everything across.
  • It has almost no behaviour. There is no "remove this item", no "do you already contain ana?", no "sort yourself". You write all of that by hand, in every project, again and again.
  • It cannot promise anything. Want "no duplicates"? You must check it yourself on every single insert.

What people did instead (and why it hurt)

Very early Java (1.0) shipped a few helper classes — Vector, Stack, Hashtable — but they shared no common type, so you could not swap one for another. Everyone else wrote their own list class. Your MyList and my FastList had different method names, so our code could not talk. Java 2 fixed this by shipping one Collections Framework that everybody uses (Oracle — Collections, Introduction).

The one big idea: interface vs implementation

The framework splits every box into two halves, and that split is the whole point:

  • An interface says what the box promises. List promises "I keep your order, and copies are fine."
  • An implementation is how that promise is kept inside. ArrayList keeps it with an array; LinkedList keeps it with chained nodes.

So you write your code against the promise, and name the build only once — at creation:

List<String> names = new ArrayList<>();   // promise on the left, build on the right
Every other line in your program only knows that names is a List. So the day you decide LinkedList suits you better, you change one word and nothing else breaks. That is the payoff for programming to the interface (Oracle — Collection Interfaces).

§3How it works

The family tree

Everything above List/Set/Queue is shared. Collection is where the basic verbs live — add, remove, contains, size, isEmpty, iterator — so those work on any of them. Each child only adds its own promise on top.

The three promises, one at a time

1
List — "I keep your order, and copies are fine." Every element gets a position: 0, 1, 2… You can ask for "the item at 2". You can put "tea" in twice and it stays twice. Think of a shopping list or a chat history: the order means something, and repeats are real.
2
Set — "I hold each value only once." Add the same value again and the set quietly ignores it. There is no "item at position 2", because a set is about membership, not position. Think of the set of user IDs that have already voted.
3
Queue / Deque — "I hand things back in a fixed order." A Queue is a waiting line: first in, first out. A Deque ("deck") is a line you can push and pull at both ends, so one class can act as a queue or as a stack (last in, first out). Think of jobs waiting to be processed, or an undo history.

Now the builds — the only difference is storage

Here is the key insight of the whole lesson. ArrayList and LinkedList answer every question identically. Same results, always. What differs is the shape of the memory behind them — and that shape decides which operations are cheap.

How ArrayList grows (the bit people assume is magic)

An ArrayList is "resizable", but arrays are not. So how? It holds an array that is a little bigger than needed, plus a size counter. When you add:

  1. Is there a spare slot? Then write into it and bump size. Done — one step.
  2. Is it full? Then it creates a new, bigger array (about 1.5× in the OpenJDK code), copies everything across, and uses that from then on.

Step 2 is expensive, but it happens rarely, and each grow buys room for many more adds. Spread across all the adds, the cost per add is tiny. That is what "amortised O(1)" means — not "always cheap", but "cheap on average" (Oracle — ArrayList).

Idiom: if you already know roughly how many items are coming, say so — new ArrayList<>(10000). You skip every grow-and-copy round.

Why ArrayList usually wins anyway

On paper LinkedList looks great for inserts. In practice ArrayList wins most of the time, for two reasons you can feel in the benchmark in §7:

  • Memory locality. An array sits in one continuous block, so the CPU cache pulls in the neighbours for free. Linked nodes are scattered across the heap, so each hop can be a cache miss.
  • Extra objects. Every LinkedList item needs its own node object holding two extra references. More memory, and more work for the garbage collector.
Rule of thumb: start with ArrayList. Reach for LinkedList only when you genuinely need fast adds/removes at the ends — and even then ArrayDeque is usually faster.

Sets: the same three flavours

Sets come in the exact trio you will meet again for maps in Part 2:

How does a set know a value is already inside? It does not compare against every element — that would be slow. It uses the hashing trick. In fact HashSet literally wraps a HashMap inside and ignores the values. That machinery is Part 2, and the rules your class must follow for it to work are Part 3.

Queues and deques

ArrayDeque stores items in a ring buffer — an array with a "head" marker and a "tail" marker that wrap around when they reach the end. Nothing is ever shifted; only the two markers move. That makes both ends cheap, which is why it is the right pick for stacks and queues (Oracle — ArrayDeque).

§4When to use which

  • Need positions, or duplicates that matter? → List, and ArrayList unless you have a measured reason not to.
  • Need "have I seen this before?" or "drop the duplicates"? → Set. HashSet for speed, LinkedHashSet when output order must be stable (logs, reports), TreeSet when you need it sorted or need "the next value above X".
  • Processing things in arrival order? → ArrayDeque as a queue. Jobs, events, breadth-first search.
  • Undo history, bracket matching, depth-first search? → ArrayDeque as a stack. Never the old Stack class.
  • "Always give me the most urgent one"? → PriorityQueue.
  • Several threads sharing it? → the concurrent versions (CopyOnWriteArrayList, ConcurrentLinkedQueue) — see lesson 11.

§5Explain it to a 12-year-old

Picture your bedroom. You need somewhere to put your stuff, and the furniture you choose changes what is easy.

A List is a numbered shelf. Slot 1, slot 2, slot 3. You can keep two identical comics, and you can say "give me whatever is in slot 7" without looking at the rest. A Set is a sticker album: each sticker fits only once. Try to stick in a duplicate and it just will not go — which is exactly why it is perfect for "have I already got this one?" A Queue is the lunch line: whoever arrived first is served first. A Deque is an odd lunch line where people can join or leave at both ends — so you can also use it as a stack of plates, where you always take the top one.

And why two kinds of shelf (ArrayList vs LinkedList)? One is a real shelf with numbered slots: you walk straight to slot 7. The other is a treasure hunt — each box holds a note saying where the next box is. To reach box 7 you must open 1, 2, 3, 4, 5 and 6 first. But adding a box to the hunt is easy: write one new note. Numbered shelf = fast to find. Treasure hunt = fast to add in the middle. Neither is "better"; they are good at different jobs.

§6Connections

  • ← generics: List<String> is generics doing its job — the compiler stops you putting an Integer in. Because of erasure, at run time the list just holds Objects.
  • ← memory: the collection object and every element live on the heap. A long-lived collection you never clear is the most common memory leak in Java.
  • → Part 2: HashSet is a HashMap in disguise, so sets only fully make sense after you have seen hashing.
  • → Part 3: "no duplicates" means nothing until you define what "the same" means — that is equals/hashCode.
  • → streams: list.stream() starts a pipeline; collect(toList()) lands back in a collection.
  • Same idea elsewhere: Python has list / set / deque; JavaScript has Array / Set; C++ has vector / set / deque. Different spellings, identical shapes — learn them once and they travel.

§7In practice — one file, dissected

Everything below was run on JDK 1.8; every output block is copied from a real run of code/CollectionsDemo2.java.

A — a list keeps order and copies; a set does not

List<String> list = new ArrayList<String>();
list.add("tea"); list.add("coffee"); list.add("tea");

Set<String> hashSet   = new HashSet<String>();
Set<String> linkedSet = new LinkedHashSet<String>();
Set<String> treeSet   = new TreeSet<String>();
for (String s : new String[]{"tea", "coffee", "tea", "milk"}) {
    hashSet.add(s); linkedSet.add(s); treeSet.add(s);
}
list        = [tea, coffee, tea]
list.get(1) = coffee
size        = 3

HashSet       = [tea, coffee, milk]
LinkedHashSet = [tea, coffee, milk]
TreeSet       = [coffee, milk, tea]
The list kept both teas; all three sets kept one. Notice TreeSet came out alphabetically — it sorted for you without being asked. And here is a trap worth flagging now: the HashSet line happens to match insertion order on this run. That is luck, not a promise, and it can change with a different JDK or different data. Only LinkedHashSet and TreeSet actually guarantee an order.

B — the cost difference you can measure

// 100,000 items in each, then read every one by index
for (int i = 0; i < arrayList.size(); i++) sumA += arrayList.get(i);
for (int i = 0; i < linkedList.size(); i++) sumL += linkedList.get(i);
same sum?                  true
ArrayList  get(i) loop ms: 12
LinkedList get(i) loop ms: 12952
Identical answers. About a thousand times apart in time. The ArrayList jumps straight to each slot. The LinkedList restarts at the front and walks for every single get(i) — n walks of average length n/2, so the whole loop is O(n²). This is the clearest proof that the interface (List) tells you what, and the build tells you what it costs. (Fair-play note: looping a LinkedList with a for-each is fine — that walks once. It is get(i) inside a loop that kills it.)

C — one class, two jobs

Deque<String> stack = new ArrayDeque<String>();
stack.push("a"); stack.push("b"); stack.push("c");
stack.pop();   // push added at the front, pop takes the front -> "c"

Queue<String> queue = new ArrayDeque<String>();
queue.offer("a"); queue.offer("b"); queue.offer("c");
queue.poll();  // offer added at the back, poll takes the front -> "a"
stack pop order:  c, b
queue poll order: a, b
Same class, same memory layout. The only difference is which end you add to. Declaring the variable as Deque or Queue is how you tell the next reader which of the two you meant.

D — the classic crash: changing a collection while looping it

List<String> drinks = new ArrayList<String>(Arrays.asList("tea", "coffee", "milk"));
for (String d : drinks) {
    if (d.equals("tea")) drinks.remove(d);   // changing the list the loop is reading
}
removing "tea"    -> ConcurrentModificationException
removing "coffee" -> no exception, but only saw [tea, coffee]
Read those two lines carefully — the second one is the scary one.

A for-each loop secretly uses an Iterator, which remembers a modification count taken when the loop began. Change the list through the list itself and that count no longer matches, so the next next() throws ConcurrentModificationException. It is a safety alarm, not a threading problem — one single thread triggers it perfectly well.

But look at the second line. Removing the second-to-last element throws nothing at all. The size drops to 2, the cursor is already at 2, so hasNext() reports "done" and the loop quietly exits early — and "milk" is never even looked at. A silent wrong answer is worse than a crash. Never rely on the exception to catch this for you. 
// the two correct ways
Iterator<String> it = drinks.iterator();
while (it.hasNext()) { if (it.next().equals("coffee")) it.remove(); }  // the iterator removes

drinks.removeIf(d -> d.equals("coffee"));   // Java 8+, one line, preferred
iterator.remove() -> [tea, milk]
removeIf()        -> [tea, milk]
it.remove() works because the iterator updates its own expected count as it removes. removeIf does the same thing internally and reads far better.
Idiom: use removeIf. Drop down to a manual Iterator only when you need to do more than a simple test.

E — a read-only view is a promise, not a copy

List<String> readOnly = Collections.unmodifiableList(drinks);
readOnly.add("water");   // -> UnsupportedOperationException
unmodifiableList.add -> UnsupportedOperationException
Useful when you return a collection from a getter and do not want callers mutating your internals. Two warnings: it is a view, so later changes to the original drinks still show through it, and it does not freeze the elements themselves. On Java 9+, List.of(...) gives a genuinely immutable list instead (not available on the JDK 8 used here).
Predict the output, then run it. (1) Build a list of 100,000 items and time add(0, "x") 10,000 times on an ArrayList versus a LinkedList. Which wins now, and why is it the opposite of benchmark B? (2) Replace the LinkedList get(i) loop with a for-each loop. Does the thousand-fold gap survive? (Hint for both: ask "how far must it walk?" and "what has to shift?")

§8Pitfalls

Relying on HashSet order. There is none. It can differ between runs, JDK versions and data sets. If a test depends on it, the test is wrong. Use LinkedHashSet or TreeSet.
Changing a collection inside a for-each. Either an exception or — worse — a silently skipped element, as shown above. Use removeIf or the iterator.
Arrays.asList(...) is not a normal list. It is a fixed-size view onto the array, so add and remove throw UnsupportedOperationException. Wrap it: new ArrayList<>(Arrays.asList(...)).
list.remove(2) vs list.remove(Integer.valueOf(2)) on a List<Integer>. The first removes position 2; the second removes the value 2. A real and nasty production bug.
Choosing LinkedList because "inserts are O(1)". They are O(1) only once you are already at the spot. add(i, x) still walks there first, and cache misses eat the theoretical win. Measure before switching.
Using the legacy Vector / Stack. They lock on every method call — a cost even in single-threaded code — and Stack iterates bottom-up, the wrong way round for a stack. Use ArrayList and ArrayDeque.
Declaring the variable as the build. ArrayList<String> x = new ArrayList<>() leaks your choice into every signature. Declare List<String>.

§9Recap

  • The framework = interfaces (the promise) × implementations (the storage). Declare the interface; choose the build once.
  • List = order + duplicates. Set = no duplicates. Queue/Deque = a defined take-out order.
  • ArrayList = one numbered block → instant get(i); grows by copying into a bigger array (amortised O(1) add).
  • LinkedList = chained nodes → cheap at the ends, but get(i) walks. Measured: ~12 ms vs ~12,952 ms for the same loop.
  • Set flavours mirror the map flavours: HashSet (no order), LinkedHashSet (insertion), TreeSet (sorted).
  • ArrayDeque is both your stack and your queue. Prefer it over Stack/Vector.
  • Never change a collection while a for-each is reading it — use removeIf or Iterator.remove().
  • Default choice when unsure: ArrayList.

Glossary

Collection
Root interface for groups of single elements — List, Set, Queue. (Map is not one; see Part 2.)
Interface vs implementation
The promise (List) versus the storage that keeps it (ArrayList).
Iterator
The little cursor a for-each loop uses behind the scenes; it can also remove safely.
Amortised O(1)
Usually one step; occasionally expensive (a resize), but cheap averaged over all operations.
Ring buffer
An array used in a circle with head and tail markers — how ArrayDeque keeps both ends cheap.
Deque
"Double-ended queue"; add and remove at both ends, so it serves as both stack and queue.
ConcurrentModificationException
The alarm raised when a collection changes underneath an active iterator.
Fail-fast
The design choice of failing loudly and immediately instead of returning a wrong answer later.
