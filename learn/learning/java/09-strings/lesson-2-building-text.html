Building Text

Java › strings cluster · lesson 9, part 2 of 3 · DEEP — +, StringBuilder, and the everyday toolbox

Strings cluster: 1. What a String really is · 2. Building text · 3. Characters, bytes & encoding

In one line — Because a string can never be changed, every join makes a new object. One join on one line is fine — the compiler quietly uses a StringBuilder for you. A join inside a loop is not fine: it copies the whole text again on every pass. There, you must make the builder yourself, append to it, and turn it into a string once at the end.

§1Where it fits

Part 1 ended on a promise. Strings are frozen, which is wonderful for safety — but programs do need to assemble text: a CSV line, a log message, a SQL query, an HTML fragment. This lesson is how you do that without accidentally writing slow code, plus a tour of the methods you will reach for every single day.

Everything here rests on one fact from part 1: a String never changes. If you do not have that firmly in your head, go back and re-read §3.2 before continuing.

§2Why it exists — the cost of being frozen

The loop that looks innocent

Here is code that appears in almost every beginner's project:

String s = "";
for (int i = 0; i < 20000; i++) {
    s += "x";          // looks like "add one letter"
}

It does not add one letter. It cannot, because s is frozen. What actually happens on each pass is: make a fresh buffer big enough for everything so far plus one, copy every old character into it, add the new one, build a new String, and throw the previous one away as garbage.

So the work on each pass grows with what you have already built:

pass 1:  copy 0 chars
pass 2:  copy 1 char
pass 3:  copy 2 chars
...
pass n:  copy n-1 chars
------------------------------
total:   0+1+2+...+(n-1)  =  n(n-1)/2  copies

That is O(n²). For n = 20,000 it is about 200 million character copies, plus 20,000 throwaway String objects and 20,000 throwaway arrays for the garbage collector to clean up. The measured cost on JDK 8 (see §7): 470 ms for the loop above, versus 0 ms for the builder version. Same answer, same 20,000 characters.

Why Java did not just make String mutable

It could have. It would have made this loop fast — and thrown away every benefit in part 1: safe sharing, free thread safety, safe map keys, the cached hash, the pool. Java's choice is to keep the common case (passing text around) safe and give you a separate tool for the rare case (assembling text). That tool is StringBuilder.

§3How it works

3.1 What the compiler already does for you

A single expression like "Hi " + name + ", you are " + age is not slow. On JDK 8 the compiler rewrites it into one builder behind your back (JLS SE 8 §15.18.1: "an implementation may choose to perform conversion and concatenation in one step ... using a StringBuffer or similar"): 

// what you write
String msg = "Hi " + name + ", you are " + age;

// what javac actually emits (JDK 8)
String msg = new StringBuilder()
        .append("Hi ").append(name)
        .append(", you are ").append(age)
        .toString();

You can see this yourself with javap -c YourClass: the bytecode is full of invokevirtual StringBuilder.append calls.

Java 9 changed the machinery again. From JDK 9, javac emits a single invokedynamic instruction and lets the runtime build an optimal recipe for that exact concatenation — often beating the hand-written builder (JEP 280 — Indify String Concatenation). The advice is unchanged: write the readable + on one line, and use a builder for loops.

Now you can see exactly why the loop is different. The rewrite is per expression, and the expression lives inside the loop body, so you get a new builder every single pass:

for (...) {
    s = new StringBuilder().append(s).append("x").toString();  // built and thrown away, n times
}
The rule in one sentence: + is fine when the whole join happens in one expression; make the builder yourself the moment the join is spread across several statements or passes of a loop.

3.2 Inside a StringBuilder

A builder is the mutable twin of a String. It holds a character array and a count of how much of it is used:

class StringBuilder {       // (simplified, from AbstractStringBuilder)
    char[] value;            // NOT final — this is the whole point
    int count;               // how many cells are actually in use
}

Three facts follow from that, and they explain everything a builder does:

1
It has spare room. new StringBuilder() starts with room for 16 characters (Oracle, StringBuilder API). append just writes into the next free cell and bumps count. No allocation, no copying.
2
When it runs out, it doubles. The new capacity is (old * 2) + 2. Measured in §7: capacity 16 → append a 17th character → capacity becomes 34. Because it doubles rather than growing by one, the copies get rarer and rarer, and the total copying over n appends stays O(n).
3
toString() copies once. It must, because the String it returns has to be frozen and the builder will keep mutating. So building text costs exactly one real copy — at the end — instead of one per step.
Size it up front if you know. new StringBuilder(1024) skips the doubling entirely. A nice micro-win in hot code, and free to write.

3.3 Chaining: why append returns the builder

append changes the builder and returns this — the very same object. That is what makes sb.append("a").append("b") work. It is not making copies; every link in the chain is the same object. Verified in §7: b == b.append("c") prints true.

This matters for a subtle reason. Methods like reverse() and deleteCharAt() mutate in place, so unlike strings there is no new object to assign. Writing sb.reverse(); on its own line is correct here — the exact opposite of the string rule from part 1.

StringStringBuilder

A builder is not a string. StringBuilder does not override equals or hashCode, so two builders with identical contents are never "equal", and a builder is useless as a map key. Call toString() the moment you want to compare or store it.

3.4 StringBuffer — the older, slower twin

StringBuffer arrived in Java 1.0 and every one of its methods is synchronized, so it is thread-safe. That was a reasonable default in 1996. But almost all text building happens inside one method, on one thread, so almost everybody was paying for a lock they did not need. Java 5 added StringBuilder — the identical API with the locks removed (Oracle, StringBuilder API: "This class provides an API compatible with StringBuffer, but with no guarantee of synchronization ... it is recommended that this class be used in preference").

Use StringBuilder. Choose StringBuffer only if one buffer is genuinely shared and appended to by several threads — which, in practice, is a design you should probably change anyway.

3.6 A piece of history worth knowing: substring

Before Java 7u6, substring did not copy. The small string shared the big string's array and just kept an offset and a length. Clever — until you read a 10 MB file, took a 5-character substring, and the whole 10 MB array stayed in memory because the little string still pointed at it. A famous memory leak. Since 7u6 substring always copies the characters it needs, so the big array can be collected (OpenJDK bug JDK-6924259).

This is a good illustration of the trade this whole lesson is about: sharing costs no copy but holds memory; copying costs time but frees memory. Java chose copying.

Never build SQL, HTML, or shell commands by concatenation with user input. "SELECT * FROM users WHERE name='" + input + "'" is the textbook SQL injection hole — the user types ' OR '1'='1 and reads your whole table. Use parameter placeholders (PreparedStatement), or a proper escaping library for HTML. Builders make this easier to get wrong, so flag it in review.

§5Explain it to a 12-year-old

Strings are words carved in stone (part 1). Now imagine your homework is to write a 500-word essay, one word at a time, in stone.

If you only have stones, here is what each new word costs you: fetch a bigger slab, re-carve every word you have already written, then carve the new one, and throw the old slab away. By word 500 you are re-carving 499 words to add one. You will be there all day, and the yard is full of discarded slabs.

A StringBuilder is a whiteboard. You write the next word in the empty space at the end. Nothing is re-written. If you run out of board, you get a board twice as big — which happens rarely, and less and less often. When the essay is finished, you take one photo of the whiteboard. That photo is your stone.

"So why not write everything on whiteboards?" Because whiteboards are not safe to hand to other people — anyone can rub out your words, and two people writing on one board at once makes a mess. Stones are safe to lend. So: whiteboard while you are working, stone the moment you are done.

§7In practice — one file, dissected

Full source: code/StringDemo2.java, compiled and run on JDK 1.8.0_411.

long t1 = System.nanoTime();
String s = "";
for (int i = 0; i < 20000; i++) s += "x";
long t2 = System.nanoTime();

StringBuilder sb = new StringBuilder();
for (int i = 0; i < 20000; i++) sb.append("x");
String s2 = sb.toString();
The same job twice. Both produce 20,000 characters. The first does ~200 million character copies and creates 20,000 dead objects; the second writes into one buffer that doubles about 11 times. The measured gap is 470 ms vs 0 ms. This is not a micro-optimisation — it is two different complexity classes. (This is a rough wall-clock timing, not a JMH benchmark; the point is the shape of the difference, not the exact millisecond.)
StringBuilder b = new StringBuilder("ab");
b == b.append("c")      // true — append returns THIS, not a copy
b.reverse()              // mutates in place
Proof that a builder is mutable: the object before and after append is the same object. That is what makes chaining work. Note the role reversal from part 1 — here, calling a method on a line by itself does change things.
StringBuilder g = new StringBuilder();
g.capacity()                    // 16 — the default spare room
g.append("1234567890123456");  // exactly fills it
g.capacity()                    // still 16
g.append("7");                 // one too many -> grow
g.capacity()                    // 34  =  16 * 2 + 2
The doubling rule, observed rather than remembered. Doubling is what keeps the total cost of n appends linear: each character is copied only a handful of times across the whole run, not once per append.
String csv = "  ana,bob , cara  ";
csv.trim()                          // "ana,bob , cara"
csv.trim().split("\\s*,\\s*")    // regex: comma with optional spaces around it
String.join(" | ", parts)
csv.trim().replace(',', ';')
"hello world".substring(6)
"hello world".indexOf('o')        // 4 — the FIRST one
"apple".compareTo("banana")      // -1 — 'a' is one before 'b'
String.format("%s scored %.1f%%", "ana", 91.25)
The toolbox in action. Three things to notice: the split pattern is a regex, which is why it can swallow the stray spaces in "bob , cara"; compareTo returns a difference, not a boolean, which is exactly what sorting needs; and %% is how you print a literal percent sign. The last line also rounds 91.25 to 91.3.
System.out.println("csv still : [" + csv + "]");
The punchline. After trim, split and replace, the original csv still has every one of its leading and trailing spaces. Nothing was modified. Everything was copied.

§8Pitfalls

1. + inside a loop. The headline mistake. O(n²) time plus a flood of garbage. Hoist a StringBuilder outside the loop.
2. Creating the builder inside the loop. A real version of the same bug: for(...) { StringBuilder sb = new StringBuilder(); ... } throws the buffer away each pass. Declare it before the loop.
3. Forgetting split and replaceAll are regex. Splitting on ".", "|" or "$" will not do what you expect. Escape them ("\\.") or use Pattern.quote(text).
4. Assuming split keeps trailing empties. "a,b,,".split(",") gives ["a","b"] — trailing empty strings are dropped. Pass a negative limit, split(",", -1), to keep them.
5. indexOf returning -1. Feeding that straight into substring throws StringIndexOutOfBoundsException. Always check for -1 first.
6. Using a StringBuilder where a String belongs. It has no useful equals, it is not thread-safe, and it cannot be a key. Call toString() as soon as the text is finished, then pass the string around.
7. Concatenating user input into SQL/HTML/shell commands. Injection. Use PreparedStatement parameters or a proper escaper — never string glue.
8. Logging with + on a disabled level. log.debug("x=" + expensive()) builds the whole message even when debug is off. Use the placeholder form, log.debug("x={}", value).

§9Recap

  • Because strings are frozen, every join creates a new object. That is the one fact behind this whole lesson.
  • + in one expression is fine — the compiler turns it into one builder (JDK 8) or one invokedynamic (JDK 9+).
  • + in a loop is O(n²): each pass copies everything so far. Measured: 470 ms vs 0 ms for 20,000 appends.
  • StringBuilder = mutable char[] + count. Starts at capacity 16, grows old*2+2, copies once in toString(). Net: O(n).
  • append returns this, which is why chaining works and why a builder mutates in place — the opposite of String.
  • StringBuffer is the synchronized older twin. Prefer StringBuilder unless one buffer is genuinely shared across threads.
  • Every String method returns a new string; the original is never touched.
  • split and replaceAll take regex; replace takes plain text.
  • Never glue user input into SQL, HTML, or shell commands.

Glossary

Concatenation
Joining two pieces of text, written with + in Java.
Capacity
How many characters a builder's array can hold before it must grow. Not the same as length.
Amortised O(1)
Each append is cheap on average, because the rare doubling cost is spread over many cheap appends.
Constant folding
The compiler joining constants at compile time (see part 1, §3.5).
invokedynamic
A bytecode instruction that lets the runtime decide how to implement a call — used for string concatenation from Java 9 (JEP 280).
Regex
Regular expression: a pattern language. split and replaceAll use it; replace does not.
Synchronized
Guarded by a lock so only one thread at a time may run the method — what StringBuffer adds over StringBuilder.
