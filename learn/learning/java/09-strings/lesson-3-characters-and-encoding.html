Characters, Bytes & Encoding

Java › strings cluster · lesson 9, part 3 of 3 · DEEP — what a "letter" really is underneath

Strings cluster: 1. What a String really is · 2. Building text · 3. Characters, bytes & encoding

In one line — A computer stores only numbers, so text needs a rulebook that says which number means which letter. Java holds text as 16-bit char units internally, which means length() counts storage slots, not the letters you see — an emoji takes two. And the moment text leaves Java (a file, a socket, a database) it must be turned into bytes, which requires you to name the rulebook. Name it. Always. UTF-8.

§1Where it fits

Part 1 said a string holds "letters". Part 2 showed how to assemble them. Both were polite lies: Java does not store letters, it stores numbers. This lesson opens that box.

It matters more than it sounds. The bug where a name arrives as cafÃ© instead of café, the bug where a password check fails only in Turkey, the bug where cutting a string in half splits an emoji into two broken halves — all three are in this lesson, and all three are ordinary production bugs, not trivia.

§2Why it exists — numbers pretending to be letters

The first rulebook: ASCII

Memory holds numbers. To store the letter A you must agree on a number for it. In 1963 everyone agreed on ASCII: A = 65, a = 97, 0 = 48. 128 values, fitting in 7 bits. Enough for English. Not enough for é, ü, ß, ñ, α, 日 or 😀.

The dark age: one byte, many rulebooks

The 1980s answer was to use the spare 128 values of a byte for "the rest" — but every region chose a different "rest". Western Europe used ISO-8859-1, Cyrillic used ISO-8859-5, Windows used its own code pages. The same byte 0xE9 meant é in one rulebook and something else entirely in another. A document was only readable if you already knew which rulebook made it — and that information was never stored in the file. This is where the word mojibake (text turned to garbage) comes from.

The fix: Unicode

Unicode gives every character in every writing system one permanent number, called a code point, written U+0041 (A), U+00E9 (é), U+1F600 (😀). One global rulebook, with room for about 1.1 million characters.

But Unicode only assigns the numbers. It does not say how to store them. That second job is an encoding, and there are several: UTF-8, UTF-16, UTF-32. This is the distinction people trip over, so hold on to it:

Unicode = which number means which character. Encoding = how that number is written as bytes. They are two different decisions.

Java's choice, and the accident of history

Java was designed in the early 1990s, when Unicode still fit in 16 bits. So Java made char 16 bits and declared the problem solved. Then Unicode grew past 65,536 characters — and Java was stuck. Changing char would have broken every Java program on earth.

So Java kept char at 16 bits and adopted UTF-16: characters that fit in 16 bits use one char; everything beyond uses two chars together, called a surrogate pair (Oracle, Character API — Unicode Character Representations). That compromise is the direct cause of the "emoji has length 2" surprise below.

§3How it works

3.1 Three layers, and three different counts

Whenever text confuses you, it is nearly always because you mixed up two of these layers:

Java gives you a different method for each count, and they do not always agree:

QuestionMethodFor "A" + 😀
How many storage slots?length()3
How many real characters?codePointCount(0, length())2
How many bytes in a file?getBytes(UTF_8).length5

All three numbers are verified output in §7. None of them is "wrong" — they answer different questions.

3.2 Surrogate pairs — why half a character exists

Unicode permanently reserved the range U+D800–U+DFFF for this trick. Those values are not characters; they only ever appear in pairs. A high surrogate (D800–DBFF) followed by a low surrogate (DC00–DFFF) together encode one code point above U+FFFF.

In §7 you will see charAt(1) return 55357, which is 0xD83D — a high surrogate. On its own it is meaningless: it is half a character. But codePointAt(1) returns 128512 = U+1F600, because it reads both slots and reassembles them.

This is why naive string surgery breaks. substring(0, 2) on text ending mid-pair, charAt in a for loop, reverse() on a builder, or truncating a tweet to 140 chars — each can slice a pair in half and produce a broken character. Characters outside the 16-bit range include emoji, many Chinese characters, musical symbols and most historic scripts, so this is no longer an exotic case.
Safe ways to walk text: use for (int cp : s.codePoints().toArray()) (Java 8+), or s.offsetByCodePoints(i, 1) to step an index, or java.text.BreakIterator when you need what a user would call a character (which can be several code points — think flag emoji or an accent written as letter + combining mark).

3.3 Encoding: the only moment bytes appear

Inside the JVM you never see bytes. They appear at exactly two moments: when text leaves (file, socket, database, console) and when it arrives. Those two moments are encoding and decoding, and both need a named charset.

Look at the measured byte counts for café:

CharsetBytesNotes
UTF-863 61 66 C3 A9 — 5ASCII stays 1 byte; é needs 2. The web standard.
ISO-8859-163 61 66 E9 — 4Fits only 256 characters; cannot hold 😀 at all.

UTF-8 is variable width: 1 byte for ASCII, 2 for most European and Middle Eastern letters, 3 for most CJK, 4 for emoji. That is why it won — English text costs nothing extra, yet everything is representable.

3.4 The platform default charset is a trap

Every byte/text method has an overload that takes no charset: s.getBytes(), new String(bytes), new FileWriter(f), new InputStreamReader(in). They do not skip the charset — they silently use the platform default.

On the machine this lesson was run, that default is windows-1252. On your colleague's Linux CI box it is UTF-8. So the same code writes different bytes on different machines, and the bug only appears once a non-ASCII character shows up — usually in production, usually in a customer's name.

Rule: never call a charset-less overload. Write StandardCharsets.UTF_8 every time. It is a constant, not a string name, so it cannot be misspelled and throws no checked exception (Oracle, StandardCharsets).
// fragile — depends on the machine
byte[] b = s.getBytes();
String t = new String(b);

// correct — says what it means, everywhere
byte[] b = s.getBytes(StandardCharsets.UTF_8);
String t = new String(b, StandardCharsets.UTF_8);
Java 18 finally fixed the default. Since Java 18 the default charset for file and stream APIs is UTF-8 everywhere, regardless of the operating system (JEP 400 — UTF-8 by Default). Keep writing the charset explicitly anyway: it still documents intent, and most real code bases are not on 18+ yet.

3.5 Case conversion depends on language

toUpperCase() with no argument uses the machine's default locale. In Turkish, lower i upper-cases to İ (dotted capital I, U+0130), not I. Measured in §7: "i".toUpperCase(new Locale("tr")) gives character 304, while Locale.ROOT gives 73.

This is the legendary "Turkish i" bug. Code like if (header.toUpperCase().equals("CONTENT-TYPE")) silently fails on a machine with a Turkish locale — and only there.

Rule: for machine-facing text (protocol headers, file extensions, enum names, commands) always pass Locale.ROOT. Use the user's locale only for text shown to that user. And for case-insensitive comparison, prefer equalsIgnoreCase over converting both sides.

3.6 Secrets do not belong in a String

Pulling together three facts you already know:

  1. A string cannot be changed, so you cannot overwrite it.
  2. It lives until the GC decides to collect it — you cannot force that.
  3. A literal password would even be pooled, so it lives as long as the program does.

Result: a password in a String sits in memory for an unknown length of time and will appear in any heap dump taken in between. That is why JPasswordField.getPassword() returns a char[] and the JCA guide recommends arrays for secrets: you can overwrite an array the instant you are done (Oracle, JCA Reference Guide). 

char[] password = readPassword();
try {
    login(password);
} finally {
    Arrays.fill(password, '\0');   // the secret is gone from memory now
}

§5Explain it to a 12-year-old

Computers can only remember numbers. So long ago people made a codebook: 65 means A, 66 means B. That worked fine until the rest of the world wanted to write too — and every country wrote its own codebook. The number 233 meant "é" in France's book and something completely different in Russia's. If you opened a French file using the Russian book, you got gibberish. Nobody wrote on the file which book they had used.

Unicode is the world finally agreeing on one codebook with a number for every character on Earth, including emoji. But there is still a second question: how do you write those numbers down as bytes? That is the encoding, and UTF-8 is the one everyone uses now. It is clever — plain English letters still take one byte, and only unusual characters take more.

Java has one quirk. It was built when people thought every character would fit in a two-byte box. Then emoji arrived and did not fit. Rather than change every box, Java splits a big character across two boxes. So if you ask Java "how long is 😀?" it answers "2" — it is counting boxes, not characters. And if you cut the text between those two boxes, you get half an emoji, which is nonsense.

"So why can't Java just count properly?" It can — you have to ask with the right method (codePointCount instead of length). The old answer has to stay for the sake of every program written in the last thirty years.

§6Connections

  • ← part 1: char[] (JDK 8) or byte[] + coder (JDK 9+) is the storage this lesson decodes.
  • ← part 2: substring, reverse and index arithmetic are exactly the operations that break on surrogate pairs.
  • ← type system: char is a 16-bit unsigned primitive — the only unsigned type in Java. (int) c gives you its number.
  • → exceptions: strict decoding can throw CharacterCodingException; the String constructors instead replace bad bytes with U+FFFD and stay silent — a design trade-off worth noticing.
  • → modern Java: text blocks, strip, repeat, and UTF-8 by default.
  • → tooling: set -encoding UTF-8 on javac and project.build.sourceEncoding in Maven, or your build is machine-dependent too.
  • Same idea elsewhere: Python 3 strings are sequences of code points (so len("😀") is 1) and bytes are a separate type; JavaScript made the same UTF-16 choice as Java, so "😀".length is 2 there as well; Go strings are UTF-8 bytes, and range walks code points. The layers are universal — only the default answer changes.

§7In practice — one file, dissected

Full source: code/StringDemo3.java, compiled and run on JDK 1.8.0_411. Non-ASCII is written with \u escapes and results are printed as numbers, so the console's own encoding cannot distort the evidence.

String accented = "caf\u00e9";       // c a f e-acute
String emoji    = "A\uD83D\uDE00";      // 'A' + grinning face
Two test subjects. é is U+00E9 — inside the 16-bit range, so it is one char. 😀 is U+1F600 — outside it, so it is written as the surrogate pair D83D DE00: two chars for one character.
accented.length()                          // 4
emoji.length()                             // 3   <- not 2!
emoji.codePointCount(0, emoji.length())    // 2   <- the real answer
(int) emoji.charAt(1)                    // 55357 = 0xD83D, half a character
emoji.codePointAt(1)                       // 128512 = U+1F600, both halves read together
The core lesson, in five lines. length() counts storage slots. codePointCount counts characters. charAt can hand you a meaningless half; codePointAt never does. If a method name says "char", assume it means "16-bit slot".
byte[] utf8   = accented.getBytes("UTF-8");        // 5 bytes: 99 97 102 -61 -87
byte[] latin1 = accented.getBytes("ISO-8859-1");   // 4 bytes: 99 97 102 -23
Same text, two rulebooks, two different byte strings. In UTF-8 the é became two bytes (-61 -87 is 0xC3 0xA9 — Java bytes are signed, which is why they print negative). In ISO-8859-1 it fits in one byte (-23 = 0xE9). ASCII letters are identical in both — that is UTF-8's whole design.
new String(utf8, "ISO-8859-1").length()   // 5 — mojibake, the pair read as 2 letters
new String(utf8, "UTF-8").length()        // 4 — correct
new String(utf8, "UTF-8").equals(accented) // true — a perfect round trip
The mojibake bug, reproduced in three lines. The bytes were never corrupted. They were simply read with the wrong rulebook, and 4 characters became 5. Encode and decode must agree.
Charset.defaultCharset()   // windows-1252 on this machine
And there is the trap from §3.4, live. Any charset-less call on this machine silently writes windows-1252 — which cannot even represent 😀.
(int) "i".toUpperCase(new Locale("tr")).charAt(0)   // 304 = 'I-with-dot'
(int) "i".toUpperCase(Locale.ROOT).charAt(0)        // 73  = plain 'I'
The Turkish-i bug in two lines. The same method, the same input, two different answers — chosen by a machine setting you do not control. Pass Locale.ROOT for anything a machine will read.
char[] password = {'s','3','c','r','e','t'};
Arrays.fill(password, '\0');   // prints [, , , , , ] — the secret is gone
The thing a String can never do. The printed output shows six empty slots: the characters really were overwritten in place. With a String the old letters would still be sitting in the heap, waiting for a GC that may not come for minutes.

Predict, then run.
  1. emoji.substring(0, 2) — what is its length, and what does codePointCount say about it? Is the result valid text?
  2. new StringBuilder("A\uD83D\uDE00").reverse().toString() — is the emoji still intact? (reverse is specified to keep surrogate pairs together; verify that it really does.)
  3. "\uD83D\uDE00".getBytes("ISO-8859-1") — ISO-8859-1 has no emoji. What bytes come out, and is the damage recoverable?
  4. Print Integer.toHexString(55357) and check it against the range D800–DBFF. Is it a high or a low surrogate?

§8Pitfalls

1. Any charset-less call. getBytes(), new String(bytes), FileWriter, FileReader, InputStreamReader, PrintWriter. All silently platform-dependent before Java 18. Pass UTF_8.
2. Treating length() as a character count. Wrong for every emoji and many scripts. Use codePointCount for limits, and remember a user-visible "character" may still be several code points.
3. Cutting text at an arbitrary index. Truncating a message to N chars can split a surrogate pair and produce a broken character. Use offsetByCodePoints, or BreakIterator for user-facing text.
4. toUpperCase() / toLowerCase() with no locale. The Turkish-i bug. Pass Locale.ROOT for machine-facing text.
5. Double-encoding. Taking bytes that are already UTF-8, decoding them as ISO-8859-1, then re-encoding as UTF-8. You get Ã© where é should be, and it is a pain to unpick. Fix it at the one layer that is wrong, not by adding another conversion.
6. Forgetting the other charsets in the stack. The database column and connection, the HTTP Content-Type header, the HTML <meta charset>, the terminal, and the compiler's -encoding flag each have their own setting. One mismatch anywhere produces mojibake. Set them all to UTF-8.
7. Secrets in a String. Unwipeable and possibly pooled. Use char[] and clear it in a finally.
8. Assuming trim() removes all whitespace. trim only removes characters ≤ U+0020, so a non-breaking space survives it. Java 11's strip is the Unicode-aware version.

§9Recap

  • Computers store numbers. Unicode says which number is which character; an encoding says how that number becomes bytes. Two separate things.
  • Java stores text as UTF-16: one char for most characters, a surrogate pair (two chars) for anything above U+FFFF.
  • length() counts char slots. codePointCount() counts real characters. For "A"+😀 they are 3 and 2.
  • charAt can return half a character; codePointAt cannot. Walk text with codePoints().
  • Bytes appear only at the boundary. Always name the charset — StandardCharsets.UTF_8. The platform default differs per machine (windows-1252 here) until Java 18.
  • Encoding and decoding must use the same rulebook, or you get mojibake. The bytes are never corrupted — only misread.
  • Case conversion is locale-sensitive. Use Locale.ROOT for machine-facing text; that is the Turkish-i bug.
  • Never keep a secret in a String. Use a char[] you can wipe.

Glossary

Character set (charset)
A named rulebook mapping characters to bytes, e.g. UTF-8, ISO-8859-1.
Unicode
The standard assigning a unique number (code point) to every character.
Code point
One Unicode number, e.g. U+1F600. What a human calls "a character".
Code unit
One storage slot of the encoding. In Java that is a 16-bit char.
UTF-16
Java's in-memory encoding: 1 or 2 code units per code point.
UTF-8
Variable-width byte encoding, 1–4 bytes per code point. The web default.
Surrogate pair
Two chars in the range D800–DFFF that together encode one code point above U+FFFF.
BMP
Basic Multilingual Plane — code points U+0000–U+FFFF, the ones that fit in a single char.
Mojibake
Garbled text caused by decoding bytes with the wrong charset.
Locale
Language and region settings that change case conversion, sorting and formatting.
Encode / decode
Text → bytes / bytes → text.
