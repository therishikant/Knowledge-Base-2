What a String Really Is

Java › strings cluster · lesson 9, part 1 of 3 · DEEP — the most-used type in the language

Strings cluster: 1. What a String really is · 2. Building text · 3. Characters, bytes & encoding

In one line — A String is a box of letters that can never be changed. Once Java makes one, nobody can edit a single letter inside it. Every method that looks like it edits a string actually hands you a brand-new string and leaves the old one alone. This one rule explains everything else in this lesson: why strings are safe to share, why Java keeps one copy of repeated text, and why == gives such strange answers.

§1Where it fits

Text is the thing your program handles most. Names, messages, file paths, JSON, SQL, log lines, HTTP headers — all of it is text. In Java, all of it is String.

This sits right on top of everything you have learnt so far. A string is an object, so a String variable holds an arrow to it, not the letters themselves. It lives on the heap, so the garbage collector cleans it up. And it is the most common map key in all of Java. By the end of this cluster you should be able to answer, from first principles, the question every Java interview asks: "what is the difference between == and equals?"

The subject is big, so it is split into three small lessons:

  • Part 1 (this one) — what a string is made of, why it cannot be changed, the shared pool, and == vs equals.
  • Part 2 — how to actually build and slice text: +, StringBuilder, and the everyday method toolbox.
  • Part 3 — what a letter is underneath: characters, Unicode, bytes, and encoding.

§2Why it exists — the problem before String

Start from nothing: text as a bag of letters

Suppose Java had no String class. The only way to hold the word "hello" would be an array of letters: 

char[] greeting = {'h','e','l','l','o'};

This works. It is exactly what the C language does. But it hurts in four ways.

1
It has no behaviour. There is no "make this upper case", no "does this start with 'he'?", no "split this on commas". You would write every one of those by hand, in every project, forever.
2
Anyone can edit it behind your back. An array is mutable. If you pass greeting to a method, that method can do greeting[0] = 'j'. Your variable now says "jello" and you never asked for it. You could never hand your text to code you do not control.
3
It cannot be a safe key. Think of a HashMap. You file a value under the key "alice". A map finds things by the key's hash number. If someone later edits the letters of that key, the hash changes, and the map can no longer find its own entry. The value is lost inside the map.
4
It cannot be trusted across a security check. Imagine code that checks isAllowed(path) and then opens path. If path can be edited, another thread can change it in between the check and the open. You checked one file and opened a different one. This class of bug has a name: time-of-check to time-of-use.

The fix: make editing impossible

Java's answer is blunt and very effective. The class is declared public final class String, the letters are kept in a private final array, and not one single method writes to that array (Oracle, String API: "Strings are constant; their values cannot be changed after they are created"). The array is never handed out, so nobody outside can reach it.

All four problems dissolve at once:

  • You can hand a string to any method, even untrusted code, and it comes back untouched. No copying needed.
  • Many threads can read the same string at the same time with no locks. An object that cannot change is automatically thread-safe.
  • It is a perfect map key — its hash can never go stale.
  • Because the letters are frozen, two strings with the same letters are interchangeable, so Java can quietly keep one shared copy and save memory. That is the pool, below.
The trade you make. Immutability is not free. "Changing" a string means building a whole new one, so a loop that keeps appending creates a mountain of garbage. Java's answer to that is StringBuilder — a separate, mutable class — which is all of part 2.

§3How it works

3.1 What is actually inside a String object

A String is an ordinary object on the heap. Nothing magic. On JDK 8 it holds exactly two interesting fields: 

public final class String {
    private final char[] value;   // the letters (JDK 8)
    private int hash;             // cached hashCode, 0 until first asked
}

So a string variable is really a chain of three things: variable → String object → character array.

JDK 9 changed the storage, not the idea. Since Java 9 the field is a byte[] plus a one-byte coder flag. Text that is all Latin-1 then uses one byte per letter instead of two, roughly halving the memory most applications spend on text. This is called compact strings (JEP 254). Nothing in your code changes — the class is still immutable and the API is identical.

3.2 What "immutable" actually feels like

Every method on String that sounds like an edit — concat, toUpperCase, replace, trim, substring — builds a new string and returns it. The one you called it on is untouched. This is the single most common beginner bug in Java: 

String s = "hello";
s.toUpperCase();              // result thrown away! s is still "hello"
System.out.println(s);        // hello

s = s.toUpperCase();          // correct: point s at the NEW string
System.out.println(s);        // HELLO

Read the second version carefully. The old "hello" object did not change. You moved the arrow s so it points at a different object. The original "hello" is still out there, unchanged, until the garbage collector notices nobody is pointing at it.

3.3 The string pool — one copy of repeated text

Now the pay-off. Because strings can never change, two strings with the same letters behave identically forever. So why store "hello" a thousand times if your program writes it a thousand times?

Java keeps a hidden table called the string pool (also: the intern table). Every string literal you type in your source — anything in double quotes — is put in that table once. Every other place in your whole program that types the same literal gets a pointer to that same one object (JLS §3.10.5: string literals "are 'interned' so as to share unique instances").

But if you write new String("hello"), you are explicitly ordering Java to build a fresh object. It obeys. You now have two objects with identical letters: the pooled one, and your private one.

Where does the pool live? Up to Java 6 it lived in PermGen, a small fixed area, so interning too much could blow up the JVM. Since Java 7 interned strings live in the normal heap, so they can be garbage collected like anything else (Oracle, JDK 7 performance enhancements). That ties straight back to lesson 3.

3.4 == versus equals — the question every interview asks

Two different questions, and people confuse them constantly:

a == ba.equals(b)
Asks"Are these the same object?""Do these have the same letters?"
ComparesThe two arrowsCharacter by character
CostOne instructionUp to the length of the text
You want thisAlmost never, for textAlmost always

Here is the trap. Because of the pool, == accidentally works for literals typed in your source. So beginners use it, every test passes, and then it fails in production the first time a string arrives from a user form, a file, a database, or a network call — because those strings are built at run time and are not in the pool.

Rule with no exceptions: compare text with equals (or equalsIgnoreCase). If you ever feel a genuine need for == on strings, you are either writing the JDK or you are wrong.

3.5 Compile time versus run time — why "ja" + "va" is special

If every part of a join is a constant the compiler can work out by itself, the compiler does the join while compiling and stores the finished text as one literal — which means it lands in the pool. This is called constant folding (JLS §15.28, constant expressions).

If any part is an ordinary variable, the compiler cannot know its value yet, so the join happens while the program runs — producing a brand-new object that is not in the pool. 

              "java" == "ja" + "va"      // true  — both constants, folded at compile time
String var = "ja";
              "java" == var + "va"       // false — joined at run time, new object
final String con = "ja";
              "java" == con + "va"       // true  — a final local holding a literal IS a constant

That third line surprises almost everyone. A final local variable initialised with a literal counts as a constant expression, so the compiler folds it too. All three results are verified output in §7.

3.6 The cached hash code

String.hashCode() walks every character, so it costs time proportional to the length. Because the letters can never change, the answer can never change — so String computes it once and stores it in that hash field. Every later call is instant. This is exactly why a HashMap with string keys stays fast even when the keys are long (Oracle, String.hashCode). Immutability is what makes that cache legal — a mutable class could never do it.

§5Explain it to a 12-year-old

A String is a word carved into stone. Once it is carved, nobody can rub out a letter. If you want "HELLO" instead of "hello", you do not fix the old stone — you carve a brand-new one and look at that instead. The old stone just sits there until the town cleaner takes it away.

Because stones never change, the town keeps one shared stone for each common word in the main square. That is the pool. Everyone who writes "hello" is pointing at that one square stone. That is why two people's "hello" are literally the same stone.

But if you insist — new String("hello") — the mason carves you a private "hello" stone for your own garden. It reads exactly the same. It is not the same stone. So "is it the same stone?" (==) says no, while "does it say the same word?" (equals) says yes. Almost always you care about the word, not the stone.

"But why not just let us edit the stone?" Because you lend your stones to other people all the time. If they could re-carve them, you would hand someone your name and get back something else. Frozen stones are safe to lend, safe for many people to read at once, and safe to use as labels on filing cabinets.

§6Connections

  • ← type system & OOP: a string variable holds a reference. Everything odd about == comes from that one fact.
  • ← runtime data areas: the pool is a JVM-managed table; it moved out of PermGen into the heap in Java 7.
  • ← memory & GC: discarded strings are ordinary garbage; pooled ones stay alive as long as the table holds them.
  • ← equality & ordering: String is the textbook example of equals/hashCode done right — and of why keys must be immutable.
  • → part 2: immutability is the reason StringBuilder has to exist.
  • → exceptions: every exception message is a string you should build carefully.
  • Same idea elsewhere: Python and JavaScript strings are also immutable, and C# also interns literals — so the "equals, not ==" instinct transfers. C strings are raw mutable char arrays, which is precisely the pain Java is avoiding here.

§7In practice — one file, dissected

Full source: code/StringDemo.java, compiled and run on JDK 1.8.0_411.

String a = "hello";              // literal -> goes in the pool
String b = "hello";              // same letters -> same pooled object
String c = new String("hello");  // "new" forces a separate object
Three variables, but only two objects. a and b are two arrows pointing at one pooled object. c is an arrow to its own copy. (Strictly, the literal written inside new String("hello") is pooled too — so the pool holds one object, and the heap holds the extra one that new built.)
a == b            // true  — same object
a == c            // false — different objects
a.equals(c)       // true  — same letters
a == c.intern()   // true  — intern() returns the pooled copy
The whole mental model in four lines. intern() means "give me the pool's copy of this text". Since a already is the pool's copy, the two arrows match.
String s = "a";
String s2 = s.concat("b");       // builds a NEW string; s is untouched
Proof of immutability. After this line s is still "a". If you had written s.concat("b"); on a line by itself and thrown the result away, nothing at all would have happened — a very common bug.
StringBuilder sb = new StringBuilder();
for (int i = 0; i < 3; i++) sb.append(i);
The escape hatch, previewed here and explained fully in part 2: one mutable buffer, appended three times, turned into a string once at the end.
String var = "ja";
final String constant = "ja";
"java" == "ja" + "va"       // compile-time join
"java" == var + "va"        // run-time join
"java" == constant + "va"   // final local = constant -> compile-time join
The constant-folding experiment from §3.5. The only difference between the last two lines is the word final — and it flips the answer.

§8Pitfalls

1. Comparing text with ==. It works by luck for literals and fails for anything read from input, a file, a DB, or built with new. Use equals. Always.
2. Throwing away the result. s.trim(); or s.toUpperCase(); on their own do nothing at all. You must write s = s.trim();. Strings never change in place.
3. new String("hi"). Pointless. It creates a second object with identical letters and opts out of pooling. Just write "hi".
4. NullPointerException from equals. input.equals("yes") explodes if input is null. Flip it — "yes".equals(input) — or use Objects.equals(input, "yes").
5. Over-using intern(). Interning thousands of dynamic strings by hand bloats the intern table and slows it down. Trust the compiler; reach for intern() only with a measurement in hand.
6. Passwords and secrets in a String. You cannot erase one. It stays in memory until the GC happens to collect it, and it may show up in a heap dump. Use char[] and overwrite it — see part 3 (Oracle, JCA Reference Guide).

§9Recap

  • A String is a final class wrapping a private final array of letters that is never written to and never handed out. That is immutability.
  • Immutability buys four things: safe sharing, free thread safety, a safe map key, and a cached hash code.
  • Every "editing" method returns a new string. Write s = s.trim(), never a bare s.trim().
  • Literals are pooled — one shared object per distinct text. new String(...) deliberately opts out; intern() opts back in.
  • == asks "same object"; equals asks "same letters". For text, use equals.
  • Joins of constants are folded at compile time and pooled; joins involving variables happen at run time and are not.
  • Since Java 9 the letters are stored as a byte[] plus a coder flag (compact strings) — same behaviour, about half the memory.

Glossary

Immutable
Cannot be changed after it is created. Operations return new objects instead.
Literal
Text written directly in source code between double quotes, e.g. "hello".
String pool (intern table)
A JVM-managed table holding one shared instance per distinct literal.
intern()
Returns the pool's shared instance equal to this string, adding it if it is not there yet.
Reference
The arrow a variable holds, pointing at an object on the heap.
Constant folding
The compiler evaluating an expression made only of constants, before the program runs.
Compact strings
Java 9+ storage using one byte per character for Latin-1 text (JEP 254).
Defensive copy
Copying a mutable object before sharing it. Never needed for strings.
