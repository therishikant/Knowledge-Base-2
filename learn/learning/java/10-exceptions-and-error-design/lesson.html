Exceptions & Error Design

Java › lesson 10 of 14 · SKIM — handling failure as part of your API

In one line — An exception is Java's way of saying "I can't finish this normally." You throw one when something goes wrong and catch it where you can actually handle it. The real skill isn't syntax — it's designing which failures are part of your contract (checked) and which are bugs (unchecked), and never swallowing them silently.

§1Where it fits

Mostly transferable, so we skim the mechanics and dwell on the design angle you'll be judged on as an architect. It builds on the type hierarchy (lesson 5) — exceptions are just objects — and pairs with try-with-resources, which needs the AutoCloseable interface.

§2Why it exists

The old C way — return -1 and set a global error code — mixes the happy path with error checks and is easy to ignore. Exceptions separate "what to do" from "what if it fails," carry a message and a stack trace to the point of failure, and can't be silently dropped (an uncaught one crashes loudly). Java went further and made some exceptions checked — the compiler forces you to deal with them (Oracle Java Tutorials — Exceptions).

§3How it works

try / catch / finally / try-with-resources

try guards risky code, catch handles specific types (most specific first), finally always runs (cleanup). Better still, try-with-resources auto-closes anything AutoCloseable in reverse order, even on exception — no leaked files or connections, no verbose finally.

Wrapping & the cause chain

When you catch a low-level exception and rethrow a meaningful one, pass the original as the cause (new ServiceException("load failed", e)). The stack trace keeps both, so you don't lose the root. This is exception translation — expose failures in your layer's vocabulary, not the plumbing's.

§4When to use (design rules)

  • Throw at the point you detect a broken assumption; validate inputs early (fail fast).
  • Catch only where you can actually do something (retry, fallback, user message). Otherwise let it propagate.
  • Unchecked for programming errors; checked only when the caller can realistically recover.
  • try-with-resources for every closeable resource.
  • Custom exception types to give callers meaningful, catchable categories.

§5Explain it to a 12-year-old

Cooking dinner, you hit a problem: no eggs. You don't quietly serve an empty plate — you shout "out of eggs!" (throw). Whoever can fix it — maybe a roommate who'll run to the shop — hears and handles it (catch). And no matter what, you turn off the stove on your way out (finally). A checked problem is "we might run out of eggs — have a plan." An unchecked one is "you tried to fry a rock" — that's just a mistake to fix.

§6Connections

  • ← type-system-and-oop: exceptions are objects in a hierarchy; you catch by supertype.
  • ← strings: a good message is a carefully built string with context.
  • → java8-functional: lambdas + checked exceptions clash — a real friction point (wrap or use unchecked).
  • → concurrency: exceptions in threads/futures surface differently (via Future.get).
  • Same idea elsewhere: C#/Python have exceptions but no checked kind; Go and Rust prefer returned error values / Result — a live design debate.

§7In practice — one file, dissected

try (Resource a = new Resource("A");
     Resource b = new Resource("B")) {   // both are AutoCloseable
    a.use(); b.use();
    throw new RuntimeException("boom");       // simulate a failure
} catch (RuntimeException e) {
    System.out.println("caught: " + e.getMessage());
} finally {
    System.out.println("finally always runs");
}
Watch the ordering in the output: B closes before A (reverse of opening), and it happens before the catch — the resources are cleaned up as the exception unwinds, automatically. That's the whole reason try-with-resources exists: correct cleanup with none of the error-prone finally boilerplate.

Real output (JDK 1.8 — code/ExceptionDemo.java)

open B

use B

caught: boom
finally always runs
Predict the output. Put a return "X"; inside the try and a return "Y"; inside the finally. Which is returned? (Hint: finally runs last and its return wins — which is exactly why you should never return from a finally.)

§8Pitfalls

Swallowing exceptions. An empty catch {} hides bugs. At minimum, log with context; better, handle or rethrow.
Catching Exception (or Throwable) broadly. You'll accidentally hide bugs and even Errors. Catch the specific type.
Exceptions for control flow. They're for exceptional cases, not loops/branches — throwing is expensive and obscures intent.
Losing the cause. Rethrowing without passing e as the cause deletes the root-cause trace.
return in finally. It silently overrides the real return/exception. Never do it.

§9Recap

  • Everything thrown is a Throwable: Error (don't catch), checked Exception (recoverable), RuntimeException (bugs).
  • Checked = compiler-enforced, expected failure; unchecked = programming error.
  • finally always runs; try-with-resources auto-closes in reverse — prefer it.
  • Catch only where you can act; otherwise let it propagate to a layer that can.
  • Translate exceptions to your layer's vocabulary and keep the cause.
  • Never swallow, never use for control flow, never return from finally.

Glossary

Throwable
Root of everything you can throw/catch.
Checked exception
Compiler forces handling or declaration; a recoverable condition.
Unchecked exception
RuntimeException subclass; usually a bug, no compiler obligation.
Error
Serious JVM-level problem (OOM, stack overflow) you shouldn't catch.
finally
Block that always runs, for cleanup.
try-with-resources
Auto-closes AutoCloseable resources in reverse order.
Cause chain
The wrapped original exception preserved via the cause constructor.
