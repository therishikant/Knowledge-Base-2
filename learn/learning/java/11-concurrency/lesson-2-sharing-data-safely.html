Sharing Data Safely

Java › concurrency cluster · lesson 11, part 2 of 4 · DEEP — what breaks when two threads touch one thing

Concurrency cluster: 1. Threads · 2. Sharing data safely · 3. Thread pools & futures · 4. Virtual threads

In one line — Starting threads is easy; the hard part is that they share the heap. When two threads touch the same data you hit three separate problems: updates get lost (atomicity), one thread never sees the other's change (visibility), and the code may not even run in the order you wrote it (ordering). Java gives you three tools — synchronized, volatile, and atomics — and one rulebook, the happens-before relation, that says exactly when your data is safe.

§1Where it fits

Part 1 ended on a cliff: every thread has its own stack, but they all share one heap. This part is the fall. It is the single most important lesson in the cluster — everything in part 3 (pools, futures, concurrent collections) is really just pre-packaged versions of what you learn here, and part 4's virtual threads change none of it.

It is also where interviews live. "What does volatile do?", "is i++ atomic?", "explain happens-before", "how do you avoid deadlock" — all of them are this one page.

§2Why it exists — one innocent line, three different bugs

Here is the entire problem, in one statement:

count++;

It looks like one step. It is three. The CPU must read count from memory into a register, add one, then write the result back. In bytecode that is literally getstatic, iconst_1, iadd, putstatic. And from part 1 you know the scheduler may pause a thread anywhere — including between those steps.

Bug 1 — Atomicity: the lost update

The section of code that must not be interleaved — read, modify, write — is called a critical section. The property it needs is atomicity: all of it happens, or none of it, with nobody else interleaving (Oracle — Synchronization).

Bug 2 — Visibility: the change that never arrives

Now a different program, with no increment at all:

static boolean running = true;

// thread 1
while (running) { doWork(); }     // may loop forever

// thread 2
running = false;                   // "please stop"

There is no lost update here — only one thread writes. Yet thread 1 may spin forever. Why? Because "memory" is a lie you have been told for simplicity. Between the CPU core and RAM sit several layers of cache, and each core has its own. Thread 2's write may sit in core 2's cache for a while. Worse, the JIT compiler sees that thread 1 never modifies running inside the loop, so it is entitled to hoist the read out: 

if (running) { while (true) doWork(); }   // a legal optimisation!
That transformation is perfectly valid for a single thread — and single-thread correctness is the only thing the compiler promises you by default. Both the hardware and the compiler are allowed to assume nobody else is looking, unless you tell them otherwise.

Bug 3 — Ordering: your lines did not run in your order

Compilers and CPUs reorder independent instructions for speed. Within one thread you can never tell, because the result is identical. Across threads you absolutely can:

// thread 1              // thread 2
config = loadConfig();    if (ready) use(config);   // config might still be null!
ready = true;
Thread 1's two writes are independent of each other, so they may reach memory in the other order. Thread 2 then sees ready == true while config is still null. This is not theoretical — it is the classic broken double-checked-locking bug.
Hold these three apart; they are genuinely different.
Atomicity — "did my whole update survive?" → fixed by locks or atomics.
Visibility — "can the other thread see my write at all?" → fixed by volatile or locks.
Ordering — "did my writes land in the order I wrote them?" → fixed by volatile or locks.
Notice that locks fix all three; volatile fixes only the last two. That one sentence answers most volatile interview questions.

§3How it works

The rulebook: happens-before

Rather than describe caches (which differ per CPU), Java defines a portable rule called the Java Memory Model. Its core idea is a relation named happens-before: if action X happens-before action Y, then everything X did is guaranteed visible to Y. If no happens-before link exists between two actions on shared data, you have a data race and the result is undefined (JLS SE 21 §17.4.5).

You do not need to memorise the whole model. These six rules cover real code:

#RuleIn plain words
1Program orderWithin one thread, things appear to happen in source order.
2Monitor lockUnlocking a monitor happens-before any later lock of that same monitor.
3VolatileA write to a volatile field happens-before every later read of it.
4Thread startt.start() happens-before anything inside t.
5Thread joinEverything inside t happens-before t.join() returns.
6final fieldsValues assigned to final fields in a constructor are visible to any thread that later sees the object (if this did not escape).

And it is transitive: if A happens-before B and B happens-before C, then A happens-before C. That is how a chain of handovers keeps data safe across many threads.

Tool 1 — synchronized: the big hammer

Every Java object carries a hidden lock called its monitor (or intrinsic lock). synchronized acquires it on entry and releases it on exit — including when you exit by throwing. 

private final Object lock = new Object();
private int count;

void bump() {
    synchronized (lock) {     // acquire -> import others' writes
        count++;               // now genuinely atomic
    }                          // release -> publish my writes
}

Two shorthands mean exactly the same thing as a block, and it matters which object they lock:

You writeIt really locksRisk
synchronized void m()thisany outside code holding your object can block you
static synchronized void m()YourClass.classone lock for the whole class, shared app-wide
synchronized (lock) { }whatever you namednone — you control it. Preferred.
Idiom: lock a private final object you own. private final Object lock = new Object();. Locking on this leaks your lock into the public API: any caller can write synchronized (yourObject) and freeze your class from the outside, and you will never find out why.

Three more facts that come up constantly:

  • Reentrant. A thread that already holds a monitor can enter another synchronized block on the same object without deadlocking itself. The JVM keeps a hold count.
  • The lock is on the object, not the code. Two threads using two different instances do not block each other at all. If your state is static, your lock must be too.
  • sleep() inside a lock keeps the lock. Only wait() releases it.
Lock granularity is a real trade-off. Too wide (synchronized on a method doing network I/O) and you have serialised your whole program — you have written a single-threaded app with extra steps. Too narrow and you break the invariant you were protecting. Rule of thumb: hold the lock for exactly the statements that must be all-or-nothing, and never do I/O or call unknown code while holding one.

Tool 2 — volatile: visibility only, and it is cheap

Marking a field volatile tells the JVM: never cache this in a register, always read and write real memory, and do not reorder around it.

private volatile boolean running = true;   // now the stop-flag works

What you get, and what you do not:

volatilesynchronized / LockAtomics
Visibilityyesyesyes
Prevents reorderingyesyesyes
Atomic read-modify-writenoyesyes (single variable)
Can a thread block?neveryesnever (it retries)
Costvery lowmoderatelow

So volatile is right for exactly one shape: a flag or a reference that one thread writes and others read, where the new value does not depend on the old one. The moment you write volatileCount++ you are back to the lost update — proved with real numbers in §7.

Tool 3 — Atomics and CAS: locking without a lock

AtomicInteger, AtomicLong, AtomicReference and friends give you atomic read-modify-write on a single variable with no lock at all. They sit on a hardware instruction called compare-and-swap (CAS): "set this to 8, but only if it is still 7; otherwise tell me you failed." 

counter.incrementAndGet();            // atomic, no lock
ref.compareAndSet(expected, updated); // true if it swapped
max.updateAndGet(v -> Math.max(v, x));// retry loop, written for you

Underneath, incrementAndGet is a tiny loop: read the value, compute the new one, try to swap; if someone beat you to it, start again. Nobody ever sleeps, so there is no context switch — this is lock-free code, and under moderate contention it beats a lock comfortably.

When atomics stop being enough. They protect one variable. If your invariant spans two fields — "from.balance down by 50 and to.balance up by 50" — no single CAS can express it, and you need a lock. Also note LongAdder (Java 8): under very heavy contention it spreads a counter over several cells and sums them on read, beating AtomicLong for write-heavy statistics.

Tool 4 — ReentrantLock: synchronized with extra controls

Same semantics, explicit syntax, and three things synchronized cannot do.

ReentrantLock lock = new ReentrantLock();
lock.lock();
try {
    // critical section
} finally {
    lock.unlock();      // MUST be in finally - this is not automatic
}
Extra abilityWhy it matters
tryLock() / tryLock(t, unit)give up instead of waiting forever — the standard deadlock escape
lockInterruptibly()a thread waiting for the lock can still be cancelled
new ReentrantLock(true)fair ordering (FIFO), preventing starvation — at a real throughput cost
newCondition()several independent wait-sets on one lock (e.g. "not full" and "not empty")

Related: ReentrantReadWriteLock lets many readers in at once but only one writer — a big win when reads vastly outnumber writes. StampedLock (Java 8) adds an even faster optimistic read mode.

Default to synchronized. It is shorter, cannot leak a lock, and the JVM optimises it well. Reach for ReentrantLock only when you need one of the four abilities above.

The classic failure: deadlock

Three practical cures, in order of preference:

  1. Hold one lock at a time. By far the best fix. Most deadlocks come from nesting you did not need.
  2. Global lock ordering. If you must take two, every thread takes them in the same agreed order (e.g. by account id). The cycle becomes impossible.
  3. tryLock with a timeout. Take what you can, release everything and retry if you cannot. Demonstrated in §7.

Two cousins worth naming: livelock (threads keep politely backing off and retrying forever — busy but making no progress) and starvation (one thread never gets the lock because others keep taking it; fair locks fix this).

The best tool of all: don't share

Every technique above manages shared mutable state. The strongest move is to remove one of those words:

  • Remove "shared" — confinement. Keep data in locals, or hand each thread its own copy. A local variable can never race. (ThreadLocal is the explicit form.)
  • Remove "mutable" — immutability. An object whose fields are all final and set once in the constructor is safe for every thread, forever, with no synchronisation at all (JMM rule 6). This is why String and the Java 21 record are such good concurrent citizens.
  • Remove "state" — stateless services. A class with no fields is automatically thread-safe. This is why a Spring @Service with only method parameters needs no locking.
Safe publication. Even an immutable object must be handed over correctly. Publish shared references through a volatile field, a final field, an AtomicReference, a lock, or a concurrent collection — never by a plain write to a plain field.

§5Explain it to a 12-year-old

You and your sister share a jar of sweets and a notebook on the fridge saying how many are left. It says 7.

You read "7", take one, and get distracted by the TV before you write "6". Meanwhile your sister reads "7", takes one, and writes "6". You come back and write "6". Two sweets are gone but the notebook says six. Nobody lied — you both just read before the other had written. That is a lost update.

A lock is a rule: you must be holding the kitchen key to touch the jar and the notebook, and you put the key back when you are done. Only one of you can be at the fridge at a time, so the count is always right.

Visibility is a different problem. Suppose your sister writes on her own little notepad in her room instead of the fridge. She did update the number — but you cannot see it. volatile means "always write it on the fridge where everyone can see", and that is all it means. It does not stop both of you writing at once.

Deadlock is when you are holding the kitchen key waiting for the fridge key, and she is holding the fridge key waiting for the kitchen key. Both of you wait politely, forever. The fix is a house rule: always take the kitchen key first.

§7In practice — measuring the damage

Run on JDK 1.8 — code/ConcurrencyDemo3.java and code/ConcurrencyDemo.java. All output below is real.

A. Visibility — and why this bug is so nasty

static boolean plainFlag = false;
static volatile boolean volatileFlag = false;
// a reader thread spins until the flag flips (or 2s pass); main flips it after 100ms
plain    reader saw the flag? true  (spins=308671200)
volatile reader saw the flag? true
Read that carefully: the unsafe version worked. On this JVM, this run, the write did become visible — which is exactly what makes visibility bugs so dangerous. They pass your tests. Change the JIT's mind (a longer-running loop, a different machine, a server VM) and the same code spins forever. The volatile version is not "luckier" — it is guaranteed. Also note the spin count: 308 million useless loop iterations in 100ms, which is why busy-waiting is itself a bad idea.

B. Atomicity — four threads, 100,000 increments each

for (int i = 0; i < 100_000; i++) {
    volatileCounter++;                        // visible, but NOT atomic
    synchronized (LOCK) { guardedCounter++; } // atomic + visible
    atomicCounter.incrementAndGet();          // atomic + visible, lock-free
}
expected              = 400000
volatile counter      = 394790
synchronized counter  = 400000
atomic counter        = 400000
This is the single most important output in the cluster. The volatile counter lost 5,210 updates — proof that volatile does not make ++ atomic. It is also proof of how sneaky the bug is: it was 98.7% correct. A test asserting "roughly 400,000" would pass. Run it again and you will get a different number; that non-determinism is the signature of a data race.

C. The retry loop hiding inside every atomic

int current;
do {
    current = max.get();                 // 1. read what's there
    if (s <= current) break;          // 2. decide
} while (!max.compareAndSet(current, s)); // 3. swap ONLY if unchanged; else retry
running max = 11
If another thread changed max between steps 1 and 3, compareAndSet returns false and the loop simply runs again with fresh data. Nothing blocks, nothing sleeps. This is the shape of every lock-free algorithm, and incrementAndGet is just this loop with the body filled in.

D. Escaping a deadlock with tryLock

if (first.tryLock(50, TimeUnit.MILLISECONDS)) {
    try {
        if (second.tryLock(50, TimeUnit.MILLISECONDS)) { /* work */ }
    } finally { first.unlock(); }   // release even if the second grab failed
}
T1 got both locks (left->right) on attempt 3
T2 got both locks (right->left) on attempt 3
both threads finished - no deadlock
The two threads deliberately take the locks in opposite order — the textbook deadlock setup. With synchronized this program would hang forever. Here, both needed three attempts (so they really did collide twice) and then both completed. The crucial detail is the finally: if you grab the first lock and fail to get the second, you must let go of the first, or you have built a deadlock with extra steps.

E. The original race, side by side

expected      = 400000
unsafe (race) = 316089
safe (atomic) = 400000
The same experiment run through a thread pool. Note the unsafe number is wildly different from §7B's — same code, same machine, different day. That is the point.
Predict, then run. (1) Replace synchronized (LOCK) with synchronized (new Object()). Is the counter still correct? (Why is locking a fresh object every time exactly equivalent to no lock at all?) (2) Swap atomicCounter.incrementAndGet() for atomicCounter.set(atomicCounter.get() + 1) — every operation is still atomic, so is the total still 400,000? (3) Change the tryLock demo to plain lock() and watch the program hang; then take a thread dump with jstack and find the words "Found one Java-level deadlock".

§8Pitfalls

Thinking volatile makes operations atomic. It does not. §7B lost 5,210 updates on a volatile field.
Thinking synchronized is only about mutual exclusion. Half its value is the happens-before edge. Reading a field without the lock is broken even if only one thread writes it.
Locking on a different object than the one you are protecting — or on a non-final field you later reassign. The lock silently stops working.
Locking on this, a String literal, or a boxed Integer. These are shared globally through the string/Integer caches, so unrelated code can block you.
Check-then-act on a thread-safe object. if (!map.containsKey(k)) map.put(k, v); is a race even on a ConcurrentHashMap: each call is atomic, the pair is not. Use putIfAbsent / computeIfAbsent / merge.
Forgetting unlock() in a finally. One exception and the lock is held for the life of the process.
Calling unknown code while holding a lock — a listener, a callback, an override. You have no idea what locks it takes, so you cannot reason about deadlock.
Double-checked locking without volatile. The classic lazy-singleton bug: without volatile on the field, another thread can see a non-null reference to a half-constructed object (bug 3, ordering).
"It works on my machine." A race that never fires on a 4-core laptop fires in the first minute on a 64-core server. Correctness here is proved by reasoning, not by testing.

§9Recap

  • Shared mutable state creates three problems: atomicity, visibility, ordering.
  • count++ is read-modify-write — three steps, interruptible between any of them.
  • happens-before is the rulebook: no happens-before edge between two accesses to shared data = a data race = undefined behaviour.
  • The edges you will actually use: unlock→lock, volatile write→read, start(), join(), and final fields. It is transitive.
  • synchronized gives exclusion and visibility, is reentrant, locks an object, and always releases on exit.
  • volatile gives visibility and ordering but never atomicity — perfect for a one-writer flag.
  • Atomics give lock-free atomic updates to one variable via CAS retry loops; LongAdder wins under heavy contention.
  • ReentrantLock = synchronized + tryLock, timeouts, interruptibility, fairness, multiple conditions — at the cost of a mandatory finally.
  • Deadlock = a cycle of waiting. Prevent it by holding one lock at a time, or by a global lock order.
  • The strongest fix is to delete the problem: confinement, immutability, statelessness.

Reference — one-line answers to the usual questions

Is i++ atomic?No — read, add, write.
Is long/double assignment atomic?Not guaranteed for non-volatile 64-bit fields (JLS §17.7). volatile makes it so.
Does volatile replace a lock?Only when the new value does not depend on the old one.
Does sleep() release the lock?No. wait() does.

Glossary

Race condition
Correctness depends on the timing of threads.
Data race
Two threads access the same location, one writes, with no happens-before edge between them.
Critical section
Code that must not be run by two threads at once.
Mutual exclusion
The guarantee that only one thread is in the critical section.
Monitor / intrinsic lock
The hidden lock every Java object has, used by synchronized.
Reentrancy
A thread may re-acquire a lock it already holds.
happens-before
The JMM relation guaranteeing one action's writes are visible to another.
volatile
A field read/written straight from memory, never reordered around.
CAS
Compare-and-swap: update only if the value is still what I last saw.
Lock-free
Progress without blocking; failed attempts retry instead of waiting.
Deadlock / Livelock / Starvation
Waiting in a cycle / retrying forever / never getting a turn.
Safe publication
Handing a reference to another thread so it is guaranteed to see a fully built object.
Confinement
Keeping data reachable by only one thread.
