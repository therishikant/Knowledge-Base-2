Thread Pools & Futures

Java › concurrency cluster · lesson 11, part 3 of 4 · DEEP — how real programs actually run concurrent work

Concurrency cluster: 1. Threads · 2. Sharing data safely · 3. Thread pools & futures · 4. Virtual threads

In one line — In real code you almost never write new Thread(...). You hand tasks to an ExecutorService — a pool of reusable threads — and get back a Future, a receipt you redeem for the answer later. CompletableFuture lets you chain those answers without ever blocking, and java.util.concurrent ships ready-made thread-safe collections and coordination tools so you rarely have to write a lock by hand.

§1Where it fits

Part 1 gave you threads. Part 2 gave you the rules for sharing data. Both were about mechanism. This part is about the library that Java 5 introduced — java.util.concurrent — which wraps all of that into pieces you can safely use without re-deriving the memory model every time.

This is the layer you will write day to day. When an interviewer asks "how would you call three services in parallel and combine the results?", the answer lives on this page.

§2Why it exists — what goes wrong with raw threads

The obvious design is "one new thread per task":

while (true) {
    Socket s = serverSocket.accept();
    new Thread(() -> handle(s)).start();   // looks fine. is a trap.
}

It fails in four separate ways, and each one maps to a feature of the executor framework:

Problem with thread-per-taskWhat the executor gives you
Creation cost. Each thread is a system call plus ~1 MB of stack. For a 2 ms task, setup can cost more than the work.Threads are created once and reused for task after task.
No limit. 10,000 clients means 10,000 OS threads. The machine thrashes on context switches, then dies with OutOfMemoryError: unable to create new native thread.A fixed pool size — a hard ceiling you choose.
No backpressure. Nothing tells the caller "I am full, slow down".A bounded queue plus a rejection policy.
No results, no errors. Runnable returns nothing, and an exception inside it vanishes.Callable + Future: a value, or the exception, delivered to you.

Underneath all four is one idea: separate what to run from how it is run. Your code submits a task and stops caring which thread executes it. That one separation is why you can later switch a fixed pool for a virtual-thread executor (part 4) by changing one line (Oracle — Executors).

§3How it works

The three interfaces

  • Executor — one method, execute(Runnable). "Run this somehow."
  • ExecutorService — adds submit() (returns a Future), invokeAll(), and lifecycle (shutdown()). This is the one you use.
  • ScheduledExecutorService — adds "run this in 5 seconds" and "run this every minute".

Inside a thread pool

The growth rule surprises people, so learn it explicitly. When a task arrives:

1
Fewer than corePoolSize threads? Start a new thread, even if others are idle.
2
Otherwise, try to queue it. If the queue accepts it, done.
3
Queue full? Start another thread, up to maximumPoolSize.
4
At max and queue still full? Hand the task to the rejection policy (by default, throw RejectedExecutionException).
The consequence everyone trips over: with an unbounded queue, step 3 never happens, so maximumPoolSize is meaningless and the pool never grows past core size. Instead the queue grows until you run out of heap. An unbounded queue does not remove backpressure — it converts it into an OutOfMemoryError.

The factory methods, and their traps

Production idiom: build it yourself. A bounded queue and a named thread factory are worth the extra five lines. 
new ThreadPoolExecutor(
    8, 16,                                  // core, max
    60L, TimeUnit.SECONDS,                  // idle timeout for extra threads
    new ArrayBlockingQueue<>(1000),         // BOUNDED: real backpressure
    namedThreadFactory("orders-"),          // readable thread dumps
    new ThreadPoolExecutor.CallerRunsPolicy() // full? the submitter runs it, slowing itself
);
CallerRunsPolicy is the elegant one: when the pool is saturated, the submitting thread executes the task itself, which automatically throttles the producer instead of dropping work or exploding.

How big should the pool be?

  • CPU-bound work (maths, parsing, compression): about Runtime.getRuntime().availableProcessors(), give or take one. More threads than cores just adds context switches.
  • I/O-bound work (HTTP, database): threads spend most of their life blocked, so you want many more. The classic formula is threads ≈ cores × (1 + waitTime / computeTime). A call that waits 50 ms and computes 1 ms on 8 cores suggests ~400 threads — which is also exactly where platform threads start hurting, and the reason part 4 exists.
  • Never share one pool between the two kinds. A slow I/O task will occupy a thread your CPU work needed. Separate pools, separately sized, are easier to reason about and to bulkhead.

Runnable vs Callable vs Future

Returns a value?noyes

Submit withexecute() or submit()submit()

submit() immediately returns a Future — a placeholder for a value that does not exist yet. Four methods matter: get() (block until ready, then return the value or throw ExecutionException wrapping whatever the task threw), get(timeout, unit), isDone(), and cancel(mayInterruptIfRunning).

Submit everything first, then get(). 
// WRONG - fully sequential, the pool is pointless
for (Task t : tasks) pool.submit(t).get();

// RIGHT - all tasks in flight, then collect
List<Future<R>> fs = new ArrayList<>();
for (Task t : tasks) fs.add(pool.submit(t));
for (Future<R> f : fs) results.add(f.get());
Calling get() inside the submission loop waits for each task before submitting the next one. It is the most common way to accidentally un-parallelise a program.

Shutting down properly

A pool's threads are non-daemon by default, so a pool you forget to shut down keeps the JVM alive forever.

CallMeaning
shutdown()stop accepting new tasks; finish everything already submitted
shutdownNow()also drop the queue and interrupt() running tasks; returns what never ran
awaitTermination(t, unit)wait up to t for the above to complete; returns true if it did
 
pool.shutdown();
if (!pool.awaitTermination(30, TimeUnit.SECONDS)) {
    pool.shutdownNow();                 // escalate
    pool.awaitTermination(10, TimeUnit.SECONDS);
}

In Java 19+ ExecutorService implements AutoCloseable, so try (var pool = ...) { } does the graceful version for you.

CompletableFuture — composing instead of blocking

Future.get() has one fatal flaw: it blocks. A thread sitting in get() is a wasted thread, and you cannot say "when this finishes, do that" without someone waiting. Java 8's CompletableFuture fixes this by letting you describe the pipeline up front and letting the completing thread push the work forwards. 

CompletableFuture<String> page =
    CompletableFuture.supplyAsync(() -> loadUser(id), pool)   // start async, on YOUR pool
        .thenApply(User::displayName)                         // transform the value
        .thenCombine(ordersFuture, (name, orders) -> render(name, orders))  // join two
        .exceptionally(ex -> "sorry, try again");             // recover from failure
MethodUse it when…
supplyAsync / runAsyncstart async work that returns / returns nothing
thenApplytransform the result (like Stream.map)
thenComposethe next step itself returns a future (like flatMap) — avoids CF<CF<T>>
thenCombinetwo independent futures, combine both results
allOf / anyOfwait for all / first of many
exceptionally / handlerecover from failure / see both value and error
thenApplyAsync(fn, pool)force the next step onto a specific pool
Always pass your own executor. With no executor argument, supplyAsync uses the shared ForkJoinPool.commonPool(), whose size is cores − 1 and which is shared with parallel streams across your whole application. One blocking call in there can starve everything else.

Fork/join and parallel streams

ForkJoinPool is a special pool for divide-and-conquer CPU work: split the problem, solve the halves, merge. Its trick is work stealing — an idle worker takes tasks from the back of a busy worker's queue, so the load balances itself. list.parallelStream() is simply a friendly face over the common pool.

Parallel streams pay off only when all of these hold: a large data set, work per element that is genuinely expensive, a cheaply splittable source (array, ArrayList), and no blocking or shared mutable state in the lambda. For a few thousand cheap operations, the plain sequential stream usually wins.

The ready-made thread-safe collections

Before you write a lock around a map, check whether the library has already done it better.

UseClassHow it stays safe

hand-off with no bufferSynchronousQueueeach put waits for a matching take
delayed/scheduled itemsDelayQueue, PriorityBlockingQueueordering by time or priority
read-mostly list (listeners)CopyOnWriteArrayListevery write copies the array; reads never lock. Terrible for frequent writes.
non-blocking queueConcurrentLinkedQueueCAS-based, never blocks
ConcurrentHashMap vs Collections.synchronizedMap. The wrapper puts one global lock around every method — correct, but all threads queue at a single door, and you still must lock manually while iterating. ConcurrentHashMap locks only the affected bin, lets readers through without locking, and its iterators are weakly consistent (they never throw ConcurrentModificationException). Prefer it.

§4When to use what

  • A pool — the default for any background or parallel work. Bounded queue, named threads, sized for the workload.
  • Future + invokeAll — a fixed batch of independent tasks you need all the answers to.
  • CompletableFuture — multi-step async flows: call A, then B with A's result, combine with C, fall back on error.
  • Parallel stream / fork-join — one big CPU-bound computation over a large, splittable collection.
  • BlockingQueue — any producer/consumer pipeline; it gives you backpressure for free.
  • Semaphore — rate-limiting a shared downstream resource.
  • ScheduledExecutorService — periodic jobs. Never java.util.Timer: one thread, and one thrown exception kills every future task.

§5Explain it to a 12-year-old

Think of a small café with four staff.

The silly way to run it would be to hire a brand-new person for every single order, then fire them the moment the coffee is handed over. Hiring takes longer than making the coffee, and on a busy morning you would have two hundred people crammed behind the counter, unable to move. That is new Thread() per task.

A café instead keeps four staff and a spike of order tickets. Whenever someone is free, they take the next ticket. That is a thread pool: fixed staff, a queue of work.

When you order, you do not stand frozen at the counter. You get a buzzer and go sit down. The buzzer is a Future — not the coffee, but a promise of coffee. get() is choosing to stand and stare at the buzzer until it goes off.

CompletableFuture is better still: you tell the staff "when it is ready, add oat milk and bring it to table six." Now nobody stands waiting — the work continues by itself when the coffee is done.

And if the ticket spike is full, the café has to say "sorry, we are full" rather than accept ten thousand orders it can never make. That is the bounded queue, and saying no on time is what keeps the café standing.

§6Connections

  • ← part 1: a pool exists because platform threads are expensive to create and limited in number.
  • ← part 2: every concurrent collection here is locks and CAS applied for you; submitting a task and reading its result via Future.get() is itself a happens-before edge, so you need no extra synchronisation for the result.
  • ← java8-functional: thenApply/thenCompose are map/flatMap for a value that has not arrived yet.
  • ← exceptions: ExecutionException is the wrapper that carries a task's failure across the thread boundary — always inspect getCause().
  • → part 4: virtual threads make pool sizing for I/O largely obsolete, while the ExecutorService interface stays.
  • → application-architecture: separate, bounded pools per dependency is the bulkhead pattern — one slow service cannot sink the whole app.
  • Same idea elsewhere: JavaScript's Promise.then/all is CompletableFuture with different names; C#'s Task/async-await and Python's concurrent.futures are the same two ideas — a pool and a promise.

§7In practice — seven experiments, with real output

Run on JDK 1.8 — code/ConcurrencyDemo4.java. All output is real.

A. Two threads, six tasks

ExecutorService pool = Executors.newFixedThreadPool(2);
for (int i = 1; i <= 6; i++) results.add(pool.submit(() -> {
    Thread.sleep(20);
    return "task " + id + " ran on " + Thread.currentThread().getName();
}));
task 1 ran on pool-1-thread-1
task 2 ran on pool-1-thread-2
task 3 ran on pool-1-thread-2
task 4 ran on pool-1-thread-1
task 5 ran on pool-1-thread-1
task 6 ran on pool-1-thread-2
terminated cleanly = true
Six tasks, exactly two thread names. The threads were never re-created — they finished one task and pulled the next from the queue. Note the default naming (pool-1-thread-N): useful, but a custom ThreadFactory naming them orders-1 would be far better in a thread dump. The last line is awaitTermination confirming a clean shutdown.

B. invokeAll — parallel really is parallel

List<Future<Integer>> fs = pool.invokeAll(jobs);  // 3 jobs sleeping 50, 100, 150ms
sum of squares = 14
serial would take ~300ms; parallel took about 150ms
Three tasks that would take 50+100+150 = 300 ms one after another finished in ~150 ms — the duration of the slowest one, because all three were in flight at once. That is the whole payoff of a pool in one number. invokeAll blocks until every task is done, so by the time it returns, every Future is complete and get() will not wait.

C. A failure asleep inside a Future

Future<Integer> f = pool.submit(() -> 1 / 0);
submitted; nothing printed yet - the failure is still asleep
get() rethrew it: java.lang.ArithmeticException: / by zero
The division by zero happened on the pool thread immediately — but printed nothing, logged nothing, and the program carried on. The exception was stored in the Future and only surfaced at get(), wrapped in an ExecutionException. This is why a Future you never get() is a silently swallowed bug, and why execute() (which has no Future) needs an UncaughtExceptionHandler.

D. A CompletableFuture pipeline

user.thenCombine(orders, (u, o) -> u + " | " + o)
    .thenApply(String::toUpperCase)
    .exceptionally(ex -> "fallback page");
page = USER:ANA | ORDERS:3
fallback: db down
Two independent 60 ms lookups ran at the same time and were joined by thenCombine; nothing blocked until the final get(). The second line is a different future that threw immediately — exceptionally turned the failure into a usable fallback value rather than an exploding call stack. Note that ex here is a CompletionException, so the real cause is ex.getCause().

E. Producer/consumer with a queue of size 2

BlockingQueue<String> queue = new ArrayBlockingQueue<>(2);
queue.put(item);    // blocks while full
String item = queue.take();  // blocks while empty
produced item-1 (queue size 1)
produced item-2 (queue size 2)
produced item-3 (queue size 2)
  consumed item-1
produced item-4 (queue size 2)
  consumed item-2
produced item-5 (queue size 2)
  consumed item-3
  consumed item-4
  consumed item-5
Watch the queue size: it reaches 2 and stays there. The producer is faster than the consumer, so put() blocked until a slot freed up — and from then on the two ran in lock-step, one produced for one consumed. That is backpressure, achieved with no locks, no wait/notify and no sleep. The __done__ marker ("poison pill") is the standard way to tell a consumer there will be no more work.

F. CountDownLatch — wait for N things

CountDownLatch ready = new CountDownLatch(3);
// each worker: ... ready.countDown();
ready.await();   // main waits until the count hits zero
  worker 1 warmed up
  worker 2 warmed up
  worker 3 warmed up
all workers ready - starting traffic
"all workers ready" can only print after three countDown() calls, no matter how long each took. A latch counts down only — once it hits zero it stays there, which is why it is one-shot. If you need the same gate again next round, that is CyclicBarrier.

G. Atomic map updates without a lock

counts.merge(word, 1, Integer::sum);   // read-modify-write, atomic per key
counts = {a=3, b=2, c=1}
HashMap is fine when only one thread touches it: {a=1}
Six tasks on four threads updating three keys, and every count is exact. Written by hand as counts.put(w, counts.get(w) + 1) this would lose updates exactly like §7B of part 2 — get and put are each atomic, but the pair is not. merge, compute and computeIfAbsent exist precisely to make the pair atomic too.
Predict, then run. (1) In A, change pool.submit(...) to f.get() inside the loop. How many distinct thread names appear now, and what happened to the parallelism? (2) Delete pool.shutdown() from any demo — does the JVM still exit? Why not? (3) In E, make the queue size 10. Does the output interleave differently? Which number stops appearing? (4) Replace merge in G with put(w, counts.getOrDefault(w,0)+1) and run it twenty times. How often is it wrong?

§8Pitfalls

Unbounded queues. newFixedThreadPool queues without limit. Under overload you do not get backpressure, you get an OutOfMemoryError.
newCachedThreadPool in a server. No thread ceiling. A burst of traffic creates a thread per request and takes the process down.
Calling get() inside the submission loop. Fully sequential execution that looks parallel.
Never shutting the pool down. Non-daemon threads keep the JVM alive; in a web app this also leaks a classloader on redeploy.
Blocking inside the common ForkJoinPool. supplyAsync without an executor, or a blocking call in a parallelStream, starves every other parallel task in the JVM.
Ignoring the Future returned by submit(). Exceptions disappear into it. If you do not want the result, at least handle failure with whenComplete/exceptionally.
Pool-within-a-pool deadlock. Tasks in a fixed pool that submit to the same pool and then get() can occupy every thread waiting for tasks that can never start.
Thinking a thread-safe collection makes your logic thread-safe. if (!map.containsKey(k)) map.put(k, v) is still a race.
Leaking ThreadLocals in a pool. Threads are reused, so a value you set is still there for the next task — a classic source of leaked user context. Always remove() in a finally.
Unnamed threads. A production thread dump full of pool-3-thread-7 tells you nothing. Pass a ThreadFactory.

§9Recap

  • Don't write new Thread() per task: it costs too much, has no limit, no backpressure, and no results.
  • ExecutorService separates what to run from how it runs — that is the whole design.
  • A pool = workers + queue + size policy + rejection policy. Growth order: core threads → queue → extra threads → reject.
  • Unbounded queue ⇒ maximumPoolSize is ignored and overload becomes an OOM. Use a bounded queue and CallerRunsPolicy.
  • Size CPU-bound pools ≈ cores; I/O-bound pools much larger (cores × (1 + wait/compute)). Keep them separate.
  • Callable returns a value and may throw; submit() hands back a Future; get() blocks and rethrows as ExecutionException.
  • Submit everything first, then collect — otherwise you have written sequential code.
  • Always shutdown() then awaitTermination(), escalating to shutdownNow().
  • CompletableFuture composes async steps without blocking: thenApply, thenCompose, thenCombine, allOf, exceptionally — always with your own executor.
  • Prefer the library: ConcurrentHashMap, BlockingQueue, CountDownLatch, Semaphore over hand-rolled locking.

Glossary

A fixed set of reusable worker threads fed by a queue.

Work queue
Where tasks wait. Bounded = backpressure; unbounded = a memory risk.

What happens when the pool and queue are both full (AbortPolicy, CallerRunsPolicy, …).
