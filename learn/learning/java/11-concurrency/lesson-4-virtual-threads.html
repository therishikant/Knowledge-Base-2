Virtual Threads

Java › concurrency cluster · lesson 11, part 4 of 4 · DEEP — millions of threads, and simple code that scales

Concurrency cluster: 1. Threads · 2. Sharing data safely · 3. Thread pools & futures · 4. Virtual threads

In one line — A normal (platform) thread is an OS thread: heavy, limited to a few thousand. A virtual thread (Java 21, JEP 444) is a thread the JVM manages itself — so cheap you can have a million. Many virtual threads take turns on a small set of real threads, and a virtual thread stepping aside to wait for I/O costs nothing. The payoff: you can go back to writing plain, blocking, easy-to-debug code and still scale like an asynchronous framework.

§1Where it fits

This closes the cluster by removing the constraint the other three worked around. Part 1 said threads are expensive. Part 3 built pools because they are expensive, and CompletableFuture chains because blocking a pooled thread is wasteful. Virtual threads attack the root cause.

What does not change: everything in part 2. Virtual threads still share the heap, still race, still deadlock. They make threads cheap, not safe.

§2Why it exists — the two bad options before Java 21

The number that forces the choice

Little's Law: concurrency = throughput × latency. If each request takes 50 ms and you want 10,000 requests per second, you must have 500 requests in flight at once. Want 2,000/s at 100 ms? 200 in flight. The arithmetic is unforgiving, and it is the whole motivation for JEP 444 (JEP 444 — Motivation).

So you needed thousands of concurrent requests in flight. You had exactly two ways to get there, and both hurt.

Option A — thread per request (simple, does not scale)

// one thread owns one request from start to finish
String user   = userService.get(id);        // blocks 30ms
List<Order> o = orderService.list(id);      // blocks 40ms
return render(user, o);

This is wonderful code: top to bottom, ordinary try/catch, a stack trace that tells you the truth, a debugger that steps through it. But each in-flight request holds an OS thread, and the OS thread is the scarce resource. At a few thousand you run out of memory or drown in context switches. A pool of 200 does not help either — it just means only 200 requests make progress and the rest queue (JEP 444).

Option B — asynchronous (scales, and costs you everything else)

userFuture.thenCombine(ordersFuture, (u, o) -> render(u, o))
          .exceptionally(ex -> errorPage());

Never block a thread; hand back a callback instead. It scales — but you pay a heavy price, which JEP 444 states bluntly: you lose sequential composition. for loops and try/catch no longer work across the steps, stack traces become useless (the stack belongs to whichever pool thread happened to run that stage, not to your request), debuggers cannot step through the logic, and profilers cannot attribute cost to a caller.

The real diagnosis. The problem was never the thread-per-request style — that style is excellent. The problem was that Java's thread was welded 1:1 to an OS thread. Java's unit of concurrency (the thread) had become more expensive than the application's unit of concurrency (the request). Virtual threads fix the implementation and keep the style.

§3How it works

M:N scheduling: many virtual threads on few carriers

A platform thread is a thin wrapper over an OS thread, scheduled by the OS (1:1). A virtual thread is scheduled by the JVM onto a small pool of platform threads (M:N). The platform thread a virtual thread is currently running on is called its carrier.

  • Mount — the scheduler places a virtual thread on a carrier and it runs.
  • Unmount — the virtual thread hits a blocking operation, so its stack is copied to the heap and the carrier is released for someone else.

That unmount is the whole trick. A blocked virtual thread holds no OS thread. The scheduler itself is a work-stealing ForkJoinPool in FIFO mode whose parallelism defaults to the number of cores (JEP 444 — Scheduling virtual threads).

Creating them — three ways, all one line

// 1. fire and forget
Thread.startVirtualThread(() -> handle(request));

// 2. builder, when you want a name or an unstarted thread
Thread t = Thread.ofVirtual().name("req-", 1).start(runnable);

// 3. the one you will actually use: an ExecutorService that makes one per task
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    IntStream.range(0, 10_000).forEach(i -> executor.submit(() -> {
        Thread.sleep(Duration.ofSeconds(1));
        return i;
    }));
}   // close() waits for every task — try-with-resources, since Java 19
That third form is deliberately the same ExecutorService interface from part 3. Migrating a service is often a one-line change from newFixedThreadPool(200) — which is exactly why the executor abstraction was worth having. Note what this "pool" is not: it has no threads to reuse, no queue and no size. It creates a brand-new virtual thread per task, and that is the point (JEP 444).

That last row matters more than it looks: Thread.currentThread(), ThreadLocal, interrupt(), synchronized, every java.util.concurrent lock and every BlockingQueue all work unchanged. Existing libraries run on virtual threads without being rewritten.

Pinning — the one leak in the abstraction

A virtual thread normally unmounts when it blocks. In a few situations it cannot, and stays pinned to its carrier — blocking a real OS thread. In Java 21 there were two causes: blocking inside a synchronized block/method, and blocking inside a native method or foreign function call. Pinning is not a correctness bug; it is a scalability bug, and a bad one if it happens on a hot path (JEP 444 — Executing virtual threads). 

// Java 21: this pins the carrier for the whole network read
synchronized byte[] getData() {
    return socket.getInputStream().read(buf);
}
// Java 21 workaround: a ReentrantLock does not pin
lock.lock();
try { return socket.getInputStream().read(buf); } finally { lock.unlock(); }
Good news, and a version warning. JEP 491, delivered in JDK 24, changed the JVM so synchronized no longer pins — a virtual thread can now unmount while holding or waiting for a monitor. The JEP explicitly withdraws the old "migrate to ReentrantLock" advice and returns to the classic guidance: use synchronized where practical, ReentrantLock when you need its extra powers. So the right answer depends on your JDK: on 21–23, avoid blocking inside synchronized; on 24+, stop worrying about it. Native-call pinning remains in both. Diagnose it with the jdk.VirtualThreadPinned JFR event.

Limiting concurrency without a pool

Pools used to do two jobs: reuse expensive threads and cap how many things happen at once. Virtual threads kill the first job but not the second — your database still has 20 connections. Do not pool virtual threads to throttle; JEP 444 says use a construct designed for it: 

private final Semaphore dbPermits = new Semaphore(20);

dbPermits.acquire();
try { return query(sql); }    // at most 20 at a time;
finally { dbPermits.release(); } // the other 9,980 virtual threads just park, cheaply

Two companions: structured concurrency and scoped values

Cheap threads make a second problem visible. If a request spawns three subtasks and the client disconnects, who cancels them? Structured concurrency (JEP 453, a preview feature in Java 21 and still evolving) says a task's subtasks must finish before the block exits — so they form a tree you can cancel, observe and trace as a unit: 

try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    Supplier<User>        user   = scope.fork(() -> findUser(id));
    Supplier<List<Order>> orders = scope.fork(() -> fetchOrders(id));
    scope.join().throwIfFailed();      // if either fails, the other is cancelled
    return render(user.get(), orders.get());
}   // nothing escapes this block — no leaked threads, ever

Scoped values (JEP 446, also preview in 21) are the companion to that: an immutable, inherited replacement for ThreadLocal, which becomes a memory problem when you have a million threads. Both are preview APIs — know them for interviews and prototypes, and check the current status of your JDK before shipping them.

Say this sentence in an interview: "Virtual threads give scale (throughput), not speed (latency). An individual task does not run one instruction faster — you can just have vastly more tasks in flight." That is JEP 444's own framing, and it separates people who have read it from people who have heard of it.

§5Explain it to a 12-year-old

A restaurant has 20 waiters. Each waiter looks after one table from start to finish — simple, and the service is great. But a waiter who has taken an order must stand at that table doing nothing until the food arrives. With 20 waiters you can serve 20 tables, and the 21st group waits at the door even though the kitchen is half idle.

Hiring 10,000 waiters is impossible: there is no room for them, and they spend all day bumping into each other. That is platform threads.

The other old fix was to ban waiters from staying at a table: take an order, run away, and let whoever is free deliver the food later. It works, but now no one person knows your table's story, and when something goes wrong nobody can say what happened. That is asynchronous code and its useless stack traces.

Virtual threads are the obvious third answer: let the waiter sit down and take a break while the food cooks. The waiter still "belongs" to your table and remembers everything about your order — they just stop occupying the floor while waiting. Now 20 pairs of feet can look after 10,000 tables, and each table still has one waiter who knows the whole story.

One catch: if a waiter falls asleep standing in a doorway (that is pinning), they block everyone else. And no matter how many waiters you have, the kitchen still only has four stoves — more waiters never cook food faster. That is why virtual threads do nothing for CPU-bound work.

§6Connections

  • ← part 1: "~1 MB per thread, a few thousand max" was the constraint; this is the removal of it.
  • ← part 2: unchanged. Races, happens-before and deadlocks apply identically — cheap threads are not safe threads.
  • ← part 3: same ExecutorService interface, opposite philosophy — never pool, and throttle with a Semaphore instead.
  • ← memory-model-and-gc: virtual thread stacks are heap objects, so thread count becomes a GC question rather than an OS question.
  • → modern-java-9-to-21: virtual threads are the flagship of Java 21, alongside records, sealed types and pattern matching.
  • → application-architecture: they weaken the case for reactive stacks (WebFlux, RxJava) whose main justification was thread scarcity.
  • Same idea elsewhere: Go's goroutines and Erlang's processes are the same M:N user-mode threads; Kotlin coroutines and C#'s async/await solve it in the language instead. JEP 444 explicitly rejects async/await for Java — it would split the world into thread-APIs and coroutine-APIs.

§7In practice — the one-line migration

Note on verification. Every other lesson in this cluster shows output from code actually run on the local JDK 1.8. Virtual threads need JDK 21+, which is not installed here, so the snippets below are taken from or modelled on the official JEP rather than executed locally. Treat the numbers as the JEP's claims, not as measurements made on this machine (JEP 444).

A. 10,000 tasks, three ways

try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    IntStream.range(0, 10_000).forEach(i -> executor.submit(() -> {
        Thread.sleep(Duration.ofSeconds(1));
        return i;
    }));
}
JEP 444 walks through exactly this program with three different executors, and the comparison is the clearest summary of the whole feature:
  • newVirtualThreadPerTaskExecutor() — 10,000 virtual threads run concurrently on perhaps a single OS thread; it finishes in about a second. Change 10_000 to 1_000_000 and it still works.
  • newCachedThreadPool() — attempts 10,000 OS threads; the program may crash, depending on the machine.
  • newFixedThreadPool(200) — survives, but caps throughput at ~200 tasks/second, so the run takes ~50 seconds.
Same tasks, same code shape. Only the executor changed.

B. What the request handler looks like now

void handle(Request request, Response response) {
    try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
        var future1 = executor.submit(() -> fetchURL(url1));
        var future2 = executor.submit(() -> fetchURL(url2));
        response.send(future1.get() + future2.get());   // blocking - and that's fine
    } catch (ExecutionException | InterruptedException e) {
        response.fail(e);
    }
}
Compare this with the CompletableFuture version in part 3. Both fetch two URLs concurrently. But here the two calls to get() block virtual threads, which costs nothing — the carriers are released and reused. And look at what you keep: an ordinary try/catch spanning both calls, a real stack trace if fetchURL throws, and a debugger that can step straight through. That is the trade asynchronous code could never make.

C. Proving which kind of thread you are on

Thread.startVirtualThread(() -> {
    Thread t = Thread.currentThread();
    System.out.println(t + " virtual=" + t.isVirtual() + " daemon=" + t.isDaemon());
});
// expected shape of the output on JDK 21:
VirtualThread[#21]/runnable@ForkJoinPool-1-worker-1 virtual=true daemon=true
Read the name: the virtual thread #21 is currently riding ForkJoinPool-1-worker-1 — its carrier. Run it again and it may be on a different worker, because the scheduler keeps no affinity. daemon=true is forced: virtual threads can never be non-daemon, so main returning will not wait for them. That is exactly why the try-with-resources form of the executor matters — close() is what waits.

D. Finding pinning before production does

# JDK 21-23: log a stack trace whenever a virtual thread blocks while pinned
java -Djdk.tracePinnedThreads=short -jar app.jar

# any version: the JFR event, enabled by default with a 20ms threshold
jdk.VirtualThreadPinned
Pinning is silent — your app is simply slower than it should be. These two switches turn it into something you can see. (JEP 491 removes the jdk.tracePinnedThreads property in JDK 24, where synchronized no longer pins; the JFR event stays for native-call pinning.)
Think it through (no JDK 21 needed). (1) A service handles 5,000 concurrent requests, each 95% waiting on a database. Would virtual threads help? Now change it to 95% JSON parsing — same answer? (2) You wrap every DB call in synchronized and move to virtual threads on JDK 21. Why might throughput barely improve, and what two fixes exist? (3) Why is Executors.newFixedThreadPool(10_000) a terrible idea but newVirtualThreadPerTaskExecutor() with 10,000 tasks fine? (4) Your code caches a database connection in a ThreadLocal. What happens when you switch to one virtual thread per request?

§8Pitfalls

Pooling virtual threads. newFixedThreadPool of virtual threads defeats the entire design. Create one per task; they are not a resource worth sharing.
Using them for CPU-bound work. Throughput is capped by cores. A million threads computing primes is slower, not faster.
Blocking inside synchronized on JDK 21–23. Pins the carrier and silently destroys scalability. Use ReentrantLock there, or upgrade to JDK 24 (JEP 491).
Expensive ThreadLocal values. Caching a connection per thread was smart with 200 threads and catastrophic with a million. JEP 444 warns about this explicitly; scoped values are the intended replacement.
Forgetting that unbounded concurrency is still unbounded. A million virtual threads can open a million database connections. Throttle with a Semaphore.
Expecting jstack to work. Traditional thread dumps list only platform threads. Use jcmd <pid> Thread.dump_to_file -format=json.
setDaemon / setPriority on a virtual thread. Silently has no effect — they are always daemon and always normal priority.
Thinking they solve concurrency bugs. They do not. Part 2 applies in full: races, visibility, deadlocks — all identical.
Native and file I/O. Calls into native code still pin, and some filesystem operations do not unmount. The JDK compensates by temporarily growing the scheduler, but it is not free.

§9Recap

  • Little's Law forces thousands of concurrent requests; platform threads could not supply them.
  • The old choice was thread-per-request (readable, unscalable) or async (scalable, unreadable — no usable stack traces, no try/catch across steps).
  • A virtual thread is a java.lang.Thread scheduled by the JVM, not the OS — M:N onto carrier threads.
  • It unmounts on blocking I/O, releasing its carrier; its stack parks on the heap. Blocking becomes nearly free.
  • The scheduler is a FIFO work-stealing ForkJoinPool with parallelism = cores.
  • Never pool them. One virtual thread per task; limit concurrency with a Semaphore.
  • They are always daemon, fixed priority, and otherwise behave like any thread — existing libraries just work.
  • Pinning (blocking in synchronized on JDK 21–23, or in native code) blocks the carrier and kills scalability. JDK 24's JEP 491 fixes the synchronized case.
  • Structured concurrency (JEP 453) and scoped values (JEP 446) are the companion APIs — preview in Java 21.
  • Virtual threads give scale, not speed: great for I/O-bound concurrency, useless for CPU-bound work, and they fix none of part 2's safety problems.

Glossary

Virtual thread
A java.lang.Thread scheduled by the JVM, not the OS. Cheap and plentiful.
Platform thread
The traditional 1:1 wrapper around an OS thread.
Carrier
The platform thread a virtual thread is currently mounted on.
Mount / unmount
Placing a virtual thread on a carrier / stepping off it when blocking.
M:N scheduling
Many user-mode threads multiplexed onto fewer OS threads.
Pinning
A virtual thread that cannot unmount, so it blocks its carrier too.
Little's Law
concurrency = throughput × latency — why high throughput needs many in-flight tasks.
Thread-per-request
One thread owns one request end to end. Readable; only scalable with virtual threads.
Structured concurrency
Subtasks must complete within the block that started them (JEP 453, preview in 21).
Scoped value
An immutable, inherited alternative to ThreadLocal (JEP 446, preview in 21).
