Threads

Java › concurrency cluster · lesson 11, part 1 of 4 · DEEP — how a program does two things at the same time

Concurrency cluster: 1. Threads · 2. Sharing data safely · 3. Thread pools & futures · 4. Virtual threads

In one line — Normally your program reads your code one line at a time, top to bottom. That single line of reading is called a thread. Java lets you start more threads, so several lines of your code can be read at the same time. This part answers only three questions: what is a thread, how do I start one, and what does it do while it is alive. The trouble — what happens when two threads touch the same data — is part 2.

§1Where it fits

Everything you have learnt so far assumed one reader walking through your code. One call stack, one main, one thing happening at a time. That assumption is about to break, and almost every rule you know quietly depends on it.

This topic is the biggest one in Java, so it is split into four small lessons:

  • Part 1 (this one) — what a thread is, how to start one, what it does while it lives, and what it costs.
  • Part 2 — the hard bit: two threads touching the same data, and the three tools that fix it (synchronized, volatile, atomics).
  • Part 3 — how real programs actually do it: thread pools, Future, CompletableFuture, and the ready-made safe collections.
  • Part 4 — the modern answer: virtual threads in Java 21, and why they change the advice.

It leans on three earlier lessons. From lesson 3: every thread gets its own stack. From lesson 6: all threads share one heap. From lesson 7: a lambda is just a small block of work you can hand to someone else — which is exactly what you hand to a thread.

§2Why it exists — the problem before threads

Problem 1: your program spends most of its life waiting

Think about what a normal web server does for one request: read the request, ask the database, wait, call another service, wait, write the answer back. Measured honestly, the CPU does work for maybe a millisecond and then waits for fifty. During that wait a single-threaded program can do nothing at all. If a second user arrives, they simply queue behind the first one. Ten slow users and your program looks dead.

Waiting is not rare — it is the normal state of software. Disk, network, database, user input: all of them are thousands of times slower than the CPU. A thread that is waiting costs you almost nothing to have; what costs you is having nothing else ready to run.

Problem 2: you bought eight cores and are using one

A single CPU core really can only run one instruction stream at a time. Modern machines have many cores. A program with one thread can physically only ever use one of them, no matter how big the machine is. Everything else sits idle.

The fix: more than one line of execution

A thread is one independent path through your code — one "reader" with its own place in the program and its own scratch space. Give your program two threads and two things can be in flight at once: while thread A waits for the database, thread B serves another user; on a multi-core machine they can even run at the same instant on different cores (Oracle — Processes and Threads).

Two words people mix up.
Concurrency = your program is dealing with several tasks in the same period of time. This can happen on a single core, by switching quickly between them. It is about structure.
Parallelism = several tasks are literally running in the same instant, on different cores. It is about execution.
You write concurrency. The hardware decides how much of it becomes parallelism. A one-core machine runs your concurrent program correctly — just not faster.

Why not just use more processes?

A process is a whole running program with its own private memory — your JVM is one process. You could start ten JVMs instead of ten threads. Two reasons people don't: a process is expensive (its own memory space, its own JVM warm-up), and processes cannot see each other's objects, so passing data between them means serialising it across a pipe or a socket. Threads live inside one process and share its memory, so passing data is just passing a reference.

That same sharing is the gift and the curse. It makes threads cheap to talk to, and it is the entire reason part 2 exists.

§3How it works

What a thread owns, and what it shares

This single diagram explains most of concurrency. Each thread gets its own stack and its own program counter (the bookmark saying which instruction is next). Everything else — the heap with all your objects, the loaded classes, static fields — is shared by all of them.

Carry this rule with you: a local variable (or a method parameter) is automatically thread-safe, because each thread has its own copy on its own stack. A field of a shared object, or any static field, is automatically at risk. Almost every concurrency bug you will ever write is a shared field pretending to be a local.

Starting a thread

Two steps, always: (1) describe the work, (2) hand it to a thread and press start().

// 1. the work, as a Runnable: "something to run, returning nothing"
Runnable job = () -> System.out.println("hello from " + Thread.currentThread().getName());

// 2. the thread, and the button that actually makes it a thread
Thread t = new Thread(job, "worker-1");
t.start();
Naming the thread ("worker-1") costs nothing and will save you an hour one day, because the name is what you see in every stack trace and every thread dump. Always name your threads.
The classic beginner trap: t.run() instead of t.start(). run() is an ordinary method. Calling it just executes the body on your current thread — no new thread is created, and nothing is concurrent. Only start() asks the JVM for a new thread. The compiler will never warn you, because both are perfectly legal calls. You will see this proved in §7.

You may also see the older style, class MyTask extends Thread. Prefer Runnable: your task is a job, not a kind of thread, and extending Thread burns your one superclass slot for no benefit. The Runnable form is also what thread pools take (part 3).

The life of a thread

A thread moves through a small set of states, listed in Thread.State. Learn these six — they are what you read in a thread dump when production is stuck (Javadoc — Thread.State).

StateIn plain wordsHow it got there
NEWobject exists, not startednew Thread(...)
RUNNABLErunning right now, or queued waiting for a free CPU corestart()
BLOCKEDstuck at the door of a synchronized block someone else is insidelock contention
WAITINGparked until someone wakes it, with no deadlinewait(), join(), park()
TIMED_WAITINGsame, but with a deadlinesleep(ms), wait(ms), join(ms)
TERMINATEDfinished, for goodrun() returned or threw
RUNNABLE does not mean "running". Java merges "on a core" and "ready, waiting for a core" into one state, because the JVM does not control the OS scheduler. If you have 200 RUNNABLE threads on 8 cores, 192 of them are doing nothing at this instant — they are just in the queue.

Who decides which thread runs? The scheduler

Not you. The operating system's scheduler hands each RUNNABLE thread a small slice of core time (typically a few milliseconds), then saves its registers, loads another thread's, and lets that one run. That save/load is a context switch, and it is not free — it costs microseconds and throws away the CPU's caches. This is why "just add more threads" eventually makes a program slower: past a point you are paying for switching instead of working.

Two consequences you must accept emotionally, not just intellectually:

  • The order of events between threads is not defined. Run the same program twice and you can get two different outputs. You will see this in §7.
  • A thread can be paused anywhere — even halfway through count++. That one fact is the root of every race condition in part 2.

Thread.setPriority() exists but is only a hint, and different operating systems treat it differently. Never build correctness on priorities.

Interruption: how you stop a thread (and why you can't force it)

Java has no "kill this thread" button. Thread.stop() existed and was deprecated decades ago because killing a thread mid-update leaves shared objects half-written and broken forever (Oracle — Why Thread.stop is deprecated).

Instead there is interruption, which is a cooperative signal:

  • t.interrupt() sets a boolean flag on t — that is all it does.
  • If t is sleeping or waiting, that call also wakes it by throwing InterruptedException inside it (and clears the flag).
  • If t is busy computing, nothing happens unless t chooses to check Thread.currentThread().isInterrupted().
The rule for catching InterruptedException: either stop the work and return, or re-set the flag with Thread.currentThread().interrupt() so your caller can see it. Never write catch (InterruptedException e) {} — that silently throws away a shutdown request and is one of the most common causes of a service that will not stop.

Daemon threads, and when the JVM is allowed to exit

The JVM shuts down when the last non-daemon thread finishes — not when main finishes. So a forgotten background thread keeps your whole process alive. Mark a thread as a daemon (t.setDaemon(true), before start()) to say "this one does not count; kill it on exit". Use it for background helpers such as metric tickers; never for work that must complete, because a daemon is stopped abruptly with no chance to finish.

What a thread costs

A normal Java thread (now called a platform thread) is a thin wrapper around a real operating-system thread. Creating it is a system call, and each one reserves a stack — commonly around 1 MB of address space (tunable with -Xss). So:

  • Creating a thread per task is wasteful if tasks are small — the setup can cost more than the work. → thread pools, part 3.
  • You cannot have a million of them; a few thousand is the practical ceiling. → virtual threads, part 4.

§4When to use it

  • Keep something responsive. A UI or a server must not freeze while a slow job runs. Move the slow job to another thread.
  • Overlap waiting. Three independent HTTP calls take max(a,b,c) instead of a+b+c.
  • Use all the cores. Split a genuinely CPU-heavy job (image processing, big sort) across cores.
  • Background upkeep. Flushing logs, refreshing a cache, sending metrics — classic daemon work.
When not to. If the task is short and already fast, threads only add overhead and bugs. If the work is one unbroken chain where each step needs the previous step's answer, there is nothing to overlap. The correct first question is always "is there real waiting, or real parallel work, to win here?"

§5Explain it to a 12-year-old

Imagine cooking dinner alone. You put rice on to boil, and then you just stand there staring at the pot for twenty minutes before starting the curry. That is a one-thread program: most of the time is spent waiting while doing nothing.

A smarter cook starts the rice, and while it boils chops the onions. Same single pair of hands, same kitchen — but the waiting gaps are now filled. That is concurrency.

Now a friend joins you. Two pairs of hands, two chopping boards, genuinely doing two things in the same second. That is parallelism.

Each cook keeps their own chopping board and their own knife — nobody else can touch them. That is the thread's stack, and it is why local variables are safe. But the fridge and the spice rack are shared. That is the heap. And the moment you both reach for the last onion at the same time, you have discovered part 2 of this lesson.

§7In practice — five experiments, with real output

Run on JDK 1.8 — code/ConcurrencyDemo2.java. Every line below is actual output.

A. Everything already runs on a thread

static void log(String msg) {
    System.out.println("[" + Thread.currentThread().getName() + "] " + msg);
}
[main] main is running
You never opted in to threads. The JVM already started one for you and called it main. Every program you have written so far was a one-thread concurrent program.

B. run() versus start() — the proof

Thread t1 = new Thread(job, "worker-1");
System.out.println("state before start = " + t1.getState());
t1.run();    // plain method call: NO new thread
t1.start();  // real new thread
t1.join();   // wait for worker-1 to finish
System.out.println("state after join   = " + t1.getState());
state before start = NEW
[main] doing the work
[worker-1] doing the work
state after join   = TERMINATED
Identical code, two different thread names. run() printed [main] — the work happened on the caller. start() printed [worker-1]. If you ever "add threads" and the program gets no faster at all, check this first. Note also the states: NEW before, TERMINATED after — and join() is what guarantees we are looking after it finished.

C. Order between threads is not yours to decide

Thread a = new Thread(() -> { for (int i=1;i<=3;i++) log("tick "+i); }, "A");
Thread b = new Thread(() -> { for (int i=1;i<=3;i++) log("tock "+i); }, "B");
a.start(); b.start();
a.join();  b.join();
[A] tick 1
[A] tick 2
[B] tock 1
[B] tock 2
[B] tock 3
[A] tick 3
[main] both finished
A got two ticks in, B ran all three of its lines, then A finished. Run it again and you will very likely get a different order — this is the scheduler, not a bug. What is guaranteed: within one thread, order is kept (tick 1 always precedes tick 2), and after both join() calls, both threads are definitely done.

D. Sleep, states, and a polite interruption

Thread sleeper = new Thread(() -> {
    try { Thread.sleep(5000); log("woke up normally after 5s"); }
    catch (InterruptedException e) { log("interrupted -> stopping early"); }
}, "sleeper");
sleeper.start();
Thread.sleep(100);
System.out.println("sleeper state = " + sleeper.getState());
sleeper.interrupt();
sleeper state while sleeping = TIMED_WAITING
[sleeper] interrupted -> stopping early (flag now = false)
sleeper state after join     = TERMINATED
Three things worth stopping on. (1) A 5-second sleep ended after ~100ms — interrupt() woke it by throwing inside it. (2) The state while sleeping was TIMED_WAITING, exactly as the table predicted. (3) Look at flag now = false: throwing InterruptedException clears the interrupt flag. That is the subtle part — if you catch it and keep going, the information that someone asked you to stop is simply gone unless you call interrupt() again yourself.

E. A daemon does not hold the JVM open

Thread d = new Thread(ticker, "background-ticker");
d.setDaemon(true);   // must be set BEFORE start()
d.start();
[main] daemon started, isDaemon=true
[main] main ends - JVM exits anyway because only daemons are left
The ticker loops forever, yet the program ended. Delete the setDaemon(true) line and this program never exits — which is precisely how a hung service happens in production.
Predict, then run. (1) Call t1.start() twice. What exception, and why does the state machine make it unavoidable? (2) Remove both join() calls in experiment C — can "both finished" now print before tick 3? (3) Remove setDaemon(true) in E and time how long the program takes to exit.

§8Pitfalls

Calling run() instead of start(). Compiles, runs, and is completely sequential. The only clue is the thread name in your logs.
Expecting an order between threads. "It printed in the right order on my machine" is not a guarantee — it is luck that will change under load, on a different CPU, or after the JIT warms up.
Swallowing InterruptedException. An empty catch block destroys the only shutdown signal Java has. Stop, or re-interrupt.
Using Thread.stop() / suspend(). Deprecated for good reason: they can leave shared data permanently half-updated.
Forgetting an exception kills only that thread. A try/catch around t.start() catches nothing from inside the thread. The task dies quietly and your program carries on as if everything is fine.
sleep() as a synchronisation tool. "Sleep 100ms so the other thread finishes first" works on your laptop and fails in production. Use join(), a latch, or a future.
One thread per request. At 10,000 users that is 10,000 OS threads and ~10 GB of stack. Use a pool (part 3) or virtual threads (part 4).
setDaemon(true) after start(). Throws IllegalThreadStateException. The flag must be set while the thread is still NEW.

§9Recap

  • A thread is one independent path through your code. Your program already has one: main.
  • Concurrency = handling several tasks in the same period (structure). Parallelism = running them in the same instant (needs cores).
  • Threads exist for two reasons: fill the time your program spends waiting, and use all the cores.
  • Each thread owns its stack (so locals are safe); all threads share the heap and statics (so fields are not).
  • start() creates a thread; run() is just a method call on the current one.
  • States: NEW → RUNNABLE → (BLOCKED / WAITING / TIMED_WAITING) → TERMINATED, and TERMINATED is final.
  • The OS scheduler decides the order, and can pause a thread anywhere — even mid-statement.
  • You cannot kill a thread; you interrupt it, and it must cooperate. Never swallow InterruptedException.
  • The JVM exits when the last non-daemon thread ends.
  • A platform thread is an OS thread: ~1 MB of stack, real creation cost. That is why pools and virtual threads exist.

Glossary

Process
A running program with its own private memory. One JVM = one process.
Thread
One path of execution inside a process, with its own stack and program counter.
Platform thread
A normal Java thread, backed 1:1 by an OS thread. Costly (~1 MB stack).
Concurrency
Structuring a program so several tasks are in progress in the same period.
Parallelism
Several tasks literally executing in the same instant, on different cores.
Scheduler
The OS component that decides which RUNNABLE thread gets a core next.
Context switch
Saving one thread's CPU state and loading another's. Cheap but not free.
Runnable
A functional interface describing work that takes nothing and returns nothing.
Daemon thread
A background thread the JVM will not wait for at shutdown.
Interruption
A cooperative "please stop" flag; the only safe way to end a thread.
