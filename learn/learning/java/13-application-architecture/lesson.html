Application Architecture

Java › lesson 13 of 14 · DEEP — the weighted capstone: designing systems, not just classes

In one line — Architecture is how you arrange classes so the system stays easy to change and test as it grows. The core moves: keep each part doing one job (SOLID), depend on interfaces not concrete classes, wire dependencies from outside (dependency injection), and separate layers (web → service → data) so changing one doesn't ripple through the others.

§1Where it fits

This is your mission's target — the weighted capstone. It ties every earlier lesson together: types & interfaces (5), immutability & value objects (5, 6, 12), collections (8), and concurrency-safe design (11). Here the question shifts from "does this class work?" to "will this system still be changeable in two years?"

§2Why it exists

Software cost is dominated by change, not first write. Without structure, every feature touches everything, tests need the whole world spun up, and one change breaks three unrelated things (high coupling). Good architecture buys changeability: clear boundaries so a change stays local, and testability: parts you can test in isolation by swapping fakes for real dependencies (Martin, Clean Architecture; Bloch, Effective Java).

Layering & dependency direction

Dependency injection — wire from outside

Instead of a class building its own dependencies (new JpaUserRepo() — welded to one implementation), it receives them through its constructor. Now the caller decides what to pass: the real repo in production, a fake in tests. This is Dependency Inversion + Injection in practice, and it's why frameworks like Spring exist.

Composition & patterns, used idiomatically

Most reuse should be composition (hold a collaborator) not inheritance. The classic Gang-of-Four patterns are named solutions — Strategy (swap an algorithm via an interface), Factory (centralise construction), Adapter (make one API fit another), Observer (publish/subscribe). Use them when the shape fits, not as decoration.

The through-line: program to interfaces, inject dependencies, prefer immutability, keep each module's public surface small. Do those four and SOLID mostly falls out for free.

§4When to use

  • Interfaces + DI — anywhere you cross a boundary (DB, network, clock, randomness) so you can test without it.
  • Layering — separate web/transport, business logic, and persistence in any non-trivial app.
  • Strategy — when one step has several interchangeable algorithms.
  • Immutability (records) — for domain values passed around and across threads.
  • Package/module boundaries — expose a thin API, hide internals (private, package-private, JPMS).

§5Explain it to a 12-year-old

A good restaurant separates the waiter (takes orders), the chef (cooks), and the pantry (stores food). The chef doesn't care which pantry supplies the tomatoes — a fresh market or a can — as long as it fits the "give me tomatoes" slot (an interface). So you can swap suppliers without retraining the chef. If instead the chef personally grew every tomato, changing suppliers would mean rebuilding the whole kitchen. Architecture is keeping those jobs separate so any one can change on its own.

§6Connections

  • ← type-system-and-oop: interfaces + composition are the raw materials; SOLID is how you use them.
  • ← modern-java: sealed + records make domain models precise and immutable.
  • ← concurrency: stateless services + immutable values sidestep most threading bugs.
  • → tooling-and-ecosystem: modules, build tools, and tests enforce these boundaries mechanically.
  • Same idea elsewhere: SOLID, DI, and layering are language-agnostic — identical in C#, Python, Go, TypeScript.

§7In practice — dependency inversion, dissected

// The boundary: the service depends on THIS, not on a database.
interface UserRepository { Optional<User> findById(String id); }

// Business logic — knows nothing about JPA, SQL, or HTTP.
final class UserService {
    private final UserRepository repo;             // depend on the abstraction
    UserService(UserRepository repo) { this.repo = repo; } // injected from outside

    String greet(String id) {
        return repo.findById(id)
                   .map(u -> "Hi " + u.name())
                   .orElse("Unknown user");       // Optional from lesson 7
    }
}

// Production wires the real one; a test wires a fake — no DB needed.
UserService prod = new UserService(new JpaUserRepository(dataSource));
UserService test = new UserService(id -> Optional.of(new User("Ada")));
The whole point sits in that last line: because UserService only knows the UserRepository interface, the test hands it a one-line lambda fake and verifies the logic in microseconds — no database, no framework. Flip it around (a new JpaUserRepository() hard-coded inside the service) and the class becomes untestable and welded to one storage choice. Interface + injection is the smallest change that buys the most flexibility.
Design drill. Add email + SMS notifications to this app. Sketch it with a Notifier interface and two implementations injected into the service (Strategy pattern). Which SOLID letters did you just satisfy? (Hint: O — add a new notifier without editing the service; D — the service depends on the interface.)

§8Pitfalls

God classes. A class that does everything violates S and can't be tested. Split by responsibility.
Leaky layers. A controller reaching straight into the database skips the service and spreads logic everywhere.
Inheritance for reuse. Deep hierarchies to share a method are brittle — compose instead (lesson 5).
Over-engineering. Patterns and layers for a 200-line tool are cost, not value. Add structure as complexity demands.
New-ing dependencies inside a class. It couples you to one implementation and blocks testing. Inject them.
Anemic + leaky domain. Exposing mutable internals breaks encapsulation; prefer immutable value objects (records).

§9Recap

  • Architecture optimises for change and testability, not first-write speed.
  • SOLID = five habits; the practical core is "one job per class" + "depend on abstractions."
  • Program to interfaces and inject dependencies so you can swap and test.
  • Layer the system (web → service → data); dependencies point one way, across interfaces.
  • Prefer composition and immutability; use GoF patterns when the shape genuinely fits.
  • Keep module surfaces small; don't over-engineer — add structure as the system grows.

Glossary

Coupling / Cohesion
How much parts depend on each other / how focused a part is. Aim low coupling, high cohesion.
SOLID
Five design principles for changeable OO code.
Dependency Injection
Passing a class its collaborators from outside rather than constructing them.
Layered architecture
Separating presentation, business logic, and data with one-way dependencies.
Strategy pattern
Swap an algorithm behind a common interface.
Repository
An interface abstracting data access from business logic.
Immutability
Objects that don't change after creation; safe to share.
