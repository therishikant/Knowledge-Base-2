Tooling & Ecosystem

Java › lesson 14 of 14 · SKIM — how real Java projects are built, tested, and shipped

In one line — You rarely run javac by hand. A build tool (Maven or Gradle) compiles, fetches dependencies, runs tests, and packages a JAR — all from one command. Around it sits the ecosystem: a dependency repository, a test framework (JUnit), and profilers (JFR) to see what your program actually does at runtime.

§1Where it fits

The final, mostly-transferable lesson: the machinery that turns your source into a shippable artifact and keeps a team's project consistent. It closes the loop from lesson 1 (javac → bytecode) up to a real, deployable application.

§2Why it exists

A real app has dozens of libraries, hundreds of files, tests, and multiple environments. Compiling that by hand is impossible and non-repeatable. Build tools give a declarative, reproducible description of "how to build this," resolve the whole dependency tree automatically, and give everyone — you, your teammates, the CI server — the same build (Apache — What is Maven?).

Maven vs Gradle

Maven uses an XML pom.xml with a fixed lifecycle and strong conventions — predictable and everywhere. Gradle uses a concise Groovy/Kotlin script, is more flexible, and caches aggressively for speed. Both do the same three jobs: dependency management (declare a library + version, it fetches it and everything it needs), build lifecycle, and plugins (tests, packaging, coverage).

Testing & profiling

JUnit 5 is the standard test framework (@Test, assertions), usually with Mockito for fakes and AssertJ for fluent checks — and the DI design from lesson 13 is what makes units testable. Java Flight Recorder (JFR) records what the JVM does (allocations, locks, GC) with almost no overhead; view it in JDK Mission Control to find real bottlenecks instead of guessing.

Semantic versioning. Dependencies use MAJOR.MINOR.PATCH (e.g. 2.15.3): major = breaking, minor = new features, patch = fixes. Pin versions for reproducible builds.

§4When to use

  • Maven — teams that value convention and stability; the safe default.
  • Gradle — big/multi-module builds or Android; when you need speed and flexibility.
  • JUnit + Mockito — every project, from day one.
  • jlink / jpackage — shipping a small self-contained runtime.
  • JFR + Mission Control — diagnosing a real performance or memory problem in a running app.

§5Explain it to a 12-year-old

Building a Lego castle from a huge box, you don't hunt for each brick yourself. The build tool is a helper who reads your instruction sheet, fetches every needed brick set from the warehouse (dependencies), snaps them together (compile), checks it doesn't fall over (test), and boxes the finished castle (package) — all when you say one word. And a profiler is a stopwatch that watches which room took longest to build, so you fix the real slow part instead of guessing.

§6Connections

  • ← jvm-bytecode-pipeline: the tool just orchestrates the javac→java steps from lesson 1.
  • ← application-architecture: DI and interfaces are what make the JUnit tests fast and isolated.
  • ← modern-java: jlink and modules (JPMS) shrink and lock down what you ship.
  • ← memory-model-and-gc: JFR is how you actually watch GC and allocation in production.
  • Same idea elsewhere: npm (JS), pip/Poetry (Python), Cargo (Rust) play Maven/Gradle's role — same concept, different files.

§7In practice — a minimal pom.xml, dissected

<project>
  <groupId>com.example</groupId>          // who owns it
  <artifactId>myapp</artifactId>            // this project's name
  <version>1.0.0</version>                  // its version (semver)

  <dependencies>
    <dependency>                          // declare a library...
      <groupId>org.junit.jupiter</groupId>
      <artifactId>junit-jupiter</artifactId>
      <version>5.10.2</version>
      <scope>test</scope>                    // ...only needed for tests
    </dependency>
  </dependencies>
</project>
Those three coordinates — groupId : artifactId : version — are how Maven finds any library in the world (Maven Central). You declare JUnit once and Maven downloads it and everything it depends on, at the right versions. scope=test keeps it out of your shipped JAR. This tiny file is a full, reproducible recipe: anyone running mvn package gets the identical build.
Try it. Run mvn dependency:tree (or gradle dependencies) on any project. You'll see the transitive dependencies — the libraries your libraries pull in. (Predict: how many total dependencies does adding one web framework really bring in?)

§8Pitfalls

Dependency conflicts ("JAR hell"). Two libraries want different versions of a third. Use dependency:tree and pin/exclude.
Unpinned/SNAPSHOT versions. Non-reproducible builds. Pin exact versions for releases.
Committing build output. target/ and build/ belong in .gitignore, not the repo.
Guessing at performance. Profile with JFR before optimizing; intuition about hotspots is usually wrong.
Skipping tests in the build. Tests in the lifecycle are your safety net; don't -DskipTests as a habit.
Security: stale dependencies. Old libraries carry known CVEs. Scan (e.g. OWASP Dependency-Check) and update.

§9Recap

  • A build tool (Maven/Gradle) compiles, resolves dependencies, tests, and packages — one command, reproducible.
  • Under it are the JDK commands: javac, java, jar, jlink, jshell.
  • Maven = XML + convention; Gradle = script + flexibility + caching. Same three jobs.
  • Libraries are addressed by group : artifact : version; declare one, get its transitive tree.
  • JUnit (+ Mockito) for tests — enabled by the DI design from lesson 13.
  • JFR + Mission Control to measure real runtime behaviour; profile before optimizing.

Glossary

Build tool
Automates compile → test → package with dependency resolution (Maven/Gradle).
JAR
A ZIP of compiled classes + resources; the standard Java artifact.
Dependency
An external library your project uses, addressed by group:artifact:version.
Transitive dependency
A dependency pulled in by one of your dependencies.
Lifecycle / phase
Maven's ordered build steps (validate→compile→test→package→install→deploy).
JUnit
The standard Java unit-testing framework.
JFR
Java Flight Recorder — low-overhead runtime event recording.
jlink
Builds a minimal custom runtime image from modules.
