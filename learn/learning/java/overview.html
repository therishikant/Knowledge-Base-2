The picture in 30 seconds

Java is a language built for big programs, for doing many things at once, and around objects. Its main idea is "write once, run anywhere." You never ship code made for one kind of computer. You ship .class files full of bytecode, and any Java Virtual Machine (JVM) can load it, check it, speed it up, and run it on any system. The JVM only understands bytecode — it does not even know the word "Java" (Oracle, JVM Spec SE 21, §1.2). That one choice — putting a small machine between your code and the hardware — is the reason behind almost everything we will study: running anywhere, safety, automatic memory cleanup, speed-up at run time, and the rules for sharing memory.

Why learn how it's built first?

Most Java courses teach the words and rules. But you already write Java. What helps you now is knowing why Java behaves the way it does: why generics disappear at run time, why equals and hashCode always go together, why sharing data between threads needs rules, why records and sealed types were added, why virtual threads change how servers are built. Each lesson starts with how the JVM works, then shows the design choice it leads to.

Glossary (quick reference)

JVM
A small machine that loads and runs .class bytecode. It gives Java "runs anywhere" and safety.
Bytecode
The simple instructions inside a .class file — what javac makes.
JDK / JRE
JDK = tools to build Java (like the compiler) plus a way to run it. JRE = just the run part (the JVM + libraries).
Class loading
Bringing a class in: load → link (check, set up, wire) → start (JVM Spec Ch. 5).
JIT
The part that turns busy bytecode into fast machine code while the program runs.
GC
Garbage Collection: automatically clears out objects you no longer use.
Erasure
Generic types exist only when you build; they are removed from the bytecode (to stay compatible with old code).
Happens-before
The rule that makes one thread's writes visible to another thread.
LTS
Long-Term-Support version (8, 11, 17, 21) — the ones companies usually stick with.
