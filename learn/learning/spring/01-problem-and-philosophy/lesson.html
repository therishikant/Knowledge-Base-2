Problem & Philosophy

Spring & Spring Boot › lesson 1 of 18 · DEEP — why this framework exists at all

In simple English — In a real server application, writing the business logic is easy; the painful part is building and connecting hundreds of objects in the right order and repeating the same plumbing code (opening database connections, committing/rolling back transactions, parsing HTTP URLs, converting JSON) in every single class. Spring's core idea is Inversion of Control (IoC): you write plain Java classes that simply ask for what they need in their constructor, and Spring's machine builds them, connects them, and wraps them with transaction/security plumbing automatically.

Across this entire 18-lesson course, every piece of Spring Boot fits into one 3-Phase Timeline and 6 Core Boxes. Before we open Box 1 or Box 2, this first lesson shows you why those 6 boxes had to be invented in the first place.

§2Why it exists — write BookVault in plain Java first

Let's build a small slice of BookVault (our course project) with zero frameworks: an HTTP endpoint that looks up a book in a relational database and returns JSON. Watch how quickly clean business code drowns in repetitive plumbing.

Step 1 — The business logic (this part is already clean!)

public class BookService {
    private final BookRepository repo;

    // Notice: BookService does NOT call "new JdbcBookRepository()".
    // Someone outside hands it an implementation of BookRepository.
    public BookService(BookRepository repo) {
        this.repo = repo;
    }

    public Book findById(long id) {
        return repo.findById(id)
                   .orElseThrow(() -> new BookNotFound(id));
    }
}
Crucial realization: BookService is already using Dependency Injection! Dependency Injection is just a fancy name for "pass the helper objects into the constructor instead of calling new inside the class." You do not need Spring to do Dependency Injection. You need Spring because of what happens in Steps 2, 3, and 4.

Step 2 — Pain #1 & #4: The manual wiring & config mess in main() / init()

If BookService doesn't call new JdbcBookRepository(), somebody has to. In a plain Java app with 200 classes, your startup method turns into a fragile 500-line assembly script where you must instantiate every leaf object before the object that needs it: 

public class BookServlet extends HttpServlet {
    private BookService service;
    private HikariDataSource ds;

    @Override
    public void init() {
        // PAIN #4 (Config): Reading raw strings by hand, no type safety, no profiles
        this.ds = new HikariDataSource();
        ds.setJdbcUrl(System.getProperty("db.url"));
        ds.setUsername(System.getProperty("db.user"));

        // PAIN #1 (Wiring): You must build objects in exact bottom-up dependency order!
        BookRepository repo = new JdbcBookRepository(ds);
        this.service = new BookService(repo);
        // And who remembers to call ds.close() when the server stops?
    }

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse res) throws IOException {
        // PAIN #3 (Web plumbing): Manual URL string chopping, headers, and JSON writing
        long id = Long.parseLong(req.getPathInfo().substring(1));
        Book b = service.findById(id);
        res.setContentType("application/json");
        res.getWriter().write(new ObjectMapper().writeValueAsString(b));
    }
}

Step 3 — Pain #2: The JDBC & manual transaction nightmare

Now look at what happens when you have to run two database updates in a single atomic transaction (for example, reserving inventory and charging a payment). Without a framework, you have to write this try / catch / finally block in every single service method: 

public void checkout(Order order) {
    Connection c = null;
    try {
        c = ds.getConnection();
        c.setAutoCommit(false);          // 1. start transaction

        inventory.reserve(c, order);     // ← HORRIBLE: Connection 'c' must be passed as a
        payments.charge(c, order);       //   parameter into EVERY business method!

        c.commit();                      // 2. commit if both succeeded
    } catch (Exception e) {
        if (c != null) try { c.rollback(); } catch (SQLException ignored) {}
        throw new RuntimeException(e);
    } finally {
        if (c != null) try { c.setAutoCommit(true); c.close(); } catch (SQLException ignored) {}
    }
}
Look at what went wrong here: (1) 14 lines of identical try/catch/finally boilerplate surround 2 lines of business work, and (2) the low-level JDBC Connection c polluted the method signature of reserve() and charge()! If you forget c.close() in one branch, your database connection pool runs dry at 2 a.m.

§3How it works — Plain Java first, then Spring

Level 1 Zoom: Inversion of Control (IoC) vs Dependency Injection (DI)

Interviewers love to ask: "What is the difference between Inversion of Control and Dependency Injection?" Let's strip away the academic jargon:

  • Inversion of Control (IoC) is the broad rule: "Don't call us, we'll call you." When you use a normal library (like StringUtils or ArrayList), your code is the boss: your main() method runs the loop and calls the library whenever it wants. When you use a framework (like Spring, JUnit, or Tomcat), the framework is the boss: it owns the main loop and calls your methods when an event happens.
  • Dependency Injection (DI) is one specific way to do IoC for building objects (Martin Fowler — Inversion of Control Containers and the Dependency Injection pattern): instead of `BookService` reaching out to create or look up its `BookRepository`, the outside caller pushes (injects) the `BookRepository` into `BookService`'s constructor.

Level 2 Zoom: Step-by-Step Control Flow (Hand-Rolled vs Spring)

How the control flow changes when you move from plain Java to Spring:
  1. Step 1 (You write classes): You write BookService(BookRepository repo) and put a sticky-note annotation @Service on top. The annotation does nothing by itself — it is just a passive label in the compiled .class file.
  2. Step 2 (Box 2 — Recipe Scan): When SpringApplication.run() starts, Spring scans your package folders for classes with @Component / @Service / @Repository and puts a recipe (BeanDefinition) for each class into a Map<String, BeanDefinition>.
  3. Step 3 (Box 3 — Recursive Creation): Spring loops through the Recipe Map. To build bookService, it inspects its constructor via Java Reflection, sees it needs a BookRepository, builds jdbcBookRepository first, and calls new BookService(jdbcBookRepository).
  4. Step 4 (Box 4 — Proxy Wrapping): Before putting bookService into the live warehouse (Map<String, Object> singletonObjects), Spring checks if any method has @Transactional. If yes, it wraps your BookService inside a generated Proxy object that opens and commits database transactions around your method.

What the exact same BookVault code looks like with Spring

@Service                                        // Sticky note for Box 2: "put my recipe in the Recipe Map"
public class BookService {
    private final BookRepository repo;

    public BookService(BookRepository repo) {     // Box 3 calls this constructor and passes the repo
        this.repo = repo;
    }

    @Transactional(readOnly = true)              // Box 4 wraps this class in a Proxy that opens/closes the DB TX
    public Book findById(long id) {
        return repo.findById(id).orElseThrow(() -> new BookNotFound(id));
    }
}

@RestController                                 // Sticky note for Box 6: "register my methods in DispatcherServlet"
class BookController {
    private final BookService service;
    BookController(BookService service) { this.service = service; }

    @GetMapping("/books/{id}")                   // Box 6 parses {id} and converts the returned Book to JSON
    Book get(@PathVariable long id) {
        return service.findById(id);
    }
}
The POJO Principle (Why Spring beat EJB 2): Look closely at BookService above. Does it extend SpringService? No. Does it implement a framework interface? No. If you strip off the annotations, it compiles and runs as a Plain Old Java Object (POJO). In 2002, Java's official enterprise standard (EJB 2) forced every class to implement bulky framework interfaces that couldn't be instantiated in a unit test. Rod Johnson created Spring specifically to prove that a container should serve plain Java objects, not enslave them (Spring Framework Reference — Introduction to the Spring IoC Container and Beans).

§5Explain it to a 12-year-old

Imagine you are putting on a school play with 50 actors.

In the No-Spring Play, the moment the curtain rises, every actor has to run out to the shops to buy their own hat, hammer together their own wooden sword, plug in the stage lights, and remember to turn the lights off before walking offstage. If you want to do a rehearsal in the classroom with plastic swords instead of real ones, you can't — because every actor has "buy real metal sword from Main Street" tattooed onto their arm!

In the Spring Play, there is a Stage Crew (the Container). Actors aren't allowed to build their own props. Instead, an actor simply says: "To do my scene, somebody needs to hand me a Sword." Before the show starts, the Stage Crew reads every actor's wish list, builds all the props in the backstage warehouse, and hands each actor what they asked for.

"Wait — why does having a Stage Crew help with database transactions?" Because the Stage Crew is the one handing out props, they can play a clever trick: before handing Actor A to Actor B, the Stage Crew puts a look-alike stunt double (a Proxy) in front of Actor A. Whenever anyone talks to Actor A, the stunt double secretly turns on the microphone first, lets Actor A speak their lines, and turns the microphone off afterwards. Actor A just acts; the stunt double handles the switches!

§7In practice — runnable plain-Java DI + Proxy demo & Interview Derivation

Let's prove two things in runnable Java 8 code with zero libraries: (1) Dependency Injection is just passing an interface into a constructor, and (2) a Proxy is just a wrapper class implementing the same interface. 

// Full runnable file: learn/learning/spring/code/01-no-spring/DiByHand.java
interface BookRepository {
    Optional<Book> findById(long id);
}

// 1. Real implementation
static class InMemoryBookRepository implements BookRepository {
    private final Map<Long, Book> data = new HashMap<Long, Book>();
    InMemoryBookRepository() { data.put(1L, new Book(1, "Dune", "Herbert")); }
    public Optional<Book> findById(long id) { return Optional.ofNullable(data.get(id)); }
}

// 2. Test Fake — zero Mockito needed!
static class AlwaysEmptyRepository implements BookRepository {
    public Optional<Book> findById(long id) { return Optional.empty(); }
}

// 3. Hand-written Proxy wrapper — implements the SAME interface and wraps a target!
static class LoggingBookRepository implements BookRepository {
    private final BookRepository delegate;
    LoggingBookRepository(BookRepository delegate) { this.delegate = delegate; }
    public Optional<Book> findById(long id) {
        System.out.println("  [log] looking up " + id);   // extra plumbing BEFORE
        return delegate.findById(id);                     // call the real target
    }
}

// 4. Business class — has NO IDEA which of the 3 it was handed!
static class BookService {
    private final BookRepository repo;          // final = immutable, thread-safe
    BookService(BookRepository repo) {          // <-- THE injection point
        this.repo = repo;
    }
    String describe(long id) {
        return repo.findById(id).map(b -> b.title() + " by " + b.author()).orElse("not found");
    }
}

// 5. The Composition Root (in Spring, Box 3 + Box 4 do these exact 3 lines automatically)
public static void main(String[] args) {
    BookService real    = new BookService(new InMemoryBookRepository());
    BookService test    = new BookService(new AlwaysEmptyRepository());
    BookService audited = new BookService(new LoggingBookRepository(new InMemoryBookRepository()));

    System.out.println(real.describe(1));
    System.out.println(test.describe(1));
    System.out.println(audited.describe(1));
}

not found
  [log] looking up 1
Dune by Herbert
Code Dissection (code/01-no-spring/DiByHand.java):
  • Chunk 1–2 (Polymorphism): BookService only knows the interface BookRepository. Swapping from real storage to AlwaysEmptyRepository required changing zero lines inside BookService.
  • Chunk 3 (The Proxy secret): Look at new BookService(new LoggingBookRepository(new InMemoryBookRepository())). Because LoggingBookRepository implements BookRepository, BookService thinks it is talking directly to the repository, while the wrapper intercepts every call. In Lesson 04 and Lesson 06, you will see that Spring's @Transactional is literally an automated version of LoggingBookRepository!
Try this / Predict the output: Open code/01-no-spring/DiByHand.java and add a second method int count() to BookRepository that calls findById(1) internally inside InMemoryBookRepository. If BookService calls repo.count() through LoggingBookRepository, will [log] looking up 1 be printed when InMemoryBookRepository.count() calls this.findById(1)?
Answer: No! Once execution is inside InMemoryBookRepository, calling this.findById(1) calls the raw target object directly, bypassing the outer LoggingBookRepository wrapper! You just discovered Universal Rule #2 (Who You Call: Proxy vs this) — the #1 Spring interview question in the world.

How to Think in Interviews — Derive, Don't Memorize

Every lesson in this course ends with a table showing how to derive classic interview answers in 10 seconds using the 6-Box Map and the 3 Universal Rules (Rule 1: Order of Steps · Rule 2: Who You Call · Rule 3: Where State Lives):

Classic Interview QuestionWhich Box / Rule to Picture10-Second Derived Answer
"What is the difference between IoC and DI?" Box 3 (Object Warehouse) IoC is the general principle that the framework owns the flow and calls your code (Servlets and JUnit do IoC too). DI is the specific form of IoC where the container supplies an object's dependencies through its constructor instead of the object calling new or looking them up.
"Why is Dependency Injection better than the Service Locator pattern (calling ctx.getBean() inside your class)?" POJO Principle + Box 3 If BookService calls ctx.getBean(BookRepository.class), it now compiles against Spring and hides what it needs inside method bodies. With constructor DI, BookService has zero Spring imports and you can test it with new BookService(fakeRepo) in 1 millisecond.
"What do annotations like @Service or @Transactional actually do at runtime?" Box 2 (Recipes) & Box 4 (Proxy Inspector) By themselves, nothing — they are passive bytecode labels. They only work because Box 2 scans for @Service to create recipes, and Box 4 inspects beans for @Transactional and wraps them in a Proxy.
"If I instantiate a class myself with new BookService(repo) inside a Spring app, why does @Transactional stop working on it?" Rule 2 (Who You Call) + Box 4 Because you bypassed Box 3 and Box 4! When you call new yourself, Box 4's BeanPostProcessor never gets a chance to wrap that object in a Transaction Proxy. You are calling the raw target object directly.

§8Pitfalls

Pitfall 1: Thinking "Spring = Annotations." Annotations are passive sticky notes. Putting @Transactional or @Autowired on a class that Spring did not create (for example, an object you created with new) does nothing at all, because that object never went through Box 3 and Box 4.
Pitfall 2: Re-inverting control with Service Locator (context.getBean()). Injecting ApplicationContext into your business service and calling context.getBean(PaymentGateway.class) turns Spring back into a manual lookup dictionary. Your class's constructor now lies about what collaborators it needs, and unit tests must mock the entire Spring container. Always ask for the dependency directly in the constructor.
Pitfall 3: Using field injection (@Autowired private BookRepository repo;) out of habit. If a field is private and has no constructor parameter, the only way to set it in a unit test is ugly reflection or booting the Spring container. Use a constructor with private final fields so your class works with plain new.

§9Recap & Glossary / Reference

  • The 4 Pains of Plain Java: Manual startup wiring in topological order (Pain #1), repetitive transaction/JDBC plumbing that leaks Connection into method signatures (Pain #2), manual HTTP/JSON parsing (Pain #3), and raw string config (Pain #4).
  • The 6 Boxes solve the 4 Pains: Box 1 (Environment), Box 2 (BeanDefinition Recipe Map), Box 3 (Singleton Object Warehouse), Box 4 (BeanPostProcessor Proxy Wrapper), Box 5 (Tomcat + FilterChain), Box 6 (DispatcherServlet + ThreadLocal).
  • IoC vs DI: IoC = the framework calls you. DI = dependencies are handed to your constructor from outside instead of created with new.
  • POJO Principle: Your business classes should remain plain Java classes with constructor injection so they can be tested with plain new without booting Spring.

Glossary

Inversion of Control (IoC)
Design principle where the framework controls the execution flow and object creation instead of application code.
Dependency Injection (DI)
A specific form of IoC where an object receives its collaborators from an external caller (ideally via constructor parameters) rather than instantiating them itself.
POJO (Plain Old Java Object)
An ordinary Java class that does not extend framework-specific base classes or implement framework-specific interfaces.
Bean
Any normal Java object whose creation, wiring, and lifecycle are managed by the Spring container (stored in Box 3).
Composition Root
The single place in an application where concrete implementations are chosen and wired together (main() in plain Java; ApplicationContext in Spring).
Proxy
A wrapper object that implements the same interface (or subclasses the same class) as your real bean, intercepting method calls to add transactions, security, or logging (created in Box 4).
