The IoC Container & Beans

Spring & Spring Boot › lesson 2 of 18 · DEEP — the engine room (Boxes 2 & 3)

In simple English — The Spring IoC Container is literally two Java Maps that run one after the other at startup. First, Spring builds Box 2 (The Recipe Book): a Map<String, BeanDefinition> that lists what classes could be created, before any business object exists. Second, Spring builds Box 3 (The Object Warehouse): a Map<String, Object> singletonObjects by looping over the recipes and calling constructors via reflection. Keeping recipes separate from live objects is **Universal Rule #1 (Order of Steps)** and explains nearly every startup error in Spring.

§2Why it exists — why not just call new immediately?

Suppose you were asked to write a program that scans a folder for `@Component` classes and creates one instance of each. Your first instinct in plain Java would be a single loop: "As soon as I see `BookService.class` on disk, call `new BookService(...)` right away!"

Why would that single-loop approach crash immediately in a real project? Because of four problems: 

// ❌ THE NAIVE SINGLE-PASS IDEA (Why scanning + instant 'new' fails)
for (Class<?> clazz : scanFolder("com.bookvault")) {
    // Problem 1 (Ordering): Scan finds BookService.class alphabetically BEFORE JdbcBookRepository.class!
    //   We can't call new BookService(repo) yet because 'repo' hasn't been scanned or created!
    // Problem 2 (Conditions): What if a @Bean later says "only create this if no other DataSource exists"?
    //   You can't know if another DataSource exists until you've finished reading ALL classes!
    // Problem 3 (Placeholders): What if a class needs "${db.url}", and a config post-processor
    //   needs to replace "${db.url}" before any constructor runs?
    // Problem 4 (Scopes): What if Ticket is marked @Scope("prototype") and shouldn't be created at boot?
    Object obj = clazz.getDeclaredConstructor().newInstance(); // 💥 CRASH!
}

To solve all four problems cleanly, Spring splits startup into two separate phases (**Universal Rule #1: Recipes before Objects**):

  1. Phase 1A (Box 2 — Fill the Recipe Book): Scan everything first and write down a metadata recipe (BeanDefinition) for each class inside Map<String, BeanDefinition>. Zero business constructors have been called yet! Because they are just recipes in a Map, Spring can inspect the whole picture, check conditions, and fill in ${...} placeholders before cooking a single object.
  2. Phase 1B (Box 3 — Cook the Objects into the Warehouse): Loop over the finished Recipe Book, recursively create dependencies in the right order, and store the finished singleton objects in Map<String, Object> singletonObjects.

§3How it works — Plain Java Data Structures First

Level 1 Zoom: The Two Maps inside the Container

Forget the long Spring class names for 60 seconds. In plain Java, the entire IoC container is just a class holding two `Map`s and a `Set`: 

public class PlainJavaContainer {
    // BOX 2: The Recipe Book (key = bean name like "bookService", value = metadata recipe)
    // In real Spring: DefaultListableBeanFactory.beanDefinitionMap
    private final Map<String, BeanDefinition> beanDefinitionMap = new ConcurrentHashMap<>();

    // BOX 3: The Singleton Object Warehouse (key = bean name, value = the live Java object)
    // In real Spring: DefaultSingletonBeanRegistry.singletonObjects
    private final Map<String, Object> singletonObjects = new ConcurrentHashMap<>();

    // Breadcrumb trail of beans currently halfway through construction (detects A -> B -> A cycles!)
    // In real Spring: DefaultSingletonBeanRegistry.singletonsCurrentlyInCreation
    private final Set<String> singletonsCurrentlyInCreation = new HashSet<>();
}
The Golden Sentence of Spring: "A BeanDefinition (Box 2) is a recipe card; a Bean (Box 3) is the cooked dish."
  • When Spring throws NoSuchBeanDefinitionException, it means Box 2 (the Recipe Map) didn't have a recipe card matching the type you asked for (maybe you forgot @Service or put the class in the wrong package).
  • When Spring throws BeanDefinitionOverrideException, it means two recipe cards tried to use the same key in Box 2's beanDefinitionMap.

How Bean Names (the Map Keys in Box 2 & Box 3) Are Chosen

Both `beanDefinitionMap` (Box 2) and `singletonObjects` (Box 3) use a **`String` bean name** as their Map key — not the `Class` object! When you ask for a bean by type (`getBean(BookRepository.class)`), Spring searches the values of `beanDefinitionMap` to find the matching String key first, then looks up that String key in `singletonObjects`.

  • For a scanned class @Service class BookService → key is "bookService" (first letter lowercased).
  • For a config method @Bean DataSource primaryDb() → key is "primaryDb" (the method name).
  • Edge case worth knowing: if the first two letters are capitalized (like URLParser), Java's Introspector.decapitalize leaves the name unchanged: "URLParser".

(Scope rules per Spring Framework Reference — Bean Scopes.)

Universal Rule #3 (Where State Lives): Singleton beans are shared by ALL threads! Because there is only one BookService instance inside Box 3's singletonObjects Map, if 200 users send HTTP requests at the same millisecond, 200 Tomcat threads (Box 5) execute methods on that exact same BookService object simultaneously! Never store per-user data in an instance field of a singleton bean (e.g. private User currentUser;) — User B will overwrite User A's field! Keep per-request data in local variables/method parameters (which live on each thread's own call stack) or in ThreadLocal (Box 6).

§4When to use

GoalWhat to UseTrade-off / Rule to Remember
Stateless service, controller, repository, or client Default singleton scope (do nothing) Zero GC allocation per request; must be 100% thread-safe (no mutable fields).
Need a fresh stateful builder/command object on every method call inside a Singleton @Scope("prototype") on the target + inject ObjectProvider<T> into the Singleton If you inject T directly into a singleton constructor, the constructor only runs once at boot, so you get 1 instance forever! Calling provider.getObject() asks Box 3 for a fresh instance each time.
A heavyweight bean (e.g., PDF report engine) is rarely used and slows down local startup @Lazy Skips eager creation in Step 5 of refresh(); trades away fail-fast startup validation for faster boot time.

§5Explain it to a 12-year-old

Think of Spring's container as a Restaurant Kitchen preparing for dinner service.

Box 2 (beanDefinitionMap) is the Recipe Binder on the counter. At 3 p.m., the Head Chef walks through the kitchen, collects every recipe card, and puts them in a binder. Not a single pot of soup has been cooked yet! Because they are still just paper cards, an assistant chef (a BeanFactoryPostProcessor) can walk by with a pen and cross out "secret-spice-placeholder" and write in "paprika" on all the cards before the stoves are even turned on.

Box 3 (singletonObjects) is the Steam Table of Big Pots. At 4:30 p.m. (before the restaurant doors open at 5 p.m.), the cooks read the Recipe Binder and cook one giant pot of each Singleton dish. Why cook them before customers arrive? Because if the kitchen is missing tomatoes, you want the alarm to ring at 4:30 p.m. while you can still fix it — not at 8 p.m. when a customer orders!

And what is a Prototype bean? That's a Cook-to-Order Ice Cream Cone. You can't put an ice cream cone in a hot steam table at 4:30 p.m.! So whenever someone asks for one, the kitchen makes a brand-new cone, hands it over the counter, and never sees it again — which is also why the kitchen can't clean up your cone when you finish eating it (no @PreDestroy on prototypes!).

§7In practice — Build Box 2 & Box 3 in 60 lines of Java & Interview Derivation

Let's look at code/02-mini-container/MiniContainer.java. This 60-line class implements Box 2 (`definitions`), Box 3 (`singletons`), recursive dependency ordering, circular dependency detection (`inCreation`), and the Box 4 proxy hook (`postProcess`) using nothing but plain Java: 

// Full runnable file: learn/learning/spring/code/02-mini-container/MiniContainer.java
static class Container {
    // BOX 2 — The Recipe Book (Spring: DefaultListableBeanFactory.beanDefinitionMap)
    private final Map<String, Class<?>> definitions = new LinkedHashMap<String, Class<?>>();
    // BOX 3 — The Singleton Object Warehouse (Spring: DefaultSingletonBeanRegistry.singletonObjects)
    private final Map<String, Object> singletons = new HashMap<String, Object>();
    // Cycle detector (Spring: singletonsCurrentlyInCreation)
    private final Set<String> inCreation = new LinkedHashSet<String>();

    // PHASE 1A (Fill Box 2): Register recipes by bean name. Zero objects created here!
    void register(Class<?>... classes) {
        for (Class<?> c : classes) {
            if (!c.isAnnotationPresent(MiniComponent.class))
                throw new IllegalArgumentException(c + " is not a @MiniComponent");
            definitions.put(name(c), c);           // "BookService" -> key "bookService"
        }
    }

    // PHASE 1B (Fill Box 3): Eagerly build every non-prototype recipe at startup
    void refresh() {
        for (Map.Entry<String, Class<?>> e : new ArrayList<>(definitions.entrySet())) {
            if (!isPrototype(e.getValue())) getBean(e.getKey());
        }
    }

    Object getBean(String n) {
        Object cached = singletons.get(n);                       // Step 1: Already in Box 3? Return it!
        if (cached != null) return cached;

        Class<?> type = definitions.get(n);                      // Step 2: Look up recipe in Box 2
        if (type == null) throw new IllegalStateException("No bean named '" + n + "'");
        if (!inCreation.add(n))                                  // Step 3: Already inCreation? Cycle!
            throw new IllegalStateException("Circular dependency: " + inCreation + " -> " + n);
        try {
            Constructor<?> ctor = type.getDeclaredConstructors()[0];
            Class<?>[] paramTypes = ctor.getParameterTypes();
            Object[] args = new Object[paramTypes.length];
            for (int i = 0; i < paramTypes.length; i++)
                args[i] = getBean(paramTypes[i]);                // Step 4: RECURSION builds dependencies first!

            ctor.setAccessible(true);
            Object bean = ctor.newInstance(args);                // Step 5: Call constructor
            bean = postProcess(bean);                            // Step 6: Box 4 Proxy hook!
            if (!isPrototype(type)) singletons.put(n, bean);     // Step 7: Cache ONLY singletons in Box 3
            return bean;
        } catch (ReflectiveOperationException e) {
            throw new IllegalStateException("Failed to create bean '" + n + "'", e);
        } finally {
            inCreation.remove(n);
        }
    }
}

Code Dissection (code/02-mini-container/MiniContainer.java):
  • Why did BookRepository print before BookService even though we registered BookService first? In main(), we called ctx.register(BookService.class, BookRepository.class, Ticket.class). When refresh() started with getBean("bookService"), Step 4 inspected BookService(BookRepository) and recursively called getBean(BookRepository.class) before calling new BookService(...)! Recursion automatically topologically sorts your dependency graph.
  • Why did same prototype? print false? Look at Step 7: if (!isPrototype(type)) singletons.put(n, bean);. Because Ticket is a prototype, it is never put into singletons (Box 3), so Step 1 (singletons.get("ticket")) always returns null and cooks a fresh Ticket every time!

Answer: Only ONE! Why? Trace the code above: the second time you call ctx.getBean("bookService"), Step 1 hits singletons.get("bookService") and returns the cached BookService immediately! BookService's constructor never runs a second time, so getBean(Ticket.class) is never called a second time.

How to Think in Interviews — Derive, Don't Memorize

Classic Interview QuestionWhich Box / Rule to Picture10-Second Derived Answer
"What is the difference between a Spring Singleton and the Gang-of-Four (GoF) Singleton pattern?" Box 3 (singletonObjects Map) A GoF Singleton uses a private static field, so there is 1 instance per ClassLoader / JVM and it is hard to unit-test. A Spring Singleton is just a normal POJO stored once as a value inside Box 3's Map<String, Object> — so there is 1 instance per ApplicationContext, and you can still call new in unit tests.
"Are Spring singleton beans thread-safe?" Rule 3 (Where State Lives) + Box 3 & Box 5 No, Spring does not synchronize your bean! Box 3 holds 1 shared instance in singletonObjects while Box 5's Tomcat thread pool runs 200 request threads through it concurrently. Stateless beans (final dependencies only) are completely thread-safe; mutable fields on a singleton cause data races.
"What happens when you inject a Prototype bean into a Singleton bean, and how do you fix it?" Rule 1 (Order of Steps) + Box 3 The Singleton's constructor runs only once at startup (when Box 3 populates singletonObjects), so it receives one Prototype instance and holds onto it forever. Fix it by injecting ObjectProvider<MyPrototype> (or using @Lookup) so each method call asks Box 3 for a fresh instance at runtime.
"What is the difference between BeanFactory and ApplicationContext?" Box 2 & Box 3 + refresh() BeanFactory is the core lazy lookup engine. ApplicationContext extends it and runs refresh() at boot to auto-register post-processors (Box 4), eagerly instantiate all singletons (Box 3) so config errors fail fast at startup, and add Environment (Box 1) and Events.
"Why doesn't Spring call @PreDestroy on a prototype bean?" Box 3 (singletonObjects Map) Because Box 3 only stores references to singleton beans. For a prototype, Spring creates the object and hands the reference to the caller without storing it in any Map — if Spring kept references to every prototype ever created just to call @PreDestroy at shutdown, your app would run out of memory!

§8Pitfalls

Pitfall 1: Storing request-specific data in a singleton field (Data Race). Writing private Long currentCustomerId; inside an @Service class means Customer A's HTTP thread and Customer B's HTTP thread will overwrite each other's ID inside Box 3's single shared object. Pass customerId as a method argument instead.
Pitfall 2: Enabling spring.main.allow-bean-definition-overriding=true to silence a startup error. When two beans share the same name key in Box 2's beanDefinitionMap, Spring Boot 2.1+ throws BeanDefinitionOverrideException at startup. Turning overriding back on means whichever recipe gets scanned last silently overwrites the other in the Map! Rename one of the beans instead.
Pitfall 3: Using @Lazy everywhere to hide broken beans. Marking beans @Lazy stops Step 5 of refresh() from creating them at boot. If a lazy bean has a missing dependency or broken SQL query, your server will boot "healthy" and then crash in production on the first user request that touches that bean.

§9Recap & Glossary / Reference

  • Two Maps, Two Phases (Rule #1): First fill Box 2 (Map<String, BeanDefinition> recipes), then fill Box 3 (Map<String, Object> singletonObjects live instances).
  • Map Keys are Bean Names: Both Maps are keyed by String bean name ("bookService"), not Class. Looking up by type searches Box 2's values first.
  • Dependency Ordering is Recursion: Calling getBean("bookService") recursively calls getBean() on each constructor parameter type before calling new.
  • Scopes: singleton = 1 per context, cached in Box 3, must be stateless (Rule #3). prototype = new every time, not cached in Box 3, never destroyed by Spring.

Glossary

BeanDefinition (Box 2)
The metadata recipe object describing a bean's class, scope, lazy flag, and init/destroy methods before any instance is created.
singletonObjects (Box 3)
The internal ConcurrentHashMap<String, Object> inside DefaultSingletonBeanRegistry that caches live singleton beans by name.
BeanFactory
The root interface for accessing a Spring bean container (provides lazy getBean() lookups).
ApplicationContext
The full container interface extending BeanFactory; eagerly pre-instantiates singletons during refresh() and integrates Environment, events, and post-processors.
refresh()
The master startup method in AbstractApplicationContext that executes Phase 1 (load recipes → run post-processors → instantiate singletons).
ObjectProvider<T>
A lightweight handle to Box 3 that lets a singleton fetch a fresh prototype instance (or an optional bean) on demand via getObject() / getIfAvailable().
