Dependency Injection in Depth

Spring & Spring Boot › lesson 3 of 18 · DEEP — how Box 3 resolves & wires dependencies

In simple English — When Box 3 is building a bean and sees a constructor parameter like PaymentGateway gw, how does it pick the right object? It searches Box 2's Recipe Map by Java type first, then narrows multiple matches using @Qualifier → @Primary → parameter name. Always use Constructor Injection (not field injection): it runs in Step 1 of creation so fields can be final, works in plain-Java unit tests without Spring, and stops circular dependencies right at startup.

§2Why it exists — Three ways Java lets Spring hand a dependency in

When Box 3 builds your object, Java's reflection API gives Spring only three possible doors to pass a collaborator into your class:

  1. Door 1 — Constructor Injection (Box 3 Step 1): Pass the dependency into Constructor.newInstance(args) at the exact moment the object is born.
  2. Door 2 — Setter Injection (Box 3 Step 2): Call new MyService() with an empty constructor first, then call Method.invoke(bean, dep) on a @Autowired void setRepo(...) method afterwards.
  3. Door 3 — Field Injection (Box 3 Step 2): Call new MyService() with an empty constructor first, then use field.setAccessible(true); field.set(bean, dep) to shove the value directly into a private field.

Why does the Spring team (and every senior interviewer) strongly insist on **Constructor Injection** over Field Injection? Look at what happens because of **Universal Rule #1 (Order of Steps: Step 1 Constructor runs BEFORE Step 2 Field/Setter Injection)**:

    private final AuditLog audit;

    // Zero @Autowired needed! Clean, readable, and works with plain 'new' in JUnit.
    public BookService(BookRepository repo, AuditLog audit) {
        this.repo = repo;
        this.audit = audit;
    }
}

§3How it works — Plain Java Data Structures First

Level 1 Zoom: How Box 3's Recursive Loop Resolves a Dependency

Suppose Box 3 is running `getBean("bookService")` and sees that `BookService`'s constructor asks for a parameter `PaymentGateway gw`. What plain Java code runs inside Box 3 to find the right bean? 

// Plain-Java mental model of DefaultListableBeanFactory.resolveDependency(...)
Object resolveDependency(Class<?> requiredType, String paramName, Annotation[] paramAnnotations) {
    // STEP 1: Search Box 2 (beanDefinitionMap) for ALL recipes whose class implements requiredType
    List<String> candidates = findBeanNamesForType(beanDefinitionMap, requiredType);

    if (candidates.isEmpty()) {
        throw new NoSuchBeanDefinitionException(requiredType);      // 0 matches!
    }
    if (candidates.size() == 1) {
        return getBean(candidates.get(0));                          // 1 match! Recursively cook/fetch it!
    }

    // --- 2 OR MORE MATCHES! Run the 3 Tie-Breakers in strict order: ---

    // TIE-BREAKER A: Does the parameter have @Qualifier("...")? Filter candidates by qualifier!
    if (hasQualifier(paramAnnotations)) {
        candidates = filterByQualifier(candidates, paramAnnotations);
        if (candidates.size() == 1) return getBean(candidates.get(0));
    }

    // TIE-BREAKER B: Is one of the remaining recipes marked @Primary in Box 2?
    String primaryName = findPrimaryCandidate(candidates);
    if (primaryName != null) return getBean(primaryName);

    // TIE-BREAKER C: Does the parameter variable name (e.g. "stripeGateway") match a bean name key?
    if (candidates.contains(paramName)) return getBean(paramName);

    // Still tied? Crash loudly at startup!
    throw new NoUniqueBeanDefinitionException(requiredType, candidates);
}

How Circular Dependencies Happen in the Recursion Stack (and Why Constructor Injection Catches Them)

Suppose `ServiceA` has constructor `ServiceA(ServiceB b)` and `ServiceB` has constructor `ServiceB(ServiceA a)`. Let's trace what happens in Box 3's recursion stack (**Universal Rule #1: Order of Steps**):

Tracing a Constructor Circular Dependency inside Box 3:
  1. Step 1: Box 3 calls getBean("serviceA"). Not in singletonObjects yet. Adds "serviceA" to singletonsCurrentlyInCreation Set: inCreation = ["serviceA"].
  2. Step 2: To call new ServiceA(b), Box 3 must first get ServiceB! So it recursively calls getBean("serviceB"). Adds "serviceB" to Set: inCreation = ["serviceA", "serviceB"].
  3. Step 3: To call new ServiceB(a), Box 3 must first get ServiceA! So it recursively calls getBean("serviceA").
  4. Step 4: getBean("serviceA") checks inCreation.add("serviceA") — it returns false because "serviceA" is already sitting on the call stack waiting for ServiceB! Spring immediately throws BeanCurrentlyInCreationException.

§4When to use — Practical Decision Table

SituationWhat to WriteWhy
Standard mandatory dependency (95% of cases) Single constructor with private final fields Guaranteed non-null at birth (Step 1), immutable, zero annotations needed.
Two implementations of an interface exist, and one is the standard default (e.g. StripeGateway vs PaypalGateway) Put @Primary on the default class; use @Qualifier("paypalGateway") only where the non-default is needed Callers asking for PaymentGateway get the default without clutter; special callers opt in with @Qualifier.
You want to run all implementations of an interface (e.g., validation rules, notification channels, discount calculators) Inject List<Rule> or Map<String, Rule> into the constructor Spring automatically collects every bean implementing Rule! Adding a new rule later requires zero changes to the caller (Open/Closed Principle).
A dependency might not exist in some environments (e.g., an optional metrics exporter) Inject Optional<MetricsExporter> or ObjectProvider<MetricsExporter> Avoids NoSuchBeanDefinitionException while keeping constructor injection clean.
You hit a BeanCurrentlyInCreationException (Circular Dependency) 1st choice: Extract shared logic into a 3rd class.
2nd choice: Use @Lazy on one constructor parameter (injects a tiny proxy placeholder).		 Extracting a 3rd class fixes the design tangle; @Lazy defers calling getBean() until the first method call.

§5Explain it to a 12-year-old

Imagine you are building a Lego spaceship, and the instruction manual says: "Step 1: Snap the Pilot into the cockpit."

If there is only one Lego person in your toy box, you grab them and snap them in. Easy!

What if there are zero Lego people in your toy box? You stop and yell: "Hey! There is no Pilot!" (NoSuchBeanDefinitionException).

What if there are two Lego people in your toy box — Batman and Astronaut? You can't guess! If you guess wrong, you ruin the spaceship. So you stop and yell: "There are two people! Which one do you want?" (NoUniqueBeanDefinitionException). To help you choose, your friend can either put a Gold "Default" Sticker on Astronaut (@Primary = "always use Astronaut unless I say otherwise"), or write "Put Batman here" right on the cockpit seat (@Qualifier("batman")). And if it's a Passenger Bus with a sign saying "Give me a List of all Lego people" (List<Person>), you put both Batman and Astronaut on the bus!

§7In practice — Zero-Wiring Plugin Registry & Interview Derivation

One of the cleanest patterns in production Spring Boot code is injecting `List` into a constructor to build a lookup Map of strategies once at startup: 

public interface Notifier {
    String channel();                       // "email", "sms", "push"
    void send(String to, String msg);
}

@Component
class EmailNotifier implements Notifier {
    public String channel() { return "email"; }
    public void send(String to, String msg) { System.out.println("email -> " + to); }
}

@Component
class SmsNotifier implements Notifier {
    public String channel() { return "sms"; }
    public void send(String to, String msg) { System.out.println("sms -> " + to); }
}

@Service
public class NotificationService {
    private final Map<String, Notifier> byChannel;

    // Box 3 sees List<Notifier> and injects ALL beans implementing Notifier!
    public NotificationService(List<Notifier> notifiers) {
        this.byChannel = notifiers.stream()
            .collect(Collectors.toUnmodifiableMap(Notifier::channel, Function.identity()));
    }

    public void notify(String channel, String to, String msg) {
        Notifier n = byChannel.get(channel);
        if (n == null) throw new IllegalArgumentException("Unknown channel: " + channel);
        n.send(to, msg);
    }
}
Code Dissection:
  • Zero-wiring extensibility: When a teammate adds @Component class SlackNotifier implements Notifier next month, NotificationService automatically discovers it at startup without a single line of NotificationService changing!
  • Thread-safety (Universal Rule #3): Because byChannel is populated once inside the constructor using toUnmodifiableMap and stored in a final field, 200 concurrent request threads can call notify() safely with zero locks.
  • Alternative: You can also inject Map<String, Notifier> directly, and Spring will populate the map using each bean's bean name ("emailNotifier", "smsNotifier") as the key. Building the map from an explicit channel() method is safer because renaming a Java class won't break your API keys!
Try this / Predict the output: Suppose a developer writes this class using field injection instead of constructor injection: 
@Service
public class BrokenService {
    @Autowired private EmailNotifier email;
    public BrokenService() {
        System.out.println("Channel is: " + email.channel());
    }
}
What happens when Spring boots?
Answer: Instant NullPointerException inside the constructor! By Universal Rule #1 (Order of Steps), Box 3 must finish running new BrokenService() (Step 1) before it can use reflection to inject @Autowired fields (Step 2). Inside the constructor body, every @Autowired field is still null!

How to Think in Interviews — Derive, Don't Memorize

Classic Interview QuestionWhich Box / Rule to Picture10-Second Derived Answer
"Why is Constructor Injection recommended over Field Injection?" Rule 1 (Order of Steps) + Box 3 1. Runs in Step 1 (`new`), so fields can be `final` and the object is never half-built.
2. You can instantiate the class in a JUnit test with plain `new` without reflection or Spring.
3. Catches circular dependencies immediately at startup.
"If a bean has both @Primary on Bean A and @Qualifier("beanB") at the injection point, which one wins?" Box 3 Resolution Flowchart (Step 2 vs Step 3) @Qualifier("beanB") wins! In Box 3's tie-breaker order, explicit `@Qualifier` (Step 2) filters the candidates before `@Primary` (Step 3) is checked. `@Primary` is only the fallback default when no qualifier is specified.
"How does Spring handle Circular Dependencies, and why does Constructor vs Setter injection matter?" Rule 1 (Order of Steps) + Box 3 `inCreation` Set With Constructors, Step 1 of A needs Step 1 of B which needs Step 1 of A — impossible, so Box 3's `inCreation` Set throws `BeanCurrentlyInCreationException`. With Setters, Step 1 (`new A()`) takes 0 args, so Spring can expose an early reference to A before Step 2 (`setB`). (Note: Boot 2.6+ disables circular references by default for both!)
"Why is an @Autowired field or @Value field null inside the constructor?" Rule 1 (Order of Steps: Step 1 before Step 2) In Java bytecode, an object cannot have its fields set by outside reflection until `Constructor.newInstance()` (Step 1) returns the object reference! Field/setter population is Step 2. Move the code to constructor parameters or `@PostConstruct` (Step 3).

§8Pitfalls

Pitfall 1: Switching to Field Injection to hide a 10-argument constructor. When a constructor grows to 10 parameters, it feels ugly to type — so people switch to 10 @Autowired fields to make the file look shorter. Don't! A 10-argument constructor is a helpful alarm bell telling you your class violates the Single Responsibility Principle. Split the class into two smaller services.
Pitfall 2: Magic strings in @Qualifier("typoName"). String qualifiers are not checked until startup. When you have multiple beans of the same type (like a read replica `DataSource` and a primary `DataSource`), create a custom annotation meta-annotated with `@Qualifier` (e.g. `@ReadOnlyDb`) so the Java compiler checks it at compile time!
Pitfall 3: Relying on the order of an injected List<T> without @Order. When you inject `List`, the order of beans depends on classpath scanning order unless you explicitly put `@Order(1)`, `@Order(2)` (or implement `Ordered`) on the classes.

§9Recap & Glossary / Reference

  • 3 Doors into a Bean: Constructor (Box 3 Step 1 — always prefer this), Setter (Box 3 Step 2 — optional deps only), Field (Box 3 Step 2 — avoid in production code).
  • 4-Step Resolution Order: Match by Type (including generics) → filter by @Qualifier → check @Primary → match bean name to parameter variable name.
  • Collections & Optionals: Inject List<T> or Map<String, T> to get all implementations; inject Optional<T> or ObjectProvider<T> when a bean may be absent.
  • Circular Dependencies: Caught by Box 3's singletonsCurrentlyInCreation Set; rejected by default since Spring Boot 2.6.

Glossary

Injection Point
A constructor parameter, setter parameter, or field where Box 3 supplies a dependency.
Autowiring
Box 3 automatically resolving which bean from Box 2/Box 3 satisfies an injection point by inspecting types and qualifiers.
@Qualifier
An annotation placed on both a bean and an injection point to narrow down candidate beans when multiple beans share the same type.
@Primary
Marks a bean recipe in Box 2 as the default winner when multiple candidates match by type and no @Qualifier is present.
Circular Dependency
When Bean A requires Bean B and Bean B (directly or indirectly) requires Bean A in order to be created.
ResolvableType
Spring's reflection wrapper that reads generic type arguments (like Repo<Book>) preserved in bytecode signatures.
