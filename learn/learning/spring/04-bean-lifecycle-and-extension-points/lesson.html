Bean Lifecycle & Extension Points

Spring & Spring Boot › lesson 4 of 18 · DEEP — the 4-stage assembly line (Box 2C, Box 4 & Phase 3)

In simple English — Instead of memorizing 12 random callbacks, group a bean's life into 4 intuitive stages on an assembly line: Stage A edits the recipe card before any object exists (BeanFactoryPostProcessor in Box 2C); Stage B calls your constructor and populates @Autowired/@Value fields (Box 3); Stage C runs setup hooks (@PostConstruct) and lets BeanPostProcessor wrap your object inside a Proxy (Box 4); and Stage D runs cleanup on shutdown (@PreDestroy in Phase 3).

§1Where it fits — You Are Here on the 6-Box Map

🧭 You Are Here: Box 2C (BeanFactoryPostProcessor) + Box 4 (BeanPostProcessor) + Phase 3 (Shutdown @PreDestroy)

Why this lesson is the Rosetta Stone for interviews: Almost every tricky Spring interview question ("Why is @Value null in my constructor?", "Why doesn't @Transactional work inside @PostConstruct?", "What is the difference between BeanFactoryPostProcessor and BeanPostProcessor?") is just asking you to read Stages A → B → C → D in order (**Universal Rule #1**)!

§2Why it exists — Annotations do nothing unless an Inspector reads them

In java/01 you learned a fundamental truth: a Java annotation is just a passive sticky note in the .class file. Writing `@Transactional` or `@PostConstruct` or `@Value("${db.url}")` contains zero executable code. The JVM completely ignores it.

If Spring didn't have extension hooks during bean creation, how would you make `@Transactional` or `@PostConstruct` work? You would have to hard-code every feature inside `BeanFactory` itself. Worse, you could never add your own custom cross-cutting behaviour!

Spring's Open/Closed Design Insight: Instead of hard-coding `@Autowired`, `@PostConstruct`, and `@Transactional` into the container's core loop, Spring added two plug-in hooks to the assembly line:
  1. Hook 1 (BeanFactoryPostProcessor in Box 2C): Lets plug-ins inspect and edit the Recipe Map (Map<String, BeanDefinition>) before any object is constructed.
  2. Hook 2 (BeanPostProcessor in Box 4): Lets plug-ins inspect, initialize, or swap out each newly created object for a Proxy wrapper before it is stored in Box 3's singletonObjects warehouse!
Even Spring's own core annotations (`@Configuration`, `@Autowired`, `@Value`, `@PostConstruct`, `@Transactional`, `@Async`) are implemented as ordinary `BeanFactoryPostProcessor`s and `BeanPostProcessor`s!

§3How it works — Plain Java First, Then the 4 Stages

Level 1 Zoom: The Assembly Line in 25 Lines of Plain Java

Here is the exact code that runs inside `AbstractApplicationContext.refresh()`. Read the comments — you can see Stages A, B, C, and D in plain Java: 

// STAGE A (Box 2C — Once per startup, BEFORE any business object is created):
for (BeanFactoryPostProcessor bfpp : beanFactoryPostProcessors) {
    bfpp.postProcessBeanFactory(beanDefinitionMap);   // Edits recipes in Box 2 (e.g. resolves ${...})
}

// Now loop over every Singleton recipe in Box 2 to build Box 3:
for (BeanDefinition recipe : beanDefinitionMap.values()) {

    // STAGE B (Box 3 — Birth & Wiring):
    Object bean = recipe.getConstructor().newInstance(resolveConstructorArgs());  // B1: Constructor runs FIRST!
    populateFieldsAndSetters(bean);                                               // B2: @Autowired / @Value fields set SECOND!
    invokeAwareInterfaces(bean);                                                  // B3: BeanNameAware, ApplicationContextAware

    // STAGE C (Box 4 — Setup & Inspector Hooks):
    for (BeanPostProcessor bpp : beanPostProcessors) {
        bean = bpp.postProcessBeforeInitialization(bean, name);                   // C1: BPP Before (triggers @PostConstruct!)
    }
    invokeInitMethods(bean, recipe);                                              // C2: afterPropertiesSet() -> initMethod
    for (BeanPostProcessor bpp : beanPostProcessors) {
        bean = bpp.postProcessAfterInitialization(bean, name);                    // C3: ★ BPP After — WRAPS BEAN IN PROXY!
    }

    singletonObjects.put(name, bean);   // Store final object (the Proxy!) in Box 3 Warehouse
}

// STAGE D (Phase 3 — When JVM shuts down / context.close() is called):
for (Object singleton : singletonObjects.values()) {
    invokeDestroyMethods(singleton);    // D1: @PreDestroy -> DisposableBean.destroy() -> destroyMethod
}

Three Ways to Run Setup / Cleanup Code (Stage C & Stage D)

@Component
public class CacheWarmer {
    // 1. @PostConstruct / @PreDestroy (jakarta.annotation) — ★ BEST PRACTICE for your own classes
    //    No Spring imports required; runs first in Stage C1 / D1.
    @PostConstruct
    public void init() { System.out.println("1. @PostConstruct runs in Stage C1"); }

    @PreDestroy
    public void cleanup() { System.out.println("1. @PreDestroy runs in Stage D1"); }
}

// 2. InitializingBean / DisposableBean — Avoid in modern code (couples your class to Spring interfaces)
class LegacyBean implements InitializingBean, DisposableBean {
    public void afterPropertiesSet() { ... }   // Stage C2 (runs right after @PostConstruct)
    public void destroy() { ... }              // Stage D1 (runs right after @PreDestroy)
}

// 3. @Bean(initMethod, destroyMethod) — ★ BEST for third-party classes you cannot edit!
//    Bonus: If a 3rd-party class has a public close() or shutdown() method, Spring calls it on shutdown automatically!
@Bean(initMethod = "start", destroyMethod = "stop")
ThirdPartyClient client() { return new ThirdPartyClient(); }

Bonus Extension Point: FactoryBean<T> ("A Factory Object Stored in Box 3")

Sometimes constructing a complex object (like a dynamic JPA Repository interface that has no concrete class!) takes too much logic for a normal constructor. Spring provides the `FactoryBean` interface (Spring Framework Reference — Customizing Instantiation Logic with a FactoryBean):

  • When you register `JpaRepositoryFactoryBean` under bean name `"bookRepository"`, calling `ctx.getBean("bookRepository")` does not return the factory — it calls `factory.getObject()` and returns the generated `BookRepository` proxy!
  • Classic trivia question: What if you actually want the `FactoryBean` instance itself? Prefix the bean name with an ampersand: **`ctx.getBean("&bookRepository")`**!

§4When to use — Choosing the Right Startup Hook

What You Want to DoWhich Hook to UseWhy
Validate injected fields or pre-compute an in-memory lookup table inside one bean Constructor body (if using constructor injection) or @PostConstruct (Stage C1) Runs as soon as the bean's dependencies are wired. Keep it fast (<10ms) and avoid network/DB calls!
Seed database rows, call an external HTTP API, or start a background consumer at boot ApplicationRunner / CommandLineRunner or @EventListener(ApplicationReadyEvent.class) Runs after Stage C3 finishes for ALL beans — so every @Transactional proxy is active and the container is 100% ready!
Close a thread pool, flush a buffer, or close a socket on graceful shutdown @PreDestroy (Stage D1) or implement AutoCloseable.close() Triggered automatically when the JVM receives SIGTERM and runs Spring's shutdown hook.
Measure execution time or wrap every bean annotated with a custom annotation BeanPostProcessor (Stage C3) Inspects every bean in the container and can return a dynamic proxy wrapper.

§5Explain it to a 12-year-old

Imagine a Toy Car Factory Assembly Line.

  • Stage A (BeanFactoryPostProcessor) happens in the Blueprint Office before the factory floor even opens. An engineer sees a blueprint that says "Paint color: ${FAVORITE_COLOR}", looks up today's favorite color (Red), and writes "Red" on the blueprint.
  • Stage B (Birth & Wiring) is the Moulding & Parts Station. First, the plastic body is moulded (`new Car()` — Stage B1). Next, a worker snaps on the wheels and battery (`@Autowired` and `@Value` fields — Stage B2). Notice that while the plastic body is still inside the mould (B1), the battery isn't attached yet (B2)!
  • Stage C (BeanPostProcessor) is the Inspector Conveyor Belt.
    • Inspector #1 (`@PostConstruct` in Stage C1) flips the switch to check if the headlights turn on.
    • Inspector #2 (`postProcessAfterInitialization` in Stage C3) sees a sticker on the car that says `@RemoteControlled` (like `@Transactional`). So Inspector #2 puts your plastic car inside a motorized outer shell (a Proxy) and puts that shell into the toy store box!
  • Stage D (`@PreDestroy`) is Closing Time, when the store manager turns off all the display models before locking the doors for the night.

§7In practice — Build your own @Timed Proxy in Stage C3 & Interview Derivation

Let's prove there is zero magic in Spring AOP by writing our own annotation `@Timed` and a 20-line `BeanPostProcessor` (Stage C3) that wraps any `@Timed` bean in a timing proxy: 

// 1. The passive sticky-note annotation
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
public @interface Timed {}

// 2. The Box 4 Inspector (Stage C3): inspects every bean and wraps @Timed beans in a Proxy
@Component
public class TimingBeanPostProcessor implements BeanPostProcessor {

    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName) {  // ← Stage C3!
        Class<?> type = bean.getClass();
        if (!type.isAnnotationPresent(Timed.class)) {
            return bean;   // No @Timed sticker? Return the original object untouched.
        }

        // Has @Timed sticker! Wrap the real 'bean' inside a JDK Dynamic Proxy and return the PROXY:
        return Proxy.newProxyInstance(
            type.getClassLoader(),
            type.getInterfaces(),
            (proxy, method, args) -> {
                long t0 = System.nanoTime();
                try {
                    return method.invoke(bean, args);   // Forward call to the REAL target object
                } finally {
                    long ms = (System.nanoTime() - t0) / 1_000_000;
                    System.out.println("[timed] " + beanName + "." + method.getName() + " took " + ms + "ms");
                }
            });
    }
}

// 3. Business class: has no idea it is being wrapped!
@Service @Timed
public class BookService implements BookOperations {
    public Book findById(long id) { ... }
}
Code Dissection:
  • Look at the return type of postProcessAfterInitialization: It returns Object! Whatever object it returns replaces the original bean and gets stored inside Box 3's singletonObjects Map. When BookController asks for BookOperations, Box 3 hands it the Proxy, not the raw BookService!
  • Why did we wrap in postProcessAfterInitialization (Stage C3) instead of BeforeInitialization (Stage C1)? Because Stage C1/C2 runs @PostConstruct on the raw target bean first, and only after the bean is 100% initialized does Stage C3 wrap it in a Proxy!
Try this / Predict the output: Suppose we add a @PostConstruct method inside BookService above that prints this.getClass().getName() and calls a @Transactional method on itself. What class name is printed, and does a transaction start?
Answer: It prints the raw BookService class name (not $Proxy...), and no transaction starts! Why? Look at the 4-Stage diagram: @PostConstruct runs in Stage C1, whereas the Proxy is not created until Stage C3 (postProcessAfterInitialization)! Even worse, calling this.someMethod() bypasses the proxy anyway (**Universal Rule #2**).

How to Think in Interviews — Derive, Don't Memorize

Classic Interview QuestionWhich Stage / Rule to Picture10-Second Derived Answer
"Why is my @Value("${app.url}") field null when I print it inside the constructor?" Rule 1 (Order of Steps): Stage B1 vs Stage B2 In Stage B1, Java executes your constructor (new MyService()) to create the object in memory. Spring cannot inject field values (Stage B2) until after the constructor returns the object reference! Fix: put @Value("${app.url}") String url directly on a constructor parameter (resolved before B1) or read the field in @PostConstruct (Stage C1).
"Why does calling a @Transactional or @Async method inside @PostConstruct silently ignore the annotation?" Rule 1 & Rule 2: Stage C1 vs Stage C3 Two reasons: (1) @PostConstruct runs in Stage C1, before postProcessAfterInitialization (Stage C3) has even created the AOP Proxy! (2) Even if the proxy existed, calling a method via this inside the class bypasses the proxy. Use ApplicationRunner or @EventListener(ApplicationReadyEvent.class) instead.
"What is the difference between BeanFactoryPostProcessor and BeanPostProcessor?" Stage A (Box 2C) vs Stage C (Box 4) BeanFactoryPostProcessor runs in Stage A before any bean is created and edits recipes (BeanDefinitions in Box 2, like resolving ${...}). BeanPostProcessor runs in Stage C for every created bean instance and can wrap it in a Proxy (Box 4).
"What is the exact order of initialization callbacks if a bean uses all three: @PostConstruct, InitializingBean, and @Bean(initMethod)?" Stage C1 → Stage C2 1st: @PostConstruct (triggered by a BPP in Stage C1) → 2nd: InitializingBean.afterPropertiesSet() (Stage C2) → 3rd: custom initMethod (Stage C2). Destruction in Stage D1 mirrors it: @PreDestroy → destroy() → destroyMethod.
"What does the log warning 'Bean X is not eligible for getting processed by all BeanPostProcessors' mean?" refresh() Step 4 vs Step 5 Because BeanPostProcessors (Box 4) must be instantiated before normal business beans, if you inject a business bean X into a custom BeanPostProcessor, Spring is forced to create X early during Step 4 — before the other BeanPostProcessors (like @Transactional proxying) are registered! Never inject business services eagerly into a BPP; use @Lazy or ObjectProvider.

§8Pitfalls

Pitfall 1: Doing slow database or HTTP calls inside @PostConstruct (Stage C1). Stage C1 runs synchronously on the main startup thread while Box 3 is still half-built. If a remote call hangs, your entire server hangs mid-boot; if it calls a proxied method on the same bean, the proxy doesn't exist yet (Stage C3). Put startup tasks in an ApplicationRunner or @EventListener(ApplicationReadyEvent.class).
Pitfall 2: Expecting @PreDestroy (Stage D1) to run on kill -9 or power loss. Stage D1 is triggered by a JVM shutdown hook when the process receives a polite SIGTERM (e.g., Kubernetes stopping a pod). If the OS kills the process with SIGKILL (kill -9) or the machine crashes, Stage D1 never executes. Never rely solely on @PreDestroy for data integrity — use database transactions!
Pitfall 3: Returning null from a custom BeanPostProcessor. In Stage C1 and C3, Spring passes the bean through a chain of `BeanPostProcessor`s. If your custom processor forgets `return bean;` and returns `null`, you short-circuit the rest of the assembly line! Always return either the original `bean` or a wrapper proxy.

§9Recap & Glossary / Reference

  • Stage A (Box 2C — Recipe Edit): BeanFactoryPostProcessor edits BeanDefinition recipes in Box 2 before any business constructor runs.
  • Stage B (Box 3 — Birth & Wiring): B1 runs the constructor (new) → B2 injects @Autowired and @Value fields → B3 calls *Aware interfaces.
  • Stage C (Box 4 — Setup & Proxy): C1 runs BPP.beforeInit (which calls @PostConstruct) → C2 runs afterPropertiesSet() and initMethod → C3 runs BPP.afterInit (which wraps the bean in an AOP Proxy!).
  • Stage D (Phase 3 — Shutdown): Runs @PreDestroy → destroy() → destroyMethod on singletons only.

Glossary

BeanFactoryPostProcessor (Stage A)
Container extension hook that reads and modifies BeanDefinition recipes in Box 2 before any normal beans are instantiated.
BeanPostProcessor (Stage C)
Container extension hook called before (C1) and after (C3) every bean's initialization callbacks; Stage C3 is how Spring wraps beans in AOP proxies.
@PostConstruct / @PreDestroy
Standard jakarta.annotation lifecycle annotations invoked in Stage C1 (after wiring) and Stage D1 (on context shutdown).
InitializingBean / DisposableBean
Spring-specific lifecycle interfaces providing afterPropertiesSet() (Stage C2) and destroy() (Stage D1).
FactoryBean<T>
A special bean that acts as a factory for another object via getObject(); used by frameworks like Spring Data JPA to create repository proxies.
ApplicationRunner
A Spring Boot interface whose run() method executes once after the entire ApplicationContext has finished refreshing.
