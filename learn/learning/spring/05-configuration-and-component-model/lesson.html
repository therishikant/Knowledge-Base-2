Configuration & the Component Model

Spring › lesson 5 of 18 · DEEP — how your recipes enter Box 2 (beanDefinitionMap)

Summary — Before Spring can create a single object in Box 3 (singletonObjects), it must first fill its recipe book in Box 2 (Map<String, BeanDefinition>). There are only two ways to put a recipe into that map: stick a label (@Component, @Service, @Repository, @Controller) on a class you wrote, or write a @Bean method inside a @Configuration class for a 3rd-party class someone else wrote. And to keep you from accidentally creating duplicate objects, Spring wraps every @Configuration class in a generated subclass (CGLIB proxy) that checks singletonObjects before running any @Bean method.

§1Where it fits — You Are Here on the Map

Lessons 2–4 showed how Spring takes a recipe from Box 2 (beanDefinitionMap) and cooks it into a live singleton object in Box 3 (singletonObjects). Now we step one box backward to answer: how did your recipes get into Box 2 in the first place?

📍 You Are Here on the 6-Box Map: Phase 1 (Startup) → Box 2A (Your Recipes)

§2Why it exists — the pain in plain Java

Suppose we are building our running app, BookVault, without annotations or Java configuration. Why do we need two different ways to register recipes in Box 2? Look at what happens when your app mixes classes you wrote with classes from a third-party library JAR: 

// 1. A class YOU wrote — you own the source file BookService.java
public class BookService {
    private final BookRepository repo;
    public BookService(BookRepository repo) { this.repo = repo; }
}

// 2. A class SOMEONE ELSE wrote — locked inside hikari-cp.jar (read-only bytecode!)
//    Plus it has 20 constructors/setters and needs custom setup logic:
HikariConfig cfg = new HikariConfig();
cfg.setJdbcUrl("jdbc:postgresql://localhost/bookvault");
cfg.setMaximumPoolSize(10);
DataSource ds = new HikariDataSource(cfg);

Now watch how painful it was across Spring's history to put both of those into Box 2's recipe map:

EraHow you put recipes in Box 2What hurt
Spring 1.x–2.0 (XML)Hand-type <bean id="bookService" class="…"> for every single class in a giant XML file.Thousands of lines of stringly-typed XML; rename a Java class and it compiles fine but crashes at startup.
Spring 2.5 (@Component)Put @Service right on BookService.java and let Spring scan your folder.Zero XML for your classes! Wait: how do you put @Component on HikariDataSource.class? You can't—you don't own its source code!
Spring 3.0+ (@Configuration + @Bean)Write a normal Java method that builds and returns new HikariDataSource(cfg), and mark the method @Bean.Solved. Compiler-checked Java for 3rd-party classes, and stereotypes for your own classes.
The ownership rule (memorize this once):
  • Did you write the class? Put a stereotype sticker on the class (@Service, @Repository, @Controller, @Component).
  • Did someone else write the class (DataSource, RestClient, Jackson ObjectMapper, AWS S3 client) — or do you need custom if/else builder code to construct it? Write a @Bean method inside a @Configuration class.

§3How it works (Level 1 → Level 2 Zoom)

Start with Plain Java Data Structures First

Strip away every Spring class name. At the start of Phase 1, Box 2 is just an empty Java Map of recipes, and Box 3 is an empty Java Map of live objects: 

// Box 2: The Recipe Book (NO business objects exist yet!)
Map<String, BeanDefinition> beanDefinitionMap = new ConcurrentHashMap<>();

// What is a BeanDefinition? Just a plain Java struct describing HOW to make a bean:
class BeanDefinition {
    String beanClassName;       // e.g. "com.bookvault.BookService" (for @Component)
    String factoryBeanName;     // e.g. "persistenceConfig"        (for @Bean method)
    String factoryMethodName;   // e.g. "dataSource"               (for @Bean method)
    String scope = "singleton";
    boolean isLazy = false;
}

// Channel A (@ComponentScan): reads .class files in your package and adds a Class recipe
beanDefinitionMap.put("bookService",
    new BeanDefinition("com.bookvault.BookService", null, null));

// Channel B (@Configuration + @Bean): reads @Bean methods and adds a Factory-Method recipe
beanDefinitionMap.put("dataSource",
    new BeanDefinition(null, "persistenceConfig", "dataSource"));
Step-by-step control flow inside Box 2A (Startup):
  1. Step 1 (Seed recipe): You call SpringApplication.run(BookVaultApp.class, args). Spring registers one starting recipe in Box 2: "bookVaultApp".
  2. Step 2 (The Master Chef runs): Before Box 3 cooks any normal beans, Spring invokes a built-in BeanFactoryPostProcessor named ConfigurationClassPostProcessor.
  3. Step 3 (Channel A — Classpath Scan): It sees @ComponentScan on your main class, walks your package folders on disk, inspects the raw .class bytes using ASM (without even loading the classes into the JVM!), and for every class carrying @Component (or @Service, @Repository, @Controller), inserts a BeanDefinition into beanDefinitionMap.
  4. Step 4 (Channel B — @Bean Methods): For every @Configuration class it found, it reads every @Bean method and inserts a factory-method BeanDefinition into beanDefinitionMap (where the bean's name is the method name).
  5. Step 5 (CGLIB Class Enhancement): It rewrites each @Configuration class in Box 2 to point to a generated CGLIB subclass so inter-@Bean calls are safe (explained below).

Channel A: Stereotypes — why are there four stickers if they all register a recipe?

@Component     // generic: "put a recipe for this class into Box 2"
 ├─ @Service     // business logic layer (pure label for humans & AOP pointcuts)
 ├─ @Repository  // data access layer → triggers a Box 4 Proxy that translates SQL exceptions!
 └─ @Controller  // web layer → registers routes in Box 6 (DispatcherServlet)
     └─ @RestController  // = @Controller + @ResponseBody (write JSON directly)

Open @Service.java in your IDE and you will see @Component written right on top of it. That is called a meta-annotation (a sticker on a sticker). Because the Box 2 scanner looks for @Component or anything meta-annotated with @Component, it finds all four.

  • @Repository triggers Box 4 behaviour: When Box 4 sees a bean with @Repository, PersistenceExceptionTranslationPostProcessor wraps it in a proxy that catches raw JDBC/JPA exceptions (like vendor error code 1062) and translates them into Spring's clean DataAccessException hierarchy (e.g., DuplicateKeyException).
  • @Controller triggers Box 6 behaviour: During startup, RequestMappingHandlerMapping only inspects beans marked @Controller when building its URL routing table. Put @GetMapping("/books") on a plain @Component and every request returns 404 Not Found!
The Root Package Rule: If you don't pass basePackages to @ComponentScan, where does it scan? Starting from the package of your main class and going downward into subpackages. That is why BookVaultApplication always lives at the root (com.bookvault) with com.bookvault.service and com.bookvault.web underneath it.

Channel B: @Configuration + @Bean — and the CGLIB Proxy Secret

Now look closely at this @Configuration class. What happens when jdbcTemplate() calls dataSource() directly? 

@Configuration
public class PersistenceConfig {

    @Bean
    public DataSource dataSource() {
        return new HikariDataSource(); // opens 10 physical TCP database connections!
    }

    @Bean
    public JdbcTemplate jdbcTemplate() {
        return new JdbcTemplate(dataSource()); // ← Wait! Does this call new HikariDataSource() a SECOND time?!
    }
}

In normal Java, calling dataSource() inside jdbcTemplate() would execute new HikariDataSource() a second time — leaking a second connection pool!

Why doesn't that happen in a @Configuration class? Because in Step 5 of Box 2A, Spring uses CGLIB to generate a subclass of PersistenceConfig in memory. Here is the exact plain-Java code of the subclass Spring generates and puts into Box 3: 

// Generated in memory by Spring at startup:
public class PersistenceConfig$$SpringCGLIB$$0 extends PersistenceConfig {

    private Map<String, Object> singletonObjects; // reference to Box 3 warehouse

    @Override
    public DataSource dataSource() {
        // 1. Check Box 3 (singletonObjects) FIRST!
        if (singletonObjects.containsKey("dataSource")) {
            return (DataSource) singletonObjects.get("dataSource");
        }
        // 2. Not built yet? Call your real method, store in Box 3, and return it
        DataSource ds = super.dataSource();
        singletonObjects.put("dataSource", ds);
        return ds;
    }
}
Look at that if statement! When jdbcTemplate() calls this.dataSource(), polymorphism dispatches the call to PersistenceConfig$$SpringCGLIB$$0.dataSource(). It sees "dataSource" is already in Box 3 (singletonObjects) and returns the existing pool instead of calling super.dataSource()!
The best practice that works in BOTH modes: Don't call dataSource() inside jdbcTemplate() at all! Ask Spring to pass DataSource as a method parameter: 
@Bean
public JdbcTemplate jdbcTemplate(DataSource ds) { // Spring fetches 'ds' from Box 3 for you!
    return new JdbcTemplate(ds);
}
When you use method parameter injection, you never call dataSource() yourself, so it is 100% safe even in Lite mode (@Configuration(proxyBeanMethods = false)), which avoids generating a CGLIB class and speeds up startup.

Other ways recipes enter Box 2: @Import and @Conditional

// 1. @Import pulls another recipe class (or programmatic selector) into Box 2
@Configuration
@Import({ PersistenceConfig.class, SecurityConfig.class })
class AppConfig {}

// Every @EnableXxx annotation in Spring (@EnableAsync, @EnableScheduling, @EnableAutoConfiguration)
// is literally just a meta-annotation carrying @Import(...)!

// 2. @Conditional acts as a gatekeeper at the door of Box 2:
//    If matches() returns false, the recipe is NEVER added to beanDefinitionMap!
@Bean
@ConditionalOnProperty(name = "search.engine", havingValue = "lucene")
SearchEngine luceneEngine() { return new LuceneEngine(); }

§4When to use — Decision Table

ScenarioWhich tool to useWhy
A service, controller, or repository class you wrote@Service, @Controller, @RepositoryScanned automatically into Box 2; zero boilerplate config code.
A 3rd-party class (DataSource, ObjectMapper, S3Client)@Bean inside @ConfigurationYou can't edit 3rd-party source files to add @Component.
Two beans of the exact same Java class (e.g., primaryDataSource & replicaDataSource)Two @Bean methods@Component on a class only ever registers one recipe; @Bean registers one recipe per method.
@Configuration where @Bean methods take dependencies via parameters (never calling each other)@Configuration(proxyBeanMethods = false)Skips CGLIB subclass generation (faster startup, lower memory).
Building a reusable internal library or custom @EnableXxx annotation@Import(MyConfig.class) or ImportSelectorLets users pull your recipes into Box 2 even if your JAR is in a different package.
Registering a bean only when a property, class, or other bean is present/missing@ConditionalOnProperty, @ConditionalOnMissingBeanGatekeeps Box 2 so unused recipes are never even registered.

§5Explain it to a 12-year-old

Imagine Spring is a giant automated kitchen. Before the chefs in Box 3 can cook any food, the head chef in Box 2 needs a Recipe Book listing every dish on the menu. How do recipes get into the book?

Way 1 — Stickers on your own Tupperware (@Component): For dishes you invented in your own home, you just stick a bright green label on the container saying "PUT ME ON THE MENU." Before the kitchen opens, a helper walks down your pantry shelves (@ComponentScan) and copies every stickered item into the Recipe Book.

Way 2 — Handwritten recipe cards (@Configuration + @Bean): What if you want to serve Coca-Cola? You don't own the Coca-Cola factory, so you can't walk into their building and stick a label on their blueprint. Instead, you write a little recipe card in your binder: "To get a Cola: open bottle, pour over ice."

Why the binder is magic (CGLIB proxy): Suppose your "Root Beer Float" card says: "Step 1: follow the Vanilla Ice Cream card. Step 2: add root beer." If two different cards both say "follow the Vanilla Ice Cream card," you don't want to make two giant tubs of ice cream! So the head chef secretly tapes a sticky note over every card in your binder: "Wait! Before you make this, check the fridge (Box 3). If there's already Vanilla Ice Cream in the fridge, just grab that tub!"

§7In practice — Code Dissection & Interview Derivation

Code Dissection: A production configuration class

@Configuration                                                  // ① Full mode: CGLIB-proxied
public class SearchConfig {

    @Bean                                                       // ② Recipe name in Box 2 = "luceneEngine"
    @ConditionalOnProperty(name = "bookvault.search", havingValue = "lucene")
    public SearchEngine luceneEngine(SearchProperties props) {  // ③ Parameter injection (best practice)
        return new LuceneEngine(props.indexDir());
    }

    @Bean
    @ConditionalOnMissingBean(SearchEngine.class)               // ④ Back-off if luceneEngine was registered
    public SearchEngine inMemoryEngine() {
        return new InMemorySearchEngine();
    }

    @Bean
    public static PropertySourcesPlaceholderConfigurer placeholders() { // ⑤ Why static? See Rule 1!
        return new PropertySourcesPlaceholderConfigurer();
    }
}
Chunk-by-chunk dissection: ① @Configuration tells Box 2A to parse this class for @Bean methods and wrap the class itself in a CGLIB subclass. ② Notice the return type is the interface SearchEngine, not the concrete class LuceneEngine. Always declare the interface as the return type of a @Bean method so Box 2 records the interface contract for type matching. ③ SearchProperties props is injected by Spring as a method parameter. That means we don't call another @Bean method by hand. ④ @ConditionalOnMissingBean checks Box 2's beanDefinitionMap: "Is there already a recipe for SearchEngine?" If luceneEngine was registered above, this fallback is skipped. ⑤ Why is placeholders() marked static? Because PropertySourcesPlaceholderConfigurer is a BeanFactoryPostProcessor (Box 2 phase). By Rule 1 (Order of Steps), Box 2 post-processors must run before normal singleton objects (like an instance of SearchConfig) are created in Box 3. Making the @Bean method static lets Spring call SearchConfig.placeholders() without instantiating SearchConfig too early!
Try this / Predict the output: Suppose you change @Configuration on PersistenceConfig to @Component, and inside that class you have: 
@Bean public DataSource dataSource() { return new HikariDataSource(); }
@Bean public JdbcTemplate templateA() { return new JdbcTemplate(dataSource()); }
@Bean public NamedParameterJdbcTemplate templateB() { return new NamedParameterJdbcTemplate(dataSource()); }
Predict: How many HikariDataSource instances are created at startup? How many of them are inside Box 3 (singletonObjects)?
Answer: Three HikariDataSource instances are created! One when Spring calls dataSource() to populate Box 3, a second when templateA() calls this.dataSource() directly, and a third when templateB() calls this.dataSource() directly. Only the first one is in Box 3; the other two are unmanaged ghosts that will never have close() called on shutdown!

How to Think in Interviews — Derive, Don't Memorize

Use the 6-Box Map and the 3 Universal Rules to derive every classic interview question on configuration in 10 seconds:

Classic Interview QuestionWhich Box / Rule to Check10-Second Derived Answer
"What is the difference between @Component and @Configuration when declaring @Bean methods?" Rule 2 (Who You Call) + Box 3 In @Configuration (Full mode), Spring wraps the config class in a CGLIB subclass that checks singletonObjects (Box 3) before calling super.myBean(). In @Component (Lite mode), there is no proxy—calling myBean() is a raw Java call on this, creating a duplicate unmanaged object every time.
"Are @Component, @Service, @Repository, and @Controller identical?" Box 2 → Box 4 → Box 6 All four put a recipe into Box 2 (via @Component meta-annotation). But @Repository also tells Box 4 to wrap the bean in an SQL-exception-translating proxy, and @Controller tells Box 6 (DispatcherServlet) to register its @RequestMapping URLs.
"Why can't a @Configuration class be final, or its @Bean methods be private or final?" Box 2A (CGLIB subclass) Full-mode @Configuration works by generating a subclass (extends YourConfig) that overrides each @Bean method to check Box 3 first. In Java, you cannot subclass a final class, and a subclass cannot override private or final methods.
"My class has @Service on it, why does Spring throw NoSuchBeanDefinitionException?" Rule 1 (Order) + Box 2A If the object isn't in Box 3, its recipe never entered Box 2A. 99% of the time, the class sits in a package above or beside the main @SpringBootApplication class, so downward @ComponentScan never visited that folder.
"Why should a BeanFactoryPostProcessor @Bean method be declared static?" Rule 1 (Recipes before Objects) A BeanFactoryPostProcessor runs in Box 2 (before Box 3 creates singleton objects). If its @Bean method isn't static, Spring is forced to instantiate the enclosing @Configuration object early in Box 2, skipping Box 4 BeanPostProcessors for that config class and everything it injects!

§8Pitfalls

Calling a @Bean method inside a @Component (or proxyBeanMethods = false) class. Because there is no CGLIB subclass intercepting the call, this.dataSource() executes the method body directly and constructs a second, unmanaged instance outside Box 3. Fix: use @Configuration or inject dependencies as method parameters.
Placing your @SpringBootApplication class in a sub-package like com.bookvault.app. Component scanning only looks at com.bookvault.app.* and completely misses com.bookvault.service.*, so those recipes never enter Box 2. Fix: keep the main class in the root package com.bookvault.
Putting @GetMapping on a @Component or @Service instead of @Controller. The bean is created in Box 3, but Box 6's RequestMappingHandlerMapping only scans @Controller beans for web routes. Result: silent 404s.
Using @ConditionalOnBean inside your own user @Configuration classes. By Rule 1 (Order of Steps), Box 2A scans your classes in filesystem/import order. If Config A checks @ConditionalOnBean(B.class) before Config B has been parsed into beanDefinitionMap, the check returns false even though B exists! Only use @ConditionalOnMissingBean inside Auto-Configuration (Box 2B), which runs after all user recipes in Box 2A are registered.
Returning a concrete class instead of an interface from a @Bean method. Writing @Bean HikariDataSource ds() instead of @Bean DataSource ds() limits type information in Box 2 before instantiation and can cause subtle proxy casting issues when JDK dynamic proxies are used.

§9Recap, Reference & Glossary

  • Box 2A holds your recipes (Map<String, BeanDefinition>): zero business objects exist while Box 2 is being populated.
  • Two channels into Box 2A: @ComponentScan (for classes you own: @Component, @Service, @Repository, @Controller) and @Configuration + @Bean methods (for 3rd-party classes you don't own).
  • Stereotypes are not identical: @Repository activates SQL exception translation in Box 4; @Controller activates URL route registration in Box 6.
  • Full mode vs Lite mode: @Configuration is subclassed by CGLIB so calling a @Bean method checks singletonObjects (Box 3) first; @Component / proxyBeanMethods=false does not proxy, so direct method calls create duplicate objects.
  • Always prefer method parameter injection in @Bean methods — it is clean and safe in both Full and Lite mode.
  • Every @EnableXxx annotation is just @Import pulling more recipes into Box 2.

Glossary

BeanDefinition (Box 2 recipe)
The metadata object stored in beanDefinitionMap describing a bean's class, factory method, scope, and dependencies before any object is instantiated.
Stereotype annotation
@Component and its specialized meta-annotations (@Service, @Repository, @Controller) that mark a class for component scanning.
Component scanning
Walking a package tree using ASM bytecode inspection to discover stereotype-annotated classes and add their recipes to Box 2.
Full mode (@Configuration)
The default mode where Spring wraps a configuration class in a CGLIB subclass that checks singletonObjects (Box 3) before executing any @Bean method.
Lite mode
Declaring @Bean methods inside a @Component or @Configuration(proxyBeanMethods = false) where no CGLIB proxy is created.
ConfigurationClassPostProcessor
The built-in BeanFactoryPostProcessor that executes Box 2A (scanning packages, parsing @Bean methods, processing @Import, and creating CGLIB config subclasses).
@Import
An annotation that pulls additional configuration classes, ImportSelectors, or ImportBeanDefinitionRegistrars into Box 2.
@Conditional
A gatekeeper annotation on a class or @Bean method that skips registering the recipe in Box 2 unless its Condition.matches() returns true.
