AOP & Proxies

Spring › lesson 6 of 18 · DEEP — how Box 4 wraps your bean and why Rule 2 ("Who You Call") governs everything

Summary — Spring AOP (Aspect-Oriented Programming) lets you attach cross-cutting plumbing (like @Transactional, @Async, @Cacheable, security checks, and timing) without polluting your business methods. There is zero magic: during startup, Box 4 (BeanPostProcessor) generates a wrapper class in memory (a Proxy) that holds a reference target to your real object, and stores the Proxy in Box 3 (singletonObjects). When another bean calls your service, it actually calls the Proxy first—which explains both how AOP works and why calling this.someMethod() from inside the same class completely bypasses it!

§1Where it fits — You Are Here on the Map

Lesson 4 introduced Box 4's assembly-line hook: BeanPostProcessor.postProcessAfterInitialization(bean, name) can return a wrapper object instead of your raw bean. This lesson opens that wrapper, writes out its exact Java code, and shows what happens at both Startup (Phase 1) and Request Time (Phase 2).

§2Why it exists — the tangling & scattering problem

Suppose your business rule in BookService.place(Cart cart) is one line of code. Then your team lead asks you to add permission checking, logging, latency metrics, and a database transaction. Without AOP, look at what you have to write by hand in plain Java: 

// What you WANTED to write (1 line of business logic):
public Order place(Cart cart) {
    return orders.save(Order.from(cart));
}

// What you HAD to write by hand without AOP (18 lines of plumbing around 1 line of business logic):
public Order place(Cart cart) {
    if (!security.hasRole("USER")) throw new AccessDeniedException(); // 1. security
    log.info("Calling place({})", cart);                              // 2. logging
    long t0 = System.nanoTime();                                      // 3. timing
    Connection conn = dataSource.getConnection();                     // 4. transaction
    conn.setAutoCommit(false);
    try {
        Order o = orders.save(Order.from(cart));                      // ★ THE ONLY BUSINESS LINE!
        conn.commit();
        return o;
    } catch (RuntimeException e) {
        conn.rollback();
        throw e;
    } finally {
        conn.close();
        metrics.record("place", System.nanoTime() - t0);
    }
}

Two disasters just happened:

  • Tangling: Four unrelated infrastructure concerns are braided inside one method.
  • Scattering: You have 200 service methods in your app, so that exact try / commit / catch / rollback / finally block is copy-pasted 200 times.

§3How it works (Level 1 → Level 2 Zoom)

Start with Plain Java Data Structures First: What is a Proxy?

Forget the word "bytecode" for a moment. If you wanted to run transaction code before and after BookService.place(cart) without touching BookService.java, how would you write it in plain Java? You would write a subclass wrapper that holds a pointer (target) to the real BookService!

This is the exact Java class that Box 4 generates in memory at startup: 

// 1. Your real class (the TARGET)
public class BookService {
    @Transactional
    public Order place(Cart cart) {
        return orders.save(Order.from(cart));
    }
}

// 2. The wrapper class Spring generates in memory inside Box 4 (the PROXY)
public class BookService$$SpringCGLIB$$0 extends BookService {

    private final BookService target; // ← points to your real BookService object!
    private final TransactionManager txManager;

    @Override
    public Order place(Cart cart) {
        TransactionStatus tx = txManager.begin(); // ① Runs BEFORE target (binds Connection to ThreadLocal)
        try {
            Order result = target.place(cart);    // ② Delegates to the REAL object!
            txManager.commit(tx);                 // ③ Runs AFTER target returns normally
            return result;
        } catch (RuntimeException ex) {
            txManager.rollback(tx);               // ④ Runs on exception
            throw ex;
        }
    }
}

And what does Box 3 (singletonObjects) store under the key "bookService"? 

BookService rawTarget = new BookService(repo);
BookService proxy     = new BookService$$SpringCGLIB$$0(rawTarget, txManager);

// Box 3 stores the PROXY, not the raw target!
singletonObjects.put("bookService", proxy);
Zero magic: Your OrderController asked for a BookService. Because BookService$$SpringCGLIB$$0 extends BookService, it is a BookService! So Spring injects the Proxy into OrderController. Your raw BookService object sits privately inside proxy.target.
Step-by-step control flow (Startup → Request):
  1. Step 1 (Startup — Box 3 Instantiation): Spring creates the raw target object (new BookService()), injects its fields/constructor, and runs its @PostConstruct method. (Notice: no proxy exists yet during @PostConstruct!)
  2. Step 2 (Startup — Box 4 Inspection): AnnotationAwareAspectJAutoProxyCreator (a BeanPostProcessor) inspects the bean in postProcessAfterInitialization. Does any method match an @Aspect pointcut or carry @Transactional / @Async / @Cacheable?
  3. Step 3 (Startup — Box 4 Wrapping → Box 3 Storage): Yes! It generates BookService$$SpringCGLIB$$0 wrapping the raw target, and hands that Proxy to Box 3's singletonObjects map.
  4. Step 4 (Request — Caller invokes Proxy): An HTTP request arrives in Box 6. OrderController calls bookService.place(cart). Because OrderController holds the Proxy, execution enters BookService$$SpringCGLIB$$0.place().
  5. Step 5 (Request — Interceptor Chain → Target): The Proxy runs every matching advice in order (e.g., Security → Logging → Transaction open), calls target.place(cart) on your real object, and unwinds back out (Transaction commit → Logging → return to Controller).

★ Universal Rule 2 ("Who You Call"): External Call vs Self-Invocation

Now look at the single most famous bug in all of Spring. Why does @Transactional (or @Async, or @Cacheable) silently do nothing when method A() calls method B() inside the same class? 

@Service
public class BookService {

    public void importAll(List<Book> books) {    // Notice: NO @Transactional on importAll()
        for (Book b : books) {
            this.saveOne(b);                     // ← Calling `this.saveOne(b)`! Who is `this`?!
        }
    }

    @Transactional
    public void saveOne(Book b) {                // ← @Transactional is SILENTLY IGNORED!
        repo.save(b);
    }
}

Trace the exact pointer on every arrow below. Remember: once the Proxy delegates to target.importAll(books), execution is inside the raw BookService target object. Inside that method, the Java keyword this points to the raw target, NOT the Proxy!

@Aspect
@Component // ← Must be a bean in Box 2/3, or Spring ignores @Aspect!
public class LoggingAndTimingAspect {

    @Before("@annotation(Audited)")
    public void logEntry(JoinPoint jp) { /* runs BEFORE target method */ }

    @AfterReturning(pointcut = "@annotation(Audited)", returning = "res")
    public void logSuccess(Object res) { /* runs ONLY when target returns normally */ }

    @AfterThrowing(pointcut = "@annotation(Audited)", throwing = "ex")
    public void logFailure(Exception ex) { /* runs ONLY when target throws (cannot swallow exception) */ }

    @After("@annotation(Audited)")
    public void cleanup() { /* runs in a `finally` block (success OR exception) */ }

    @Around("@annotation(Audited)")
    public Object measure(ProceedingJoinPoint pjp) throws Throwable {
        long t0 = System.nanoTime();
        try {
            return pjp.proceed(); // ← Calls next advice / target.place()!
        } finally {
            metrics.record(pjp.getSignature().getName(), System.nanoTime() - t0);
        }
    }
}

§5Explain it to a 12-year-old

Imagine the school principal's office. The principal (the Target) only wants to do principal work—she doesn't want to check visitor passes, start a stopwatch, or write in a logbook every time someone walks in.

So the school puts a Secretary's Desk (the Proxy) right outside the principal's door. In fact, when anyone asks the school directory (Box 3) for the principal's room number, it gives them the Secretary's Desk!

When a teacher (Controller) visits the principal, they must talk to the Secretary first. The Secretary checks their pass, starts a timer, opens the inner door, lets the principal answer the question, and stops the timer on the way out.

Why does this.saveOne() fail? Suppose the principal is already sitting inside her private office (importAll) and walks over to her own filing cabinet (this.saveOne). Did she walk out of her office, past the Secretary's desk, and back in? No! She stayed inside her room the whole time. The Secretary never saw her move, so no pass was checked and no timer was started.

§7In practice — Code Dissection & Interview Derivation

Code Dissection: A Redis Idempotency Aspect

@Retention(RUNTIME) @Target(METHOD)
public @interface Idempotent { long ttlSeconds() default 300; }

@Aspect
@Component
@Order(Ordered.HIGHEST_PRECEDENCE + 10)                       // ① Outer wrapper: run BEFORE @Transactional!
public class IdempotencyAspect {

    private final StringRedisTemplate redis;
    public IdempotencyAspect(StringRedisTemplate redis) { this.redis = redis; }

    @Around("@annotation(idempotent)")                       // ② Matches method & binds annotation instance
    public Object guard(ProceedingJoinPoint pjp, Idempotent idempotent) throws Throwable {
        String key = RequestContext.idempotencyKey();
        if (key == null) return pjp.proceed();

        Boolean firstTime = redis.opsForValue()               // ③ Atomic Redis SET NX before DB tx opens
            .setIfAbsent("idem:" + key, "1", Duration.ofSeconds(idempotent.ttlSeconds()));
        if (Boolean.FALSE.equals(firstTime)) {
            throw new DuplicateRequestException(key);         // ④ Aborts call; target never runs
        }
        try {
            return pjp.proceed();                             // ⑤ Calls next interceptor (@Transactional) → target
        } catch (Throwable ex) {
            redis.delete("idem:" + key);                      // ⑥ Target failed → clear lock so user can retry
            throw ex;
        }
    }
}
Chunk-by-chunk dissection: ① @Order controls the onion layers when multiple aspects wrap the same method. Lower number = outer layer. Because @Transactional defaults to Ordered.LOWEST_PRECEDENCE (innermost), setting HIGHEST_PRECEDENCE + 10 ensures we check Redis outside the database transaction—without holding a precious DB connection during a Redis network call! ② Writing @annotation(idempotent) (matching the parameter name idempotent) both matches the method and passes the annotation object into guard() so we can read idempotent.ttlSeconds(). ⑤ Calling return pjp.proceed() is mandatory if you want the target method to execute. Forget return and the caller receives null!
Try this / Predict the output: Suppose OrderService.place() has both @Retryable(maxAttempts = 3) and @Transactional. What happens if @Retryable has a higher order number (meaning it sits inside @Transactional) and attempt #1 fails with a database constraint error?
Answer: The outer @Transactional proxy opened one transaction before attempt #1. When attempt #1 throws an exception, attempts #2 and #3 run inside the same already-broken transaction (which is marked rollback-only)! Outer aspects must always have a lower @Order number so each retry starts a fresh transaction.

How to Think in Interviews — Derive, Don't Memorize

Classic Interview QuestionWhich Box / Rule to Check10-Second Derived Answer
"Why does @Transactional or @Async not work when called from another method in the same class?" Rule 2 (Who You Call) + Box 4 Box 3 stores the Proxy, which wraps the raw target. External callers call the Proxy. Inside the target, this is the raw target, so this.methodB() never passes through the Proxy. Fix by extracting methodB() into a separate bean or injecting self-proxy.
"Why does @Transactional on a private or final method silently fail?" Box 4 (CGLIB subclass) Spring Boot builds AOP proxies using CGLIB (class Service$$Proxy extends Service). In Java, a subclass cannot override a private or final method, so the proxy cannot intercept the call.
"Why didn't @Transactional work inside my @PostConstruct method?" Rule 1 (Order of Steps) + Box 3 → Box 4 During startup, @PostConstruct runs on the raw target object before Box 4's postProcessAfterInitialization wraps the bean in an AOP proxy! At the moment @PostConstruct runs, no proxy exists yet. Use ApplicationReadyEvent or ApplicationRunner instead.
"What is the difference between JDK Dynamic Proxy and CGLIB Proxy?" Box 4 JDK Dynamic Proxy implements the target's interfaces (implements Foo), so it cannot be cast to the concrete class. CGLIB generates a subclass (extends FooImpl) and overrides non-final methods. Spring Boot defaults to CGLIB (proxy-target-class=true).
"What is the difference between a Servlet Filter, a Spring MVC HandlerInterceptor, and a Spring AOP @Aspect?" Box 5 vs Box 6 vs Box 4 A Filter sits in Box 5 (Tomcat container, sees raw HttpServletRequest before MVC). A HandlerInterceptor sits in Box 6 (DispatcherServlet, sees the matched @Controller handler). An @Aspect sits in Box 4 (wraps any Spring bean method—even background jobs with no HTTP request).

§8Pitfalls

Self-invocation (this.b()). Calling another method on this stays inside the raw target object and bypasses the Box 4 proxy completely. Every proxy-based annotation (@Transactional, @Async, @Cacheable, @PreAuthorize, @Retryable) is silently skipped.
Putting @Transactional or @Cacheable on private, final, or static methods. CGLIB proxies work by overriding instance methods in a generated subclass. Java forbids overriding private, final, or static methods, so the proxy never intercepts them.
Forgetting return pjp.proceed() inside @Around advice. If you forget pjp.proceed(), the target method never runs. If you call pjp.proceed() but forget return, your service method runs and saves to the DB, but returns null to the controller!
Writing @Aspect on a class without @Component (or @Bean). @Aspect is not a stereotype annotation! Box 2A's @ComponentScan ignores @Aspect unless the class is also registered as a bean in Box 2.
Wrong @Order between @Retryable / @Cacheable and @Transactional. Without explicit ordering, a retry aspect might run *inside* a doomed transaction, or a cache aspect might cache uncommitted data before the transaction commits. Lower @Order = outer wrapper.

§9Recap, Reference & Glossary

  • Box 4 (BeanPostProcessor) creates AOP proxies in postProcessAfterInitialization (after @PostConstruct) and stores the Proxy in Box 3 (singletonObjects).
  • A Proxy is just a generated wrapper class holding a pointer target to your real instance.
  • Two proxy mechanisms: JDK Dynamic Proxy (implements interfaces) vs CGLIB (extends your class; Spring Boot's default).
  • Universal Rule 2 ("Who You Call"): External calls hit the Proxy (caller → Proxy → target); internal calls (this.b()) hit the raw target directly and bypass all aspects.
  • Five advice types: @Before, @AfterReturning, @AfterThrowing, @After (finally), and @Around (wraps call via ProceedingJoinPoint.proceed()).
  • @Order controls aspect nesting: lower number = outer layer (runs first on the way in, last on the way out).

Glossary

Proxy (Box 4 wrapper)
The runtime-generated wrapper class stored in Box 3 (singletonObjects) that runs aspect advice before and after delegating to target.
Target object
Your real, unwrapped Java instance (new BookService()) held inside the Proxy.
Self-invocation
When a method on target calls this.anotherMethod(), staying inside the raw object and bypassing the Proxy.
JDK dynamic proxy
A proxy built with java.lang.reflect.Proxy that implements the target's interfaces.
CGLIB proxy
A proxy built by generating a bytecode subclass (extends BookService) that overrides non-final, non-private methods. Default in Spring Boot.
Aspect
A Spring bean annotated with @Aspect that combines pointcuts (where) and advice (what to run).
Join point
A candidate point in program execution; in Spring AOP, always a bean method execution.
Pointcut
A predicate expression (like @annotation(...) or execution(...)) that matches join points.
Advice
The interceptor logic (@Before, @After, @Around, etc.) executed by the Proxy when a matched method is called.
ProceedingJoinPoint
The handle passed to @Around advice whose .proceed() method advances down the interceptor chain to the target.
