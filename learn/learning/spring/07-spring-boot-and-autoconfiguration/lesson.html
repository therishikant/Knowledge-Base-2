Spring Boot & Auto-configuration

Spring › lesson 7 of 18 · DEEP — how SpringApplication.run() orchestrates Boxes 1 → 2A → 2B → 3 → 4 → 5

Summary — Spring Boot does not invent a new container. It is simply a collection of ~150 pre-written @Configuration classes guarded by @Conditional annotations (Box 2B), listed inside a plain text file in spring-boot-autoconfigure.jar. Because Spring Boot always scans your recipes first (Box 2A) and loads its auto-config recipes second (Box 2B) with @ConditionalOnMissingBean, any bean you define automatically overrides Boot's default! Add Starters (curated dependency POMs), an embedded Tomcat bean (Box 5), and a fat-JAR loader, and you have all of Spring Boot.

§2Why it exists — what you had to write by hand before Spring Boot

Before Spring Boot arrived in 2014, setting up a simple REST API with a database in plain Spring required writing all of this boilerplate plumbing by hand in every single microservice: 

// In plain Spring (without Boot), YOU had to write all of this before writing 1 line of business code:
@Configuration
@EnableWebMvc
@EnableTransactionManagement
public class ManualInfrastructureConfig {

    @Bean public DataSource dataSource() {
        HikariConfig c = new HikariConfig();
        c.setJdbcUrl(env.getProperty("db.url"));
        return new HikariDataSource(c);
    }

    @Bean public JdbcTemplate jdbcTemplate(DataSource ds) { return new JdbcTemplate(ds); }
    @Bean public PlatformTransactionManager txManager(DataSource ds) { return new DataSourceTransactionManager(ds); }
    @Bean public ObjectMapper objectMapper() { return new ObjectMapper().registerModule(new JavaTimeModule()); }
    @Bean public DispatcherServlet dispatcherServlet(WebApplicationContext ctx) { return new DispatcherServlet(ctx); }
    // ...plus 200 lines of pom.xml version numbers that had to match each other
    // ...plus installing an external Tomcat server and deploying a .war file!
}

Every team copy-pasted those exact same 200 lines across 50 services. Spring Boot's insight was simple: If hikari-cp.jar is on your classpath and you haven't defined your own DataSource bean yet, 99% of the time you want a HikariDataSource configured from application.yml!

§3How it works (Level 1 → Level 2 Zoom)

Start with Plain Java Data Structures First: How Box 2A + Box 2B Work Together

Why does defining your own @Bean DataSource myDataSource() automatically disable Spring Boot's default DataSource without any special "override" keyword? Look at the plain Java code running inside Box 2: 

// Box 2: The Recipe Book
Map<String, BeanDefinition> beanDefinitionMap = new LinkedHashMap<>();

// ── STEP 2A: Scan YOUR code first (@ComponentScan + your @Configuration classes) ──
// Suppose you wrote your own @Bean DataSource customPool() in your code:
beanDefinitionMap.put("customPool", new BeanDefinition(DataSource.class));

// ── STEP 2B: Load Spring Boot's AutoConfiguration.imports file SECOND ──
List<String> bootCandidates = Files.readAllLines(
    Path.of("META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports")
); // ~150 class names: DataSourceAutoConfiguration, JacksonAutoConfiguration, ...

for (String candidate : bootCandidates) {
    // Check 1 (@ConditionalOnClass): Is the library JAR even on the classpath?
    if (!classpathHas("javax.sql.DataSource")) continue;

    // Check 2 (@ConditionalOnMissingBean): Did the user ALREADY put a DataSource recipe in Box 2A?
    if (!containsRecipeForType(beanDefinitionMap, DataSource.class)) {
        beanDefinitionMap.put("dataSource", new BeanDefinition(HikariDataSource.class));
    } else {
        // User already defined one in Step 2A! Back off silently!
    }
}
Universal Rule 1 ("Order of Steps") in action: Because Box 2A (your recipes) always runs before Box 2B (Boot's auto-config recipes), by the time Boot checks @ConditionalOnMissingBean, your recipe is already sitting in beanDefinitionMap! That is the entire secret of how you customize Spring Boot.
Full Step-by-Step Trace of SpringApplication.run(BookVaultApp.class, args):
  1. Step 1 (Prepare Box 1 — Environment): Reads command-line args, OS environment variables, and application.yml into Box 1's List<PropertySource>, and activates profiles.
  2. Step 2 (Create Empty Context): Checks the classpath to pick the right context class (if spring-webmvc is present → creates AnnotationConfigServletWebServerApplicationContext with empty Box 2 and Box 3 maps).
  3. Step 3 (Populate Box 2A — Your Recipes): Sees @SpringBootApplication (which contains @ComponentScan). Scans your root package downward and registers all your @Component / @Service / @Controller / @Bean recipes into beanDefinitionMap.
  4. Step 4 (Populate Box 2B — Auto-Config Recipes): Sees @EnableAutoConfiguration (which imports AutoConfigurationImportSelector). Reads all META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports files across all JARs (~150 configs), filters them via @ConditionalOnClass, @ConditionalOnProperty, and @ConditionalOnMissingBean, and adds only the surviving recipes to beanDefinitionMap.
  5. Step 5 (Populate Box 3 & Box 4 — Cook Beans & Wrap Proxies): Loops over the final beanDefinitionMap, calls constructors, injects dependencies, runs @PostConstruct, wraps beans in Box 4 AOP proxies, and stores live singletons in Box 3 (singletonObjects).
  6. Step 6 (Start Box 5 — Embedded Tomcat): At the end of refresh() (in onRefresh / finishRefresh), starts the auto-configured TomcatWebServer bean, which opens ServerSocket(8080) and wires Box 6's DispatcherServlet into Tomcat.
  7. Step 7 (Runners): Invokes any ApplicationRunner or CommandLineRunner beans now that all 6 Boxes are live.

What is @SpringBootApplication really?

Open @SpringBootApplication in your IDE. It is a 3-in-1 meta-annotation combining lessons 5 and 7: 

@SpringBootConfiguration      // 1. Same as @Configuration (so you can put @Bean methods in your main class)
@ComponentScan                // 2. Triggers Box 2A: scan this package and subpackages for your components
@EnableAutoConfiguration      // 3. Triggers Box 2B: @Import(AutoConfigurationImportSelector.class)
public @interface SpringBootApplication { ... }

The Other Two Pillars: Starters (BOM) & The Executable Fat JAR

  • Starters & the BOM (Bill of Materials): A starter like spring-boot-starter-web contains zero Java code. It is just a pom.xml that pulls in compatible libraries (spring-webmvc, jackson-databind, tomcat-embed-core) whose exact versions are pinned in spring-boot-dependencies (the BOM). Because the JARs are now on the classpath, Box 2B's @ConditionalOnClass gates see them and automatically register DispatcherServlet, ObjectMapper, and TomcatWebServer!
  • The Fat JAR & JarLauncher: Standard Java cannot load a .jar nested inside another .jar. When you run mvn package, Spring Boot packages your code in BOOT-INF/classes/, puts all dependency JARs inside BOOT-INF/lib/*.jar, and sets Main-Class: org.springframework.boot.loader.launch.JarLauncher. That launcher installs a custom ClassLoader that knows how to read nested JARs and then invokes your main() method.

§4When to use — Customizing Spring Boot (Best to Worst)

GoalWhat to doWhy
Tweak a setting (port, pool size, timeout, SQL logging)1. Set a property in application.yml (Box 1)Every auto-configured bean reads its settings from @ConfigurationProperties. Zero Java code needed.
Add a module or tweak Jackson / WebClient / Tomcat without losing Boot's defaults2. Define a *Customizer bean (e.g., Jackson2ObjectMapperBuilderCustomizer)Boot's auto-config calls your customizer while keeping all other sensible defaults intact.
Completely replace one default bean (e.g., custom DataSource or SecurityFilterChain)3. Declare your own @Bean of that type in Box 2ABoot's @ConditionalOnMissingBean in Box 2B sees your recipe and steps aside automatically.
Disable an entire unwanted subsystem (e.g., JPA is on the classpath, but this service has no DB)4. @SpringBootApplication(exclude = DataSourceAutoConfiguration.class)Last resort: removes that class from Box 2B completely.

§5Explain it to a 12-year-old

Imagine moving into a new apartment.

Plain Spring is moving into an empty concrete shell: before you can sleep on night one, you have to buy and wire your own ceiling lights, bolt your own stove into the kitchen, and plumb your own sink.

Spring Boot is moving into a smart furnished apartment with a helpful building manager. Look at the order the manager follows on move-in day (Rule 1):

  1. First (Box 2A): You carry your own furniture into the rooms. Maybe you brought your own favourite espresso machine, but you didn't bring a couch or a fridge.
  2. Second (Box 2B): The building manager walks through with a clipboard of 150 standard items. He checks each room: "Is there a kitchen? Yes (@ConditionalOnClass). Did the tenant already bring an espresso machine? Yes (@ConditionalOnMissingBean)—okay, I won't put our standard coffee maker in here! Did they bring a fridge? No—okay, I'll roll in our default fridge!"

And if you ever ask, "Wait, why is this toaster on my counter?" you just ask for the manager's clipboard printout (--debug), and it says: "Installed standard toaster because you have a kitchen and didn't bring your own."

§7In practice — Code Dissection & Interview Derivation

Code Dissection: Inside a Real Spring Boot Auto-Configuration Class

// Inside spring-boot-autoconfigure.jar (loaded in Box 2B):
@AutoConfiguration(after = DataSourceAutoConfiguration.class)     // ① Lite mode + explicit Box 2B order
@ConditionalOnClass({ DataSource.class, JdbcTemplate.class })     // ② Gate 1: Is spring-jdbc.jar present?
@ConditionalOnSingleCandidate(DataSource.class)                   // ③ Gate 2: Is a DataSource recipe in Box 2?
@EnableConfigurationProperties(JdbcProperties.class)              // ④ Bind spring.jdbc.* from Box 1
public class JdbcTemplateAutoConfiguration {

    @Bean
    @Primary
    @ConditionalOnMissingBean(JdbcOperations.class)               // ⑤ Gate 3: Back off if user defined one in 2A!
    public JdbcTemplate jdbcTemplate(DataSource dataSource, JdbcProperties properties) {
        JdbcTemplate template = new JdbcTemplate(dataSource);
        JdbcProperties.Template t = properties.getTemplate();
        template.setFetchSize(t.getFetchSize());                  // ⑥ Apply Box 1 property defaults
        template.setMaxRows(t.getMaxRows());
        return template;
    }
}
Chunk-by-chunk dissection: ① @AutoConfiguration sets proxyBeanMethods = false (Lite mode) so Spring Boot doesn't waste startup time generating CGLIB proxies for 150 auto-config classes, and after = DataSourceAutoConfiguration.class guarantees the DataSource recipe is evaluated before JdbcTemplate. ② @ConditionalOnClass inspects bytecode on disk using ASM. Even if JdbcTemplate.class is completely absent from your pom.xml, the JVM never throws ClassNotFoundException! ⑤ @ConditionalOnMissingBean(JdbcOperations.class) checks Box 2 (beanDefinitionMap). If you defined a @Bean JdbcTemplate in Box 2A, this condition returns false and Boot skips its method.

Try this / Predict the output: Suppose you add spring-boot-starter-data-jpa to your pom.xml, do NOT configure spring.datasource.url in application.yml, and do NOT have H2/HSQL/Derby on the classpath. What happens at startup and why?
Answer: Box 2B's DataSourceAutoConfiguration passes Gate 1 (@ConditionalOnClass(DataSource.class) is true because starter-data-jpa brought spring-jdbc). It passes Gate 3 (@ConditionalOnMissingBean is true because you didn't define a DataSource). Then when Box 3 tries to instantiate the DataSource bean, it has no URL and no embedded DB driver, so startup halts and Boot's DataSourceBeanCreationFailureAnalyzer prints a friendly report telling you to either set spring.datasource.url or add an embedded database JAR!

How to Think in Interviews — Derive, Don't Memorize

Classic Interview QuestionWhich Box / Rule to Check10-Second Derived Answer
"How does Spring Boot Auto-Configuration work under the hood?" Box 2A → Box 2B @SpringBootApplication includes @EnableAutoConfiguration, which imports AutoConfigurationImportSelector. After Box 2A scans your code, Box 2B reads ~150 config classes from META-INF/spring/...AutoConfiguration.imports, filters them via @ConditionalOnClass and @ConditionalOnMissingBean, and registers matching recipes in beanDefinitionMap.
"Why does my custom @Bean override Spring Boot's default bean without any conflict?" Rule 1 (Order: Box 2A before Box 2B) Spring always scans user configuration (Box 2A) *before* evaluating auto-configuration (Box 2B). Boot's @Bean methods are annotated with @ConditionalOnMissingBean, so when Box 2B checks beanDefinitionMap, it sees your recipe from Box 2A and backs off.
"Why doesn't @ConditionalOnClass(SomeMissingClass.class) throw NoClassDefFoundError when that JAR isn't in pom.xml?" Box 2B (ASM Bytecode Reader) Before asking the JVM ClassLoader to load an auto-config class, Spring reads the .class file's raw bytes from the JAR using ASM and checks if the string "com/foo/SomeMissingClass" exists as a .class resource on the classpath.
"How does an executable Spring Boot fat JAR run java -jar app.jar when Java doesn't support nested JARs?" Startup (Before Box 1) The JAR's MANIFEST.MF sets Main-Class to Boot's JarLauncher. JarLauncher creates a custom LaunchedClassLoader that can stream bytecode directly from uncompressed nested JARs inside BOOT-INF/lib/, and then invokes your Start-Class main() method.
"How do you debug why an auto-configured bean was or wasn't created?" Box 2B Report Start the app with --debug (or debug: true in application.yml, or check /actuator/conditions). It prints the CONDITIONS EVALUATION REPORT showing every Positive and Negative match in Box 2B and the exact @Conditional that passed or failed.

§8Pitfalls

Replacing a complex bean (like ObjectMapper or WebMvcConfigurationSupport) when you only wanted to tweak one setting. If you define @Bean ObjectMapper or put @EnableWebMvc on a class, Boot's @ConditionalOnMissingBean backs off completely—wiping out all of Boot's date formatting, Kotlin/JavaTime modules, and resource handlers! Fix: register a Jackson2ObjectMapperBuilderCustomizer or implement WebMvcConfigurer (without @EnableWebMvc).
Hardcoding library versions in pom.xml for dependencies managed by Boot's BOM. Specifying a manual <version> for Jackson, Hibernate, or Netty overrides Boot's tested Bill of Materials and leads to NoSuchMethodError crashes at runtime.
Looking for spring.factories in Spring Boot 3.x. Prior to Spring Boot 2.7, auto-configurations were listed in META-INF/spring.factories. In Spring Boot 3.x, spring.factories is no longer supported for auto-configurations; they live in META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports.
Putting your main @SpringBootApplication class in a deep subpackage. Both @ComponentScan (Box 2A) and @AutoConfigurationPackage (which tells JPA/Hibernate where to scan for @Entity classes) use the main class's package as their root.

§9Recap, Reference & Glossary

  • SpringApplication.run() executes Phase 1 in strict order: Box 1 (Environment) → Box 2A (your recipes) → Box 2B (Boot auto-config recipes) → Box 3 & 4 (instantiate singletons & wrap proxies) → Box 5 (start Embedded Tomcat).
  • @SpringBootApplication = @SpringBootConfiguration + @ComponentScan (Box 2A) + @EnableAutoConfiguration (Box 2B).
  • Box 2B reads META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports (~150 classes) and filters them via @ConditionalOnClass, @ConditionalOnProperty, and @ConditionalOnMissingBean.
  • Universal Rule 1: Because Box 2A runs before Box 2B, any bean you declare causes Boot's @ConditionalOnMissingBean to back off automatically.
  • Starters + BOM solve dependency version alignment; JarLauncher + BOOT-INF/lib/ solve single-file deployment.
  • Run with --debug to read the Conditions Evaluation Report whenever you want to know why a bean was or wasn't registered.

Glossary

Auto-configuration (Box 2B)
Conditional @Configuration classes shipped inside JARs and listed in AutoConfiguration.imports that register default recipes in beanDefinitionMap after user recipes are scanned.
AutoConfigurationImportSelector
The ImportSelector triggered by @EnableAutoConfiguration that reads AutoConfiguration.imports and filters candidates in Box 2B.
@ConditionalOnMissingBean
The condition on Boot's @Bean methods that skips registering Boot's default recipe if a recipe of that type is already in beanDefinitionMap (from Box 2A).
@ConditionalOnClass
The condition that checks via ASM bytecode inspection whether a library class is present on the classpath before registering a recipe.
Starter
An empty Maven/Gradle POM (like spring-boot-starter-web) that transitively pulls a curated set of libraries for a capability.
BOM (Bill of Materials)
spring-boot-dependencies, the master POM that pins compatible versions for ~1,000 libraries.
Fat JAR (Executable JAR)
A single archive containing your classes (BOOT-INF/classes/), nested dependency JARs (BOOT-INF/lib/), and Boot's JarLauncher.
Condition Evaluation Report
The diagnostic report printed by --debug listing every Positive and Negative match in Box 2B.
