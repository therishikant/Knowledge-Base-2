Externalized Configuration & Profiles

Spring › lesson 8 of 18 · DEEP — zooming into Box 1 (Environment & List<PropertySource>)

Summary — To deploy the exact same JAR file to dev, staging, and production, you must keep environment-specific settings outside your Java code. Spring stores all settings in Box 1 (Environment), which is simply an ordered Java List<PropertySource> (a list of Map<String, Object> searched from index 0 downward so the first match wins) plus a Set<String> activeProfiles. You bind those settings into your beans using immutable @ConfigurationProperties records (with @Validated and relaxed binding), while @Profile acts as a gatekeeper on Box 1 files and Box 2 recipes.

§1Where it fits — You Are Here on the Map

Lesson 7 traced SpringApplication.run() and showed that Step 1 of startup is building Box 1 (Environment) before any recipes in Box 2 or beans in Box 3 exist. Now we open Box 1 to see the exact data structures inside it and how its values flow into Box 2 and Box 3.

📍 You Are Here on the 6-Box Map: Phase 1 (Startup) → Box 1 (Environment)

§2Why it exists — the pain in plain Java

Suppose your BookVault app needs a database URL, a connection pool size, and an HTTP timeout. Without Box 1 (Environment) and @ConfigurationProperties, look at the plain Java code you would have to write by hand: 

// Without Spring's Environment + @ConfigurationProperties:
public class ManualConfigLoader {
    public static CatalogConfig load(String[] args) throws IOException {
        // 1. Read defaults from a file inside the JAR
        Properties fileProps = new Properties();
        fileProps.load(ManualConfigLoader.class.getResourceAsStream("/app.properties"));

        // 2. Manually check CLI args first, then OS env var (with uppercase_underscore!), then file:
        String timeoutStr = findCliArg(args, "--catalog.timeout");
        if (timeoutStr == null) timeoutStr = System.getenv("CATALOG_TIMEOUT");
        if (timeoutStr == null) timeoutStr = System.getProperty("catalog.timeout");
        if (timeoutStr == null) timeoutStr = fileProps.getProperty("catalog.timeout", "2s");

        // 3. Manually parse strings into Duration/int and validate constraints:
        Duration timeout = parseDurationByHand(timeoutStr);
        String url = System.getenv("CATALOG_BASE_URL");
        if (url == null || url.isBlank()) {
            throw new IllegalArgumentException("Missing catalog.base-url!");
        }
        return new CatalogConfig(url, timeout);
    }
}

Doing that for 50 properties across 10 sources is error-prone misery. Box 1 (Environment) automates the lookup ladder, and @ConfigurationProperties automates the parsing, relaxed naming, and startup validation.

§3How it works (Level 1 → Level 2 Zoom)

Start with Plain Java Data Structures First: Inside Box 1 (Environment)

Strip away the Spring jargon. What is Environment in plain Java? Just two fields—an ordered List of Maps and a Set of profile names: 

public class SimpleEnvironment {

    // 1. Ordered list of Maps — index 0 is highest priority, last index is lowest priority!
    private final List<Map<String, Object>> propertySources = List.of(
        cliArgsMap,             // Index 0: --server.port=9000           (HIGHEST PRIORITY)
        jvmSystemPropsMap,      // Index 1: -Dserver.port=9000
        osEnvVarsMap,           // Index 2: SERVER_PORT=9000             (Docker / K8s)
        applicationProdYmlMap,  // Index 3: application-prod.yml         (Profile-specific file)
        applicationYmlMap       // Index 4: application.yml              (LOWEST PRIORITY)
    );

    // 2. Active profiles (e.g. ["prod"])
    private final Set<String> activeProfiles = new HashSet<>();

    // How getProperty("server.port") works:
    // Loop from index 0 downward; FIRST MAP THAT CONTAINS THE KEY WINS!
    public Object getProperty(String key) {
        for (Map<String, Object> source : propertySources) {
            if (source.containsKey(key)) {
                return source.get(key); // ← First hit returns immediately!
            }
        }
        return null;
    }
}
That for loop is the entire precedence ladder! Why does --server.port=9000 on the command line override SERVER_PORT=8081 in Docker, which overrides server.port: 8080 in application.yml? Simply because cliArgsMap sits at an earlier index in List<PropertySource> than osEnvVarsMap, which sits at an earlier index than applicationYmlMap!
Step-by-step control flow (How Box 1 feeds Box 2 and Box 3):
  1. Step 1 (Box 1 Assembly): SpringApplication.run() populates List<PropertySource> in precedence order (CLI args → JVM -D props → OS ENV_VARS → application-{profile}.yml → application.yml).
  2. Step 2 (Box 2 Gatekeeping — @Profile & @ConditionalOnProperty): While scanning recipes into Box 2 (beanDefinitionMap), Spring checks @Profile("prod") against environment.getActiveProfiles() and @ConditionalOnProperty against environment.getProperty(...). Non-matching recipes never enter Box 2.
  3. Step 3 (Box 3 Constructor & @ConfigurationProperties Binding): When Box 3 instantiates a @ConfigurationProperties record, Spring's Binder queries Box 1 using relaxed binding (BOOKVAULT_MAX_PAGE_SIZE → bookvault.max-page-size), converts strings into Duration / DataSize / int, runs Jakarta @Validated checks, and calls the record's constructor.
  4. Step 4 (Box 3/4 @Value Injection): When Box 3 creates a bean with @Value("${my.key}"), it resolves the string from Box 1. (Note: if @Value is on a field instead of a constructor parameter, by Rule 1 it is injected *after* the constructor runs!)

@ConfigurationProperties vs @Value — and Relaxed Binding

Why do Linux/Docker environment variables look like DB_POOL_SIZE=20, while YAML files look like db.pool-size: 20, and Java fields look like int poolSize? Because Linux shells only allow letters, digits, and underscores in environment variable names!

Spring Boot bridges this gap with Relaxed Binding: when binding a @ConfigurationProperties(prefix = "db") object, Boot automatically normalizes all of these to the Java field poolSize:

  • db.pool-size (kebab-case in application.yml — canonical)
  • db.poolSize (camelCase in .properties)
  • db.pool_size (snake_case)
  • DB_POOL_SIZE (UPPERCASE_SNAKE_CASE in OS environment variables)

How @Profile Gatekeeps Box 1 and Box 2

A profile (like dev, test, or prod) is just a string in Box 1's Set<String> activeProfiles, activated via SPRING_PROFILES_ACTIVE=prod or --spring.profiles.active=prod. It controls two things:

  1. In Box 1 (Which property maps get loaded): Activating prod adds application-prod.yml (or the spring.config.activate.on-profile: prod section of application.yml) into List<PropertySource> above application.yml.
  2. In Box 2 (Which bean recipes get registered): Putting @Profile("prod") on a @Component or @Bean method acts as a @Conditional gatekeeper—if "prod" is not in activeProfiles, that recipe is never added to beanDefinitionMap!

§5Explain it to a 12-year-old

Imagine you are asking your family what temperature to set the house thermostat to. Instead of asking everyone at random, you have a strict Priority List (Box 1's List<PropertySource>) taped to the wall:

  1. Line 1: What Mom just shouted from the kitchen right now (Command-line args).
  2. Line 2: The sticky note on the fridge (OS Environment Variables).
  3. Line 3: The "Winter Rules" booklet (application-winter.yml).
  4. Line 4: The factory manual that came with the thermostat (application.yml).

You read the list from Line 1 downward. The very first line that gives you an answer wins, and you stop reading! So if the manual says 20°C, the fridge note says 22°C, and Mom shouts 18°C, you set it to 18°C because Line 1 is at the top of the list.

§7In practice — Code Dissection & Interview Derivation

Code Dissection: Immutable @ConfigurationProperties Record + Constructor Binding

// 1. Group related properties into an immutable, validated Java record:
@ConfigurationProperties(prefix = "bookvault.catalog")
@Validated                                                      // ① Fail at startup if constraints fail!
public record CatalogProperties(
    @NotBlank String baseUrl,                                   // ② Binds bookvault.catalog.base-url / BOOKVAULT_CATALOG_BASE_URL
    @DefaultValue("2s") Duration timeout,                       // ③ Parses "2s", "500ms", "PT2S" automatically
    @Min(1) @Max(200) @DefaultValue("50") int maxPageSize
) {}

// 2. Register it (or place @ConfigurationPropertiesScan on BookVaultApplication):
@Configuration
@EnableConfigurationProperties(CatalogProperties.class)         // ④ Registers CatalogProperties recipe in Box 2
public class CatalogConfig {}

// 3. Inject into your service via constructor:
@Service
public class CatalogClient {
    private final RestClient http;

    public CatalogClient(RestClient.Builder builder, CatalogProperties props) {
        // ⑤ Safe inside constructor! `props` is already bound and validated in Box 3!
        this.http = builder.baseUrl(props.baseUrl()).build();
    }
}
Chunk-by-chunk dissection: ① @Validated triggers Jakarta Bean Validation the moment Box 3 constructs CatalogProperties. If bookvault.catalog.base-url is missing or max-page-size: 999, the app refuses to start and prints the exact offending property name and value. ② Because CatalogProperties is a Java record, Spring Boot uses constructor binding automatically—there are no setter methods, so no code can mutate your configuration at runtime. ⑤ Because CatalogProperties is passed as a constructor parameter, props.baseUrl() is non-null and ready to use right inside CatalogClient's constructor.
Try this / Predict the output: Suppose a developer writes this service class: 
@Service
public class PaymentService {
    @Value("${payment.api-url}")
    private String apiUrl;

    public PaymentService() {
        System.out.println("Connecting to: " + apiUrl.toUpperCase());
    }
}
Predict: Even if payment.api-url=https://pay.example.com is present in application.yml, what happens at startup?
Answer: Startup crashes with a NullPointerException inside PaymentService()! By Universal Rule 1 (Order of Steps), Java must finish running new PaymentService() (the constructor) before Box 4's AutowiredAnnotationBeanPostProcessor can inject @Value onto the private field apiUrl. Inside the constructor, apiUrl is still null! Fix: put @Value("${payment.api-url}") String apiUrl as a constructor parameter (or better, inject a @ConfigurationProperties record).

How to Think in Interviews — Derive, Don't Memorize

Classic Interview QuestionWhich Box / Rule to Check10-Second Derived Answer
"If a property is defined in application.yml, an OS environment variable, and a CLI --arg, which one wins and why?" Box 1 (List<PropertySource>) The CLI --arg wins (followed by OS env var, then application.yml). Box 1's Environment holds an ordered List<PropertySource> with CLI args near index 0 and application.yml near the bottom; getProperty() searches top-to-bottom and returns the first match.
"Why was my @Value field null inside the bean's constructor?" Rule 1 (Constructor before @Value field injection) In Box 3, Spring must call new MyBean() first before any BeanPostProcessor (Box 4) can reflectively set @Value fields on the constructed instance. Pass the @Value (or @ConfigurationProperties record) as a constructor parameter instead.
"When should you use @ConfigurationProperties vs @Value?" Box 1 → Box 3 Binding Use @ConfigurationProperties (on a @Validated record) whenever you have related settings: it gives type-safe grouping, JSR-380 startup validation, nested lists/maps, and full relaxed binding (DB_POOL_SIZE → db.pool-size). Use @Value only for isolated single keys or SpEL expressions.
"How does @Profile("prod") work under the hood?" Box 1 (activeProfiles) → Box 2 (@Conditional) @Profile is a meta-annotation carrying @Conditional(ProfileCondition.class). During Box 2 recipe scanning, ProfileCondition checks if "prod" is in Box 1's environment.getActiveProfiles(). If not, the recipe is skipped and never enters beanDefinitionMap.
"What happens if you override a YAML List property inside application-prod.yml?" Box 1 (getProperty first-hit rule) Unlike Map properties (which merge key-by-key across property sources), a List in a higher-priority PropertySource (application-prod.yml) replaces the entire list from application.yml rather than appending to it.

§8Pitfalls

Reading a @Value field inside a constructor. By Rule 1, the constructor runs before field injection, so the field is always null inside the constructor. Always use constructor injection (public MyService(@Value("${...}") String url) or CatalogProperties props).
Creating a @ConfigurationProperties class and forgetting @EnableConfigurationProperties or @ConfigurationPropertiesScan. @ConfigurationProperties alone does not register a bean recipe in Box 2! Without enabling it, Spring fails with NoSuchBeanDefinitionException when you try to inject it.
Expecting @Value to support full relaxed binding with OS environment variables. While @ConfigurationProperties(prefix = "bookvault") effortlessly binds BOOKVAULT_MAX_PAGE_SIZE to maxPageSize, @Value lookups are much stricter and easily break when dots, dashes, and camelCase mix with OS env vars.
Expecting List properties in application-prod.yml to append to application.yml. Lists in higher-precedence PropertySources completely overwrite lists in lower-precedence sources.
Hardcoding secrets in application.yml or exposing /actuator/env publicly. Never commit passwords or API keys to Git; pass them via configtree:/run/secrets/, Vault, or environment variables, and lock down Actuator endpoints in Box 5 (SecurityFilterChain).

§9Recap, Reference & Glossary

  • Box 1 (Environment) is built first during Phase 1 (Startup) and holds List<PropertySource> + Set<String> activeProfiles.
  • Precedence is just list order: getProperty(key) loops from index 0 downward (CLI args → JVM -D props → OS ENV_VARS → application-{profile}.yml → application.yml) and returns the first hit.
  • Relaxed binding maps DB_POOL_SIZE (env var) ↔ db.pool-size (YAML) ↔ poolSize (Java field) on @ConfigurationProperties.
  • Prefer @ConfigurationProperties + record + @Validated over scattered @Value fields for immutability, startup validation, and easy unit testing.
  • Universal Rule 1: Never read a field-injected @Value inside a constructor; inject via constructor parameters.
  • @Profile activates profile-specific YAML files in Box 1 and gatekeeps bean recipes in Box 2.

Glossary

Environment (Box 1)
The container's configuration registry holding the ordered List<PropertySource> and the Set<String> activeProfiles.
PropertySource
A named Map<String, Object> representing one source of configuration (CLI args, OS env vars, a YAML file, etc.) inside Box 1.
Precedence ladder
The top-to-bottom order of List<PropertySource> in Box 1; the first source containing a requested key wins.
Relaxed binding
Spring Boot's normalization rule that matches DB_POOL_SIZE, db.pool-size, db.pool_size, and db.poolSize to the same Java property on @ConfigurationProperties.
@ConfigurationProperties
Binds a prefix-grouped set of properties from Box 1 into a structured, type-safe Java class or record.
Constructor binding
Instantiating an immutable @ConfigurationProperties record (or class) by passing bound values directly into its constructor.
Profile
A named environment label (e.g., dev, prod) stored in Box 1 that activates application-{profile}.yml files and filters @Profile-annotated recipes in Box 2.
Config tree (configtree:)
A PropertySource that maps files in a directory (such as Kubernetes mounted secrets in /run/secrets/) where the filename is the property key and the file content is the value.
