The Web MVC Request Lifecycle

Spring › lesson 9 of 18 · DEEP — who calls your controller, and when

In simple English — When an HTTP request hits port 8080, Tomcat grabs one worker thread from its pool, runs a chain of Servlet Filters (Box 5), and hands the request to a single front-door servlet called DispatcherServlet (Box 6). That one servlet looks up your @Controller method in a routing Map, converts URL strings and JSON into Java arguments, calls your method, and converts your return object back into JSON bytes.

§2Why it exists — the pain of raw Servlets

In raw Java Servlet-land (lesson 1), every endpoint is a separate class extending HttpServlet, or a giant if/else block parsing URL strings by hand. Every single endpoint repeats the same five chores: 

// ❌ Raw Servlet WITHOUT Spring MVC — you repeat this ceremony in every endpoint
public class BookServlet extends HttpServlet {
    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws IOException {
        // 1. Parse the path by hand: "/books/42" -> "42"
        String[] parts = req.getPathInfo().split("/");
        long id = Long.parseLong(parts[1]);

        // 2. Read query params & headers by hand, handle nulls & defaults
        String currency = req.getParameter("currency") != null ? req.getParameter("currency") : "USD";

        // 3. Call business logic
        Book book = bookService.findById(id, currency);

        // 4. Set headers and serialize to JSON bytes by hand
        resp.setStatus(200);
        resp.setContentType("application/json");
        objectMapper.writeValue(resp.getOutputStream(), book);
    }
}

Thirty endpoints mean thirty repetitions of path splitting, Long.parseLong, null checks, Jackson calls, and try/catch error blocks. Worse, your business method is glued to HttpServletRequest and HttpServletResponse, making it painful to unit-test.

The Front Controller pattern fixes this once and for all: put one servlet at the front door (DispatcherServlet mapped to "/"), let it do all the string parsing and JSON conversion using a reusable pipeline, and reduce your endpoint to a plain Java method: 

// ✅ With Spring MVC — zero Servlet API imports, trivially unit-testable with plain `new`
@GetMapping("/books/{id}")
Book getBook(@PathVariable long id, @RequestParam(defaultValue = "USD") String currency) {
    return bookService.findById(id, currency);
}

§3How it works (Level 1 → Level 2 Zoom)

Start with Plain Java Data Structures First

Before learning a single Spring MVC class name, look at what DispatcherServlet actually holds inside memory (populated during Phase 1 startup when it scanned your @Controller beans in Box 3): 

// Inside DispatcherServlet (Box 6) — it is just a Map and three Lists of helper beans!
class MiniDispatcherServlet extends HttpServlet {

    // 1. The Routing Table (Spring calls this: RequestMappingHandlerMapping)
    //    Key:   "GET /books/{id}"
    //    Value: Controller bean reference (from Box 3) + java.lang.reflect.Method
    Map<RouteKey, HandlerMethod> routingTable;

    // 2. Parameter Builders (Spring calls this: List<HandlerMethodArgumentResolver>)
    //    Each helper answers: "Can I build this parameter (e.g. @PathVariable, @RequestBody)?"
    List<ArgumentResolver> argumentResolvers;

    // 3. Body Translators (Spring calls this: List<HttpMessageConverter>)
    //    Jackson JSON converter, String converter, byte[] converter
    List<MessageConverter> messageConverters;
}
That's the whole secret: DispatcherServlet does not know how to parse @PathVariable or write JSON itself. It holds List<T> strategy beans (injected via the lesson 3 collection trick) and loops through them asking, "Does anyone know how to handle this parameter / return type?"

Step-by-Step Trace: What Happens When GET /books/42 Arrives

Trace of GET /books/42 (Accept: application/json) across Box 5 → Box 6 → Box 4:
Step 1 (Tomcat Socket & Thread Pool — Box 5): Tomcat's acceptor on port 8080 accepts the TCP bytes, parses the HTTP text into HttpServletRequest, and grabs 1 worker thread (e.g., http-nio-8080-exec-1) from its thread pool.
↓
Step 2 (Servlet FilterChain — Box 5): The worker thread walks through Tomcat's FilterChain (CharacterEncodingFilter → SecurityFilterChain → custom filters). Note: Nobody knows which Controller method will run yet!
↓
Step 3 (DispatcherServlet.doDispatch() — Entering Box 6): The last filter calls DispatcherServlet.service() → doDispatch(req, resp).
↓
Step 4 (HandlerMapping Lookup — Box 6): RequestMappingHandlerMapping checks its routing Map for GET /books/42. It finds BookController#getBook(long) and returns a HandlerExecutionChain (the target method + matching HandlerInterceptors). If no route matches → 404; if only POST /books/42 exists → 405.
↓
Step 5 (HandlerInterceptor.preHandle() — Box 6): Interceptors run now. Unlike a Filter, preHandle receives the exact HandlerMethod object, so it can inspect annotations on your controller method!
↓
Step 6 (HandlerAdapter + ArgumentResolvers — Box 6): RequestMappingHandlerAdapter inspects the parameters of getBook(@PathVariable long id). The PathVariableMethodArgumentResolver extracts "42" from the URL template and converts it to 42L. (If there were a @RequestBody, it would ask Jackson's HttpMessageConverter to parse JSON bytes into a Java object here.)
↓
Step 7 (Controller → Service Proxy — Box 6 calls Box 4): Reflective call method.invoke(bookControllerBean, 42L) runs your controller. Your controller calls bookService.findById(42L) — hitting the @Transactional proxy in Box 4!
↓
Step 8 (ReturnValueHandler + HttpMessageConverter — Box 6): Your controller returns a BookResponse record. Because the class has @RestController (which includes @ResponseBody), RequestResponseBodyMethodProcessor checks the Accept: application/json header, picks MappingJackson2HttpMessageConverter, and writes JSON bytes to the HTTP response stream.
↓
Step 9 (Unwind & Cleanup — Box 6 → Box 5): Interceptor.postHandle() and afterCompletion() run → Filters unwind in reverse order (clearing ThreadLocals in finally blocks!) → Tomcat flushes the socket and returns the worker thread to the pool.

Argument resolution — how a method signature becomes an HTTP contract

@GetMapping("/books/{id}/reviews")
List<Review> reviews(
    @PathVariable long id,                       // from the URI template ("42" -> 42L)
    @RequestParam(defaultValue = "0") int page,     // ?page=2  (missing -> 0)
    @RequestParam Optional<String> sort,         // genuinely optional
    @RequestHeader("X-Tenant") String tenant,      // missing -> 400 Bad Request, not null
    @CookieValue(required = false) String sid,
    Pageable pageable,                            // Spring Data resolver (lesson 11)
    Principal principal,                          // Spring Security ThreadLocal (lesson 13)
    Locale locale) { ... }

@PostMapping("/books")
ResponseEntity<Book> create(@Valid @RequestBody CreateBook cmd) { ... }
//                          ↑ validate   ↑ MessageConverter: JSON -> object
Convention: the method signature is the API documentation. Required means required (missing @RequestHeader → automatic 400). Don't accept HttpServletRequest and dig things out by hand — that throws away every benefit of the resolver chain and makes the method harder to unit-test.

Content negotiation & message converters (406 vs 415)

@RequestBody and @ResponseBody delegate to an ordered List<HttpMessageConverter>. Spring matches the request's Content-Type header (when reading the body) or Accept header (when writing the response) against each converter: 

@GetMapping(value = "/books/{id}", produces = APPLICATION_JSON_VALUE)
@PostMapping(value = "/books",      consumes = APPLICATION_JSON_VALUE)
// Caller sends Accept: application/xml (we can't produce what they accept) -> 406 Not Acceptable
// Caller sends Content-Type: text/plain (we can't read what they sent)     -> 415 Unsupported Media Type

Threading — why Box 5's thread pool explains your p99 latency

Classic Spring MVC is thread-per-request: Tomcat takes 1 platform thread from its pool (default max 200) and that thread is blocked for the entire request, including every millisecond spent waiting on PostgreSQL or a downstream HTTP call. 200 threads × 100 ms of I/O = a hard ceiling of ~2,000 req/s. Once all 200 threads are busy waiting on I/O, request #201 sits in a queue and latency spikes.

ApproachHowCost & Trade-off
Tune platform poolserver.tomcat.threads.maxEach OS thread ≈ 1 MB stack + context-switch overhead. Doesn't scale far.
Virtual threads (Boot 3.2+, Java 21)spring.threads.virtual.enabled=trueNearly free. Same simple blocking code, millions of virtual threads unmount during I/O (java/11).
Async MVC / WebFluxReturn CompletableFuture/DeferredResult, or WebFlux (lesson 17)Completely different non-blocking programming model; harder stack traces.
The senior answer to "MVC or WebFlux for scalability?" — "Virtual threads in Boot 3.2+ removed most of the reason to rewrite blocking apps into reactive WebFlux. I stay on Spring MVC with virtual threads unless we need reactive backpressure or streaming protocols."

§5Explain it to a 12-year-old

Picture a huge hospital with one central reception desk (DispatcherServlet in Box 6). Nobody wanders the halls looking for a doctor on their own — every single visitor goes to that one desk.

Before you even reach the reception desk, you walk through the front security doors (a Filter in Box 5). The guard checks everyone walking into the building — patients, visitors, the pizza delivery guy — and he has no idea which doctor you are going to see.

At the reception desk, the receptionist checks her big directory map (HandlerMapping) to find which doctor handles your problem. Before you enter the doctor's office, a hallway nurse (HandlerInterceptor) does a quick check — and unlike the front door guard, the nurse does know which specific doctor you're seeing! Then an assistant copies your messy handwritten notes onto the clean typed chart the doctor expects (ArgumentResolvers).

The doctor (@Controller) just does doctor work and writes a prescription object. On your way out, reception translates that prescription into whatever format you asked for — printed English, Spanish, or a digital JSON message (HttpMessageConverter).

§7In practice — Code Dissection & Derive, Don't Memorize

1. A Correlation ID Filter (Box 5) vs a Rate-Limit Interceptor (Box 6)

// ---- BOX 5: Filter runs for EVERY request, before routing, sees raw bytes ----
@Component
@Order(Ordered.HIGHEST_PRECEDENCE)                 // ① earliest in Box 5, so every log line has it
public class CorrelationIdFilter implements Filter {

    private static final String HEADER = "X-Correlation-Id";

    @Override
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain)
            throws IOException, ServletException {

        HttpServletRequest http = (HttpServletRequest) req;
        String id = Optional.ofNullable(http.getHeader(HEADER))        // ② reuse upstream ID if present
                            .filter(s -> !s.isBlank())
                            .orElseGet(() -> UUID.randomUUID().toString());
        MDC.put("correlationId", id);                             // ③ Rule 3: ThreadLocal!
        ((HttpServletResponse) res).setHeader(HEADER, id);             // ④ echo back to caller
        try {
            chain.doFilter(req, res);                                  // ⑤ enters Box 6 (DispatcherServlet)
        } finally {
            MDC.remove("correlationId");                           // ⑥ MUST clean up — pooled thread!
        }
    }
}

// ---- BOX 6: Interceptor runs AFTER HandlerMapping — knows the target method! ----
@Component
class RateLimitInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {
        if (handler instanceof HandlerMethod hm) {                 // ⑦ we can inspect the controller method!
            RateLimit limit = hm.getMethodAnnotation(RateLimit.class);
            if (limit != null && !buckets.tryConsume(key(req), limit.perMinute())) {
                res.setStatus(429);
                return false;                                      // ⑧ abort: controller never runs
            }
        }
        return true;
    }
}

@Configuration
class WebConfig implements WebMvcConfigurer {            // ⑨ register without breaking Boot auto-config
    private final RateLimitInterceptor rateLimit;
    WebConfig(RateLimitInterceptor rateLimit) { this.rateLimit = rateLimit; }

    @Override public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(rateLimit).addPathPatterns("/api/**");
    }
}
Dissection. ①⑤ chain.doFilter(req, res) is the doorway from Box 5 into Box 6. Everything before it runs on the way in; everything after it runs on the way out. ③⑥ Universal Rule 3 (Where State Lives): MDC stores data in a ThreadLocal attached to Tomcat's worker thread. Because Tomcat reuses threads from its pool, forgetting MDC.remove() in finally leaks User A's correlation ID onto User B's next request! ⑦⑧ Why is RateLimitInterceptor an Interceptor instead of a Filter? Because it reads @RateLimit off the controller method (HandlerMethod), which is only known after HandlerMapping runs inside Box 6.

2. How to Think in Interviews — Derive, Don't Memorize

You never need to memorize trivia about Filters, Interceptors, or Controllers if you check the 6-Box Map and the 3 Universal Rules:

Classic Interview QuestionWhich Box / Rule?10-Second Derivation
"Why didn't my @ControllerAdvice catch an exception thrown inside my custom Filter?" Rule 1
(Box 5 vs Box 6)		 A Filter runs in Box 5, outside DispatcherServlet. @ControllerAdvice is a HandlerExceptionResolver inside Box 6. The request crashed before entering Box 6!
"Can I read the parsed @RequestBody DTO inside HandlerInterceptor.preHandle()?" Rule 1
(Order inside Box 6)		 No. Inside Box 6, preHandle() runs in Step 4, before HandlerAdapter and ArgumentResolvers (Step 5) read the JSON stream. And if you read req.getInputStream() yourself in preHandle, the stream is exhausted and @RequestBody fails!
"What happens if I put a mutable field private User currentUser; on my @RestController?" Rule 3
(Box 3 Singleton vs Thread)		 BookController lives in Box 3 (singletonObjects Map) — there is only one instance shared by all 200 Tomcat threads! Concurrent requests overwrite currentUser (race condition / data leak).
"When does the @Transactional database transaction commit relative to a HandlerInterceptor.postHandle()?" Rule 1
(Box 6 wraps Box 4)		 @Transactional is an AOP proxy in Box 4 around the @Service method. It commits as soon as the @Service method returns (inside Step 6), before DispatcherServlet reaches postHandle() (Step 8).
"What is the difference between HTTP 406 and HTTP 415 in Spring MVC?" Box 6
(HttpMessageConverter)		 415 Unsupported Media Type fails at Step 5 (input): Spring can't read the caller's Content-Type into @RequestBody. 406 Not Acceptable fails at Step 7 (output): Spring can't serialize the return value into the caller's Accept format.

§8Pitfalls

ThreadLocal leaks on pooled Tomcat threads (Rule 3). MDC, SecurityContextHolder, or any custom ThreadLocal set in a Filter or Interceptor must be cleared in a finally block (or afterCompletion). Tomcat recycles worker threads; a leftover ThreadLocal leaks one user's state into the next user's request.
Adding @EnableWebMvc in a Spring Boot app. In Boot, WebMvcAutoConfiguration is guarded by @ConditionalOnMissingBean(WebMvcConfigurationSupport.class). Adding @EnableWebMvc imports that bean and switches off Boot's entire MVC auto-configuration. Always implement WebMvcConfigurer instead.
Reading the request body twice. HttpServletRequest.getInputStream() is a one-shot network stream. If a Filter reads the body for logging, the stream is at EOF when DispatcherServlet's ArgumentResolver tries to deserialize @RequestBody. Wrap the request in ContentCachingRequestWrapper if a filter needs to inspect the body.
Expecting @ControllerAdvice to catch Filter exceptions (Rule 1). Exceptions thrown in Box 5 (Servlet Filters, including Spring Security filters) happen before DispatcherServlet runs, so Box 6's exception resolvers never see them.
Mutable instance fields on a @Controller (Rule 3). Controllers are singleton beans in Box 3. A field on a controller is shared across all 200 concurrent request threads. Keep controllers strictly stateless.
Assuming HandlerInterceptor runs on every URL. Interceptors only run when HandlerMapping matches a handler inside Box 6 — they do not wrap Filter rejections, container-level 404s, or unmapped requests. Use a Filter for universal security or logging.

§9Recap & Glossary / Reference

  • Front Controller pattern: one DispatcherServlet (Box 6) owns HTTP plumbing; your controller is just a plain Java method.
  • The 9-step chain: Tomcat Socket & Thread Pool (Box 5) → FilterChain (Box 5) → DispatcherServlet.doDispatch() (Box 6) → HandlerMapping → HandlerInterceptor.preHandle() → HandlerAdapter + ArgumentResolvers → your @Controller method → ReturnValueHandler + HttpMessageConverter → unwind & clear ThreadLocals.
  • Plain Java data structures inside Box 6: HandlerMapping is a routing Map; ArgumentResolvers and HttpMessageConverters are strategy Lists.
  • Rule 1 (Order of Steps): Filter (Box 5, pre-routing, raw bytes) → HandlerInterceptor (Box 6, post-routing, knows HandlerMethod) → @Aspect Proxy (Box 4, knows parsed Java args).
  • Content negotiation: matches Content-Type (input → 415 on mismatch) and Accept (output → 406 on mismatch) against HttpMessageConverters.
  • Threading: Tomcat blocks 1 thread per request; Java 21 virtual threads (spring.threads.virtual.enabled=true) remove the I/O blocking bottleneck without reactive code.
  • Rule 3 (Where State Lives): Controllers are shared singletons in Box 3 (must be stateless); per-request state in ThreadLocals must be cleaned up in finally.

Glossary

Front Controller
Design pattern where a single entry point (DispatcherServlet) receives all HTTP requests and delegates to handlers.
DispatcherServlet
Spring MVC's front controller servlet (Box 6) mapped to "/".
HandlerMapping
Box 6 lookup table mapping an incoming HTTP request (verb + path + headers) to a HandlerMethod and its interceptors.
HandlerAdapter
Box 6 adapter that invokes a matched handler using ArgumentResolvers and ReturnValueHandlers.
HandlerMethodArgumentResolver
Strategy bean that extracts and converts one controller method parameter (e.g., @PathVariable, @RequestBody) from the request.
HttpMessageConverter
Strategy bean that converts between raw HTTP body streams and Java objects (e.g., Jackson for JSON).
Content negotiation
Selecting the right HttpMessageConverter using the request's Content-Type and Accept headers.
Filter
Jakarta Servlet component in Box 5 that wraps the raw request/response before DispatcherServlet runs.
HandlerInterceptor
Spring MVC hook in Box 6 that runs around a resolved HandlerMethod.
Thread-per-request
Execution model where one server thread is dedicated to a single HTTP request from arrival to response flush.
Virtual thread
Lightweight Java 21 thread managed by the JVM that unmounts from its OS carrier thread during blocking I/O.
MDC (Mapped Diagnostic Context)
SLF4J's ThreadLocal<Map<String, String>> used to stamp log lines with per-request fields like correlationId.
