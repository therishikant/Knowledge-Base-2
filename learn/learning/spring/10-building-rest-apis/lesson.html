Building REST APIs

Spring › lesson 10 of 18 · DEEP — the layer your users actually see

In simple English — Every REST annotation you write maps to a specific helper inside DispatcherServlet (Box 6): @PathVariable, @RequestParam, and @RequestBody trigger ArgumentResolvers; @Valid runs Bean Validation right after Jackson parses JSON; and @RestControllerAdvice catches exceptions thrown inside Box 6 and turns them into standard RFC 9457 ProblemDetail JSON. A well-built controller speaks strictly in DTO records (never JPA entities!) so your public HTTP contract can evolve independently of your database tables.

§2Why it exists — what you'd write by hand without it

Without Spring's argument resolvers, Bean Validation integration, and @RestControllerAdvice, every single controller method gets buried in validation if statements and try/catch status-code plumbing: 

// ❌ Without @Valid and @RestControllerAdvice — repetitive, error-prone plumbing in every endpoint
@PostMapping("/api/books")
public ResponseEntity<?> createBook(@RequestBody CreateBookRequest req) {
    // 1. Manual validation checks repeated across dozens of endpoints
    if (req.title() == null || req.title().isBlank() || req.title().length() > 200) {
        return ResponseEntity.badRequest().body(Map.of("error", "Invalid title"));
    }
    if (req.isbn() == null || !req.isbn().matches("\\d{13}")) {
        return ResponseEntity.badRequest().body(Map.of("error", "ISBN must be 13 digits"));
    }
    // 2. Manual try/catch translating domain exceptions into ad-hoc error maps
    try {
        Book book = service.create(req.toCommand());
        return ResponseEntity.status(201).body(BookResponse.from(book));
    } catch (DuplicateIsbnException e) {
        return ResponseEntity.status(409).body(Map.of("error", e.getMessage()));
    } catch (Exception e) {
        return ResponseEntity.status(500).body(Map.of("error", "Unexpected failure"));
    }
}

And before REST itself, remote calls were RPC over HTTP: a single URL (POST /api) with a verb inside the JSON body ({"action":"deleteBook"}) and a 200 OK containing {"success": false}. Caches couldn't cache, proxies couldn't route, and automatic retries were unsafe.

REST uses HTTP's own built-in vocabulary: URL = which resource, HTTP method = which operation, Status code = what happened, and Headers = metadata/format:

MethodSafe? (no state change)Idempotent? (safe to retry)Typical success
GETYesYes200 (+ body) / 404
POSTNoNo (retrying creates duplicates unless guarded!)201 + Location header
PUTNoYes (replaces entire resource at known URI)200 / 204
PATCHNoNo (usually partial update)200 / 204
DELETENoYes (deleting twice leaves it deleted)204 (or 404 — pick one and document it)
Why idempotency matters in production: networks drop packets. When a client's POST /orders times out after 2 seconds, the client doesn't know if the server processed it or not. If it retries a non-idempotent POST, the customer gets charged twice! That is why production APIs use either PUT /orders/{clientGeneratedUuid} or POST with an Idempotency-Key header.
Richardson Maturity Model: L0 one URL, one verb (RPC) · L1 resources (many URLs) · L2 HTTP verbs + status codes ← where virtually every real production REST API lives · L3 HATEOAS (responses carry hypermedia links). Saying "we build clean L2 REST APIs with RFC 9457 errors, as L3 rarely pays for itself outside public hypermedia APIs" is a senior, pragmatic answer.

§3How it works (Level 1 → Level 2 Zoom)

Start with Plain Java First: What doDispatch() Actually Does

Every annotation in a REST controller corresponds to one line in DispatcherServlet's main loop inside Box 6. In plain Java, it is literally a try / catch block around your controller method: 

// Plain Java mental model of Box 6 (DispatcherServlet) handling your @RestController
try {
    // Step A: ArgumentResolvers build each parameter
    Object[] args = new Object[method.getParameterCount()];
    for (int i = 0; i < args.length; i++) {
        // - @PathVariable / @RequestParam -> parse String from URL
        // - @RequestBody -> Jackson ObjectMapper.readValue(req.getInputStream(), Dto.class)
        args[i] = resolverFor(param[i]).resolve(req);

        // - Has @Valid? -> Run Hibernate Validator immediately!
        if (param[i].hasAnnotation(Valid.class)) {
            Set<Violation> errors = validator.validate(args[i]);
            if (!errors.isEmpty()) throw new MethodArgumentNotValidException(errors); // jumps to catch!
        }
    }

    // Step B: Invoke your @RestController method (which calls @Service in Box 4)
    Object result = method.invoke(controllerBean, args);

    // Step C: ReturnValueHandler (@ResponseBody) writes JSON via Jackson
    jacksonConverter.write(result, resp.getOutputStream());

} catch (Exception ex) {
    // Step D: HandlerExceptionResolver searches your @RestControllerAdvice beans
    //         for an @ExceptionHandler matching `ex.getClass()`, and writes ProblemDetail JSON!
    exceptionResolver.handleWithControllerAdvice(ex, req, resp);
}
Step-by-Step Flow of POST /api/books with @Valid @RequestBody CreateBookRequest:
Step 1 (Jackson Deserialization): RequestResponseBodyMethodProcessor (an ArgumentResolver) uses Jackson to turn the incoming JSON stream into a CreateBookRequest record. (If JSON syntax is broken → throws HttpMessageNotReadableException → 400).
↓
Step 2 (@Valid Check): The exact same RequestResponseBodyMethodProcessor sees @Valid on the parameter and passes the record to Jakarta Bean Validation. (If any field fails @NotBlank/@Pattern → throws MethodArgumentNotValidException → your controller method is NEVER called!).
↓
Step 3 (Controller → Service): Your controller maps req.toCommand(), calls bookService.create(cmd), and maps the returned domain object to BookResponse.from(book).
↓
Step 4 (Exception Routing via @RestControllerAdvice): If Step 1, Step 2, or Step 3 throws an exception, execution jumps to the catch block in DispatcherServlet, which calls your matching @ExceptionHandler method and serializes the returned ProblemDetail as application/problem+json.

A controller, properly shaped

@RestController                                  // = @Controller + @ResponseBody on every method
@RequestMapping("/api/books")                    // one place for the base path
public class BookController {

    private final BookService service;           // constructor injection from Box 3 (lesson 3)
    BookController(BookService service) { this.service = service; }

    @GetMapping("/{id}")
    BookResponse get(@PathVariable long id) {       // 200 implicitly; 404 via @RestControllerAdvice
        return BookResponse.from(service.findById(id));
    }

    @GetMapping
    PagedModel<BookResponse> list(@RequestParam(required = false) String author,
                                  @PageableDefault(size = 20) Pageable page) {
        return new PagedModel<>(service.search(author, page).map(BookResponse::from));
    }

    @PostMapping
    ResponseEntity<BookResponse> create(@Valid @RequestBody CreateBookRequest req) {
        Book created = service.create(req.toCommand());
        URI location = ServletUriComponentsBuilder.fromCurrentRequest()
                            .path("/{id}").buildAndExpand(created.id()).toUri();
        return ResponseEntity.created(location)      // 201 Created + Location header
                             .body(BookResponse.from(created));
    }

    @PutMapping("/{id}")
    BookResponse replace(@PathVariable long id, @Valid @RequestBody UpdateBookRequest req) {
        return BookResponse.from(service.replace(id, req.toCommand()));
    }

    @DeleteMapping("/{id}")
    @ResponseStatus(HttpStatus.NO_CONTENT)         // 204 No Content, empty body
    void delete(@PathVariable long id) { service.delete(id); }
}
Notice what is absent: no try/catch, no if (book == null) return 404, no business rules. The controller's only jobs are translate HTTP ↔ domain and delegate.

Error handling — One Place (@RestControllerAdvice) + RFC 9457 ProblemDetail

@RestControllerAdvice                      // = @ControllerAdvice + @ResponseBody (Box 6 catch block)
public class ApiExceptionHandler extends ResponseEntityExceptionHandler {

    @ExceptionHandler(BookNotFoundException.class)
    ProblemDetail notFound(BookNotFoundException ex) {
        ProblemDetail p = ProblemDetail.forStatusAndDetail(NOT_FOUND, ex.getMessage());
        p.setTitle("Book not found");
        p.setType(URI.create("https://api.bookvault.com/errors/book-not-found"));
        p.setProperty("bookId", ex.id());         // custom machine-readable extension field
        return p;
    }

    @Override                                  // customize the built-in 400 for @Valid failures
    protected ResponseEntity<Object> handleMethodArgumentNotValid(
            MethodArgumentNotValidException ex, HttpHeaders h, HttpStatusCode s, WebRequest r) {

        ProblemDetail p = ProblemDetail.forStatusAndDetail(BAD_REQUEST, "Validation failed");
        p.setProperty("errors", ex.getBindingResult().getFieldErrors().stream()
                .map(f -> Map.of("field", f.getField(), "message", f.getDefaultMessage()))
                .toList());
        return ResponseEntity.badRequest().body(p);
    }

    @ExceptionHandler(Exception.class)          // the safety net — ALWAYS LAST
    ProblemDetail unexpected(Exception ex) {
        log.error("Unhandled", ex);                // log the stack trace internally…
        return ProblemDetail.forStatusAndDetail(INTERNAL_SERVER_ERROR,
                "An unexpected error occurred");   // …never leak stack traces to the client!
    }
}

Calling other services — RestClient (Spring 6.1+)

@Bean
RestClient catalogClient(RestClient.Builder builder, CatalogProperties props) {
    return builder
        .baseUrl(props.baseUrl())
        .requestFactory(ClientHttpRequestFactories.get(            // ★ ALWAYS set timeouts!
            ClientHttpRequestFactorySettings.DEFAULTS
                .withConnectTimeout(Duration.ofSeconds(2))
                .withReadTimeout(props.timeout())))
        .defaultHeader("X-Correlation-Id", () -> MDC.get("correlationId"))
        .build();
}
The #1 microservice outage cause: calling an outbound HTTP API with no read timeout. If the downstream service hangs, your Tomcat worker threads (Box 5) block forever until all 200 threads are exhausted and your entire server dies.

§5Explain it to a 12-year-old

A REST API is like a library counter. Every book has an address on the shelf (/api/books/42). Everyone who walks up uses the same four standard action words: look at it (GET), add a new book (POST), replace it (PUT), or remove it (DELETE).

When you hand the librarian a form to add a new book, her assistant checks the form right at the counter (@Valid) before bothering the head librarian: "Hey, the ISBN has to be 13 digits!" (400 Bad Request).

And most importantly: the librarian never hands you the library's internal database ledger (@Entity). Instead, she copies just the public details onto a neat visitor card (a DTO record). That way, when the library reorganizes its basement cabinets next month, your visitor card looks identical and nothing breaks!

§7In practice — Code Dissection & Derive, Don't Memorize

1. One Endpoint, End-to-End Dissection

// ---------- 1. Inbound DTO: immutable record + validation constraints ----------
public record CreateBookRequest(
        @NotBlank @Size(max = 200) String title,
        @NotBlank String author,
        @Pattern(regexp = "\\d{13}") String isbn) {

    CreateBookCommand toCommand() {                    // ① DTO -> domain command
        return new CreateBookCommand(title.strip(), author.strip(), new Isbn(isbn));
    }
}

// ---------- 2. Outbound DTO: hides internal entity state ----------
public record BookResponse(long id, String title, String author,
                            String isbn, Instant createdAt) {
    static BookResponse from(Book b) {                 // ② domain -> DTO
        return new BookResponse(b.id(), b.title(), b.author(),
                                 b.isbn().value(), b.createdAt());
    }
}

// ---------- 3. Controller (Box 6): thin translation + delegation ----------
@PostMapping(consumes = APPLICATION_JSON_VALUE, produces = APPLICATION_JSON_VALUE)
ResponseEntity<BookResponse> create(@Valid @RequestBody CreateBookRequest req,  // ③
                                    UriComponentsBuilder uriBuilder) {       // ④
    Book created = service.create(req.toCommand());                          // ⑤ calls Box 4 proxy
    URI location = uriBuilder.path("/api/books/{id}")
                             .buildAndExpand(created.id()).toUri();
    return ResponseEntity.created(location)                                  // ⑥ 201 + Location
                         .body(BookResponse.from(created));
}

// ---------- 4. Global Advice (Box 6 catch block): domain exception -> HTTP 409 ----------
@ExceptionHandler(DuplicateIsbnException.class)
ProblemDetail duplicate(DuplicateIsbnException ex) {                          // ⑦
    ProblemDetail p = ProblemDetail.forStatusAndDetail(CONFLICT,
            "A book with ISBN " + ex.isbn() + " already exists");
    p.setTitle("Duplicate ISBN");
    p.setProperty("isbn", ex.isbn().value());
    return p;
}
Dissection. ①② Static mapping methods on Java records keep the controller 5 lines long and require zero reflection. ③ @RequestBody tells Box 6's RequestResponseBodyMethodProcessor to deserialize JSON via Jackson; @Valid tells that exact same processor to run Bean Validation immediately afterwards. ⑤⑦ BookService throws a pure domain exception (DuplicateIsbnException) with zero HTTP imports; @RestControllerAdvice catches it in Box 6 and maps it to HTTP 409 ProblemDetail.

2. How to Think in Interviews — Derive, Don't Memorize

Classic Interview QuestionWhich Box / Rule?10-Second Derivation
"I put @NotBlank on my DTO fields, sent {"title":""}, and my controller still ran with an empty title! Why?" Box 6
(ArgumentResolver)		 @NotBlank is just passive metadata. Without @Valid (or @Validated) on the controller's @RequestBody parameter, RequestResponseBodyMethodProcessor deserializes the JSON via Jackson and never calls the validator!
"What is the difference between @Valid and @Validated?" Box 6 vs Box 4
(Rule 2: Proxy)		 @Valid is the standard Jakarta annotation used on @RequestBody parameters (Box 6) and nested fields. @Validated is Spring's annotation that adds validation groups and activates the AOP validation proxy (Box 4) on @Service beans (meaning Rule 2 self-invocation applies to @Validated services!).
"Why did a malformed JSON syntax error ({"price": "abc"}) throw a different exception than @Positive failing on {"price": -5}?" Rule 1
(Order inside Step 5)		 Inside the ArgumentResolver, Jackson runs first to parse bytes into Java types; if "abc" can't parse into a BigDecimal, Jackson throws HttpMessageNotReadableException before Bean Validation ever runs. When -5 parses cleanly into a BigDecimal, Bean Validation runs second and throws MethodArgumentNotValidException.
"Why shouldn't I return my @Entity Book directly from a @RestController?" Rule 1 & Rule 3
(Box 4 vs Box 6)		 1) Jackson serializes the response in Box 6 Step 7, after the @Service's @Transactional proxy (Box 4) has already closed the ThreadLocal PersistenceContext — so any lazy field throws LazyInitializationException. 2) It couples your public JSON contract to your database table columns and risks mass-assignment security bugs.
"Why do we need both a DB unique constraint AND an exception handler if we already checked if (repo.existsByIsbn(...))?" Rule 3
(Concurrency across threads)		 Two Tomcat worker threads can run existsByIsbn() at the exact same millisecond, both see false, and both insert (TOCTOU race condition). Only the database's unique constraint guarantees atomicity; Spring translates the DB error into DuplicateKeyException / DataIntegrityViolationException, which @RestControllerAdvice maps to 409.
Predict the Output / Try This.
  1. POST {"title":"","author":" Orwell ","isbn":"123"} to /api/books. Inspect the 400 application/problem+json response. Then remove @Valid and watch the invalid record enter your service!
  2. Send malformed JSON {"title": "1984", (missing closing brace) and verify that handleHttpMessageNotReadable triggers instead of handleMethodArgumentNotValid.
  3. Add spring.mvc.problemdetails.enabled=true to application.properties and trigger a 404, 405, and 415 — see how Spring formats all built-in errors as RFC 9457 ProblemDetail automatically.

§8Pitfalls

Exposing @Entity classes as request/response bodies. Couples your public API to your DB schema, leaks internal fields, triggers LazyInitializationException or accidental N+1 queries during Jackson serialization in Box 6, and opens mass-assignment vulnerabilities on input.
Forgetting @Valid on @RequestBody (or forgetting @Valid on a nested child DTO field). Constraints on a record do nothing unless triggered. And if CreateOrderRequest contains List<AddressDto> addresses, you must annotate the field @Valid List<AddressDto> or the child items won't be validated!
Unhandled ConstraintViolationException returning HTTP 500. Parameter/service validation with @Validated throws ConstraintViolationException (or HandlerMethodValidationException in Spring 6.1+). Always add an @ExceptionHandler mapping it to 400.
Returning HTTP 200 with {"success": false} on errors. Breaks HTTP semantics, API gateways, observability metrics, and client retry logic.
Leaking stack traces or SQL details in 500 responses. Your catch-all @ExceptionHandler(Exception.class) must log the full exception server-side and return a safe, generic ProblemDetail to the caller.
Unbounded list endpoints without pagination. Never return List<BookResponse> from a table that can grow unboundedly. Accept Pageable, set @PageableDefault(size = 20), and cap spring.data.web.pageable.max-page-size=100.
No timeouts on RestClient / RestTemplate. A hung downstream service will block all 200 Tomcat worker threads in Box 5 and cause a cascading outage.

§9Recap & Glossary / Reference

  • Every REST annotation is a Box 6 helper: @RequestBody runs Jackson in an ArgumentResolver; @Valid runs Bean Validation right after; @RestControllerAdvice is the HandlerExceptionResolver catch block.
  • HTTP is the contract: URL = resource, verb = operation, status code = outcome. Know which verbs are safe (GET) and idempotent (GET, PUT, DELETE — not POST).
  • Always use DTO records at the controller boundary — separate CreateXRequest, UpdateXRequest, and XResponse.
  • Keep domain exceptions HTTP-free: services throw domain exceptions (DuplicateIsbnException); one @RestControllerAdvice translates them into RFC 9457 ProblemDetail JSON.
  • Paginate collection endpoints with Pageable and always set connect/read timeouts on outbound RestClient calls.

Glossary

REST
Representational State Transfer — using HTTP's native URLs, verbs, status codes, and headers as the API contract.
DTO (Data Transfer Object)
Immutable Java record defining the public JSON shape, decoupled from JPA @Entity classes.
Idempotent
An operation where making the identical request 1 time or 10 times produces the exact same server state (GET, PUT, DELETE).
Safe method
An HTTP method that only reads data and does not modify server state (GET, HEAD).
ProblemDetail
Spring 6's built-in representation of RFC 9457 application/problem+json error responses.
@RestControllerAdvice
A global Box 6 interceptor/exception-resolver bean combining @ControllerAdvice and @ResponseBody.
Bean Validation
Jakarta specification (@NotBlank, @Size, @Positive) implemented by Hibernate Validator.
Richardson Maturity Model
L0–L3 scale measuring how completely an API uses HTTP (URIs → Verbs/Statuses → Hypermedia Links).
Mass assignment
Security vulnerability where binding raw JSON directly to a database entity lets attackers overwrite sensitive fields like role or id.
RestClient
Spring 6.1+'s fluent synchronous HTTP client replacing RestTemplate.
