Data Access & Spring Data JPA

Spring › lesson 11 of 18 · DEEP — where the magic is thickest

In simple English — Two things happen here that look like magic until you see the plain Java underneath: (1) At Startup (Boxes 2 & 4), Spring turns your empty interface BookRepository extends JpaRepository into a live JDK Dynamic Proxy backed by SimpleJpaRepository, parsing method names like findByAuthor into JPQL once at boot. (2) During a Request (Box 6 ThreadLocal), Hibernate attaches a PersistenceContext (a per-transaction Map<EntityKey, Object> + original field snapshots) to the current thread. At commit, Hibernate compares current fields to the snapshot (Dirty Checking) and auto-generates UPDATE SQL!

§1Where it fits — You Are Here on the Map

Spring Data JPA spans both Phase 1 (Startup) and Phase 2 (The Request Loop): in Phase 1, Boxes 2, 3, and 4 build the Repository Proxy and store it in singletonObjects. In Phase 2, when your service calls that proxy inside a transaction, Hibernate stores loaded entities inside a ThreadLocal map (Rule 3) that lives only until the transaction commits.

§2Why it exists — what you'd write by hand without it

In lesson 1, we saw what raw JDBC looks like without Spring: 25 lines of boilerplate per query just to borrow a connection, bind parameters, loop through a ResultSet, catch checked SQLException, and close resources in finally: 

// ❌ Raw JDBC by hand — 20 lines of ceremony surrounding 1 line of SQL
public Optional<Book> findByIsbn(String isbn) {
    String sql = "SELECT id, title, author, isbn FROM book WHERE isbn = ?";
    try (Connection conn = dataSource.getConnection();
         PreparedStatement ps = conn.prepareStatement(sql)) {
        ps.setString(1, isbn);
        try (ResultSet rs = ps.executeQuery()) {
            if (!rs.next()) return Optional.empty();
            return Optional.of(new Book(rs.getLong("id"), rs.getString("title"),
                                        rs.getString("author"), rs.getString("isbn")));
        }
    } catch (SQLException e) {
        throw new RuntimeException("DB error", e); // vendor error code lost!
    }
}

§3How it works (Level 1 → Level 2 Zoom)

Mystery #1 Demystified: How an interface with No Class Becomes a Working Bean

You write public interface BookRepository extends JpaRepository<Book, Long> {} — no class, no @Repository annotation needed — and yet @Autowired BookRepository repo injects a working object! How?

Step-by-Step Startup Flow (Phase 1: Box 2 → Box 3 → Box 4):
Step 1 (Box 2 Scanner): At startup, JpaRepositoriesRegistrar (an ImportBeanDefinitionRegistrar from lesson 5) scans your packages for any interface extending Repository.
↓
Step 2 (Box 2 Recipe Registration): For BookRepository, it registers a BeanDefinition in the recipe map whose class is JpaRepositoryFactoryBean (lesson 4's FactoryBean hook).
↓
Step 3 (Query Parsing at Startup): While creating the bean, the factory inspects every method name in BookRepository (e.g., findByAuthorOrderByTitleAsc), parses the grammar (find…By + Author + OrderBy + TitleAsc), validates that Book actually has author and title fields, and pre-builds the JPQL AST. (If you typo a field name as findByAuthr, the app fails to start right here — fail-fast!)
↓
Step 4 (Box 4 Proxy Creation): JpaRepositoryFactoryBean.getObject() calls Proxy.newProxyInstance(...) to generate a JDK Dynamic Proxy implementing BookRepository, and stores it in Box 3 (singletonObjects).

In plain Java, the generated proxy sitting in Box 3 looks like this: 

// Plain Java mental model of the JDK Dynamic Proxy Spring puts in Box 3 for BookRepository
final class $ProxyBookRepository implements BookRepository {

    private final SimpleJpaRepository<Book, Long> defaultCrudTarget; // has save(), findById(), delete()
    private final Map<Method, RepositoryQuery> parsedQueries;        // pre-parsed at startup!

    public Object invoke(Object proxy, Method method, Object[] args) {
        // Wrap in @Transactional (readOnly=true for queries, read-write for save/delete)
        // Wrap in PersistenceExceptionTranslationInterceptor (SQLException -> DataAccessException)
        if (parsedQueries.containsKey(method)) {
            return parsedQueries.get(method).execute(args);          // derived query or @Query
        }
        return method.invoke(defaultCrudTarget, args);               // inherited save(), findById(), etc.
    }
}

Mystery #2 Demystified: What the JPA PersistenceContext Actually Is in Plain Java

People call the PersistenceContext (inside Hibernate's Session / JPA's EntityManager) a "first-level cache," which sounds vague. In plain Java data structures, it is simply two HashMaps and a list of pending SQL statements attached to the current worker thread via ThreadLocal for the duration of one transaction: 

// Plain Java data structure inside Hibernate's PersistenceContext (bound to ThreadLocal in Box 6)
class SimplePersistenceContext {
    // 1. The Identity Map (1st-level cache): (EntityClass + PrimaryKey) -> live Java @Entity object
    Map<EntityKey, Object> entitiesByKey = new HashMap<>();

    // 2. The Loaded Snapshot Map: (EntityClass + PrimaryKey) -> copy of field values when SELECTed
    Map<EntityKey, Object[]> loadedSnapshots = new HashMap<>();

    // 3. At flush() / commit(): DIRTY CHECKING
    void flushToDatabase(Connection conn) {
        for (var entry : entitiesByKey.entrySet()) {
            EntityKey key = entry.getKey();
            Object currentEntity = entry.getValue();
            Object[] originalSnapshot = loadedSnapshots.get(key);

            if (!Arrays.equals(extractFields(currentEntity), originalSnapshot)) {
                // ★ Entity changed in memory! Auto-generate and run UPDATE SQL!
                executeUpdateSql(conn, key, currentEntity);
            }
        }
    }
}
Trace of Dirty Checking inside a @Transactional method:
Step 1 (Book b = repo.findById(42L).orElseThrow()): Hibernate runs SELECT ... WHERE id = 42, creates the Book object, puts (Book#42 → b) into entitiesByKey, and saves a copy of its initial field values ["1984", "Orwell"] in loadedSnapshots. The entity is now MANAGED.
↓
Step 2 (Second repo.findById(42L) in the same transaction): Hibernate checks entitiesByKey.get(Book#42) — cache hit! Zero SQL is run, and it returns the exact same Java reference (b1 == b2 is true).
↓
Step 3 (b.setTitle("Animal Farm")): You call a plain Java setter. You do not call repo.save(b).
↓
Step 4 (Transaction Commit → Flush): Before committing the transaction, Hibernate loops over entitiesByKey, compares b's current fields ["Animal Farm", "Orwell"] against loadedSnapshots ["1984", "Orwell"], sees the difference, and executes UPDATE book SET title = 'Animal Farm' WHERE id = 42!
↓
Step 5 (Transaction Ends → Detached): The ThreadLocal PersistenceContext is cleared and closed. b is now DETACHED.

★ Lazy Loading Proxies, LazyInitializationException, and the N+1 Query Problem

When a Book has a @ManyToOne(fetch = FetchType.LAZY) Author author, Hibernate does not load the Author row when loading the Book. Instead, it sets book.author to a Hibernate-generated subclass proxy (Box 4 concept applied to entities!) that holds only authorId = 7: 

// What book.getAuthor() actually holds when LAZY: a ghost proxy subclass!
class Author$HibernateProxy extends Author {
    private final long id = 7L;
    private Author target = null; // not loaded yet

    @Override
    public String getName() {
        if (target == null) {
            // Look up current thread's PersistenceContext in ThreadLocal:
            Session s = ThreadLocalSessionContext.currentSession();
            if (s == null || !s.isOpen()) {
                throw new LazyInitializationException("could not initialize proxy - no Session");
            }
            target = s.executeSelect("SELECT * FROM author WHERE id = ?", id);
        }
        return target.getName();
    }
}

Look at what that proxy code reveals:

  • Why LazyInitializationException happens: If you return Book from your @Transactional service back to the controller (Box 6), the transaction has already finished and closed the ThreadLocal session. When Jackson calls book.getAuthor().getName() to write JSON, s is closed → boom!
  • Why the N+1 Query Problem happens: If you stay inside the transaction, load 100 books with List<Book> books = repo.findAll() (Query #1), and loop over them calling b.getAuthor().getName(), the lazy proxy fires a separate SELECT * FROM author WHERE id = ? on every iteration (+100 queries = 101 queries total!).

Batch Fetchingspring.jpa.properties.hibernate.default_batch_fetch_size=50Global safety net: turns 100 lazy queries into 2 queries using WHERE id IN (?, ?, ...).
Never fix N+1 by changing fetch = FetchType.EAGER. EAGER permanently forces every query on Book to join/fetch Author even when not needed. Worse, in JPA, @ManyToOne and @OneToOne default to EAGER! Always write @ManyToOne(fetch = FetchType.LAZY) explicitly.

Connection Pooling (HikariCP) & open-in-view=false

spring.datasource.hikari.maximum-pool-size=10      # Small pool (cores * 2) beats 100!
spring.datasource.hikari.connection-timeout=3000   # Fail fast after 3s if pool exhausted
spring.jpa.hibernate.ddl-auto=validate             # Use Flyway/Liquibase for schema; validate only
spring.jpa.open-in-view=false                      # ★ Turn off Open-Session-In-View!
Why spring.jpa.open-in-view=false is mandatory in serious production apps: By default, Spring Boot registers an OpenEntityManagerInViewInterceptor in Box 6 (Step 4) that keeps the Hibernate PersistenceContext open all the way through controller execution and JSON rendering. That hides LazyInitializationException by letting Jackson fire N+1 SQL queries from the web layer while holding database connections longer than necessary! Turn it off and map Entities to DTOs inside your @Transactional service.

§5Explain it to a 12-year-old

Imagine the database is a giant filing vault in the basement. Walking down the stairs takes time. So when you start a task (@Transactional), your assistant brings a rolling cart up to your desk (PersistenceContext in ThreadLocal).

Every time you ask for Folder #42, your assistant puts it on your cart and secretly takes a photocopy of how it looked when it arrived (the snapshot). If you ask for Folder #42 again five seconds later, she just hands you the folder already sitting on your cart!

While working, you erase the title on Folder #42 and pencil in a new one (book.setTitle(...)). You don't have to shout "SAVE!" When your task finishes, your assistant compares every folder on your cart against her photocopies. She spots the changed title on Folder #42 and carries that update down to the basement automatically (Dirty Checking).

And what if Folder #42 has a sticky note saying "Author details are in Basement Box 7 — fetch only if asked" (a Lazy Proxy)? If you ask for the author while your assistant is still on duty, she runs downstairs and grabs Box 7. If you ask after she has clocked out and locked the basement door (transaction ended), she throws up her hands: LazyInitializationException!

§7In practice — Code Dissection & Derive, Don't Memorize

1. Production-Grade Entity, Repository, and JdbcClient Escape Hatch

// ---------- 1. Entity: explicit LAZY, @Version, safe equals/hashCode ----------
@Entity
@Table(name = "book", uniqueConstraints = @UniqueConstraint(columnNames = "isbn"))
public class Book {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Long id;
    @Column(nullable = false, length = 200)              private String title;
    @Column(nullable = false, unique = true, length = 13) private String isbn;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)  // ① override JPA's bad EAGER default!
    @JoinColumn(name = "author_id")
    private Author author;

    @Version private long version;                         // ② optimistic locking column

    protected Book() {}                                   // ③ required by Hibernate reflection

    @Override public boolean equals(Object o) {              // ④ null-safe id equality
        return o instanceof Book b && id != null && id.equals(b.id);
    }
    @Override public int hashCode() { return Book.class.hashCode(); }  // ⑤ constant across persist()!
}

// ---------- 2. Repository Interface (Proxy created in Box 4 at startup) ----------
public interface BookRepository extends JpaRepository<Book, Long> {

    @EntityGraph(attributePaths = "author")                 // ⑥ fetches author in 1 LEFT JOIN query
    Page<Book> findByTitleContainingIgnoreCase(String part, Pageable page);

    // ⑦ Interface projection: selects 2 columns, no managed entity or snapshot overhead
    @Query("select b.title as title, a.name as author from Book b join b.author a where a.id = :id")
    List<BookCard> findCardsByAuthor(@Param("id") long authorId);
    interface BookCard { String getTitle(); String getAuthor(); }

    @Modifying(clearAutomatically = true, flushAutomatically = true) // ⑧ bulk SQL
    @Query("update Book b set b.title = :t where b.id = :id")
    int bulkRename(@Param("id") long id, @Param("t") String title);
}
Dissection. ① Always set fetch = FetchType.LAZY on @ManyToOne and @OneToOne. ② @Version makes Hibernate append WHERE id = ? AND version = ? to every UPDATE. If another thread updated the row first, 0 rows match and Spring throws OptimisticLockingFailureException. ④⑤ Before persist(), id is null; after persist(), id becomes 42L. If hashCode() returned Objects.hashCode(id), the entity's hash bucket would change when saved, losing it inside any HashSet! Returning a constant class hashCode (or using a natural immutable business key like isbn) prevents this bug. ⑧ @Modifying runs a direct SQL UPDATE that bypasses the in-memory PersistenceContext map; clearAutomatically = true evicts stale entities from the map so subsequent reads see the updated DB data.

(Startup + Proxy)		 In Phase 1, JpaRepositoriesRegistrar (Box 2) registers a JpaRepositoryFactoryBean for the interface. That factory parses method names into JPQL at boot and wraps SimpleJpaRepository in a JDK Dynamic Proxy (Box 4) stored in Box 3.

(ThreadLocal Snapshot Map)		 book is inside the current thread's PersistenceContext (entitiesByKey Map). At transaction commit, Hibernate compares book's current fields against its load-time loadedSnapshots entry (Dirty Checking) and auto-generates the UPDATE SQL.
"What causes LazyInitializationException and what is the right vs wrong way to fix it?" Rule 1 & Rule 3
(Box 4 vs Box 6)		 Cause: Touching an uninitialized lazy proxy after the Box 4 @Transactional proxy closed the ThreadLocal PersistenceContext (e.g., during Jackson serialization in Box 6). Wrong fix: FetchType.EAGER or open-in-view=true. Right fix: Fetch needed data via @EntityGraph/JOIN FETCH and map to a DTO inside the transaction.
"Why did my entity loaded BEFORE a @Modifying @Query("UPDATE ...") still have old field values afterwards?" Rule 3
(entitiesByKey Cache)		 A bulk @Modifying query sends SQL straight to the DB, bypassing the in-memory entitiesByKey Map in the PersistenceContext. Without @Modifying(clearAutomatically = true), the PersistenceContext still returns the stale cached Java object!
"Why shouldn't I use Lombok @Data or @EqualsAndHashCode on a JPA @Entity?" §8Pitfalls

The N+1 Query Problem. Loading a list of N parent entities (1 query) and iterating over a lazy child association fires N additional queries. Fix per-query with @EntityGraph, JOIN FETCH, or DTO projections — never with FetchType.EAGER.
Leaving @ManyToOne / @OneToOne at their default FetchType.EAGER. The JPA specification made ToOne associations eager by default. Always write fetch = FetchType.LAZY explicitly.
Leaving spring.jpa.open-in-view=true (Spring Boot's default). Keeps the PersistenceContext and DB connection open during HTTP view/JSON rendering in Box 6, hiding N+1 queries and starving HikariCP under slow network clients. Set spring.jpa.open-in-view=false.
Accidental DB updates from mutating a managed entity. Any setter call on a managed entity inside a read-write transaction will be written to the database at commit! Mark query methods @Transactional(readOnly = true) or use DTO projections.
Using Page<Entity> with JOIN FETCH on a @OneToMany collection. If a Book has 10 Reviews, a SQL JOIN produces 10 rows for 1 Book, so SQL LIMIT 20 cannot paginate Books accurately! Hibernate logs HHH90003004: firstResult/maxResults specified with collection fetch; applying in memory! and loads the entire table into JVM RAM! Fix by paginating IDs first or using @BatchSize instead of collection JOIN FETCH on paged queries.
@Modifying queries without clearAutomatically = true. Bulk JPQL UPDATE/DELETE statements bypass the 1st-level cache map, leaving already-loaded entities in that transaction stale.

§9Recap & Glossary / Reference

  • Four data-access layers: Raw JDBC (HikariCP) → Spring JDBC (JdbcClient + DataAccessException translation) → JPA/Hibernate → Spring Data JPA.
  • How repository interfaces work: In Phase 1, JpaRepositoriesRegistrar (Box 2) + JpaRepositoryFactoryBean create a JDK Dynamic Proxy (Box 4) backed by SimpleJpaRepository and pre-parsed method queries.
  • What the PersistenceContext is: A thread-bound (ThreadLocal) Map<EntityKey, Object> (identity map / 1st-level cache) + Map<EntityKey, Object[]> (field snapshots) scoped to one transaction.
  • Dirty checking: At flush/commit, Hibernate diffs each managed entity against its load-time snapshot and auto-generates UPDATE SQL without needing a save() call.
  • Lazy loading & N+1: Lazy fields are Hibernate proxy subclasses. Accessing them after the ThreadLocal session closes throws LazyInitializationException; accessing them in a loop causes 1+N queries.
  • Production defaults: fetch = LAZY everywhere, spring.jpa.open-in-view=false, ddl-auto=validate + Flyway, and @Version for optimistic locking.

Glossary

DataSource
Factory for pooled database connections (HikariCP by default in Spring Boot).
PersistenceContext
JPA's per-transaction ThreadLocal cache holding managed entities (Map<EntityKey, Object>) and their initial field snapshots.
Managed / Detached / Transient
An entity's lifecycle state: Transient (new, not in DB), Managed (tracked inside the active PersistenceContext), Detached (transaction closed, no longer tracked).
Dirty checking
Hibernate's mechanism of comparing managed entities against their load-time snapshots at flush/commit and automatically issuing UPDATE statements.
Flush
Synchronizing in-memory PersistenceContext changes to the database via SQL statements (occurs before commit, before queries, or via flush()).
Lazy loading
Deferring SQL loading of an association by injecting a Hibernate subclass proxy that queries the DB only when a getter is called.
N+1 Query Problem
Executing 1 query to load N parent rows, followed by N separate queries as a loop accesses a lazy association on each parent.
@EntityGraph / JOIN FETCH
Instructions telling Hibernate to fetch an association eagerly in a single SQL JOIN for one specific query.
Projection
Selecting only specific columns directly into a Java record or interface proxy instead of loading full managed @Entity objects.
Open Session in View (OSIV)
Anti-pattern (spring.jpa.open-in-view=true) that keeps the PersistenceContext open during HTTP view rendering.
