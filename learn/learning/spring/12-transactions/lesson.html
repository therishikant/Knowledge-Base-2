Transactions

Spring › lesson 12 of 18 · DEEP — the boundary everything depends on

In simple English — @Transactional is just 10 lines of plain Java inside an AOP Proxy (Box 4) plus a ThreadLocal map (TransactionSynchronizationManager in Box 6). Before your service method runs, the proxy borrows one JDBC Connection from HikariCP, sets conn.setAutoCommit(false), and stores that connection in the current thread's ThreadLocal. Every repository called on that thread looks up that same ThreadLocal connection — which is why 3 repositories share 1 transaction without passing Connection as a parameter!

§1Where it fits — You Are Here on the Map

During Phase 1 (Startup), Box 4 wrapped your @Service bean in a CGLIB proxy containing a TransactionInterceptor. Now in Phase 2 (The Request Loop), your controller (Box 6) calls your service proxy (Box 4), which binds a database connection and JPA PersistenceContext (Lesson 11) to the current worker thread's ThreadLocal storage.

§2Why it exists — what you'd write by hand without it

Suppose borrowing a book touches three tables: (1) mark the book as loaned in book, (2) insert a row in loan, and (3) charge a deposit in wallet. If step 3 fails after steps 1 and 2 succeeded, the book is marked loaned to nobody!

Without Spring's @Transactional, look at the plain JDBC code you would have to write — and notice how you would have to pass Connection conn into every single repository method parameter so all three steps share the same transaction: 

// ❌ Without @Transactional — manual JDBC transaction management & polluted method signatures!
public Loan borrow(long bookId, long memberId) throws SQLException {
    Connection conn = dataSource.getConnection();
    try {
        conn.setAutoCommit(false);                 // 1. Start transaction
        bookRepo.markLoaned(conn, bookId);         // 2. Must pass `conn` into every method!
        Loan loan = loanRepo.insert(conn, bookId, memberId);
        walletRepo.debitDeposit(conn, memberId);
        conn.commit();                             // 3. Commit all three
        return loan;
    } catch (RuntimeException | Error e) {
        conn.rollback();                           // 4. Undo all three on failure
        throw e;
    } finally {
        conn.setAutoCommit(true);
        conn.close();                              // 5. Return to HikariCP pool
    }
}

Spring's @Transactional removes both pains at once: (1) the AOP Proxy (Box 4) writes the setAutoCommit(false) / commit / rollback / close block for you, and (2) a ThreadLocal variable (Rule 3) holds conn behind the scenes so your repository methods don't need Connection in their parameter list!

§3How it works (Level 1 → Level 2 Zoom)

The Entire Mechanism in 20 Lines of Plain Java

Never treat @Transactional as magic. Here is the exact plain-Java code that runs inside Spring's TransactionSynchronizationManager (Rule 3) and TransactionInterceptor proxy (Box 4): 

// 1. Where State Lives (Rule 3): Spring's TransactionSynchronizationManager is just a ThreadLocal Map!
public abstract class TransactionSynchronizationManager {
    private static final ThreadLocal<Map<Object, Object>> resources =
        ThreadLocal.withInitial(HashMap::new);

    // Key = DataSource (or EntityManagerFactory), Value = active Connection (or EntityManager)
    public static void bindResource(Object key, Object value) { resources.get().put(key, value); }
    public static Object getResource(Object key)              { return resources.get().get(key); }
    public static Object unbindResource(Object key)           { return resources.get().remove(key); }
}

// 2. Who You Call (Rule 2): The generated CGLIB Proxy in Box 4 wrapping your LoanService
public class LoanService$$SpringCGLIB extends LoanService {
    private LoanService target;
    private DataSource dataSource;

    @Override
    public LoanView borrow(long bookId, long memberId) {
        Connection conn = dataSource.getConnection();            // ① borrow 1 connection from HikariCP
        conn.setAutoCommit(false);                               // ② BEGIN transaction
        TransactionSynchronizationManager.bindResource(dataSource, conn); // ③ put in ThreadLocal!
        try {
            // ④ Call your real method. Inside it, bookRepo, loanRepo, and walletRepo all call
            //    TransactionSynchronizationManager.getResource(dataSource) -> they all get `conn`!
            LoanView result = target.borrow(bookId, memberId);
            conn.commit();                                       // ⑤ flush JPA dirty check + COMMIT
            return result;
        } catch (RuntimeException | Error ex) {                  // ⑥ default: UNCHECKED exceptions only!
            conn.rollback();                                     // ⑦ ROLLBACK
            throw ex;
        } finally {
            TransactionSynchronizationManager.unbindResource(dataSource); // ⑧ clean ThreadLocal!
            conn.setAutoCommit(true);
            conn.close();                                        // ⑨ return connection to HikariCP
        }
    }
}
Pause and appreciate lines ③ and ④: That ThreadLocal map is the entire answer to "How do three separate repositories called inside one service method share the exact same database connection without passing Connection as an argument?" And because it is a ThreadLocal, if you spawn a new thread inside borrow (e.g., @Async or CompletableFuture.runAsync), that new thread has an empty ThreadLocal — it is not in your transaction!

What the Annotation Actually Controls

@Transactional(
    propagation = Propagation.REQUIRED,        // what to do if a tx is already in ThreadLocal
    isolation   = Isolation.DEFAULT,           // how much other transactions can see
    readOnly    = false,                      // skip dirty-check snapshots + replica hint
    timeout     = 30,                          // seconds before forced rollback
    rollbackFor = Exception.class,             // also roll back on CHECKED exceptions
    noRollbackFor = NotFoundException.class
)

★ Rollback Rules — The #1 Silent Data-Corruption Bug

ThrownDefault Behaviour
RuntimeException (unchecked)Rollback
ErrorRollback
Checked Exception (e.g., IOException)COMMIT ← surprising, and dangerous!
Caught inside the methodCommit (the Box 4 proxy never sees it!)
Why this bizarre default? It mirrors the 2003 EJB convention: a checked exception was considered a declared, expected business outcome ("insufficient funds") that the caller handles; an unchecked one was a system bug. Reasonable in theory; a footgun in practice, because IOException is checked and will commit your half-finished transaction. Always write @Transactional(rollbackFor = Exception.class) when checked exceptions can be thrown, or use unchecked domain exceptions.
Catch-and-log inside a transactional method is the quiet killer. 
@Transactional
void process(Order o) {
    orders.save(o);
    try { payments.charge(o); }
    catch (RuntimeException e) { log.error("charge failed", e); }   // ← swallowed!
}   // COMMITS! Order saved, never paid for.
Furthermore, if payments.charge(o) was another @Transactional(REQUIRED) bean that threw a RuntimeException, its proxy already marked the shared ThreadLocal transaction rollbackOnly = true before your catch block ran! When process finishes and tries to commit, Spring throws UnexpectedRollbackException.

★ Propagation — Step-by-Step Arrow Flows for REQUIRED vs REQUIRES_NEW

Flow A: Propagation.REQUIRED (Default — 1 Physical Connection):
Step 1: OrderService.place() proxy borrows Conn #1 from HikariCP → binds Conn #1 to ThreadLocal.
↓
Step 2: OrderService calls auditService.record() (which has @Transactional(REQUIRED)).
↓
Step 3: AuditService proxy checks ThreadLocal, sees Conn #1 is already there, and reuses Conn #1. Both beans commit or roll back together as one unit!
Flow B: Propagation.REQUIRES_NEW (2 Physical Connections Simultaneously!):
Step 1: OrderService.place() proxy borrows Conn #1 from HikariCP → binds Conn #1 to ThreadLocal.
↓
Step 2: OrderService calls auditService.record() (which has @Transactional(REQUIRES_NEW) on a separate bean).
↓
Step 3 (Suspend & Borrow 2nd Connection): AuditService proxy takes Conn #1 out of ThreadLocal and puts it aside (suspended — still checked out from HikariCP!). Then it borrows a 2nd physical connection (Conn #2) from HikariCP and binds Conn #2 to ThreadLocal.
↓
Step 4 (Independent Commit): AuditService.record() inserts the audit row on Conn #2, commits Conn #2 immediately, unbinds Conn #2, and returns Conn #2 to HikariCP.
↓
Step 5 (Resume): AuditService proxy puts Conn #1 back into ThreadLocal. Even when OrderService later throws PaymentDeclined and rolls back Conn #1, the audit row on Conn #2 is already permanently saved!

Isolation Levels — What Other Transactions Can See

LevelPreventsStill allows
READ_UNCOMMITTEDnothingdirty reads, non-repeatable reads, phantoms
READ_COMMITTED (Postgres/Oracle/SQL Server default)dirty readsnon-repeatable reads, phantoms
REPEATABLE_READ (MySQL InnoDB default)dirty + non-repeatable readsphantoms (in theory; prevented in PG/InnoDB MVCC)

Practical guidance: leave isolation at DEFAULT (the database's own default) and solve concurrency races with optimistic locking (@Version, lesson 11) or a targeted SELECT … FOR UPDATE (@Lock(PESSIMISTIC_WRITE)).

readOnly = true — Do It on Every Query Method

  • Hibernate skips the dirty-check snapshot → less memory, faster flushes, and accidental mutations don't persist.
  • Sets the JDBC connection read-only hint, which some databases optimize.
  • With a routing DataSource, it is the signal to route queries to a read replica.

§5Explain it to a 12-year-old

A transaction is "all of it, or none of it." When you move money between two piggy banks, there must never be a moment where the money has left one and not arrived in the other — and if the second bank's lid is stuck, the money must go back, not vanish.

Spring's trick: you don't write any of the careful bookkeeping. You put a sticker on the job that says "all or nothing," and a secretary standing outside your office door (the Box 4 Proxy) handles it — she opens a ledger clipped to your clipboard (ThreadLocal) when you walk in, and when you walk out she either stamps it "done" (commit) or tears the page out (rollback).

Two things confuse everyone: First, if you walk from your own desk to another part of your own office (this.otherMethod()), you never walked through the front door past the secretary, so no new ledger gets opened (self-invocation, Rule 2). Second, the ledger sits on your clipboard — if you hand part of the job to a colleague in another room (@Async, another thread), they have an empty clipboard with no ledger at all (Rule 3)!

§7In practice — Code Dissection & Derive, Don't Memorize

1. Production Service Method & Its Collaborators

@Service
@Transactional(readOnly = true)                      // ① class default = read-only
public class LoanService {

    private final BookRepository books;
    private final LoanRepository loans;
    private final ApplicationEventPublisher events;
    private final AuditService audit;                   // separate bean → separate Box 4 proxy!

    // ── read: inherits readOnly = true ──────────────────────────────
    public LoanView find(long id) {
        return loans.findById(id).map(LoanView::from)     // ② map to DTO INSIDE the tx
                    .orElseThrow(() -> new LoanNotFound(id));
    }

    // ── write: overrides the class-level default ────────────────────
    @Transactional(rollbackFor = Exception.class, timeout = 10)   // ③
    public LoanView borrow(long bookId, long memberId) throws NotifyException {

        audit.record("borrow attempt " + bookId);           // ④ REQUIRES_NEW on separate bean: survives rollback

        Book book = books.findByIdForUpdate(bookId)              // ⑤ @Lock(PESSIMISTIC_WRITE)
                         .orElseThrow(() -> new BookNotFound(bookId));

        if (!book.isAvailable()) throw new BookUnavailable(bookId);  // unchecked → rollback

        book.markLoaned();                                       // ⑥ dirty checking: no save() needed
        Loan loan = loans.save(Loan.create(book, memberId));

        events.publishEvent(new LoanCreated(loan.getId()));    // ⑦ delivered AFTER_COMMIT

        return LoanView.from(loan);                           // still inside the tx — safe
    }
}

@Component
class LoanNotifier {
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)   // ⑧
    void on(LoanCreated e) { mailer.send(e.loanId()); }     // safe: data IS durable
}
Dissection. ① Class-level readOnly = true + method-level override makes "read" the safe default and "write" explicit. ② Mapping to LoanView inside the transactional method prevents LazyInitializationException (lesson 11). ③ rollbackFor = Exception.class ensures checked NotifyException rolls back instead of committing. ④ audit is a separate bean. Calling this.record(...) would bypass the Box 4 proxy (Rule 2) and run in the outer transaction. ⑦⑧ A plain @EventListener runs synchronously before commit; @TransactionalEventListener(AFTER_COMMIT) waits until the database commit actually succeeds.

2. How to Think in Interviews — Derive, Don't Memorize

Classic Interview QuestionWhich Box / Rule?10-Second Derivation
"My non-transactional method checkout() calls this.borrow() which has @Transactional. An exception is thrown halfway, and nothing rolls back! Why?" Rule 2
(Who You Call — Box 4)		 @Transactional lives on the Box 4 proxy wrapper. Calling this.borrow() inside the class invokes the raw target object directly, skipping the Box 4 proxy completely!
"How do 3 repositories called in 1 service method share the same JDBC Connection when I never pass Connection as a parameter?" Rule 3
(Where State Lives — ThreadLocal)		 When the Box 4 proxy starts the transaction, PlatformTransactionManager binds the borrowed JDBC Connection (and JPA EntityManager) into TransactionSynchronizationManager, which is a ThreadLocal<Map>. Every repository on that thread reads from that ThreadLocal.
"Why did my @Transactional method commit to the database when it threw IOException?" Box 4
(Rollback rule)		 By default, Spring's TransactionInterceptor only rolls back on unchecked exceptions (RuntimeException and Error). Checked exceptions commit unless you specify @Transactional(rollbackFor = Exception.class).
"With HikariCP maximum-pool-size=10, why did 10 concurrent requests calling a REQUIRES_NEW audit method deadlock the whole application?" Box 4 + Rule 3
(2 connections per thread)		 REQUIRES_NEW suspends the outer ThreadLocal connection (without releasing it!) and borrows a 2nd connection from HikariCP. If 10 threads all hold their 1st connection and block waiting for a 2nd connection from a pool of 10, none can finish and all 10 deadlock!
"What happens if I call an @Async method from inside an @Transactional method?" Rule 3
(ThreadLocal per thread)		 The transaction's Connection and JPA PersistenceContext live in a ThreadLocal on the request thread. The @Async worker thread has its own empty ThreadLocal — so it does not participate in the caller's transaction and cannot even see uncommitted data from the caller!
Break-and-fix drills — these are the interview answers.
  1. Replace audit.record(...) with a this.record(...) method annotated @Transactional(REQUIRES_NEW). Force a rollback. The audit row disappears. Explain why using Rule 2.
  2. Throw a checked exception without rollbackFor. Check the database and see that it committed!
  3. Set maximum-pool-size=2, make audit.record REQUIRES_NEW, and fire 5 concurrent requests. Watch the connection pool deadlock.
  4. Enable logging.level.org.springframework.transaction.interceptor=TRACE and read the begin/commit lines for one request.

§8Pitfalls

Self-invocation (this.transactionalMethod() — Rule 2). Skips the Box 4 proxy → no transaction, no REQUIRES_NEW, no warning.
private/final transactional methods. Cannot be overridden by a CGLIB proxy subclass in Box 4; silently ignored.
Checked exceptions commit by default. Always use rollbackFor = Exception.class or unchecked exceptions.
Catching and logging inside the boundary. The proxy sees a normal return and commits partial work — or throws UnexpectedRollbackException if an inner bean already marked the shared ThreadLocal transaction rollbackOnly.
@Transactional + @Async / parallel stream (Rule 3). New threads have an empty ThreadLocal and do not share the transaction.
HTTP calls inside a transaction. Holds a pooled DB connection in ThreadLocal for the entire network round-trip; use TransactionTemplate around only the DB work.
REQUIRES_NEW pool starvation. Holds two connections per thread simultaneously; under concurrency this can deadlock HikariCP.
@Transactional in @PostConstruct. Runs during bean initialization in Phase 1 before the Box 4 proxy is returned (lesson 4). Use ApplicationRunner or TransactionTemplate.

§9Recap & Glossary / Reference

  • @Transactional = Box 4 AOP proxy (TransactionInterceptor) + Rule 3 ThreadLocal (TransactionSynchronizationManager).
  • Two root causes of nearly every bug: it is a proxy (Rule 2: self-invocation via this skips it) and it is thread-bound (Rule 3: @Async threads don't have the ThreadLocal).
  • Rollback defaults: unchecked (RuntimeException, Error) → rollback; checked exceptions → commit unless rollbackFor = Exception.class.
  • Propagation: REQUIRED reuses the ThreadLocal connection; REQUIRES_NEW suspends it and borrows a 2nd connection from HikariCP; NESTED uses a JDBC savepoint.
  • readOnly = true on every query — skips dirty-check snapshots, saves memory/CPU, and can route to a read replica.
  • Keep transactions short and DB-only: use TransactionTemplate when mixing DB work with slow HTTP calls, and @TransactionalEventListener(AFTER_COMMIT) / Outbox for side effects after commit.

Glossary

ACID
Atomicity, Consistency, Isolation, Durability — what a database transaction guarantees.
PlatformTransactionManager
Spring's abstraction over JDBC (DataSourceTransactionManager) and JPA (JpaTransactionManager) transactions.
TransactionSynchronizationManager
The ThreadLocal registry holding the current thread's active JDBC Connection, JPA EntityManager, and synchronization callbacks.
Propagation
What a transactional method does when a transaction is already active in ThreadLocal (REQUIRED vs REQUIRES_NEW).
Isolation level
How much of other concurrent transactions' uncommitted/changing data is visible.
Dirty read / non-repeatable read / phantom
The three classic isolation anomalies.
Rollback-only
A flag marking a shared transaction as doomed, forcing UnexpectedRollbackException if the outer method tries to commit.
UnexpectedRollbackException
Thrown when an outer transaction tries to commit a shared transaction that an inner participant marked rollback-only.
Savepoint
A rollback point inside a single JDBC transaction (NESTED propagation).
Transactional outbox
Writing a to-be-published message to an outbox table in the same DB transaction as the business data change.
Saga
A sequence of local transactions with compensating actions instead of a distributed two-phase commit.
