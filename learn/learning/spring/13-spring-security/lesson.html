Spring Security

Spring › lesson 13 of 18 · DEEP — one filter that is really a chain

In simple English — Spring Security inserts one Servlet Filter in Box 5 (DelegatingFilterProxy) that bridges into a Spring bean (FilterChainProxy) running an ordered List<Filter> of ~15 small security filters. Together they answer "Who are you?" (Authentication → 401 on failure), store the verified user in a ThreadLocal (SecurityContextHolder), and answer "Are you allowed?" (Authorization → 403 on failure) before DispatcherServlet (Box 6) ever runs!

§1Where it fits — You Are Here on the Map

This slots into Step 2 of lesson 9's request lifecycle in Box 5 — before DispatcherServlet (Box 6), before routing, and before your controller exists in the picture. Meanwhile, method-level annotations like @PreAuthorize live in Box 4 (AOP Proxies) and read the same ThreadLocal (SecurityContextHolder).

§2Why it exists — what you'd write by hand without it

Without Spring Security, developers end up writing manual token checks inside controllers or custom filters: 

// ❌ Without Spring Security — manual auth check copy-pasted across controllers!
@DeleteMapping("/api/books/{id}")
public ResponseEntity<Void> deleteBook(@PathVariable long id, HttpServletRequest req) {
    String auth = req.getHeader("Authorization");
    if (auth == null || !auth.startsWith("Bearer ")) return ResponseEntity.status(401).build();
    User u = jwtVerifier.verify(auth.substring(7));       // what about clock skew? key rotation?
    if (!u.hasRole("ADMIN")) return ResponseEntity.status(403).build();
    bookService.delete(id, u.username());                 // must pass username through every method!
    return ResponseEntity.noContent().build();
}

Why is DIY security so dangerous? Because if a developer adds a new controller endpoint tomorrow and forgets those 6 lines, that endpoint is wide open to the public! And notice the two words people blur — get this distinction exact:

§3How it works (Level 1 → Level 2 Zoom)

Plain Java Data Structures First: What Are the Core Objects?

Before looking at any diagram, see how simple the data structures inside Spring Security actually are: 

// 1. The Bridge from Box 5 (Tomcat) into Box 3 (Spring Beans):
//    Tomcat only knows Jakarta Servlet Filters. So Boot registers ONE tiny filter with Tomcat:
public class DelegatingFilterProxy implements jakarta.servlet.Filter {
    private Filter delegate; // looks up bean named "springSecurityFilterChain" (FilterChainProxy) in Box 3!
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain) {
        delegate.doFilter(req, res, chain);
    }
}

// 2. The User Badge (Authentication) — used both BEFORE and AFTER verification:
public interface Authentication extends Principal {
    Object getPrincipal();                              // UserDetails or Jwt
    Object getCredentials();                            // raw password/token (erased to null after auth!)
    Collection<? extends GrantedAuthority> getAuthorities(); // e.g. ["ROLE_ADMIN", "SCOPE_books:write"]
    boolean isAuthenticated();
}

// 3. Rule 3 (Where State Lives): SecurityContextHolder is just a ThreadLocal!
public class SecurityContextHolder {
    private static final ThreadLocal<SecurityContext> holder = new ThreadLocal<>();
    public static SecurityContext getContext() { return holder.get(); }
    public static void clearContext()          { holder.remove(); } // called in Filter `finally` block!
}

Step-by-Step Trace: A Request with a Bearer JWT or Password

Trace of an HTTP Request through Box 5 → ThreadLocal → Box 6 → Box 4:
Step 1 (Box 5 → Box 3 Bridge): Tomcat calls DelegatingFilterProxy (Box 5), which delegates to the Spring bean FilterChainProxy (Box 3), which picks the matching SecurityFilterChain and runs its ~15 filters in order.
↓
Step 2 (Extract Credentials): The authentication filter (e.g., BearerTokenAuthenticationFilter for JWT, or UsernamePasswordAuthenticationFilter for login) extracts the token/password from the HTTP request and builds an unauthenticated Authentication token (isAuthenticated = false).
↓
Step 3 (Verify via AuthenticationManager): The filter passes that unauthenticated token to AuthenticationManager (ProviderManager), which loops over its List<AuthenticationProvider>:
• For username/password: DaoAuthenticationProvider calls your UserDetailsService.loadUserByUsername() + PasswordEncoder.matches().
• For JWT: JwtAuthenticationProvider calls JwtDecoder to verify the cryptographic signature and expiry.
↓
Step 4 (Store in ThreadLocal — Rule 3): Verification succeeds! A new authenticated Authentication (with principal + GrantedAuthority list) is stored in SecurityContextHolder.getContext().setAuthentication(auth).
↓
Step 5 (URL Authorization in Box 5): AuthorizationFilter checks your requestMatchers(...).hasRole(...) rules against the Authentication in SecurityContextHolder.
• If unauthenticated → throws AuthenticationException → caught by ExceptionTranslationFilter → calls AuthenticationEntryPoint (HTTP 401).
• If missing required role → throws AccessDeniedException → caught by ExceptionTranslationFilter → calls AccessDeniedHandler (HTTP 403).
↓
Step 6 (Enter Box 6 → Box 4 → Cleanup): If allowed, chain.doFilter() finally enters DispatcherServlet (Box 6) → Controller → Service (where @PreAuthorize in Box 4 can check method arguments). On the way out, SecurityContextHolderFilter's finally block clears the ThreadLocal!

Authentication — The Collaborators & Delegating PasswordEncoder

// The only two beans most username/password apps need to write:
@Bean
UserDetailsService users(MemberRepository repo) {
    return username -> repo.findByEmail(username)
        .map(m -> User.withUsername(m.getEmail())
                      .password(m.getPasswordHash())        // ALREADY hashed in DB
                      .authorities(m.getRoles())
                      .build())
        .orElseThrow(() -> new UsernameNotFoundException(username));
}

@Bean
PasswordEncoder passwordEncoder() {
    // Stores hashes as "{bcrypt}$2a$10$…" — algorithm prefix allows future migration without breaking existing users!
    return PasswordEncoderFactories.createDelegatingPasswordEncoder();
}

§4When to use

  • Multiple SecurityFilterChain beans (ordered with @Order and scoped with securityMatcher(...)) when areas differ: stateless JWT for /api/**, Basic/form login for /actuator/**.
  • OAuth2 Resource Server — the default for APIs behind an identity provider (Keycloak, Auth0, Entra ID, Cognito). Boot validates tokens and rotates JWKS keys automatically.
  • Method security (@PreAuthorize) — ownership and row-level rules that need method arguments.
  • Rule on CSRF: cookie-based auth → CSRF on; header-based Bearer token → CSRF off.

§5Explain it to a 12-year-old

Think of getting into a big concert stadium. Before you ever reach the arena floor (DispatcherServlet in Box 6), you walk down a corridor of checkpoints outside the gate (SecurityFilterChain in Box 5).

At the ticket booth, the guard asks "Who are you?" (Authentication). You hand over your ticket, he verifies it with the box office machine (AuthenticationManager), and he snaps a wristband onto your wrist with your name and zones (general, backstage). That wristband is the Authentication object stored on your thread's clipboard (SecurityContextHolder in ThreadLocal).

At the stadium door, a second guard checks "Are you allowed in here?" (Authorization):

  • No wristband at all? Turned back at the ticket booth (401 Unauthorized).
  • General-admission wristband trying to enter the VIP backstage door? Turned away (403 Forbidden).

Because you were turned away outside the stadium (Box 5), the stage manager inside the arena (@RestControllerAdvice in Box 6) never even knew you showed up!

§6Connections

  • ← 09-web-mvc: Security is Step 2 in Box 5, before DispatcherServlet (Box 6) — hence filter 401/403 errors bypass @ControllerAdvice.
  • ← 06-aop: @PreAuthorize is a Box 4 AOP proxy, so self-invocation (this.method()) silently skips the security check (Rule 2)!
  • ← 12-transactions & java/11-concurrency: SecurityContextHolder is a ThreadLocal (Rule 3) — so it doesn't propagate to @Async threads unless wrapped in DelegatingSecurityContextAsyncTaskExecutor, and must be cleared in finally so pooled Tomcat threads never leak identities between users.

§7In practice — Code Dissection & Derive, Don't Memorize

1. Production Stateless JWT API Configuration, Dissected

@Configuration
@EnableWebSecurity
@EnableMethodSecurity                                                   // Enable Box 4 @PreAuthorize proxies
public class SecurityConfig {

    @Bean
    @Order(1)                                                       // ① chains are tried in @Order
    SecurityFilterChain actuator(HttpSecurity http) throws Exception {
        return http
            .securityMatcher("/actuator/**")
            .authorizeHttpRequests(a -> a
                .requestMatchers("/actuator/health/**").permitAll()   // K8s probes must be open
                .anyRequest().hasRole("OPS"))                        // ② everything else locked
            .httpBasic(Customizer.withDefaults())
            .csrf(CsrfConfigurer::disable)
            .build();
    }

    @Bean
    @Order(2)
    SecurityFilterChain api(HttpSecurity http) throws Exception {
        return http
            .securityMatcher("/api/**")
            .authorizeHttpRequests(a -> a
                .requestMatchers(HttpMethod.GET, "/api/books/**").permitAll()
                .requestMatchers("/api/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated())                       // ③ deny-by-default, ALWAYS LAST

            // ④ stateless: no session, no cookie → CSRF is structurally impossible
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .csrf(CsrfConfigurer::disable)

            // ⑤ validate JWTs issued by the identity provider
            .oauth2ResourceServer(o -> o.jwt(jwt ->
                 jwt.jwtAuthenticationConverter(rolesConverter())))

            // ⑥ explicit Box 5 401 vs 403 handlers
            .exceptionHandling(e -> e
                .authenticationEntryPoint(new BearerTokenAuthenticationEntryPoint())
                .accessDeniedHandler(new BearerTokenAccessDeniedHandler()))

            .cors(Customizer.withDefaults())                         // ⑦ run CorsFilter in Box 5 before auth!
            .build();
    }

    // ⑧ map the IdP's "roles" claim onto Spring's "ROLE_" prefix convention
    private JwtAuthenticationConverter rolesConverter() {
        JwtGrantedAuthoritiesConverter granted = new JwtGrantedAuthoritiesConverter();
        granted.setAuthoritiesClaimName("roles");
        granted.setAuthorityPrefix("ROLE_");                           // hasRole("ADMIN") checks "ROLE_ADMIN"
        JwtAuthenticationConverter c = new JwtAuthenticationConverter();
        c.setJwtGrantedAuthoritiesConverter(granted);
        return c;
    }

    @Bean
    CorsConfigurationSource corsConfigurationSource() {              // ⑨
        CorsConfiguration cfg = new CorsConfiguration();
        cfg.setAllowedOrigins(List.of("https://app.bookvault.com"));  // NOT "*"
        cfg.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE"));
        cfg.setAllowedHeaders(List.of("Authorization", "Content-Type"));
        UrlBasedCorsConfigurationSource src = new UrlBasedCorsConfigurationSource();
        src.registerCorsConfiguration("/api/**", cfg);
        return src;
    }
}

// ⑩ Box 4 method security — checks method arguments that Box 5 URL filters can't see
@Service
class LoanService {
    @PreAuthorize("hasRole('LIBRARIAN') or #memberId == authentication.name")
    List<Loan> forMember(String memberId) { ... }
}
Dissection. ① Multiple chains + @Order: the first chain whose securityMatcher matches wins. Forgetting securityMatcher on @Order(1) makes it match every URL and shadow @Order(2)! ③ Rules inside authorizeHttpRequests are evaluated top-down, first-match-wins — always put .anyRequest().authenticated() last. ⑦⑨ Enabling .cors(...) in the security chain ensures unauthenticated browser OPTIONS preflight requests are answered in Box 5 before authentication rejects them. ⑧ hasRole("ADMIN") automatically prefixes "ROLE_" and looks for "ROLE_ADMIN", whereas hasAuthority("ADMIN") checks the exact string.

2. How to Think in Interviews — Derive, Don't Memorize

Classic Interview QuestionWhich Box / Rule?10-Second Derivation
"Why didn't my @RestControllerAdvice catch a 401 Invalid Token or 403 URL Forbidden error?" Rule 1
(Box 5 before Box 6)		 Filter authentication and URL authorization happen in SecurityFilterChain in Box 5, before the request ever enters DispatcherServlet (Box 6). They are handled by AuthenticationEntryPoint (401) and AccessDeniedHandler (403) inside Box 5! (By contrast, @PreAuthorize in Box 4 runs inside Box 6, so @RestControllerAdvice does see method-security AccessDeniedException!)
"Tomcat creates Servlet Filters, not Spring. So how can Spring Security filters inject Spring beans like JwtDecoder or UserRepository?" Box 5 → Box 3 Bridge Boot registers one thin bridge filter called DelegatingFilterProxy with Tomcat (Box 5). It looks up the Spring bean named springSecurityFilterChain (FilterChainProxy) inside ApplicationContext (Box 3) and delegates every request to it.
"Why did @PreAuthorize("hasRole('ADMIN')") silently do nothing when called via this.forMember(id) inside the same service?" Rule 2
(Who You Call — Box 4)		 @PreAuthorize is enforced by an AOP proxy wrapper in Box 4. Calling this.forMember(id) invokes the raw target object directly, bypassing the Box 4 security proxy!
"Why is SecurityContextHolder.getContext().getAuthentication() null inside an @Async method?" Rule 3
(ThreadLocal per thread)		 SecurityContextHolder stores the Authentication in a ThreadLocal on the Tomcat request thread. Spawning a new thread gives an empty ThreadLocal unless you wrap your executor in DelegatingSecurityContextAsyncTaskExecutor.
"My user's JWT has authority ADMIN, but hasRole("ADMIN") returns 403 Forbidden! Why?" Box 5 / Box 4
(Prefix convention)		 hasRole("ADMIN") automatically prepends "ROLE_" and checks for "ROLE_ADMIN". Either use hasAuthority("ADMIN") or configure JwtGrantedAuthoritiesConverter.setAuthorityPrefix("ROLE_").
Experiments — several are genuine security lessons.
  1. Set logging.level.org.springframework.security=DEBUG and make one request. The log prints every filter in your SecurityFilterChain in order.
  2. Remove securityMatcher from the @Order(1) chain and watch your API chain stop being consulted at all.
  3. Call a @PreAuthorize method from another method of the same bean via this.method(). Observe that the authorization check is completely skipped (Rule 2)!

§8Pitfalls

Rule order in authorizeHttpRequests. First match wins. A broad permitAll() early silently opens everything below it. Always end with .anyRequest().authenticated().
Missing securityMatcher on multiple chains. An ordered chain without securityMatcher matches /** and swallows every request; later chains become dead code.
Disabling CSRF with cookie/session auth. Only disable CSRF when authentication is sent via an explicit header (Authorization: Bearer) and sessions are STATELESS.
hasRole vs hasAuthority. hasRole("ADMIN") checks for ROLE_ADMIN. Mismatched prefixes are the #1 cause of unexpected 403s.
@PreAuthorize and self-invocation (Rule 2). An internal this.method() call bypasses the Box 4 proxy — a silent authorization bypass!
SecurityContextHolder and threads (Rule 3). Doesn't propagate to @Async or executors by default; use DelegatingSecurityContextExecutor.
Filter security exceptions bypass @ControllerAdvice (Rule 1). They happen in Box 5 before DispatcherServlet (Box 6). Use AuthenticationEntryPoint / AccessDeniedHandler.
Registering a custom security filter as a @Component and via addFilterBefore. Boot auto-registers every Filter bean in Box 3 with Tomcat too — so your filter runs twice!

§9Recap & Glossary / Reference

  • One bridge filter, ~15 security filters: Tomcat's DelegatingFilterProxy (Box 5) → Spring's FilterChainProxy (Box 3) → your ordered SecurityFilterChain.
  • Rule 1 (Order of Steps): SecurityFilterChain runs in Box 5 before DispatcherServlet (Box 6) — which explains why filter 401/403s don't hit @ControllerAdvice and why CORS preflight must be enabled in Security.
  • AuthN = who (401); AuthZ = allowed (403). The verified Authentication lives in SecurityContextHolder's ThreadLocal (Rule 3).
  • AuthN pipeline: Filter extracts token → AuthenticationManager (ProviderManager) → AuthenticationProvider (DaoAuthenticationProvider / JwtAuthenticationProvider).
  • Two authorization layers: URL rules in Box 5 (AuthorizationFilter, coarse) and method security in Box 4 (@PreAuthorize AOP proxy, data-aware — watch out for Rule 2 self-invocation!).

Glossary

Authentication / Authorization
Who you are (failure → 401) vs what you may do (failure → 403).
DelegatingFilterProxy
Tomcat-registered Servlet filter in Box 5 that delegates to a Spring bean in Box 3.
FilterChainProxy
The Spring bean holding and selecting the SecurityFilterChains.
SecurityFilterChain
An ordered list of ~15 security filters for a matching set of requests.
SecurityContextHolder
ThreadLocal holding the current request thread's verified Authentication.
Principal
The authenticated identity (e.g., UserDetails or Jwt).
GrantedAuthority
A permission string; roles are authorities with a ROLE_ prefix.
UserDetailsService
Loads user data by username for password authentication.
PasswordEncoder
Hashes and verifies passwords with a random salt; use the delegating encoder.
CSRF
Cross-Site Request Forgery — attack exploiting automatic browser cookie attachment.
CORS
Browser rules for cross-origin requests; requires server opt-in on preflight OPTIONS.
JWT / Resource server
A signed, base64-readable token carrying claims, verified by an API resource server.
Method security
Box 4 AOP proxy authorization using @PreAuthorize / @PostAuthorize.
