§2Why it exists — The Pain of Tightly-Coupled Synchronous Code

Look at what happens when LoanService.borrow() tries to do everything directly on the user's request thread: 

// ❌ THE PAINFUL WAY: Coupled, slow, and sends emails for rolled-back transactions!
@Transactional
public Loan borrow(long bookId, long memberId) {
    Loan loan = loans.save(new Loan(bookId, memberId));
    memberStats.incrementCount(memberId);
    smtpMailer.sendEmail(memberId, loan.id());   // ☠ 1. Blocks Tomcat thread for 2,000 ms!
    kafkaTemplate.send("loans", loan);           // ☠ 2. What if DB commit fails on the next line?!
    auditRepo.save(buildAuditThatMightFail());   // ☠ 3. Throws exception → DB rolls back,
    return loan;                                 //      but email & Kafka message were ALREADY SENT!
}
The Contrast Anchor: This code has three fatal flaws: (1) LoanService is hard-wired to email, Kafka, and stats; (2) the user waits 2 seconds for SMTP; and (3) if the database transaction rolls back at the end of the method, you cannot un-send an email or a Kafka message!

§3How it works — Plain Java Data Structures First (Level 1 → Level 2 Zoom)

1. Plain Java Data Structures Behind Events, @Async, and @Cacheable

  • Box 3 Event Bus (List<ApplicationListener<?>>): Inside Box 3 (ApplicationContext), Spring holds a simple list of listener methods. When you call events.publishEvent(event), Spring loops over that list with a plain for loop on the exact same thread!
  • @TransactionalEventListener (Box 6 Transaction Hook List): Instead of running the listener immediately in the for loop, Spring registers a callback into Box 6's TransactionSynchronizationManager (a ThreadLocal<List<TransactionSynchronization>>). Right after Box 4's transaction proxy calls connection.commit(), it loops through that list and fires your AFTER_COMMIT listeners!
  • Box 4 @Async Proxy + BlockingQueue<Runnable>: When you put @Async on a method, Box 4 wraps the bean in a proxy. Calling the proxy does not run your method—it packages your method call into a Runnable lambda and drops it into a ThreadPoolTaskExecutor's BlockingQueue<Runnable>, returning immediately to the caller while a background worker thread picks it up.
  • Box 4 @Cacheable Proxy + ConcurrentMap<Object, Object>: A @Cacheable("books") proxy intercepts the call, builds a key from the method parameters, checks cacheMap.get(key), and if found, returns the cached value without ever calling your target method.

2. Step-by-Step Control Flows

Flow A: @TransactionalEventListener(phase = AFTER_COMMIT)
Step 1 → Caller invokes Box 4 @Transactional proxy → binds DB Connection to Box 6 ThreadLocal.
Step 2 → loanService.borrow() runs loans.save() and calls events.publishEvent(new LoanCreated(...)).
Step 3 → Spring sees @TransactionalEventListener(AFTER_COMMIT) → does NOT run it yet; appends callback to Box 6 ThreadLocal synchronization list.
Step 4 → borrow() returns → Box 4 proxy calls connection.commit() on the database.
Step 5 → Only because commit succeeded, Spring invokes onLoanCreated(event)! (If commit rolled back, Step 5 is skipped!).
Flow B: What Happens When You Call an @Async Method (Rule 2 & Rule 3 in Action!)
Step 1 → Controller calls reportServiceProxy.generateReport(42L) (must call the Box 4 Proxy, not this.generateReport()!).
Step 2 → Box 4 AsyncExecutionInterceptor catches the call and calls taskExecutor.submit(() -> target.generateReport(42L)).
Step 3 → Worker thread bookvault-async-1 pulls the task from the BlockingQueue.
Step 4 → Rule 3 Check: Worker thread bookvault-async-1 has its own brand-new, empty ThreadLocal map! It does NOT have the HTTP thread's DB transaction, it does NOT have SecurityContextHolder's logged-in user, and it does NOT have MDC's traceId!

3. Code Building Blocks: @Async, @Scheduled, @Cacheable, and Virtual Threads

@Configuration
@EnableAsync
@EnableScheduling
@EnableCaching
class AsyncAndCacheConfig {

    @Bean(name = "taskExecutor")
    ThreadPoolTaskExecutor taskExecutor() {
        ThreadPoolTaskExecutor ex = new ThreadPoolTaskExecutor();
        ex.setCorePoolSize(4);
        ex.setMaxPoolSize(8);
        ex.setQueueCapacity(100);                                // ★ ALWAYS bound the BlockingQueue!
        ex.setThreadNamePrefix("bookvault-async-");
        ex.setRejectedExecutionHandler(new CallerRunsPolicy()); // Backpressure instead of OOM
        ex.setTaskDecorator(new ContextPropagatingTaskDecorator()); // Copies MDC traceId across threads!
        return ex;
    }
}
Why You Must Configure a Bounded ThreadPoolTaskExecutor (Or Enable Virtual Threads):
Historically, Spring's default fallback SimpleAsyncTaskExecutor did not pool threads at all—it spawned a brand-new OS thread on every call with no cap! And if you create a pool with an unbounded queue (Integer.MAX_VALUE), a traffic spike fills heap RAM until the JVM dies with OutOfMemoryError.
Java 21 Alternative: Setting spring.threads.virtual.enabled=true in Box 1 switches Box 5 (Tomcat) and Box 4 (@Async / @Scheduled) to use lightweight Virtual Threads that unmount from carrier OS threads whenever they wait on SQL, HTTP, or SMTP!

4. In-Memory Events vs Durable Message Brokers (And the Outbox Pattern)

An in-memory ApplicationEvent lives in JVM RAM—if the pod crashes 1 millisecond after connection.commit(), your AFTER_COMMIT listener never runs. When an event must survive a crash or cross into another microservice, you need a durable message broker (Kafka or RabbitMQ).

But how do you save a row to PostgreSQL and publish a message to Kafka atomically? You cannot use a database transaction across Kafka (that's the Dual-Write Problem). The industry-standard solution is the Transactional Outbox Pattern:

  1. Inside the same Box 6 database transaction that inserts the Loan row, insert an OutboxEvent row into an outbox table in PostgreSQL. Either both rows commit, or neither commits!
  2. A background @Scheduled poller (or Debezium CDC) reads unpublished rows from the outbox table, sends them to Kafka, and marks them published.
  3. Because the poller might crash right after sending to Kafka but before marking the row published, Kafka receives messages at-least-once—so every @KafkaListener consumer must be idempotent (check if eventId was already processed).

§4When to use — Practical Decision Table

MechanismWhere It LivesSurvives JVM Crash?Best Used When…
Plain @EventListener Box 3 (same thread & TX) Atomic with caller's DB TX Decoupling two domain modules inside one monolith that must commit or roll back together.
@TransactionalEventListener(AFTER_COMMIT) Box 6 TX synchronization hook No (in-memory after commit) Triggering non-critical side effects (cache eviction, best-effort notifications) only after DB commit succeeds.
@Async Box 4 Proxy → Worker Thread No (lost if JVM dies) Moving slow I/O off the HTTP thread or running 3 independent calls in parallel via CompletableFuture.allOf().
@Cacheable / @CacheEvict Box 4 Proxy → Cache Map (Caffeine/Redis) In-memory (no) / Redis (yes) Expensive, read-heavy queries that tolerate a TTL (Time-To-Live).
@Scheduled (+ ShedLock) Box 3 background timer thread Re-runs on next schedule tick Periodic jobs (nightly cleanup, polling an outbox). Always add ShedLock if running >1 pod!
Transactional Outbox + Kafka / RabbitMQ DB Table → Broker → @KafkaListener Yes (100% durable) Cross-service events or critical workflows (billing, fulfillment) where losing an event is unacceptable.

§5Explain it to a 12-year-old

Imagine you buy a toy online at a store checkout counter.

Plain @EventListener: The cashier rings up your toy and immediately hands a slip to the clerk standing right next to her on the same counter. If your credit card declines, both the cashier and the clerk tear up their slips together.

@TransactionalEventListener(AFTER_COMMIT): The cashier waits until the credit card machine prints "APPROVED" before shouting to the gift-wrapper: "Wrap it up!" That way they never gift-wrap a toy for a card that got declined.

@Async (Rule 3 Thread Jump): The cashier hands your task to a runner in the back room so you don't have to wait in line. Because the runner is a different person in a different room, he doesn't automatically have your credit card receipt or ID badge in his pocket (ThreadLocal is lost on the new thread!).

Transactional Outbox + Kafka: What if the power goes out right after your card is charged, before the runner hears the shout? To prevent that, the cashier writes your order AND a "To-Be-Shipped" sticky note into the same permanent ledger book at the exact same moment. Even if the power goes out and comes back an hour later, the delivery truck driver reads the ledger book and ships your toy!

§7In practice — Code Dissection & Derive, Don't Memorize

// ═══ 1. Immutable Past-Tense Domain Event ═══════════════════════════════════
public record LoanCreated(long loanId, long memberId, long bookId, Instant occurredAt) {}

// ═══ 2. Publisher: Saves Loan + Publishes Event Inside Box 6 Transaction ════
@Service
public class LoanService {
    private final LoanRepository loans;
    private final ApplicationEventPublisher events;

    @Transactional
    public Loan borrow(long bookId, long memberId) {
        Loan loan = loans.save(Loan.create(bookId, memberId));
        events.publishEvent(new LoanCreated(loan.id(), memberId, bookId, Instant.now())); // ①
        return loan;
    }

    @Cacheable(value = "books", key = "#bookId", unless = "#result == null")              // ② Box 4 Cache Proxy
    public Book findBookCached(long bookId) { return loans.findBook(bookId); }
}

// ═══ 3. Listener A: Writes Outbox Row INSIDE the Same DB Transaction ════════
@Component
class LoanOutboxWriter {
    @EventListener                                              // ③ Synchronous! Shares caller's Box 6 TX
    void on(LoanCreated e) {
        outboxRepo.save(new OutboxRow(e.loanId(), "loans", toJson(e))); // Atomic with Loan row!
    }
}

// ═══ 4. Listener B: Async Email AFTER Commit with Retry + Jitter ════════════
@Component
class LoanEmailNotifier {
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT) // ④ Fires ONLY if DB committed
    @Async                                                             // ⑤ Jumps to worker thread pool
    @Retryable(retryFor = MailException.class, maxAttempts = 3,
               backoff = @Backoff(delay = 1000, multiplier = 2, random = true)) // ⑥ Jitter!
    public void sendReceipt(LoanCreated e) {
        mailer.send(e.memberId(), e.loanId());
    }

    @Recover                                                           // ⑦ Fallback after 3 failed tries
    public void onMailFailed(MailException ex, LoanCreated e) {
        log.error("Failed to email receipt for loan {}", e.loanId(), ex);
    }
}
Code Dissection:
① & ③ Atomic Outbox Write: Because LoanOutboxWriter.on() uses plain @EventListener, it executes on the same thread and inside the exact same Box 6 database transaction as loans.save(). If either fails, both roll back.
④ & ⑤ Post-Commit Async Side Effect: sendReceipt() waits until the Box 6 transaction commits (AFTER_COMMIT) and then hands the slow SMTP call to the @Async thread pool so the HTTP response returns immediately.
⑥ & ⑦ Retry with Jitter + Recover: random = true spreads out retry delays so 500 failing calls don't hammer the mail server at the exact same millisecond, and @Recover prevents silent failure when all 3 attempts fail.

How to Think in Interviews — Derive, Don't Memorize

Classic Interview QuestionDerive the Answer in 10 Seconds from the 6-Box Map & 3 Rules
"I put @Async (or @Cacheable) on a method, but it runs synchronously (or never caches). Why?" Apply Rule 2 (Who You Call — Box 4 Proxy): Either you forgot @EnableAsync/@EnableCaching, the method is private, or you called this.myMethod() from inside the same class, bypassing the Box 4 proxy wrapper!
"Inside my @Async method, why is SecurityContextHolder null, and why didn't my caller's @Transactional roll back the async DB write?" Apply Rule 3 (Where State Lives — ThreadLocal): Both the active DB Connection and the SecurityContext live inside ThreadLocal variables in Box 6 on the Tomcat request thread. When @Async jumps to a worker thread, that worker thread has an empty ThreadLocal!
"Why did my DB save() inside a @TransactionalEventListener(AFTER_COMMIT) not persist or throw an error?" Look at the Transaction Timeline: When AFTER_COMMIT fires, the original Box 6 transaction has already committed! If the listener wants to write to the DB, it must open a brand-new transaction via @Transactional(propagation = Propagation.REQUIRES_NEW).
"How do you guarantee a DB update and a Kafka message happen atomically?" Use the Transactional Outbox Pattern: You cannot span a JDBC transaction across Kafka (Dual-Write Problem). Write the business row AND an outbox row in the same Box 6 DB transaction, then publish from the outbox table asynchronously to Kafka with an idempotent consumer.
Try This / Predict the Output:
You deploy 3 replicas (pods) of your Spring Boot app to Kubernetes. Inside the app is a method annotated with @Scheduled(cron = "0 0 9 * * *", zone = "UTC") that sends a daily summary email to every customer.
Question: What happens at 09:00 UTC? Why? How do you fix it?
Answer: Every customer gets 3 identical emails! Each of the 3 pods has its own independent Box 3 container running its own @Scheduled timer thread in memory. Fix it by adding a distributed lock like ShedLock (@SchedulerLock(name = "dailySummary") backed by your shared Postgres/Redis) so only 1 pod acquires the lock at 09:00.

§8Pitfalls

Pitfall 1: Thinking @EventListener is asynchronous by default.
Mechanical cause: ApplicationEventPublisher invokes @EventListener methods in a synchronous for loop on the caller's thread and inside the caller's transaction. If a listener throws an exception, the publisher's transaction rolls back!
Pitfall 2: Sending emails or Kafka messages before the transaction commits.
Mechanical cause: If you call SMTP or kafkaTemplate.send() inside a @Transactional method and the commit fails on the last line, you have sent a permanent external message about data that does not exist. Always use @TransactionalEventListener(AFTER_COMMIT) or the Transactional Outbox.
Pitfall 3: Using @Async void without an exception handler, or leaving the executor queue unbounded.
Mechanical cause: On an @Async void method, no caller holds a Future, so uncaught exceptions vanish unless an AsyncUncaughtExceptionHandler is registered. And an unbounded queue turns traffic spikes into an OutOfMemoryError.
Pitfall 4: Caching without a TTL or mutating cached objects in place.
Mechanical cause: Box 4's @Cacheable stores a reference to the returned Java object in an in-memory Map (or Redis). Without a TTL, the Map grows forever; if callers mutate fields on the returned object, they corrupt the cached entry for all other threads (Rule 3)!

§9Recap & Glossary / Reference

  • In-process Events (Box 3): @EventListener runs synchronously on the same thread and transaction; @TransactionalEventListener(AFTER_COMMIT) waits until the Box 6 DB commit succeeds.
  • @Async (Box 4 Proxy): Submits work to a TaskExecutor thread pool. Remember Rule 2 (self-invocation this.async() bypasses the proxy) and Rule 3 (the new thread loses the caller's ThreadLocal DB transaction, SecurityContext, and MDC!).
  • Java 21 Virtual Threads (spring.threads.virtual.enabled=true): Lets Box 5 Tomcat and @Async spawn millions of cheap virtual threads that unmount during blocking I/O.
  • @Cacheable & @Retryable (Box 4 Proxies): Always set a cache TTL, and always use exponential backoff with random jitter on retries.
  • Durable Messaging (Kafka/RabbitMQ): Solve the Dual-Write Problem with the Transactional Outbox pattern, and make consumers idempotent for at-least-once delivery.

Glossary

ApplicationEventPublisher
Box 3 interface used to publish domain events to all matching @EventListener beans.
@TransactionalEventListener
Event listener registered into Box 6's transaction synchronization list that runs at a specific transaction phase (default AFTER_COMMIT).
ThreadPoolTaskExecutor
Spring's bounded thread pool (wrapping Java's ThreadPoolExecutor) that executes @Async tasks.
Dual-Write Problem
The impossibility of atomically committing to two separate systems (e.g., PostgreSQL and Kafka) without a distributed transaction or outbox.
Transactional Outbox Pattern
Saving outbound events into a database table within the same ACID transaction as the business entity, then relaying them to a message broker.
Idempotent Consumer
A message consumer that tracks processed message IDs so receiving the same message twice (at-least-once delivery) produces no duplicate effect.
Backoff with Jitter
Adding randomness to exponential retry delays so failing clients don't retry in synchronized waves (thundering herd).
