§2Why it exists — The Pain of Callback Hell vs Blocking Threads

Suppose your endpoint needs to fetch a Book, and then in parallel fetch its Author and its Reviews over HTTP.

  • In classic Java 8 before Virtual Threads, blocking an OS thread for 200 ms wasted 1 MB of stack memory doing nothing.
  • If you tried to write non-blocking callback code by hand (CompletableFuture.thenCompose(...) nested 5 levels deep), error handling, timeouts, and cancellation turned into unreadable "Callback Hell"—and a fast producer could still flood a slow consumer with millions of objects in RAM!
// ❌ THE PAIN: Hand-rolled async callbacks have no backpressure & messy error handling
futureBook.thenCompose(book -> {
    CompletableFuture<Author> f1 = fetchAuthorAsync(book.authorId());
    CompletableFuture<List<Review>> f2 = fetchReviewsAsync(book.id()); // What if there are 10M reviews?!
    return f1.thenCombine(f2, (a, r) -> new BookPage(book, a, r));
}).exceptionally(ex -> ...); // Client disconnected? Too bad, queries keep running!
The Contrast Anchor: Project Reactor (Mono<T> for 0..1 items, Flux<T> for 0..N items) gives you a composable pipeline where: (1) nothing executes until .subscribe() is called, (2) the consumer controls the rate via backpressure (request(n)), and (3) if the HTTP client disconnects, cancellation propagates upstream to stop the database query immediately!

§3How it works — Plain Java Data Structures First (Level 1 → Level 2 Zoom)

1. Plain Java Data Structures: Reactive Streams & Event Loop

Underneath the scary functional words, Reactive Streams is literally just four tiny Java interfaces (built into JDK 9+ as java.util.concurrent.Flow): 

interface Publisher<T>    { void subscribe(Subscriber<? super T> s); }
interface Subscriber<T>   {
    void onSubscribe(Subscription sub);
    void onNext(T item);                       // Push 1 item downstream
    void onError(Throwable t);                 // Error signal (replaces throwing exceptions!)
    void onComplete();                         // Stream finished
}
interface Subscription    {
    void request(long n);                      // ★ BACKPRESSURE: Consumer tells Producer "send at most n items!"
    void cancel();                             // Consumer disconnects → stop producing!
}
  • Mono<T> vs Flux<T>: Both implement Publisher<T>. A Mono<T> emits at most 1 item (like an async Optional<T>). A Flux<T> emits 0 to N items over time (like an async Stream<T> with backpressure).
  • Assembly Time vs Subscription Time (Recipe vs Execution): Calling Mono<Book> m = repo.findById(1L).map(Book::title); is just building a linked list of callback objects in memory (Assembly). Zero network or DB packets are sent until someone calls m.subscribe(...)!
  • Why ThreadLocal Breaks (Rule 3) → Reactor Context: In WebFlux, step 1 of your pipeline might run on thread reactor-http-nio-1, step 2 after a database callback on r2dbc-pool-2, and step 3 on reactor-http-nio-4. Because a single request jumps across threads, a ThreadLocal set in step 1 is missing in step 2! Instead, Reactor attaches an immutable Map<Object, Object> called Context directly to the Subscriber chain.
Step-by-Step Control Flow: A Request Inside Spring WebFlux (Boxes 5 & 6)
Step 1 (Box 5 Netty) → HTTP request arrives on Netty event-loop thread reactor-http-nio-1 → passes to Box 6 DispatcherHandler.
Step 2 (Assembly) → Your Controller method runs and returns a Mono<BookPage> recipe (takes ~0.01 ms; DB query has NOT started yet!).
Step 3 (Subscribe) → DispatcherHandler calls .subscribe() on your returned Mono and calls subscription.request(1).
Step 4 (Non-Blocking) → R2DBC sends SQL bytes over the socket and registers an OS selector callback. Thread reactor-http-nio-1 is immediately freed to serve 500 other users!
Step 5 (Callback Fires) → When Postgres replies 50 ms later, any free Netty thread runs your .map() callback and writes the JSON response to the socket.

2. The Two Golden Rules of Reactive Programming

Golden Rule A: Nothing Happens Until You Subscribe!
If you write bookRepo.deleteById(42L); inside a method and don't return the Mono<Void> (or chain it into the returned pipeline with .then() / .flatMap()), the row is never deleted and zero errors are thrown! You built a recipe object and threw the recipe in the trash.
Golden Rule B: NEVER Block a Netty Event-Loop Thread!
Netty only has as many event-loop threads as your CPU cores (e.g., 4 threads on a 4-core container). If you call blocking JDBC/JPA, Thread.sleep(), or .block() on a Netty thread, 25% of your entire web server freezes! If you must call legacy blocking code, isolate it onto a separate thread pool using Mono.fromCallable(() -> blockingCall()).subscribeOn(Schedulers.boundedElastic()).

§5Explain it to a 12-year-old

Imagine a restaurant with 200 waiters (Spring MVC). A waiter takes your order, walks to the kitchen window, and stands frozen at the window for 10 minutes staring at the chef until your pizza is cooked. If 201 customers walk in, customer #201 has to wait outside because all 200 waiters are standing frozen at the kitchen window!

Now imagine a Reactive restaurant (Spring WebFlux) with only 4 super-fast waiters (Netty Event Loop). Waiter #1 takes your order, clips the ticket to the kitchen wheel with a little bell, and immediately walks to the next table. When the chef rings the bell 10 minutes later, whichever of the 4 waiters is walking past picks up the pizza and brings it to your table! Just 4 waiters can serve 5,000 tables—unless one waiter breaks the rule and stands at the kitchen window peeling potatoes for 10 minutes (blocking the event loop!).

And what is Backpressure? If the chef cooks 100 pizzas a minute, but the delivery boy's scooter only holds 3 boxes at a time, the delivery boy tells the chef: "Only slide 3 pizzas out of the oven when I ask (request(3))!" That way pizzas never pile up and fall on the floor.

§7In practice — Code Dissection & Derive, Don't Memorize

// ═══ 1. Parallel Non-Blocking Composition + Graceful Fallback ═══════════════
@RestController
public class ReactiveBookController {

    @GetMapping("/books/{id}/page")
    public Mono<BookPage> getBookPage(@PathVariable long id) {
        Mono<Book> bookMono = bookRepo.findById(id)                         // ① Lazy R2DBC recipe
            .switchIfEmpty(Mono.error(new BookNotFoundException(id)));      // ② Empty Mono → 404 Error signal

        return bookMono.flatMap(book ->                                     // ③ flatMap (returns another Mono!)
            Mono.zip(                                                       // ④ Runs Author & Reviews in PARALLEL
                catalogClient.fetchAuthor(book.authorId())
                    .timeout(Duration.ofSeconds(2))
                    .onErrorResume(ex -> Mono.just(Author.unknown())),      // ⑤ Fallback value on timeout
                reviewRepo.findByBookId(id).take(20).collectList()          // ⑥ Backpressure: request(20) rows
            ).map(tuple -> new BookPage(book, tuple.getT1(), tuple.getT2()))// ⑦ map (synchronous transform)
        ); // ⑧ WebFlux calls .subscribe() when writing the HTTP response!
    }

    // ═══ 2. Server-Sent Events (SSE) Streaming — Flat Heap Memory ═══════════
    @GetMapping(value = "/books/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<Book> streamAllBooks() {
        return bookRepo.findAll()                                           // ⑨ Streams row-by-row with backpressure
            .delayElements(Duration.ofMillis(100))
            .doOnCancel(() -> log.info("Client closed tab → stopping DB cursor!"));
    }
}
Code Dissection:
① & ⑧ Assembly vs Subscription: When getBookPage() returns the Mono<BookPage>, zero I/O has happened yet. Box 6 (DispatcherHandler) subscribes to the returned Mono.
③ vs ⑦ flatMap vs map: Use map when transforming a value synchronously (Tuple2 -> BookPage). Use flatMap when the lambda itself returns an asynchronous Mono or Flux!
④ Parallel Fan-Out: Mono.zip(...) subscribes to both the HTTP author call and the R2DBC reviews query simultaneously, so total latency is max(t1, t2) instead of t1 + t2.
⑥ & ⑨ Backpressure & Cancellation: .take(20) sends request(20) upstream, and if a browser tab closes mid-stream in ⑨, cancel() propagates all the way back to close the database cursor!

How to Think in Interviews — Derive, Don't Memorize

Classic Interview QuestionDerive the Answer in 10 Seconds from the 6-Box Map & 3 Rules
"Why did my reactive method `repo.save(entity)` inside an `if` block never save anything to the database?" Look at the Publisher interface: A `Mono` is just a lazy recipe object. Because you didn't chain it into the returned `Mono` (via `.flatMap()` or `.then()`) or call `.subscribe()`, Box 6 never subscribed to it!
"Why can't I use standard JPA / Hibernate or blocking JDBC inside a Spring WebFlux application?" Look at Box 5 (Netty Event Loop): Netty has only ~4–8 threads total for the entire server. A blocking JDBC call parks the event-loop thread, freezing thousands of other connections multiplexed onto that thread.
"Why does `SecurityContextHolder.getContext()` or SLF4J `MDC` fail in WebFlux, and what replaces it?" Apply Rule 3 (Where State Lives): `ThreadLocal` assumes 1 thread = 1 request. In WebFlux, a single request hops across multiple Netty/R2DBC threads as callbacks fire. WebFlux replaces `ThreadLocal` with **Reactor `Context`** (`ReactiveSecurityContextHolder`), which travels with the `Subscription`.
"With Java 21 Virtual Threads available, should we build our new microservice with Spring WebFlux or Spring MVC?" Compare Box 5 & Box 6 Trade-offs: Virtual threads give Spring MVC non-blocking I/O scalability while keeping simple imperative code, readable stack traces, JPA/Hibernate, and `ThreadLocal`. Choose WebFlux only if you need **backpressure (`request(n)`)**, **SSE/WebSocket streaming**, or an **API Gateway**.
Try This / Predict the Output:
Look at these two lines inside a WebFlux controller:
Mono<Book> a = bookRepo.findById(1L);
Mono<Mono<Author>> b = a.map(book -> authorClient.fetchAuthor(book.authorId()));
Question: Why did the return type become Mono<Mono<Author>>, what happens when WebFlux subscribes to the outer Mono, and what single word fixes it?
Answer: Because authorClient.fetchAuthor() returns a Mono<Author>, using synchronous .map() wraps a recipe inside another recipe—so the inner Mono<Author> is never subscribed to and the HTTP call never runs! Change .map(...) to .flatMap(...) so Reactor subscribes to the inner Mono and flattens it to Mono<Author>.

§8Pitfalls

Pitfall 1: Calling a reactive method without chaining or subscribing to its returned Mono/Flux.
Mechanical cause: Operators only assemble a pipeline graph in memory. If a Mono<Void> is not connected to the pipeline returned to Box 6 (DispatcherHandler), subscribe() is never called on it.
Pitfall 2: Blocking on a Netty event-loop thread (JDBC, Thread.sleep, .block(), synchronized locks).
Mechanical cause: Netty runs only CPU_CORES event-loop threads in Box 5. Blocking even a few threads halts all socket reads/writes across the entire server. Use BlockHound in tests to catch accidental blocking calls automatically.
Pitfall 3: Using .map() when the function returns a Mono or Flux.
Mechanical cause: Produces a nested Mono<Mono<T>> whose inner publisher is never subscribed to. Always use .flatMap() (or .concatMap() if strict sequential ordering is required).
Pitfall 4: Reading or writing ThreadLocal state inside reactive operators.
Mechanical cause: Operators execute on whichever thread emits the signal (Netty NIO thread, R2DBC thread, or boundedElastic thread). Use Reactor's contextWrite() and Mono.deferContextual() instead.

§9Recap & Glossary / Reference

  • WebFlux swaps Boxes 5 & 6: Box 5 becomes Netty's Event Loop (4–8 non-blocking threads); Box 6 becomes DispatcherHandler + Reactor Context (replacing ThreadLocal).
  • Mono<T> (0..1) and Flux<T> (0..N) are lazy recipes—nothing runs until .subscribe().
  • Backpressure (Subscription.request(n)) lets a slow consumer throttle a fast producer so memory never overflows.
  • Never block the event loop: reactive must be non-blocking end-to-end (R2DBC + WebClient), or isolate legacy blocking calls on Schedulers.boundedElastic().
  • In Java 21+, prefer Spring MVC + Virtual Threads for standard apps; reserve WebFlux for streaming, backpressure, and API Gateways.

Glossary

Netty Event Loop (Box 5 in WebFlux)
A tiny pool of non-blocking threads (typically 1–2 per CPU core) that multiplex thousands of network sockets using OS readiness notifications.
Reactive Streams
The 4-interface specification (Publisher, Subscriber, Subscription, Processor) standardizing asynchronous streams with non-blocking backpressure.
Mono & Flux
Project Reactor's Publisher implementations for 0..1 items (Mono) and 0..N items (Flux).
Backpressure
Mechanism where the downstream Subscriber calls subscription.request(n) so a fast upstream Publisher never overwhelms its memory buffer.
Reactor Context
An immutable key-value Map attached to a reactive subscription that replaces ThreadLocal across thread hops.
R2DBC
Reactive Relational Database Connectivity—non-blocking SQL driver specification used in WebFlux instead of blocking JDBC/JPA.
StepVerifier & BlockHound
Testing tools: StepVerifier asserts reactive signals step-by-step; BlockHound throws an error if any test blocks a non-blocking event-loop thread.
