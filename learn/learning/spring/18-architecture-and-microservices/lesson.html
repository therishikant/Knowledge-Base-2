§2Why it exists — The Pain of the "Big Ball of Mud" & Premature Microservices

Most teams fall into one of two traps:

  1. The Unstructured Monolith ("Package by Layer"): Putting all controllers in com.app.controller, all services in com.app.service, and all repositories in com.app.repository. Because classes in different folders must interact, every class has to be public! Soon LoanService reaches directly into CatalogRepository and BillingRepository, JPA entities are returned directly as HTTP JSON, and changing one table breaks 40 files.
  2. The Distributed Monolith (Premature Microservices): To escape the messy monolith, the team splits it into 12 microservices—but they still share a database or call each other in a synchronous chain Service A → Service B → Service C. Now when Service C slows down for 5 seconds, Service B's 200 Box 5 Tomcat threads all block waiting on C, which causes Service A's 200 Tomcat threads to block waiting on B, crashing the entire company!
The Contrast Anchor: Good architecture solves Trap 1 by organizing code by feature module (using Java's package-private visibility + Hexagonal boundaries inside Box 3), and solves Trap 2 by starting as a Modular Monolith (Spring Modulith) and—only when multiple teams genuinely need independent deployments—protecting every cross-service boundary with Timeouts, Resilience4j Circuit Breakers/Bulkheads (Box 4), and Sagas/Outbox (Lesson 16).

§3How it works — Part 1 (Inside One App) & Part 2 (Across Many Apps)

Part 1: Organizing Beans Inside Box 3 (Layered vs Feature vs Hexagonal)

  • Package-by-Feature + package-private Encapsulation: Instead of top-level controller/, service/, repository/ folders, create top-level feature folders: com.bookvault.loan, com.bookvault.catalog, com.bookvault.member. Inside com.bookvault.loan, make LoanService and LoanRepository package-private (no public keyword!) and expose only a single public class LoanFacade (and the DTO events it publishes). Now the Java compiler physically prevents catalog from touching loan's internal tables!
  • Hexagonal Architecture (Ports & Adapters) & Where DTO/Entity Boundaries Sit:
    • Outer Edge 1 — Web Adapter (Controller in Box 6): Converts HTTP Request DTO → calls Application Use Case → returns HTTP Response DTO.
    • Center — Domain Model & Ports (Pure Java): Holds rich domain objects (Loan with business methods like loan.renew(today), not just empty getters/setters!) and Port interfaces (e.g., interface LoanRepository) owned by the domain—with zero Spring or Hibernate imports.
    • Outer Edge 2 — Persistence Adapter (Box 3/4): JpaLoanRepository implements LoanRepository maps the pure Loan domain object to a @Entity LoanJpaEntity and saves it via Spring Data JPA.
  • Aggregate = Transaction Boundary (Lesson 12 Rule): One @Transactional method should modify one Aggregate (e.g., Loan) and reference other aggregates by ID (BookId, not a `@ManyToOne Book` object reference!). Cross-aggregate updates happen via domain events (Lesson 16).
Step-by-Step Boundary Flow Inside One Feature Module
Step 1 (Web Edge) → LoanController receives BorrowRequestDto (validates @Valid in Box 6) → calls BorrowBookUseCase.
Step 2 (Use Case) → BorrowBookUseCase (@Transactional proxy in Box 4) checks CatalogFacade.isAvailable(bookId).
Step 3 (Pure Domain) → Calls Loan.create(bookId, memberId, today) — pure Java business rules, zero framework code.
Step 4 (Driven Port) → Calls domain port loanRepository.save(loan) (implemented by JpaLoanRepository adapter) & publishes LoanCreated event.

Part 2: Connecting Multiple 6-Box Spring Boot Machines (Microservices)

When your organization grows to multiple independent teams and you split a module into its own Spring Boot deployment, trace how the four distributed-systems problems map onto our 6 Boxes:

1. Distributed Configuration → Feeding Box 1 (Environment)

When you have 30 microservices, you can centralize shared config using Spring Cloud Config Server or (more commonly in modern cloud-native stacks) Kubernetes ConfigMaps & Secrets mounted as environment variables into each container's Box 1 (`List<PropertySource>`).

2. Service Discovery & API Gateway → Sitting in Front of Box 5

External mobile/web clients shouldn't know the internal IPs of 30 microservices. An API Gateway (such as Spring Cloud Gateway, built on Lesson 17's non-blocking Netty event loop) sits at the edge in front of Box 5 to handle TLS, OAuth2 token validation, rate limiting, and routing, while Kubernetes DNS / Service Discovery (or Eureka) resolves service names like http://catalog-service/api/books.

3. Resilience4j (Circuit Breaker, Retry, Bulkhead) → Box 4 AOP Proxies

What happens when Service A calls Service B over HTTP, and Service B is hanging? Without protection, all 200 of Service A's Box 5 Tomcat threads block waiting on Service B (**Cascading Failure**). Resilience4j wraps outbound calls in **Box 4 AOP Proxies** with a strict execution order:

Resilience4j Box 4 Proxy Chain:
Caller → Retry → CircuitBreaker → RateLimiter → TimeLimiter → Bulkhead → Outbound RestClient Call
• Bulkhead: Plain Java Semaphore (e.g., max 20 concurrent calls to Service B) so Service B can never consume all 200 of Service A's Box 5 threads!
• TimeLimiter / HTTP Timeout: Fails fast if Service B takes >2 seconds.
• CircuitBreaker: State machine with a sliding-window array of outcomes: CLOSED (normal) → if failure rate >50%, trips to OPEN (fails immediately in 0 ms and invokes fallbackMethod without touching the network!) → after wait duration, enters HALF_OPEN (lets a few test calls through; if they succeed, closes again).
• Retry: Wraps the outer call to retry transient network blips with exponential backoff + jitter.

4. Distributed Transactions → Why 2PC Fails & How Outbox + Saga Solves It

Why doesn't @Transactional work across Service A (Order DB) and Service B (Payment DB)? Because **Box 6's `@Transactional` binds a single JDBC `Connection` to a single JVM's `ThreadLocal` (Rule 3)**! Two-Phase Commit (2PC/XA) across network services locks database rows across the network and destroys availability if any node blips.

The Saga + Transactional Outbox Pattern (Combining Lesson 12 + Lesson 16):
Step 1 (Order Service) → Local Box 6 TX: inserts `Order(status = PENDING)` + `Outbox(OrderPlaced)` → commits.
Step 2 (Payment Service) → Consumes `OrderPlaced` from Kafka → Local Box 6 TX: charges card & writes `Outbox(PaymentSucceeded)` or `Outbox(PaymentFailed)`.
Step 3 (Happy Path) → Order Service consumes `PaymentSucceeded` → updates `Order(status = CONFIRMED)`.
Step 4 (Compensation!) → If Payment failed, Order Service consumes `PaymentFailed` → runs **Compensating Transaction**: updates `Order(status = CANCELLED)`!

§4When to use — Practical Decision Table

Architectural PatternWhen to Use ItCost / Trade-Off
Package by Feature + package-private Every Spring Boot app from Day 1. Zero runtime cost; the Java compiler enforces module boundaries for free.
Thin Service + JPA Entity (No separate Domain class) Simple CRUD modules with minimal business logic. Fast to write, though persistence annotations sit on your model classes.
Hexagonal (Ports & Adapters) Complex business rules (pricing, loans, billing) that must be tested in 1 ms with 0 Boxes and outlive database/framework changes. Requires writing Mapper code between pure Domain classes and JPA `@Entity` classes.
Modular Monolith (Spring Modulith + ArchUnit) The default starting point for 95% of systems. Single deployable JAR with strict, tested module boundaries and an in-app event outbox. One deployment unit; cannot scale one module onto 64-core GPU nodes independently.
Microservices Multiple independent teams needing separate release cadences, or modules with radically different scaling/hardware needs. High operational tax: requires Distributed Tracing (Lesson 15), Outbox + Sagas (Lesson 16), Resilience4j, and Contract Testing (Lesson 14).

§5Explain it to a 12-year-old

Part 1 (Package by Feature vs Layer): Imagine organizing your Lego kits. If you put all wheels from every kit into Box A, all bricks into Box B, and all minifigures into Box C ("Package by Layer"), building a fire truck means rummaging through every box in your room! Instead, put the entire Fire Truck kit in one box and put a lid on it ("Package by Feature" + package-private).

Part 2 (Circuit Breakers & Bulkheads): Imagine a submarine divided into watertight rooms (**Bulkheads**). If one room gets a leak (a slow downstream microservice), you seal the door so only that room fills with water instead of sinking the whole submarine (saving your Box 5 Tomcat threads!). And if a toaster short-circuits, the house **Circuit Breaker** flips **OPEN** and cuts the electricity immediately so the wires don't catch fire—then after a minute you flip it half-way (**HALF_OPEN**) to test if the toaster is fixed!

Part 2 (Sagas vs 2PC): When you book a flight AND a hotel on two different websites, you can't lock both companies' databases at once. Instead, you book the flight first, then book the hotel. If the hotel is sold out, you run a **Compensating Action**: you call the airline back and cancel the flight! That sequence of local steps + undo steps is a **Saga**.

§7In practice — Code Dissection & Derive, Don't Memorize

// ═══ PART 1: Pure Domain + Port + Package-Private Adapter + ArchUnit ════════
package com.bookvault.loan.domain;
// ① ZERO Spring or JPA imports! Pure Java aggregate root:
public class Loan {
    private final LoanId id;
    private final BookId bookId;               // ② References other aggregate by ID, not @ManyToOne object!
    private LocalDate dueOn;
    private LoanStatus status;

    public void renew(LocalDate today) {       // ③ Rich domain behaviour (not an anaemic getter/setter bag)
        if (status != LoanStatus.ACTIVE || dueOn.isBefore(today)) throw new CannotRenewLoanException(id);
        this.dueOn = dueOn.plusDays(14);
    }
}

public interface LoanRepository {              // ④ Domain PORT owned by domain package
    Optional<Loan> findById(LoanId id);
    Loan save(Loan loan);
}

// ═══ PART 2: Box 4 Resilience4j Client Calling Another Microservice ═════════
package com.bookvault.loan.infrastructure;

@Component
class CatalogHttpClient {                      // ⑤ package-private! Only visible inside 'loan' module
    private final RestClient restClient;

    @CircuitBreaker(name = "catalog", fallbackMethod = "fallbackAvailable") // ⑥ Box 4 Proxy
    @Bulkhead(name = "catalog")                                             // ⑦ Caps concurrent calls
    @Retry(name = "catalog")
    public boolean isBookAvailable(long bookId) {
        return Boolean.TRUE.equals(
            restClient.get().uri("/api/books/{id}/available", bookId).retrieve().body(Boolean.class)
        );
    }

    private boolean fallbackAvailable(long bookId, Throwable ex) {          // ⑧ Graceful degradation
        return false; // Fail closed safely when Catalog service is down
    }
}

// ═══ PART 3: Enforcing the Architecture at Build Time with ArchUnit ═════════
@AnalyzeClasses(packages = "com.bookvault")
class ArchitectureTest {
    @ArchTest                                  // ⑨ Fails the Maven build if anyone imports Spring/JPA in domain!
    static final ArchRule domain_must_stay_pure_java =
        noClasses().that().resideInAPackage("..domain..")
            .should().dependOnClassesThat()
            .resideInAnyPackage("org.springframework..", "jakarta.persistence..");
}
Code Dissection:
①–④ Hexagonal Inversion: `Loan` and `LoanRepository` live in `..domain..` with zero framework imports. `JpaLoanRepository` in `..infrastructure..` implements `LoanRepository`, so the compile-time dependency arrow points inward from Infrastructure to Domain.
⑤ Compiler-Enforced Encapsulation: `CatalogHttpClient` is package-private; only the module's public facade (`LoanFacade`) can be injected by other feature packages.
⑥–⑧ Box 4 Resilience4j Proxies: `@Bulkhead`, `@CircuitBreaker`, and `@Retry` wrap `isBookAvailable()` via Box 4 AOP proxies (Rule 2: must be called through the Spring proxy, and `RestClient` must have connection/read timeouts configured!).

How to Think in Interviews — Derive, Don't Memorize

Classic Interview QuestionDerive the Answer in 10 Seconds from the 6-Box Map & 3 Rules
"Should we start a new greenfield system as Microservices or a Monolith?" Start with a Modular Monolith (Spring Modulith): Microservices solve an organizational problem (multiple teams deploying independently) at a high distributed-systems cost (network latency, Outbox/Sagas instead of Box 6 `@Transactional`, distributed tracing). Enforce package-by-feature boundaries in-process first, and extract a service only when scaling or team autonomy demands it.
"Why did one slow downstream API take down our entire Spring Boot service even though CPU and RAM were fine?" Look at Box 5 (Tomcat Thread Pool): Without HTTP timeouts, a Bulkhead, and a Circuit Breaker in Box 4, all 200 Tomcat worker threads blocked waiting on the slow downstream socket. Once all 200 threads were parked, Box 5 couldn't even answer `/actuator/health` or fast endpoints!
"Why didn't my `@CircuitBreaker` or `@Retry` annotation trigger when I called `this.fetchRemoteData()` inside my service?" Apply Rule 2 (Who You Call — Box 4 Proxy): Resilience4j annotations use Box 4 Spring AOP proxies. Self-invocation via `this.` calls the raw target object directly and skips the CircuitBreaker/Bulkhead proxy completely!
"How do you handle a transaction that spans Order Service, Payment Service, and Inventory Service?" Apply Rule 3 (`ThreadLocal` TX) → Saga + Outbox: Box 6's `@Transactional` only binds one DB connection to one JVM thread. Across microservices, avoid 2PC; use a **Saga** (a sequence of local ACID transactions published via the **Transactional Outbox**, paired with **compensating undo events** if a downstream step fails).
Try This / Predict the Output:
Suppose you stack both `@Retry(maxAttempts = 3)` and `@CircuitBreaker` on an outbound method `fetchAuthor()`. By default in Resilience4j, `Retry` is the outer aspect and `CircuitBreaker` is the inner aspect (`Caller → Retry → CircuitBreaker → Target`).
Question: What happens when the circuit breaker is **OPEN**? Does `fetchAuthor()` wait through 3 slow network timeouts, or does each retry fail in 0 ms?
Answer: Because `CircuitBreaker` is inside `Retry`, when the circuit is **OPEN**, `CircuitBreaker` rejects the call in **0 ms** (`CallNotPermittedException`) without touching the network—and if you configure `ignoreExceptions: CallNotPermittedException` on `Retry` (or invoke the `CircuitBreaker` `fallbackMethod`), it returns the fallback immediately!

§8Pitfalls

Pitfall 1: Building a "Distributed Monolith" (services sharing one database or synchronous chains A → B → C → D).
Mechanical cause: If two services share PostgreSQL tables, a schema migration in Service A breaks Service B; if 4 services with 99% uptime call each other synchronously, combined availability drops to $0.99^4 \approx 96\%$ and latencies add up.
Pitfall 2: Returning JPA `@Entity` objects directly from `@RestController` instead of DTOs.
Mechanical cause: Exposes internal database columns (and sensitive fields) as your public JSON contract, triggers `LazyInitializationException` or infinite recursion in Jackson after Box 6's transaction closes, and couples clients to your DB schema.
Pitfall 3: Calling external HTTP APIs without timeouts, Bulkheads, or Circuit Breakers.
Mechanical cause: A hanging downstream service exhausts all Box 5 Tomcat threads (or DB connections if called inside `@Transactional`!), causing a cascading outage across your entire fleet.
Pitfall 4: Making every class `public` in a Package-by-Layer structure.
Mechanical cause: When controllers, services, and repositories live in separate packages, Java forces them all to be `public`, allowing any feature to bypass another feature's service layer and query its repository directly. Use Package-by-Feature + `package-private` + ArchUnit.

§9Recap & Glossary / Reference

  • Part 1 (Inside Box 3): Organize packages by feature (`loan/`, `catalog/`), make internal classes `package-private`, and expose one public facade per module.
  • Hexagonal Architecture (Ports & Adapters): Keep the core Domain & Port interfaces free of Spring/JPA imports so all dependency arrows point inward and business rules test in 1 ms with 0 Boxes.
  • One Transaction = One Aggregate: Reference other aggregates by ID (`BookId`), not JPA object references, and use domain events for cross-aggregate updates.
  • Start with a Modular Monolith (Spring Modulith + ArchUnit): Split into microservices only when team autonomy or independent scaling requires it.
  • Part 2 (Across Many 6-Box Apps): K8s ConfigMaps/Cloud Config feed Box 1; Spring Cloud Gateway sits in front of Box 5; Resilience4j CircuitBreaker/Bulkhead proxies live in Box 4; and the Transactional Outbox + Saga pattern replaces cross-service Box 6 transactions.

Glossary

Package by Feature
Organizing packages by business capability (`loan`, `catalog`) rather than technical layer (`controller`, `service`), enabling `package-private` visibility.
Hexagonal Architecture (Ports & Adapters)
Architecture where the pure Java Domain sits at the center and owns Port interfaces, while Web Controllers (Driving Adapters) and JPA Repositories (Driven Adapters) sit on the outside pointing inward.
Aggregate
A cluster of domain objects treated as a single consistency unit modified within one ACID transaction and referenced from outside only by ID.
Modular Monolith & Spring Modulith
A single deployable application with strictly enforced internal module boundaries, verified by Spring Modulith and ArchUnit.
Cascading Failure
Outage where one slow dependency blocks caller threads in Box 5 until upstream services run out of threads and fail in a chain reaction.
Circuit Breaker & Bulkhead
Resilience patterns (in Box 4 proxies): a Bulkhead caps concurrent calls to a dependency; a Circuit Breaker trips OPEN to fail fast when error rates spike.
Saga Pattern
Managing data consistency across microservices via a sequence of local transactions + Outbox events, using compensating (undo) transactions on failure.
