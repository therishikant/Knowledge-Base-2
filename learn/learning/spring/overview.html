LEVEL 0The Whole Machine: Startup → Request → Shutdown

Strip away every annotation. When you run a Spring Boot application, it is a normal Java program with a main() method that goes through 3 Phases and uses 6 Core Boxes (Spring Framework Reference — IoC Container; Spring Boot Reference — SpringApplication):

LEVEL 1Opening the 6 Boxes: What Plain-Java Code Is Inside Each?

Why do Spring concepts sometimes feel abstract? Because people say words like "IoC Container", "BeanPostProcessor", or "PersistenceContext" without telling you what Java collection or loop they actually are. Let's open all 6 boxes in plain Java:

Box 1: Environment — Just an Ordered List of Maps

Lives in: Phase 1 (Startup) & queried anytime | Covered in: Lesson 08

Under the hood, Environment holds two simple Java fields: a Set<String> activeProfiles (e.g. ["prod"]) and a List<PropertySource> (an ordered list of key-value Maps):

// Inside Box 1 (Environment): searched from index 0 downward — FIRST MATCH WINS!
List<Map<String, Object>> propertySources = List.of(
    commandLineArgsMap,        // 0: --server.port=9000        (highest priority)
    osEnvVarsMap,              // 1: SERVER_PORT=8081
    applicationProdYmlMap,     // 2: application-prod.yml
    applicationYmlMap          // 3: application.yml           (lowest priority)
);

Intuition unlocked: You never need to memorize "which config overrides which" as disconnected trivia. Command-line args override application.yml simply because the for-loop checks index 0 first and returns immediately!

Box 2: BeanDefinition Registry — The Recipe Book (Zero Objects Exist Yet!)

Lives in: Phase 1 (Startup, Step A) | Covered in: Lessons 02, 04, 05, 07

Spring does not create objects while scanning your classes. Instead, it builds a Recipe Map first:

// Inside Box 2 (DefaultListableBeanFactory):
Map<String, BeanDefinition> beanDefinitionMap = new ConcurrentHashMap<>();

// Step 2A: Scan YOUR package (@ComponentScan + @Configuration/@Bean)
beanDefinitionMap.put("bookService", new BeanDefinition(BookService.class, "singleton", false));

// Step 2B: Read Spring Boot's AutoConfiguration.imports file (~150 default configs)
// Guarded by @ConditionalOnClass(DataSource.class) and @ConditionalOnMissingBean(DataSource.class):
if (isPresentOnClasspath("javax.sql.DataSource") && !beanDefinitionMap.containsKey("dataSource")) {
    beanDefinitionMap.put("dataSource", new BeanDefinition(HikariDataSource.class, "singleton", false));
}

// Step 2C: BeanFactoryPostProcessor — Last chance to edit Recipes before any 'new' is called!

Intuition unlocked: Why does your custom @Bean DataSource automatically replace Spring Boot's default database pool? Because Step 2A registers your recipe first, and in Step 2B Boot checks @ConditionalOnMissingBean, sees your recipe is already in the Map, and backs off!

Box 3 & Box 4: ApplicationContext & BeanPostProcessor — The Factory, Proxy Wrapper & Warehouse

Lives in: Phase 1 (Startup, Step B) & holds beans during Phase 2 | Covered in: Lessons 02, 03, 04, 06

Once all recipes in Box 2 are finalized, Spring loops through beanDefinitionMap, cooks each non-lazy singleton, passes it through Box 4 (the Assembly-Line Inspectors / Proxy wrappers), and puts the finished object into the Warehouse Map:

// Inside Box 3 (DefaultListableBeanFactory):
Map<String, Object> singletonObjects = new ConcurrentHashMap<>();

Object createBean(String name, BeanDefinition recipe) {
    // 1. INSTANTIATE: Resolve constructor dependencies recursively via getBean(), then call new
    Object rawBean = recipe.getConstructor().newInstance(resolveConstructorArgs(recipe));

    // 2. POPULATE: Inject @Autowired fields/setters and @Value("${...}") from Box 1
    populateFieldsAndValues(rawBean);

    // 3. INITIALIZE & WRAP (Box 4 — BeanPostProcessors run here!):
    runPostConstruct(rawBean); // BeanPostProcessor.postProcessBeforeInitialization

    Object finalBean = rawBean;
    if (hasAnnotation(rawBean, Transactional.class, Async.class, PreAuthorize.class)) {
        // BeanPostProcessor.postProcessAfterInitialization swaps rawBean for a PROXY!
        finalBean = generateProxyWrapper(rawBean);
    }

    // 4. STORE: What goes into singletonObjects is the PROXY, not the raw object!
    singletonObjects.put(name, finalBean);
    return finalBean;
}

Intuition unlocked (3 classic interview questions solved in 5 seconds):

  1. Why is a @Value field null inside the constructor? Look at the code: Step 1 (newInstance constructor) runs before Step 2 (populateFieldsAndValues)!
  2. Why do Circular Dependencies fail with Constructor Injection? In Step 1, A's constructor calls getBean("B"), whose constructor calls getBean("A") before A has finished Step 1. Deadlock in the recursion!
  3. Why does calling this.myTransactionalMethod() inside the same class skip @Transactional? Outside callers get finalBean (the Proxy) from singletonObjects. Inside your class, this is rawBean—calling this.method() never touches the Proxy wrapper!

Box 5 & Box 6: Embedded Tomcat, FilterChain, DispatcherServlet & ThreadLocal

Lives in: Phase 2 (Every HTTP Request) | Covered in: Lessons 09, 10, 11, 12, 13

When an HTTP request arrives on port 8080, Tomcat grabs one thread from its pool (default 200 threads) and runs this exact pipeline on that single thread:

// On Tomcat Worker Thread #17 (handling GET /books/42):
// --- BOX 5: Servlet Container & FilterChain (Runs BEFORE Spring MVC knows which Controller matches) ---
securityFilter.doFilter(req, res) {
    Authentication user = verifyJwtOrCookie(req);
    SecurityContextHolder.getContext().setAuthentication(user); // Stored in ThreadLocal!
    chain.doFilter(req, res); // hands off to Box 6
}

// --- BOX 6: DispatcherServlet (Spring MVC's single Front Controller) ---
dispatcherServlet.doDispatch(req, res) {
    try {
        HandlerMethod handler = handlerMapping.lookup(req); // "GET /books/{id}" -> BookController.getBook(Long)
        interceptors.preHandle(req, res, handler);
        Object[] args = argumentResolvers.resolve(req, handler); // "@PathVariable" -> 42L; "@RequestBody" -> Jackson
        Object result = handler.invoke(args); // Calls BookController -> @Service Proxy -> @Repository Proxy
        messageConverters.writeJson(result, res); // Jackson writes JSON to HTTP response
    } catch (Exception ex) {
        controllerAdviceExceptionResolver.handle(ex, res); // @ExceptionHandler returns ProblemDetail JSON
    }
}

PLAYBOOKThe 3 Universal Rules That Answer 90% of Interview Questions

Whenever an interviewer asks you a tricky "Why does X happen in Spring?" or "What is the difference between X and Y?" question, don't reach for a memorized definition. Ask which of these 3 Universal Rules applies:

Rule 1: Follow the Order of Steps (What runs before what?)

Spring is a strict pipeline. If Step A runs before Step B, Step A cannot see what Step B produces:

  • Recipes (Box 2) before Objects (Box 3): BeanFactoryPostProcessor edits recipes before any constructor runs. Your code is scanned (Box 2A) before Boot Auto-Config (Box 2B), so @ConditionalOnMissingBean lets your bean win.
  • Constructor → Field Injection/@Value → @PostConstruct → Proxy (Box 4): A constructor cannot read an @Autowired or @Value field because field population happens on the next line after new. Put startup logic that needs injected fields in the constructor parameters or @PostConstruct.
  • Servlet Filter (Box 5) before DispatcherServlet (Box 6): Spring Security runs in a Box 5 Filter. Therefore, a 401/403 rejected in the Security Filter never reaches your Box 6 @ControllerAdvice exception handler unless you explicitly forward it!

Rule 2: Who Are You Calling — The Proxy Wrapper or the Raw this Object?

In Spring, cross-cutting features (@Transactional, @Async, @Cacheable, @Retryable, @PreAuthorize, @Configuration) work by wrapping your object in a generated Proxy (Box 4):

  • External call (controller → serviceProxy.outer()): Goes through the Proxy doorway → opens transaction / switches thread / checks cache → calls target.outer(). Works!
  • Self-invocation (target.outer() → this.inner()): Inside target, the Java keyword this points to the unproxied raw object. Calling this.inner() bypasses the Proxy doorway completely. Silently skips @Transactional / @Async / @Cacheable!
  • Subclassing rules (CGLIB): CGLIB creates a subclass (class MyService$$Proxy extends MyService) and overrides methods. In Java, you cannot override a private or final method — so annotations on private/final methods cannot be intercepted by a proxy.

Rule 3: Where Does State Live — Shared Singleton Map vs Per-Thread ThreadLocal?

In a running app, hundreds of HTTP requests execute at the same time on different threads:

  • Beans live in singletonObjects (Box 3): There is only one instance of BookController and BookService shared by all 200 Tomcat threads. Never store per-user data in a bean field (race condition!).
  • Request state lives in ThreadLocal (Phase 2 backpack): The active DB Connection / JPA PersistenceContext (TransactionSynchronizationManager) and the logged-in user (SecurityContextHolder) are attached to the current thread.
  • Consequence: (a) When the @Transactional method finishes, the ThreadLocal DB session closes — touching a lazy JPA collection later in the Controller throws LazyInitializationException! (b) When you jump to another thread via @Async or CompletableFuture, the new thread has an empty ThreadLocal backpack (no caller transaction, no security user unless propagated)!

How Spring and Spring Boot relate (the thing people blur)

Spring Framework is the core: the IoC container, AOP, the data-access abstractions, Spring MVC. It is powerful and unopinionated — which historically meant a lot of XML and boilerplate to get a "hello world" running. Spring Boot is not a different framework; it's a layer of opinions on top: starters (curated dependency sets), auto-configuration (beans created for you when their libraries are present), an embedded server, and production features like Actuator. Boot's own docs put it plainly: it lets you create "stand-alone, production-grade Spring-based Applications that you can just run" (Spring Boot Reference Documentation).

Gives youThe container, AOP, MVC, TX abstractionsDefaults, starters, auto-config, embedded server, Actuator

Interview line"Spring is the engine.""Boot is the car built around it — you can always open the hood."
Keep this reflex: whenever Boot does something surprising, ask "which auto-configuration class did that, and what condition made it fire?" Run with --debug and read the condition evaluation report. Boot has no magic that isn't a bean created under an @Conditional.

How the versions grew (and why your old tutorials lie)

Spring's history is a steady march away from boilerplate. Knowing the arc tells you why an API looks the way it does — and lets you spot out-of-date advice instantly.

EraWhat changed
Spring 1.x (2004)XML bean definitions. IoC + AOP + JDBC/TX templates. The alternative to heavyweight EJB2.
Spring 2.5 / 3.xAnnotations (@Component, @Autowired), then Java config (@Configuration/@Bean) — XML becomes optional.
Spring 4.x (2014)Java 8, generics-aware injection, @RestController, conditional beans. Spring Boot 1.0 arrives.
Spring 5.x (2017)Reactive stack (WebFlux, Reactor), functional bean registration, Kotlin support. Boot 2.x.
Spring 6.x / Boot 3.x (2022→)Baseline Java 17, javax.* → jakarta.*, AOT + GraalVM native images, Micrometer Observability API, RestClient, virtual threads (3.2), ProblemDetail errors.
The single most common "my tutorial is broken" cause: Boot 3 moved to jakarta.persistence and jakarta.servlet. Any snippet importing javax.persistence.Entity is pre-2022 and will not compile. Second most common: WebSecurityConfigurerAdapter was removed — modern security config returns a SecurityFilterChain bean.

Glossary (quick reference)

IoC (Inversion of Control)
You don't call the framework to build your objects; the framework builds them and calls you. "Don't call us, we'll call you."
DI (Dependency Injection)
The specific form of IoC Spring uses: a dependency is handed to an object from outside (usually via its constructor) instead of being created inside it.
Bean
Any object whose creation, wiring, and lifetime the Spring container manages.
BeanDefinition
The container's recipe for a bean (class, scope, constructor args, init method) — created before any bean object exists.
ApplicationContext
The full-featured IoC container: a BeanFactory plus events, resources, i18n, and auto-detected post-processors.
Scope
How many instances exist and how long each lives: singleton (default, one per container), prototype, request, session.
Proxy
A stand-in object that looks like your bean but wraps each call to add behaviour (transaction, security check, cache lookup).
AOP
Aspect-Oriented Programming: factoring a concern that cuts across many classes (logging, TX, security) into one place and weaving it in.
Auto-configuration
Boot's conditional @Configuration classes that create sensible default beans — and back off the moment you define your own.
Starter
A dependency with no code of its own that pulls in a curated, version-aligned set of libraries (e.g. spring-boot-starter-web).
DispatcherServlet
Spring MVC's single front controller: every HTTP request enters here and is routed to a handler method.
Persistence context
JPA's per-transaction working set of managed entities — the first-level cache that makes dirty checking possible.
Propagation
What a transactional method does when a transaction is already running (join it, suspend it, start a new one, fail…).
Actuator
Boot module exposing production endpoints: health, metrics, env, mappings, thread dumps.
